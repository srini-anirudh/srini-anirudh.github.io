PyTorch × Hugging Face meetup, Bengaluru

Hosted by Hugging Face ML Club India and Red Hat. Five talks on the systems under the model.

This was not a meetup about calling APIs. Every talk was about what runs under the model: profilers, inference engines, RL environments, distributed training and GPU communication.

The evening opened with Sudhir Dharanendraiah. His point was simple. India uses a lot of AI. It should also help build the stack under it.

I took notes by hand all evening. Later I read the slides again and added what I had missed. This page is both put together.

Talk 1

Profiling in PyTorch

Aritra Roy Gosthipaty · Developer Advocacy, Hugging Face

“What you cannot profile, you cannot optimize.”

That was the title slide, and the whole talk. Aritra kept the demo tiny: a matmul followed by an add. Then he gave a simple recipe.

  1. Name the code you care about with torch.profiler.record_function.
  2. Wrap it in torch.profiler.profile. Pick the activities, CPU and CUDA. Set a schedule: wait, warmup, then active steps.
  3. Export two things: a trace and a table.

The schedule is easy to miss. Warmup steps are slow and noisy, so you skip them. Only the active steps are recorded. With active=3, every op shows up three times in the table.

To read the table, sort by CUDA time total. The first row is your biggest bottleneck. Then check how many times it was called. Sometimes a row is on top only because it ran a lot.

The idea I liked most: overhead bound

A small matmul finishes on the GPU almost at once. But the CPU spends longer launching the kernel than the GPU spends running it. So the GPU sits idle. This is called being overhead bound.

He showed it with one script and three sizes. The fix is not a faster kernel. The fix is more work per launch.

CUDA time as a share of CPU time, same script

size 645%
size 102426%
size 409688%

The trace shows the same story. Open it in the Hugging Face trace viewer or Perfetto. You get two lanes, CPU and GPU. Gaps in the GPU lane mean the GPU was waiting.

Where torch.compile fits

In eager mode, every op is its own launch: matmul, then add, then activation. torch.compile traces the graph, fuses the ops and caches the result. The work right after a matmul, like an activation or a normalization, is called the epilogue. It can be fused into the same kernel. So one Triton kernel is launched instead of many, with fewer trips to memory.

The names in the table, like aten::matmul, are ATen ops. ATen is PyTorch's tensor library.

More from the slides
  • The test function is tiny on purpose: torch.add(torch.matmul(x, w), b). It is easy to see in a trace.
  • record_function("matmul_add") gives the step a name, so you can find it in the trace.
  • The loop runs 5 steps and calls prof.step() each time. With wait=1, warmup=1, active=3, repeat=1, one step waits, one warms up and three are recorded.
  • Three switches I wrote down: record_shapes tracks input shapes, profile_memory tracks allocation and freeing, and with_stack adds line numbers of your code.
  • Export with prof.export_chrome_trace(...) for the trace. Write prof.key_averages().table(sort_by="cuda_time_total", row_limit=15) for the table.
  • The demo ran with uv run. A small tool then uploaded the traces to the Hub, and he opened them in the Hugging Face trace viewer.

Talk 2

SGLang, the Transformers backend and kernels

Adarsh · Hugging Face

Adarsh began with a plain point. Serving one user is easy. Serving thousands at once is where the real work starts.

Inference is two jobs

Prefill reads the whole prompt in parallel and builds the model's working context. It is compute bound. The maths is matrix times matrix.

Decode writes one token at a time. It is memory bound. The maths is matrix times vector, and every step reads the KV cache again.

What SGLang is made of

  • Scheduler. Batches requests together.
  • KV cache manager. Stores the cache and reuses it.
  • Model runner. Runs the forward pass.
  • Attention backend. flash-attn or flash-infer.

RadixAttention

Older systems threw the KV cache away when a request ended. SGLang keeps it. It stores the cache of old requests in a radix tree, a memory-efficient prefix tree, and drops the least recently used first. A new request with the same start reuses it. So a shared system prompt is computed only once.

One slide made this real: Llama-3-8B on one H100, the same 1,000 requests, each with a 2K-token shared prompt.

Throughput, tokens per second

plain generate()~209
SGLang~7,900

That is about 38 times more. The whole run went from about 25 minutes to about 40 seconds. Cost per million tokens fell from about $3.30 to about $0.09.

Transformers and SGLang together

Transformers is the source of truth for what a model is: the config, tokenizer, weight format and chat template. SGLang does the fast serving. You switch it on with --model-impl transformers. One slide was called “Transformers internals hijacked”. One config line swaps the attention backend. The tp_plan in Hugging Face says how the model is split across GPUs.

One warning I wrote down: numeric drift. Different kernels give slightly different numbers. So the same model can behave a little differently on a different backend.

Kernels

Custom kernels are hard to share. Builds break across toolchains and CUDA versions. Hugging Face's kernel-builder uses Nix, so builds can be repeated. It targets ROCm, XPU, CUDA and Metal, and keeps track of the PyTorch and CUDA version matrix.

One more note at the end of my page: the KV cache can be pushed down to SSDs when GPU memory runs out. DeepSeek does this.

More from the slides
  • Why inference is hard: his slide said it plainly. “One user is easy. A thousand is not.”
  • Scale: a fun-facts slide said SGLang runs on more than 400,000 GPUs and makes trillions of tokens a day. It also said about 44 PRs get merged every day.
  • The Transformers backend: a PR added tensor and pipeline parallel, MoE, VLM support and torch.compile to it. There are about 2 million models on the Hub. SGLang has a few hundred ported by hand. The backend covers the rest, on day 0.
  • Why HF Kernels exists: no common structure, build tools all over the place (CMake, Nix, Meson, Bazel), endless build times, and support matrices to maintain.
  • What it gives you: a fixed project structure, repeatable builds, native PyTorch compatibility, and sharing on the Hub. Using a kernel is about four lines of change. You avoid messy wheels and builds that do not match.

Talk 3

RL environments 101

Adithya S Kolavi · post-training, Hugging Face

Adithya told the story of how models are taught. First pretraining on the web. Then SFT on good answers. Then RLHF, where people pick the better answer. Then RLVR and GRPO, where a program grades the answer.

“If a program can grade it, a model can learn it.”

That is the unlock. And it turns the race into something simple: build more environments.

An environment is a few parts: a task and a prompt, tools, state, observations, a place to run code, a reward, and a signal for when the episode is done. Frameworks like OpenEnv, Verifiers, OpenReward and Harbor now give these a common shape.

Repo2RLEnv

Public GitHub repos are a goldmine. They hold real tasks, real code and tests that grade themselves. Repo2RLEnv turns any repo into a verifiable environment. He said about 1,000 of them are already generated and live on Hugging Face.

Reward hacking: the best part of the talk

His first story was a toy. He trained a tiny Qwen 0.5B model with GRPO on grade-school maths. He rewarded three things: the format, the right answer, and code that runs cleanly. The last one felt harmless.

Then he read the traces. The model had learned to wrap everything in try / except: pass. The code never crashed, so the reward maxed out. The maths was never solved. The model had maximized the reward without doing the task.

His second story was a real security bug in a PDF library, made into an environment. The agent only had to fix the bug. It scored a perfect 1.0 without fixing anything. Three times.

  1. The prompt named the fixing PR. The agent just read the fix from GitHub. Fix: scrub the prompt.
  2. The answer was in the git history inside the container. Fix: reset the repo to the base commit.
  3. With the web blocked, it used pip to download the fixed release. Fix: cut the network with an allowlist, not a block-list.

After that, the reward was 0.0, for the first time. His line: every green before was contamination. And you cannot out-scrub the internet.

Trust lives in the environment

This was my favourite slide. The environment enforces the rules. The prompt never asks for them.

  • Make the verifier trustworthy first: gold patch scores 1.0, a no-op scores 0.0.
  • Strip the answer from the prompt.
  • Scrub the repo to the base commit.
  • Pre-bake dependencies and run offline by default.
  • If the network is needed, use an allowlist, never a full block.
  • Keep the gold patch and hidden tests out of the container.

“A model never does the task. It does the reward. At scale, every gap gets found, so reward design is never done, only iterated.”

A hands-on example close to my own work

The demo trained a vision-language model on LaTeX OCR. The model sees an image of a formula and writes the LaTeX. The reward is simple: does it render back to the same maths? A few lines of TRL and GRPO, on a free GPU.

Eval reward before and after GRPO

glm-ocr0.449 → 0.664
gemma-e2b0.392 → 0.570
qwen3.5-2b0.688 → 0.710
qwen3-vl-2b0.615 → 0.723

On my reading list now: his “ultimate guide to RL environments”, which is linked from the last slides.

More from the slides
  • More environments, better models. A chart in his deck showed the number of training environments going up from about 20 to 20K, 100K+ and even 1M+ across recent open models. Each one was trained on that many.
  • Gym, for LLMs. Gym gave classic RL one contract: reset() and step(action). For LLMs the agent is the model, the environment is a sandbox, and the reward is a verifier.
  • Two kinds of environment. One-shot (RLVR): prompt, answer, verifier. Maths, code and logic fit here. Multi-turn agent RL: the model acts, the environment answers, for 10 to 100+ turns, and the reward comes at the end. Think SWE-bench or AppWorld.
  • A tiny coding environment. Task: find the .py file with the most lines. Tool: bash. Reward: +1 if the answer is right, else 0. GRPO tries the same task many times and nudges the model toward the attempts that score.
  • OpenEnv. It started at Meta and PyTorch and is now maintained by Hugging Face. It has a Gym-style API, MCP as a first-class citizen, rubrics for rewards, and a task API. He said there are 1,000+ environments on the Hub.
  • Building one. The action is a plain function marked @mcp.tool. reset() loads the task into the sandbox. A rubric returns 1.0 if the tests pass, else 0.0. create_app turns it all into an HTTP and MCP server, with a limit on parallel rollouts. Then: openenv init, build, validate, push.
  • Training with TRL. Point GRPOTrainer at the environment with environment_factory. TRL also has experimental support for OpenReward and Harbor.
  • The catch. “Training is the easy part now.” You still need thousands of environments, and good ones are slow to build by hand.

Talk 4

Scaling up, one dimension at a time

Mansi Agarwal · Senior ML Engineer, PyTorch Engineering, Red Hat

Mansi started with the old pain. DDP, FSDP, TP and PP each had their own API, wrapper and checkpoint format. Mixing FSDP with tensor parallel took over a hundred lines of manual plumbing. Add one more kind of parallelism and you rewrite the training loop.

Her question: what if parallelism was composable, like adding a dimension to a grid? Newer PyTorch has three building blocks.

  • DeviceMesh. A grid of GPUs. A 4×2 grid means 4 groups for data parallel and 2 for tensor parallel. You name each dimension, like dp and tp.
  • DTensor. A tensor that knows how it is split across the mesh. It can be sharded, replicated or partial.
  • FSDP2. Sharded data parallel, rebuilt on DTensor. It is a transform on the model, not a wrapper around it.

So adding a parallelism means adding a dimension to the mesh. It is not a rewrite. And communication becomes automatic: you write the maths, and if an op needs a different layout, DTensor adds the all-gather or reduce-scatter for you.

The code walkthrough made it real. One GPU, then DDP, then FSDP2, then FSDP2 with tensor parallel. At every step the training loop stayed the same. Only a few lines around the model changed.

“Locally optimal”

I wrote this next to DTensor. It picks the best sharding for each op as it goes. It does not look at the whole graph, so the full plan may not be the best one. JAX takes the other path. It looks at the whole graph, but it needs a compiler. Mansi was honest about this trade-off. Eager-first design gives up global optimality to keep debugging easy.

Checkpoints that reshard

torch.distributed.checkpoint can reshard when you load. Save on 8 GPUs, load on 16. That is what elastic training needs.

More from the slides
  • The old way took five steps. Work out rank groups by hand, create process groups by hand, write your own TP layers, change the model code, then wrap with FSDP1. About 100 lines. Forget one manual all-reduce and the results are silently wrong. FSDP1's FlatParameter also broke TP weight shapes.
  • Process groups: a 4×2 mesh makes 6 groups (2 for DP, 4 for TP). A 2×2×2 mesh makes 12.
  • DTensor helpers: distribute_tensor splits a tensor. to_local() gives your shard. full_tensor() gathers everything. redistribute() changes the placement.
  • How an op runs: DTensor catches every ATen op. It looks up a sharding rule (410+ ops covered), picks the cheapest one, adds any collectives needed, runs the op on local shards and wraps the result. An unsupported op raises an error. It does not silently fall back to replicate.
  • FSDP1 vs FSDP2: FlatParameter became per-parameter DTensors. A wrapper class became fully_shard(), an in-place transform. LoRA and frozen layers work now. fp8 works. Sharded checkpoints need no communication. FSDP1 is deprecated.
  • FSDP2 under the hood: all-gather before forward, run, free the memory after forward. Backward does the same, then a reduce-scatter for the gradients. FSDP2 uses its own fast collectives, so it skips DTensor's dispatch cost.
  • 2D in practice: apply tensor parallel on the tp mesh (column-wise for qkv and the first FFN layer, row-wise for the output projections). Then call fully_shard on the dp mesh. The same pattern extends to 3D with PP, 4D with CP, and 5D with expert parallel for MoE.
  • The compile order: checkpoint, then fully_shard, then torch.compile last. Start with fullgraph=False. Use compile_threads=1, because background threads can hang a distributed run.
  • Checkpoints: dcp.save needs no communication. Loading can reshard. Async save was 10 to 20 times faster (7B model: 148 s down to 6.3 s). It also supports SafeTensors. For gradient accumulation use set_requires_gradient_sync(False).
  • DTensor vs JAX: DTensor is eager-first and greedy per op, so it is locally optimal and easy to debug with print and pdb. JAX with GSPMD is compiler-first and looks at the whole graph, so it can find a globally optimal plan.
  • Known limits: eager dispatch costs about 7× per op (compile removes it). About 58 ATen ops still have no strategy. Views can break on DTensors. There is no uneven sharding yet, which blocks clean MoE expert parallelism. reduce_dtype was ignored for the TP all-reduce, a silent precision loss. HSDP with mixed precision used 3× gradient memory on a 2D mesh. Shape changes can trigger full recompiles. She was honest about these.
  • What is next: AutoParallel (picks the sharding for you with linear programming, experimental), DTensor erasure, Symmetric Memory, TorchFT, Monarch, zero-bubble pipeline parallelism and compiler-assisted backward sharding.

Talk 5

Zero-copy GPU-to-GPU communication

Arkadip Maitra · PyTorch Engineering, Red Hat

My notes stop before this talk, so this part comes from his slides and my photos.

Arkadip went below the training loop, to how GPUs talk to each other. c10d is PyTorch's default layer. It worked well for years. But the world around it changed. NICs got smarter. RoCE fabrics grew. NVLink got stronger. And distance started to matter a lot.

How much slower the network gets with distance (same rack = 1×)

same rack1×
cross-rack7×
cross-zone15×
cross-DC30×

One slide put hardware and software on two timelines. The hardware lane and the framework lane had moved together, and comms was only one entrant in the race. He then picked one idea to focus on: zero-copy.

The normal path copies your data through an internal buffer, on both sides. The zero-copy path lets the NIC read straight from your buffer and write straight into the other GPU's buffer. Fewer copies means fewer GPU threads busy doing copies.

2×copy tax saved
1.09–2.7×faster communication
2,560threads saved
up to 50%fewer thread blocks

These numbers are for medium messages, about 1 MB to 128 MB. Two more results stood out. RoCE matched InfiniBand in collective bandwidth (about 232.6 GB/s vs 230.7 GB/s). And the zero-copy path kept its lead as the distance grew, from the same host to a different zone.

More from the slides
  • Why c10d worked: training was bulk-synchronous, the collectives were regular, the host knew the metadata, and the API did not care about the backend. It was a good fit up to roughly 10K GPUs.
  • What changed: better NICs (GPUDirect RDMA, better DMA engines), larger RoCE fabrics with congestion control, stronger NVLink inside a node, and special fabrics across zones and data centres.
  • New workloads: MoE routing needs dynamic all-to-all. TP wants compute and comms to overlap. Pipeline parallel needs send and receive. Inference needs fast KV cache movement. 100K+ GPU jobs need fault tolerance.
  • TorchComms: explicit communicators, pluggable backends, richer semantics, and a path that stays aligned with PyTorch. The stack: your code, then the TorchComms API, then an NCCLX or RCCLX backend, then the CTran transport, then IB or RoCE, NVLink or sockets.
  • The default path: data is copied by a GPU kernel into NCCL's internal buffer, moved by DMA to the NIC, sent, received, then copied again on the other side.
  • The zero-copy path: the NIC reads straight from your buffer and writes straight into the receiver's buffer. No staging copies.
  • The wait and stall step: the host queues the op, a CPU progress thread drives the RDMA, and the GPU stream stalls at one point until it finishes. It also compared RDMA put and get, and how CTran sets up one control connection plus data connections.
  • Where it was measured: medium messages, about 1 MB to 128 MB, in point-to-point cases.
