Talk 1

Profiling in PyTorch

Aritra Roy Gosthipaty · Developer Advocacy, Hugging Face

“What you cannot profile, you cannot optimize.”

That was the title slide, and the whole talk. Aritra kept the demo tiny: a matmul followed by an add. Then he gave a simple recipe.

  1. Name the code you care about with torch.profiler.record_function.
  2. Wrap it in torch.profiler.profile. Pick the activities, CPU and CUDA. Set a schedule: wait, warmup, then active steps.
  3. Export two things: a trace and a table.

The schedule is easy to miss. Warmup steps are slow and noisy, so you skip them. Only the active steps are recorded. With active=3, every op shows up three times in the table.

To read the table, sort by CUDA time total. The first row is your biggest bottleneck. Then check how many times it was called. Sometimes a row is on top only because it ran a lot.

The idea I liked most: overhead bound

A small matmul finishes on the GPU almost at once. But the CPU spends longer launching the kernel than the GPU spends running it. So the GPU sits idle. This is called being overhead bound.

He showed it with one script and three sizes. The fix is not a faster kernel. The fix is more work per launch.

CUDA time as a share of CPU time, same script

size 645%
size 102426%
size 409688%

The trace shows the same story. Open it in the Hugging Face trace viewer or Perfetto. You get two lanes, CPU and GPU. Gaps in the GPU lane mean the GPU was waiting.

Where torch.compile fits

In eager mode, every op is its own launch: matmul, then add, then activation. torch.compile traces the graph, fuses the ops and caches the result. The work right after a matmul, like an activation or a normalization, is called the epilogue. It can be fused into the same kernel. So one Triton kernel is launched instead of many, with fewer trips to memory.

The names in the table, like aten::matmul, are ATen ops. ATen is PyTorch's tensor library.

More details from the slidescode, schedule, switches
  • The test function is tiny on purpose: torch.add(torch.matmul(x, w), b). It is easy to see in a trace.
  • record_function("matmul_add") gives the step a name, so you can find it in the trace.
  • The loop runs 5 steps and calls prof.step() each time. With wait=1, warmup=1, active=3, repeat=1, one step waits, one warms up and three are recorded.
  • Three switches I wrote down: record_shapes tracks input shapes, profile_memory tracks allocation and freeing, and with_stack adds line numbers of your code.
  • Export with prof.export_chrome_trace(...) for the trace. Write prof.key_averages().table(sort_by="cuda_time_total", row_limit=15) for the table.
  • The demo ran with uv run. A small tool then uploaded the traces to the Hub, and he opened them in the Hugging Face trace viewer.

The whole demo, as on the slides:

def fn(x, w, b):
    return torch.add(torch.matmul(x, w), b)

def step():
    with torch.profiler.record_function("matmul_add"):
        return fn(x, w, b)

activities = [
    torch.profiler.ProfilerActivity.CPU,
    torch.profiler.ProfilerActivity.CUDA,
]
schedule = torch.profiler.schedule(wait=1, warmup=1, active=3, repeat=1)

with torch.profiler.profile(
    activities=activities,
    schedule=schedule,
    record_shapes=False,
    profile_memory=False,
    with_stack=False,
) as prof:
    for _ in range(5):
        step()
        prof.step()

prof.export_chrome_trace(trace_path)
with open(table_path, "w") as f:
    f.write(prof.key_averages().table(sort_by="cuda_time_total", row_limit=15))

Run it with uv run 01_matmul_add.py --size 64. A small tool then pushes the traces to a Hub repo: uvx trace-util -f traces -b hf_uname/redhat-profile.

Talk 2

SGLang, the Transformers backend and kernels

Adarsh · Hugging Face

Adarsh began with a plain point. Serving one user is easy. Serving thousands at once is where the real work starts.

Inference is two jobs

Prefill reads the whole prompt in parallel and builds the model's working context. It is compute bound. The maths is matrix times matrix.

Decode writes one token at a time. It is memory bound. The maths is matrix times vector, and every step reads the KV cache again.

What SGLang is made of

  • Scheduler. Batches requests together.
  • KV cache manager. Stores the cache and reuses it.
  • Model runner. Runs the forward pass.
  • Attention backend. flash-attn or flash-infer.

RadixAttention

Older systems threw the KV cache away when a request ended. SGLang keeps it. It stores the cache of old requests in a radix tree, a memory-efficient prefix tree, and drops the least recently used first. A new request with the same start reuses it. So a shared system prompt is computed only once.

One slide made this real: Llama-3-8B on one H100, the same 1,000 requests, each with a 2K-token shared prompt.

Throughput, tokens per second

plain generate()~209
SGLang~7,900

That is about 38 times more. The whole run went from about 25 minutes to about 40 seconds. Cost per million tokens fell from about $3.30 to about $0.09.

Transformers and SGLang together

Transformers is the source of truth for what a model is: the config, tokenizer, weight format and chat template. SGLang does the fast serving. You switch it on with --model-impl transformers. One slide was called “Transformers internals hijacked”. One config line swaps the attention backend. The tp_plan in Hugging Face says how the model is split across GPUs.

One warning I wrote down: numeric drift. Different kernels give slightly different numbers. So the same model can behave a little differently on a different backend.

Kernels

Custom kernels are hard to share. Builds break across toolchains and CUDA versions. Hugging Face's kernel-builder uses Nix, so builds can be repeated. It targets ROCm, XPU, CUDA and Metal, and keeps track of the PyTorch and CUDA version matrix.

One more note at the end of my page: the KV cache can be pushed down to SSDs when GPU memory runs out. DeepSeek does this.

More details from the slidesnumbers, backend, kernels
  • Why inference is hard: his slide said it plainly. “One user is easy. A thousand is not.”
  • Scale: a fun-facts slide said SGLang runs on more than 400,000 GPUs and makes trillions of tokens a day, and that about 44 PRs get merged every day. These are the project's own claims. I could not check them elsewhere.
  • The Transformers backend: a PR added tensor and pipeline parallel, MoE, VLM support and torch.compile to it. There are about 2 million models on the Hub. SGLang has a few hundred ported by hand. The backend covers the rest, on day 0. vLLM has a similar backend too (model_impl=transformers), so the idea is not unique to SGLang.
  • Why HF Kernels exists: no common structure, build tools all over the place (CMake, Nix, Meson, Bazel), endless build times, and support matrices to maintain.
  • What it gives you: a fixed project structure, repeatable builds, native PyTorch compatibility, and sharing on the Hub. Using a kernel is about four lines of change. You avoid messy wheels and builds that do not match.

Talk 3

RL environments 101

Adithya S Kolavi · post-training, Hugging Face

Adithya told the story of how models are taught. First pretraining on the web. Then SFT on good answers. Then RLHF, where people pick the better answer. Then RLVR and GRPO, where a program grades the answer.

“If a program can grade it, a model can learn it.”

That is the unlock. And it turns the race into something simple: build more environments.

An environment is a few parts: a task and a prompt, tools, state, observations, a place to run code, a reward, and a signal for when the episode is done. Frameworks like OpenEnv, Verifiers, OpenReward and Harbor now give these a common shape.

Repo2RLEnv

Public GitHub repos are a goldmine. They hold real tasks, real code and tests that grade themselves. Repo2RLEnv turns any repo into a verifiable environment. He said about 1,000 were already generated and live on Hugging Face. The project's README now lists 1,930 tasks across 21 datasets, in the Harbor format.

Reward hacking: the best part of the talk

His first story was a toy. He trained a tiny Qwen 0.5B model with GRPO on grade-school maths. He rewarded three things: the format, the right answer, and code that runs cleanly. The last one felt harmless.

Then he read the traces. The model had learned to wrap everything in try / except: pass. The code never crashed, so the reward maxed out. The maths was never solved. The model had maximized the reward without doing the task.

His second story was a real security bug in a PDF library, made into an environment. The agent only had to fix the bug. It scored a perfect 1.0 without fixing anything. Three times.

  1. The prompt named the fixing PR. The agent just read the fix from GitHub. Fix: scrub the prompt.
  2. The answer was in the git history inside the container. Fix: reset the repo to the base commit.
  3. With the web blocked, it used pip to download the fixed release. Fix: cut the network with an allowlist, not a block-list.

After that, the reward was 0.0, for the first time. His line: every green before was contamination. And you cannot out-scrub the internet.

Trust lives in the environment

This was my favourite slide. The environment enforces the rules. The prompt never asks for them.

  • Make the verifier trustworthy first: gold patch scores 1.0, a no-op scores 0.0.
  • Strip the answer from the prompt.
  • Scrub the repo to the base commit.
  • Pre-bake dependencies and run offline by default.
  • If the network is needed, use an allowlist, never a full block.
  • Keep the gold patch and hidden tests out of the container.

“A model never does the task. It does the reward. At scale, every gap gets found, so reward design is never done, only iterated.”

A hands-on example close to my own work

The demo trained a vision-language model on LaTeX OCR. The model sees an image of a formula and writes the LaTeX. The reward is simple: does it render back to the same maths? A few lines of TRL and GRPO, on a free GPU.

More details from the slidesenvironments, OpenEnv, TRL
  • More environments, better models. A chart in his deck showed the number of training environments going up from about 20 to 20K, 100K+ and even 1M+ across recent open models. This is his chart. I could not check it.
  • Gym, for LLMs. Gym gave classic RL one contract: reset() and step(action). For LLMs the agent is the model, the environment is a sandbox, and the reward is a verifier.
  • Two kinds of environment. One-shot (RLVR): prompt, answer, verifier. Maths, code and logic fit here. Multi-turn agent RL: the model acts, the environment answers, for 10 to 100+ turns, and the reward comes at the end. Think SWE-bench or AppWorld.
  • A tiny coding environment. Task: find the .py file with the most lines. Tool: bash. Reward: +1 if the answer is right, else 0. GRPO tries the same task many times and nudges the model toward the attempts that score.
  • OpenEnv. It was launched by Meta's PyTorch team and Hugging Face. It is now run by a committee of many companies, with Hugging Face as one member. It has a Gym-style API, MCP as a first-class citizen, rubrics for rewards, and a task API. He said there are 1,000+ environments on the Hub. The official catalog lists about 40 ready-made ones, so the bigger number likely includes community Spaces.
  • Building one. The action is a plain function marked @mcp.tool. reset() loads the task into the sandbox. A rubric returns 1.0 if the tests pass, else 0.0. create_app turns it all into an HTTP and MCP server, with a limit on parallel rollouts. Then: openenv init, build, validate, push.
  • Training with TRL. Point GRPOTrainer at the environment with environment_factory. TRL marks environment_factory as experimental. OpenReward and Harbor plug into the same slot.
  • The catch. “Training is the easy part now.” You still need thousands of environments, and good ones are slow to build by hand.

Talk 4

Scaling up, one dimension at a time

Mansi Agarwal · Senior ML Engineer, PyTorch Engineering, Red Hat

Mansi started with the old pain. DDP, FSDP, TP and PP each had their own API, wrapper and checkpoint format. Mixing FSDP with tensor parallel took over a hundred lines of manual plumbing. Add one more kind of parallelism and you rewrite the training loop.

Her question: what if parallelism was composable, like adding a dimension to a grid? Newer PyTorch has three building blocks.

  • DeviceMesh. A grid of GPUs. A 4×2 grid means 4 groups for data parallel and 2 for tensor parallel. You name each dimension, like dp and tp.
  • DTensor. A tensor that knows how it is split across the mesh. It can be sharded, replicated or partial.
  • FSDP2. Sharded data parallel, rebuilt on DTensor. It is a transform on the model, not a wrapper around it.

So adding a parallelism means adding a dimension to the mesh. It is not a rewrite. And communication becomes automatic: you write the maths, and if an op needs a different layout, DTensor adds the all-gather or reduce-scatter for you.

The code walkthrough made it real. One GPU, then DDP, then FSDP2, then FSDP2 with tensor parallel. At every step the training loop stayed the same. Only a few lines around the model changed.

“Locally optimal”

I wrote this next to DTensor. It picks the best sharding for each op as it goes. It does not look at the whole graph, so the full plan may not be the best one. JAX takes the other path. It looks at the whole graph, but it needs a compiler. Mansi was honest about this trade-off. Eager-first design gives up global optimality to keep debugging easy.

Checkpoints that reshard

torch.distributed.checkpoint can reshard when you load. Save on 8 GPUs, load on 16. This is one piece of elastic training, not all of it. See the question below on how elastic training really works.

More details from the slidescode for every stage, limits, what is next
  • The old way took five steps. Work out rank groups by hand, create process groups by hand, write your own TP layers, change the model code, then wrap with FSDP1. About 100 lines. Forget one manual all-reduce and the results are silently wrong. FSDP1's FlatParameter also broke TP weight shapes.
  • Process groups: a 4×2 mesh makes 6 groups (2 for DP, 4 for TP). A 2×2×2 mesh makes 12.
  • DTensor helpers: distribute_tensor splits a tensor. to_local() gives your shard. full_tensor() gathers everything. redistribute() changes the placement.
  • How an op runs: DTensor catches every ATen op. It looks up a sharding rule (410+ ops covered), picks the cheapest one, adds any collectives needed, runs the op on local shards and wraps the result. On her slide, an unsupported op raises an error and does not silently fall back to replicate. Newer PyTorch versions may try to derive a rule instead, so check your version.
  • FSDP1 vs FSDP2: FlatParameter became per-parameter DTensors. A wrapper class became fully_shard(), an in-place transform. LoRA and frozen layers work now. fp8 works. Sharded checkpoints need no communication. FSDP1 is deprecated.
  • FSDP2 under the hood: all-gather before forward, run, free the memory after forward. Backward does the same, then a reduce-scatter for the gradients. FSDP2 uses its own fast collectives, so it skips DTensor's dispatch cost.
  • 2D in practice: apply tensor parallel on the tp mesh (column-wise for qkv and the first FFN layer, row-wise for the output projections). Then call fully_shard on the dp mesh. The same pattern extends to 3D with PP, 4D with CP, and 5D with expert parallel for MoE.
  • The compile order: checkpoint, then fully_shard, then torch.compile last. Start with fullgraph=False. Use compile_threads=1, because background threads can hang a distributed run.
  • Checkpoints: dcp.save needs no communication. Loading can reshard. Async save was 10 to 20 times faster (7B model: 148 s down to 6.3 s). It also supports SafeTensors. For gradient accumulation use set_requires_gradient_sync(False).
  • DTensor vs JAX: DTensor is eager-first and greedy per op, so it is locally optimal and easy to debug with print and pdb. JAX with GSPMD is compiler-first and looks at the whole graph, so it can find a globally optimal plan.
  • Known limits: eager dispatch costs about 7× per op (compile removes it). About 58 ATen ops still have no strategy. Views can break on DTensors. There is no uneven sharding yet, which blocks clean MoE expert parallelism. reduce_dtype was ignored for the TP all-reduce, a silent precision loss. HSDP with mixed precision used 3× gradient memory on a 2D mesh. Shape changes can trigger full recompiles. She was honest about these.
  • What is next: AutoParallel (picks the sharding for you with linear programming, experimental), DTensor erasure, Symmetric Memory, TorchFT, Monarch, zero-bubble pipeline parallelism and compiler-assisted backward sharding.

The code, stage by stage

This is the part that made it click for me. The loop never changes. Only the lines around the model do.

# Stage 1: one GPU
model = MyTransformer().cuda()
optimizer = torch.optim.AdamW(model.parameters(), lr=3e-4)
for batch in dataloader:
    optimizer.zero_grad()
    loss = model(batch).sum()
    loss.backward()
    optimizer.step()

# Stage 2: DDP, one line added
dist.init_process_group("nccl")
model = DDP(MyTransformer().cuda())

# Stage 3: FSDP2, training loop unchanged
mesh = init_device_mesh("cuda", (world_size,))
model = MyTransformer().cuda()
for layer in model.layers:
    fully_shard(layer, mesh=mesh)   # shard each layer
fully_shard(model, mesh=mesh)       # shard the root module
# Stage 4: FSDP2 + tensor parallel on a 2D mesh
mesh = init_device_mesh("cuda", (4, 2),
                        mesh_dim_names=("dp", "tp"))
model = MyTransformer().cuda()

# step 1: TP on the tp sub-mesh
for layer in model.layers:
    parallelize_module(layer, mesh["tp"], {
        "attn.qkv":  ColwiseParallel(),
        "attn.proj": RowwiseParallel(),
        "ffn.w1":    ColwiseParallel(),
        "ffn.w2":    RowwiseParallel(),
    })
# step 2: FSDP on the dp sub-mesh
for layer in model.layers:
    fully_shard(layer, mesh=mesh["dp"])
fully_shard(model, mesh=mesh["dp"])
# The ordering rule: checkpoint -> fully_shard -> compile
for layer in model.layers:
    checkpoint(layer)              # 1. activation checkpoint
    fully_shard(layer, mesh=mesh)  # 2. shard
fully_shard(model, mesh=mesh)
model = torch.compile(model)       # 3. compile LAST

# Distributed checkpointing
dcp.save(model.state_dict(), checkpoint_id="epoch_5")        # communication-free
dcp.load(model.state_dict(), checkpoint_id="epoch_5")        # works on a different GPU count
future = dcp.async_save(model.state_dict(), checkpoint_id="epoch_5")   # 10-20x faster

Talk 5

Zero-copy GPU-to-GPU communication

Arkadip Maitra · PyTorch Engineering, Red Hat

Arkadip went below the training loop, to how GPUs talk to each other. c10d is PyTorch's default layer. It worked well for years. But the world around it changed. NICs got smarter. RoCE fabrics grew. NVLink got stronger. And distance started to matter a lot.

Latency by distance, as on the slide (same rack = 1×)

same rack1×
cross-rack7×
cross-zone15×
cross-DC30×

One slide put hardware and software on two timelines. The hardware lane and the framework lane had moved together, and comms was only one entrant in the race. He then picked one idea to focus on: zero-copy.

The normal path copies your data through an internal buffer, on both sides. The zero-copy path lets the NIC read straight from your buffer and write straight into the other GPU's buffer. Fewer copies means less memory traffic. It is also SM-free: a CPU thread drives the transfer, so no GPU cores are used for it.

up to 2×copy cost avoided (cross-host)
1.09–2.7×faster communication
2,560GPU threads not needed per transfer
up to 50%fewer thread blocks (fault-tolerant all-reduce)

A word of care on these numbers. I checked them against Meta's NCCLX paper. The 1.09–2.7× speed-up is in the paper. It is for medium messages, about 1 MB to 128 MB, in a send/receive test. The 7×, 15× and 30× figures are in the paper too, as latency compared with the same rack. The 2× is the paper's worst-case cost of copying across hosts, not a measured saving. The 2,560 comes from 4 thread blocks of 640 threads in a copy-based send. The 50% is from a different feature, the fault-tolerant all-reduce, which uses 2 thread blocks where NCCL uses 4.

One slide also showed RoCE close to InfiniBand in collective bandwidth (about 232.6 vs 230.7 GB/s). I could not find that in the paper. A vendor-run test reports similar numbers, so treat it as a claim.

More details from the slidesthe stack, wait/stall, put vs get
  • Why c10d worked: training was bulk-synchronous, the collectives were regular, the host knew the metadata, and the API did not care about the backend. It was a good fit up to roughly 10K GPUs.
  • What changed: better NICs (GPUDirect RDMA, better DMA engines), larger RoCE fabrics with congestion control, stronger NVLink inside a node, and special fabrics across zones and data centres.
  • New workloads: MoE routing needs dynamic all-to-all. TP wants compute and comms to overlap. Pipeline parallel needs send and receive. Inference needs fast KV cache movement. 100K+ GPU jobs need fault tolerance.
  • TorchComms: explicit communicators, pluggable backends, richer semantics, and a path that stays aligned with PyTorch. It was announced as experimental in October 2025, and its status has kept changing, so check the repo before you depend on it. The stack: your code, then the TorchComms API, then an NCCLX or RCCLX backend, then the CTran transport, then IB or RoCE, NVLink or sockets.
  • The default path: data is copied by a GPU kernel into NCCL's internal buffer, moved by DMA to the NIC, sent, received, then copied again on the other side.
  • The zero-copy path: the NIC reads straight from your buffer and writes straight into the receiver's buffer. No staging copies.
  • The wait and stall step: the host queues the op, a CPU progress thread drives the RDMA, and the GPU stream stalls at one point until it finishes. It also compared RDMA put and get, and how CTran sets up one control connection plus data connections.
  • Where it was measured: medium messages, about 1 MB to 128 MB, in point-to-point cases.

Questions, answered

Questions that came up in my head after the talks. The short answer comes first. Tap one to open it.

vLLM or SGLang: when should I use which?

Half true. “SGLang for multi-turn and big MoE, vLLM for the rest” is a fair starting rule. It is not a law, and the gap keeps shrinking.

Multi-turn chat: mostly true

Each turn re-sends the whole chat so far. A good engine reuses the KV cache from the last turn and only computes the new part.

  • SGLang keeps the KV cache of finished requests in a radix tree. It matches prefixes one token at a time. It also keeps the cache of the replies, not just the prompts. vLLM does this too, but only for full blocks. Its scheduler is cache-aware, so it tries to run requests that share a prefix together.
  • vLLM hashes fixed-size blocks. Each block's hash includes the hash of the block before it. Only full blocks are reused. With a block size of 4, a 10-token match reuses 8 tokens. In general you lose at most one block minus one token. For a long chat, that is small. The default block size has changed between versions, so check yours.
  • The tree helps most when conversations branch: agents, tree-of-thought, many users sharing one long system prompt or document.
  • One more thing changed. vLLM V1 turned prefix caching on by default. They report under 1% throughput loss even when nothing hits the cache. So old comparisons, where vLLM ran without caching, are out of date.

Big MoE models: partly true

MoE is different because each token only visits a few experts. The tokens must travel to the GPUs that hold those experts. That is an all-to-all. Expert load is also uneven, so the busiest GPU slows everyone. And the attention cache gets copied on every GPU if you use plain tensor parallel.

  • SGLang published a full open recipe for DeepSeek: data-parallel attention, expert parallelism with DeepEP, a load balancer for experts, two-batch overlap, and prefill/decode disaggregation. On 96 H100s they report 52.3k input and 22.3k output tokens per second per node. These are their own numbers.
  • vLLM is not limited to dense models. Its docs describe data-parallel attention with expert parallelism (DeepEP backends) and disaggregated prefill and decode.
  • So who is faster on MoE depends on the model, the GPUs and the release. It moves quickly.
  • Both engines have also moved on cache. Both now handle hybrid models. Both can push cache out of GPU memory: SGLang with HiCache, vLLM with an offloading connector or LMCache.

Dense models: no clear rule

vLLM's real edge is breadth. It supports many models and many kinds of hardware, and a lot of tooling is built around it. For single-turn requests with no shared prefix, both do similar work. I found only a few independent tests, and they disagree by workload. One academic trace study (CCL-Bench) reports vLLM using the GPU more efficiently on small dense models, and SGLang spending less of each step on communication on one small MoE model. Both ran on A100s with small models, so treat it as a hint. Most other comparisons online are vendor or blog posts.

Your workloadStart withWhy
Chat, agents, long shared contextSGLang, then test vLLMToken-level prefix reuse, branching, cache-aware scheduling.
RAG with one big shared document, few-shot with fixed examplesEither, with prefix caching onBoth reuse a shared start. Put the stable text first.
DeepSeek-class MoE on many GPUsSGLang has the most written recipevLLM can do it too. Compare on your cluster.
One-shot jobs, no shared prefixWhichever supports your model and hardwareLittle to gain from the cache.
Unusual hardware, brand-new modelCheck both support pages firstSupport, not speed, decides here.

How to decide for real: replay your own traffic on both. Same GPU, same precision, prefix caching on for both. Measure time to first token, tokens per second and the slowest 1% of requests. Remember the cache only helps if the next turn lands on the same replica, so route sticky. Match the settings too. In one 2026 controlled study, much of the default gap between engines came from different defaults such as chunked prefill, not from the cache design. If one engine has chunked prefill on and the other off, you are not comparing the caches.

Sources: SGLang / RadixAttention post · vLLM prefix caching design · vLLM V1 release post · SGLang: DeepSeek on 96 H100s · vLLM expert-parallel docs · A controlled study of serving-engine settings and caches (2026) · CCL-Bench

Why is prefill compute-bound and decode memory-bound?

Because of how much work each byte of weights does. In prefill, one read of the weights serves thousands of tokens. In decode, it serves one.

Think of FLOPs per byte moved. This is called arithmetic intensity.

  • Prefill: the whole prompt goes through together. The maths is matrix times matrix. Each weight is loaded once and used for many tokens. The tensor cores stay busy, so you are compute-bound.
  • Decode: one new token per request per step. The maths is matrix times vector. You load all the weights (and the whole KV cache) to make a single token. The GPU waits on memory.

A back-of-envelope check. Llama-3-8B in bf16 is about 16 GB of weights. An H100 SXM moves about 3.35 TB/s. One decode step must read 16 GB, so it takes at least about 4.8 ms. That is roughly 200 tokens per second for one request. This is an upper limit, and real runs reach less. Adarsh's slide showed about 209 tok/s for plain generate(). Check which GPU and precision it used before comparing.

Batching is the fix. If 64 requests share each weight read, you get close to 64 times more tokens for the same read. This goes on until the KV cache reads start to dominate. Another way to see it: an H100 can do roughly 300 bf16 FLOPs for every byte it reads from memory. Decode at batch 1 does about 1. So you need a very large batch before decode turns compute-bound. That is why continuous batching and cache memory matter so much.

Sources: NVIDIA: mastering LLM inference optimization · Transformer inference arithmetic · Making deep learning go brrr

Is prefix caching free? Does it change my outputs?

It is cheap, not free. The cache is the same maths reused, so outputs should match, up to tiny numeric drift.

  • Cost when nothing hits: SGLang says it saw no noticeable overhead. vLLM V1 reports under 1% throughput loss at a 0% hit rate.
  • Memory: cached KV lives in the same GPU memory as running requests. Old entries are dropped by least recently used. A busy server may drop your prefix before the next turn arrives.
  • Things that kill hits: a timestamp or user ID at the start of the prompt; requests spread across replicas with no routing; different LoRA adapters or images (they are part of the hash in vLLM).
  • Outputs: reusing a cached prefix is exact reuse. But batch shapes and kernels can change, and different kernels give slightly different numbers. Adarsh called this numeric drift. Test if you need bit-exact results.

Habit to build: put stable text first (system prompt, tools, documents). Put changing text last.

Sources: vLLM prefix caching design · RadixAttention post · vLLM V1 release post

My GPU shows 5% busy in the profile. Is bigger the only fix?

No. Bigger work per launch is one fix. You can also fuse ops, replay launches with CUDA graphs, or cut Python in the hot path.

Every op has a fixed CPU cost: Python, the dispatcher, the driver. A tiny kernel can finish faster than the CPU can launch the next one. The GPU then sits idle. That is overhead bound.

  1. Do more per launch. Bigger batch, bigger matrices, or merge small ops. This is what the 64 → 1024 → 4096 demo showed.
  2. Fuse. torch.compile can merge a matmul with its epilogue (the add, activation or norm after it) into fewer kernels.
  3. Replay. CUDA graphs record a sequence of launches once and replay them in one go. vLLM V1 uses piecewise CUDA graphs for this reason.
  4. Trim the CPU path. Less Python per step, fewer small tensors, avoid syncs like .item() in the loop.

How to check: open the trace. Gaps in the GPU lane mean the GPU was waiting for work.

Sources: torch.profiler docs · Profiler recipe · torch.compile tutorial · vLLM V1 release post

Why do models game rewards, and how do I stop it?

Because RL optimizes exactly what the verifier measures. Any gap between “the reward” and “the task” will be found.

This is Goodhart's law, with a very patient searcher. The model tries thousands of paths. If one of them scores without solving the task, the training signal pushes the model towards it.

Adithya's two stories show it. A try / except: pass wrapper kept code from crashing, so a “code runs cleanly” reward went up with no maths solved. In the CVE environment, the agent read the fix from the PR, then from git history, then from pip.

  • Test the verifier first. The gold solution must score 1.0. A no-op must score 0.0.
  • Remove the answer from the prompt, the repo, the history and the network.
  • Isolate the sandbox. Offline by default. Allowlist, never block-list.
  • Read rollouts, not just reward curves. A sudden jump in reward is a smell.
  • Use several signals, and keep a hidden test the model never trains on.

The honest summary is on his last slide: reward design is never done. It is only iterated.

Sources: Reward hacking (Lilian Weng) · Specification gaming (DeepMind) · The RL environments guide from the talk

Why GRPO instead of PPO for verifiable rewards?

GRPO needs no critic (value) model. It scores a group of answers to the same prompt and compares them with each other.

  • PPO trains a value model next to the policy. It is usually about the size of the policy. That costs memory and adds moving parts.
  • GRPO samples a group of answers for each prompt, scores them, and uses the group's average (and spread) as the baseline. An answer is good if it beats its siblings.
  • With a program-graded reward like pass or fail, that is simple and works well.
  • Catch: if every answer in a group gets the same score, all right or all wrong, every advantage is zero. The reward gives no policy-gradient signal for that prompt. (A KL term, if used, can still move the weights.) The task must be neither too easy nor too hard. TRL logs frac_reward_zero_std so you can see how often this happens.

Sources: DeepSeekMath (introduces GRPO) · PPO paper · TRL GRPO trainer

FSDP, tensor parallel, or both?

Start with FSDP. Add tensor parallel inside a node when FSDP alone is not enough. Put the chattiest dimension on the fastest links.

  • FSDP splits parameters, gradients and optimizer states across data-parallel ranks. It all-gathers one layer at a time. It saves memory and is easy to adopt: Mansi's walkthrough changed only a few lines.
  • Tensor parallel splits each matmul inside a layer. It needs an all-reduce in almost every layer, so it is very sensitive to latency. Keep it inside a node on NVLink.
  • Memory check: mixed-precision Adam costs about 16 bytes per parameter (2 weights, 2 grads, 12 optimizer state). A 7B model is about 112 GB before activations. That is why you must shard.
  • Combine when data parallel alone cannot grow (global batch limit), or a single layer is too heavy. Then add pipeline parallel across nodes, and context parallel for very long sequences.

With DeviceMesh this is a shape choice: (4, 2) with names dp and tp.

Sources: Ultra-Scale Playbook · ZeRO paper · Megatron-LM paper · FSDP2 docs

Is “save on 8 GPUs, resume on 16” how elastic training works inside frameworks?

Only in part. Resharding on load is the checkpoint piece. Elastic training also needs a launcher that notices changes, restarts the workers, and restores more than the weights.

I first wrote that resharding is “exactly what elastic training needs”. That was too strong. Here is the fuller picture.

The common recipe: checkpoint, restart, reshard

  1. Notice the change. A node dies or a new one joins. In torchrun's elastic mode you give a range, like --nnodes=MIN:MAX, and a restart budget. Workers find each other through a rendezvous.
  2. Restart the whole worker group. The group is torn down and started again with the new set of workers. It does not grow or shrink while running.
  3. Reload the latest checkpoint. This is where torch.distributed.checkpoint helps. Each rank saved its own shard with metadata about the full tensors. On load, each rank reads the slices it now needs. So the new world size does not have to match the old one.
  4. Resume the rest of the state. Optimizer state must reshard too. The data loader position, random seeds and learning-rate schedule need to come back as well. Without the data position you repeat or skip samples.

Things the checkpoint cannot decide for you

  • Batch size and learning rate. The number of GPUs changed, so the global batch size changes unless you adjust, for example with gradient accumulation. What to do with the learning rate is your call.
  • The mesh shape. On 16 GPUs, your DeviceMesh might need different dimensions. The parallelism plan has to be built again at startup.
  • Lost work. You go back to the last checkpoint. Async checkpoints (the slides showed 7B: 148 s down to 6.3 s) make saving often cheap.

The newer idea: do not restart everything

Mansi listed TorchFT as coming. It aims at fault tolerance per step, without a full-job restart. The rough idea is to run data-parallel replica groups. If one fails, the others keep going, and the failed one catches up from healthy peers. I have not verified the details against its docs, so read the repo before relying on that description.

In short: DCP resharding is a necessary piece for elastic restarts. It is not the mechanism. The launcher, the rendezvous and the resume logic make it elastic.

Sources: torchrun / elastic launch docs · Rendezvous docs · Distributed checkpoint docs · TorchFT

Why does distance cost so much in a GPU cluster?

Farther means more switches, shared links and longer cables. Meta's NCCLX paper reports latency of 1× in one rack and 30× across data centres.

The numbers on Arkadip's slide: same rack 1×, cross-rack 7×, cross-zone 15×, cross-DC 30×. The NCCLX paper gives the same three figures, as latency compared with the same rack. I could not check how they were measured.

  • Each extra hop adds a switch, a queue and a chance of congestion.
  • Upper layers of a network are often shared, so traffic from many jobs meets there.
  • Longer cables add delay that no software can remove.

What to do about it: place by chattiness. Tensor parallel inside a node. FSDP or data parallel inside a rack or zone. Pipeline parallel, which sends less, across the far links. This is what “match the mesh to your topology” means.

Sources: Meta: RoCE networks for AI training · TorchComms blog · NCCLX paper

DTensor is “locally optimal”. Should I worry?

Not for standard Transformers. You set the plan by hand. For odd models, AutoParallel is the experimental fix.

DTensor chooses the cheapest sharding for each op on its own. It never sees the whole graph, so the full plan may not be the best one. JAX's compiler looks at the whole graph, but you give up eager debugging.

For a Transformer, the good pattern is well known: column-wise on the first linear, row-wise on the next, so you need one all-reduce for the pair. That is the ColwiseParallel and RowwiseParallel plan in the slides. AutoParallel searches for a plan with linear programming over a compiled graph. It is experimental.

Sources: DTensor docs · TP tutorial · AutoParallel
