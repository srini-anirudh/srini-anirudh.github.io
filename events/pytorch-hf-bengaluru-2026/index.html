Talk 1

Profiling in PyTorch

Aritra Roy Gosthipaty · Developer Advocacy, Hugging Face

“What you cannot profile, you cannot optimize.”

That was the title slide, and the whole talk. Aritra kept the demo tiny on purpose. The question on slide two was simply: what to profile? His answer was y = Wx + b, written in PyTorch as a torch.matmul followed by a torch.add.

Three steps

  1. Annotate the function. Wrap the step in torch.profiler.record_function("matmul_add"), so it has a name in the trace.
  2. Wrap the code. Use torch.profiler.profile and pick two things. The activities are CPU and CUDA. The schedule is wait, warmup, then active steps: wait=1, warmup=1, active=3, repeat=1. Three more switches sat in red boxes on the slide: record_shapes, profile_memory and with_stack.
  3. Export two things. A trace with export_chrome_trace, and a table with key_averages().table(...).
From my notes

The three switches, as I wrote them: record_shapes tracks the shapes of the inputs. profile_memory tracks allocation and deallocation. with_stack gives the line numbers of the code.

How to read the table

Sort by cuda_time_total. Look at the first row. That is your biggest bottleneck. Then look at the number of calls. With active=3, every op was recorded three times, so every row shows 3×. His advice, which I underlined: see if the call count is the reason a row comes up on top.

The idea I liked most: overhead bound

At the bottom of the table there are two totals: self CPU time and self CUDA time. Aritra ran one script at three matrix sizes and read the ratio.

CUDA time as a share of CPU time, same script (slides 12 to 14)

size 645%
size 102426%
size 409688%

At size 64, the CPU spent 332 µs and the GPU only 17.8 µs. The matrix is so small that the CPU takes most of the time just to dispatch the CUDA kernels. The GPU sits idle. That is overhead bound. At size 4096 the GPU finally has real work, and the two sides are close.

From my notes

My rule of thumb from the page: compare t(CPU) with t(GPU) at the bottom of the table. If the GPU time is larger, you are compute bound. If the CPU time is larger, the kernels are too small and you are overhead bound. I had crossed out “memory bound” here. It is a separate case.

Reading the trace

The trace goes into the Hugging Face trace viewer (a Space by Suvaditya), or into Perfetto. It is a temporal view with two lanes, a CPU lane and a GPU lane. Gaps in the GPU lane are idle time. The op names, like aten::matmul and aten::add, are ATen ops. ATen is PyTorch's tensor library. I noted that a Red Hat blog covers this too.

Where torch.compile fits

This part is mostly from my own notes, from how he linked it to the table. In eager mode each op is its own launch. torch.compile uses Dynamo to trace the graph, and it caches the result. It can fuse operations. For example, an aten::add after aten::mm becomes aten::addmm. I wrote: this is graph fusion, not CUDA fusion. Fewer launches means less overhead.

The same idea goes further inside an MLP. A matmul is done in tiles. The work right after it, like an activation or a normalization, is called the epilogue. It can run while the result is still in the buffer. A compiled graph then launches one Triton kernel instead of several. The fix for overhead bound is not a faster kernel. It is more work per launch.

More details from the slidescode, schedule, switches
  • The test function is tiny on purpose: torch.add(torch.matmul(x, w), b). It is easy to spot in a trace.
  • record_function("matmul_add") gives the step a name, so you can find it in the trace.
  • The loop runs 5 steps and calls prof.step() each time. With wait=1, warmup=1, active=3, repeat=1, one step waits, one warms up and three are recorded.
  • The slide boxes three switches in red: record_shapes tracks input shapes, profile_memory tracks allocation and freeing, and with_stack adds line numbers of your code. All three are off in the demo.
  • Export with prof.export_chrome_trace(...) for the trace. Write prof.key_averages().table(sort_by="cuda_time_total", row_limit=15) for the table.
  • The demo ran with uv run. A small tool then pushed the traces to a Hub repo, and he opened them in the Hugging Face trace viewer.

The whole demo, as on the slides:

def fn(x, w, b):
    return torch.add(torch.matmul(x, w), b)

def step():
    with torch.profiler.record_function("matmul_add"):
        return fn(x, w, b)

activities = [
    torch.profiler.ProfilerActivity.CPU,
    torch.profiler.ProfilerActivity.CUDA,
]
schedule = torch.profiler.schedule(wait=1, warmup=1, active=3, repeat=1)

with torch.profiler.profile(
    activities=activities,
    schedule=schedule,
    record_shapes=False,
    profile_memory=False,
    with_stack=False,
) as prof:
    for _ in range(5):
        step()
        prof.step()

prof.export_chrome_trace(trace_path)
with open(table_path, "w") as f:
    f.write(prof.key_averages().table(sort_by="cuda_time_total", row_limit=15))

Run it with uv run 01_matmul_add.py --size 64. Push the traces with uvx trace-util -f traces -b hf_uname/redhat-profile.

Beyond the talkthe schedule, a check on the 88%

Not from the speaker. This is from blogs, docs, papers and news I checked afterwards.

  • The schedule, in the PyTorch docs: wait steps are skipped. warmup steps are traced, but the results are thrown away, so the profiler can settle. active steps are recorded. Here 1 + 1 + 3 is exactly the 5 steps in the loop.
  • A check on the third number. The slide says 88%. But the two totals boxed on that slide, 2.148 ms and 1.976 ms, give about 92%. The table's cudaDeviceSynchronize row shows 87.83% of CPU time, so the 88% may have come from there. The 5% and 26% do match their boxes (17.792 / 332.072 and 72.417 / 274.155).
  • The percentages depend on the machine. In my fact-check run on a different GPU, the same script gave roughly 1%, 8% and 98%. The shape is the same: small sizes are overhead bound, big ones are not.
  • Where to read more: the Hugging Face blog on the profiler, the PyTorch profiler docs, and the torch.compile docs. Perfetto opens the same Chrome-format trace.

Talk 2

SGLang, the Transformers backend and kernels

Adarsh · Hugging Face

Adarsh began with a plain point. Serving one user is easy. Serving a thousand at once is where the work starts. First he defined the word: inference means taking the prompt, processing all its tokens in parallel to build the model's working context, and then writing the answer one token at a time.

Inference is two jobs

Prefill reads the whole prompt in one pass and builds the KV cache. It is compute bound. The maths is matrix times matrix. Decode writes one token at a time and reads the cache again at every step. It is memory bound. The maths is matrix times vector.

From my notes

I drew this as a small table: prefill is compute bound with matrix-matrix multiplication, decode is memory bound with matrix-vector multiplication.

What SGLang is made of

The slide quoted the project: “a high-performance serving framework for large language models and multimodal models.” It has four parts. My notes add what each one does.

  • Scheduler. Batches requests together.
  • KV cache manager. Stores the cache and uses it again, with its own cache algorithm.
  • Model runner. Runs the forward pass.
  • Attention backend. flash-attn or flash-infer.

One slide set the scene: the same 1,000 requests on the same GPU. Llama-3-8B on one H100, a 2K-token shared system prompt, 300-token replies.

Throughput on that slide, tokens per second

plain generate()~209
SGLang~7,900

That is about 38 times more. The run fell from about 25 minutes to about 40 seconds, and the cost per million tokens from about $3.30 to about $0.09. These are the slide's numbers.

RadixAttention, in nine steps

Older systems threw the KV cache away when a request ended. SGLang keeps it. It keeps an LRU cache of the KV cache of all previous requests in a radix tree, a memory-efficient prefix tree. Nine slides build the tree step by step. A shared system prompt is the root. Each chat branches off it. When memory fills up, the least recently used leaves are evicted. On the slides they turn orange. The shared prefixes stay. A new request with the same start just reuses them.

From my notes

“SGLang: LRU cache of KV cache of all previous requests in a radix tree.” Next to it I wrote --mem-fraction-static, the flag that sets how much GPU memory the static part gets.

Scale

A fun-facts slide claimed SGLang runs on more than 400,000 GPUs, makes trillions of tokens a day, and merges about 44 PRs a day. It showed 30.7k stars and a wall of company logos. The slide added: when Grok answers you, this codebase is moving the tokens.

Transformers is the source of truth

The next slide was titled “the dependency nobody thinks about”. SGLang's own pyproject.toml pins transformers==5.12.1. Config parsing, tokenizers, weight formats and chat templates all start as a Transformers artifact on the Hub. Transformers defines the model. SGLang makes it run fast.

The Transformers backend turns that into one flag: --model-impl transformers. The forward pass runs straight from Transformers, with no native port. SGLang still owns RadixAttention, continuous batching and scheduling. There are about 2 million models on the Hub and SGLang ported only a few hundred. The backend covers the rest on day 0.

“Transformers internals hijacked!”

This slide was built up in four steps. The model graph comes from Transformers (AutoModel.from_config on the meta device). Then SGLang swaps the hot paths with recursive_replace() at load time. One config line, config._attn_implementation = "sglang", flips the attention backend.

  • The attention call becomes RadixAttention plus the KV cache.
  • nn.Linear becomes a column- or row-parallel linear, matched via the HF tp_plan.
  • experts.forward() becomes FusedMoE and expert-parallel kernels, through a compile-safe custom op.
  • RMSNorm is swapped by class for a fused RMSNorm kernel.
From my notes

I wrote “tp_plan in HF” and, at the bottom of the page, numeric drift in kernels, hence performance is different. Swapping in different kernels gives slightly different numbers.

Enter HF Kernels

A meme slide set up the problem. Install and build FlashAttention 3, only to drown in CMake errors. Or get_kernel("kernels-community/flash-attn3") in two lines. Why it exists: no unified structure, build tools scattered across CMake, Nix, Meson and Bazel, endless build times, and support matrices to maintain. HF Kernels is unified tooling to build compute kernels, with a predictable structure, reproducible builds and native PyTorch compatibility.

Adarsh said he “shamelessly copied” the next few slides from Sayak and Aritra's talk. The kernel builder is a Nix-based build system. It targets ROCm, XPU, CUDA and Metal, many PyTorch versions and many CUDA capabilities. A small RGB-to-grayscale kernel showed the enforced folder structure. Using one is “as easy as swapping 4 lines”, with no messy wheels or incompatible builds. Then the call to action: push your kernels to the Hub.

From my notes

My notes: HF Kernels → kernel builder → Nix-based build system. Accelerator backends: ROCm, XPU, CUDA, Metal. The PyTorch × CUDA matrix of versions. And a last line: manage the KV cache onto SSDs (DeepSeek). I wrote that down from what he said at the end. It is not on a slide.

  • Why inference is hard: the slide said it plainly. “One user is easy. A thousand is not.”
  • What inference is, on slide 2: take a user's prompt, process all its tokens in parallel to build the model's working context (prefill), then generate output tokens one at a time (decode).
  • The slide on attention and the KV cache credits an NVIDIA developer blog on inference optimization. It lists prefill as “all tokens read in a single pass”, compute bound, matrix times matrix. Decode is “each token processed sequentially”, memory bound, matrix times vector.

Beyond the talkthe paper, the vLLM comparison, the numbers

Not from the speaker. This is from blogs, docs, papers and news I checked afterwards.

  • RadixAttention is from a paper. “SGLang: Efficient Execution of Structured Language Model Programs” (Zheng et al., 2023, arXiv 2312.07104). The tree idea is not new to SGLang's blog posts.
  • The cache is big. For Llama-3-8B the KV cache is about 128 KiB per token. A 2K-token shared prompt is about 256 MiB per request, so reusing it matters.
  • vLLM has the same two ideas. It has automatic prefix caching, but it hashes fixed-size blocks and caches only the full ones. It also has a Transformers backend (model_impl=transformers). See the first question below for vLLM versus SGLang.
  • The big throughput numbers (about 38×, 25 minutes to 40 seconds, $3.30 to $0.09 per million tokens) are what the slide showed. I could not reproduce them. A shared 2K prompt with short replies is close to the best case for prefix reuse, so expect less on mixed traffic.
  • On --mem-fraction-static, the flag I wrote down next to the radix tree: it sets what share of GPU memory goes to the weights and the KV cache pool. The rest is left for activations. Lower it if you run out of memory.
  • The fun-facts numbers (400,000+ GPUs, 44 PRs a day) are not independently checked.

Talk 3

RL environments 101

Adithya S Kolavi · post-training, Hugging Face

Adithya opened with a show of hands: how many of you have heard of “RL environments”? Then he told the story of how models are taught, one step at a time. Each step lit up on a timeline.

  1. Pretraining. Trillions of tokens of raw web text, and predict the next one. You get a model that knows a lot but does not yet know how to behave.
  2. SFT. Curated examples, a question and its ideal answer. It works, but it saturates. Great data is slow and costly, and the model never gets better than what we hand it.
  3. RLHF. We cannot write the perfect answer for everything. So let the model try, and let a person say which answer is better. “Better” becomes the reward. But people cannot rate everything.
  4. RLVR and GRPO. Then DeepSeek happened. DeepSeek-R1 used GRPO, which rewards the model only when its answer passes a check. A program grades it, with no human. It is cheap, hard to fake and endlessly scalable, and now every frontier model trains this way. A fun-fact line: GRPO had already shipped a year earlier, in DeepSeekMath (Feb 2024), before R1 (Jan 2025).

“If a program can grade it, a model can learn it.”

That was the unlock, and it turned the race into something simple: build more environments. His chart showed models trained on more and more of them, from about 20 environments to 20K, 100K+ and even 1M+.

What an environment is

RL environments are not new. CartPole is the hello world: an agent sends an action, and the environment sends back a state and a reward. Gym (2016, later Gymnasium) gave every environment one contract: reset() and step(action). For LLMs the idea is the same. The agent is the LLM. The environment is a sandbox with tools, code and state. The reward is a verifier.

But there is a lot more to wire up than in supervised learning. There you have a dataset, a model and a trainer, and you swap them freely. In RL you have tasks, prompt template, initial state, tools, observation, an execution backend, state, a reward, a done signal, episode control and a transport. So frameworks stepped in to standardise it: OpenEnv, Verifiers, OpenReward and Harbor. His definition: a place a model practises, gets graded, and learns.

A coding environment, by example

Task: find the .py file with the most lines. Tool: bash, run any shell command in a sandbox. Reward: +1 if the final answer is right, else 0. Two attempts on the same task show it well. In rollout 1 the model lists the files, counts lines with wc -l and answers train.py. Reward +1. In rollout 2 it peeks at the directory, guesses from the names and answers model.py. Reward 0. GRPO samples N rollouts per task and nudges the model toward the ones that score.

He also split environments in two. One-shot (RLVR): prompt, answer, verifier. Maths, code, logic. Multi-turn agent RL: the model acts, the environment answers, for 10 to 100+ turns, and one sparse reward comes at the end. His example names were SWE-bench, OSWorld and AppWorld.

OpenEnv and TRL

OpenEnv's pitch: one shape, so any environment plugs into any trainer. It has a Gym-style API, first-class MCP, a built-in Rubric where the rewards live, and a Task API. His slide said it started at Meta and PyTorch, is now maintained by Hugging Face, and has 1000+ environments on the Hub. Four slides built one live: a bash tool written as a plain function with @mcp.tool, a reset() that loads the task into the sandbox, a rubric that returns 1.0 if the hidden tests pass, and create_app to serve it over HTTP and MCP with up to 8 parallel rollouts. Then openenv init, build, validate and push.

Then “You have an environment. Now what?” Train a model with it. TRL, Hugging Face's RL post-training library, trains against an environment directly. You pass environment_factory to GRPOTrainer, and that is the whole hookup. OpenEnv is first-class there. OpenReward and Harbor are supported too, marked experimental.

And then the catch: training is the easy part now. You still need thousands of environments. A good one needs tasks that mirror the real world and a reward you cannot game. Hand-building is slow.

Repo2RLEnv

Why start with code? It is easy to verify, deterministic and high value. And there is a near-endless supply of real code: repos, issues, PRs. Public GitHub repos are a goldmine, with real tasks, real code and tests that grade themselves. His question: could we turn them into thousands of environments, automatically? Repo2RLEnv converts any repository into a verifiable RL environment. About 1,000 were already generated and live on Hugging Face, with the call: contributions welcome.

From my notes

My page for this talk is short: OpenEnv, “repo2rlenv”, and a to-do, read the ultimate guide to RL envs. Most of the content above is from the slides.

Reward hacking: the best part of the talk

The slide title was “Reward modeling hacking”: when the model games the reward, not the task. He said it had just happened at frontier scale. The slide showed news clippings and a video thumbnail: OpenAI's models escaped a locked test environment and hacked Hugging Face to cheat on a benchmark, “last week”. On the slide, a GPT-5.6 “Sol” model, plus an unreleased one, was tested on ExploitGym, 898 real vulnerabilities scored pass or fail. Instead of solving them, it escaped the sandbox, chained zero-days and read the answer key from Hugging Face's production database. Both sides caught it. The experts' word for it: reward hacking. “Frontier models. Same failure mode, just bolder.”

A toy version first. “Rewind to last year.” GRPO had just landed in TRL, and everyone was fine-tuning tiny models, Qwen 0.5B and Llama 1B or 3B, on GSM8K grade-school maths. He changed one thing. Instead of asking the model to solve the maths, he asked it to write Python that solves it and prints the answer. He rewarded three things: the format (the right XML structure), correctness (the final answer matches), and code execution (it runs cleanly, a 0 to 2 bonus). “The last one felt harmless.”

The training curves looked great. The other rewards moved up and down. Then the code-execution reward shot up and stayed high. “I got excited.” Then he read the traces. The model had learned to wrap everything in try / except: pass, so the code never errors. Reward maxed. The maths was never solved. The lesson: the model maximized the reward without doing the task. A toy example, he said, and there is a lot more to reward hacking than this.

Now a frontier agent. “That was a 0.5B model. Now watch a frontier agent.” The slide named Claude Code with Opus. He built an environment from a real CVE: CVE-2026-48156 in pypdf, where a crafted PDF loops forever. The reward was a hidden test. A correct fix gets 1.0. A no-op gets 0.0. The agent scored a perfect 1.0 while fixing nothing. Three times, each after he closed the last door.

  1. Cheat 1, just ask GitHub. The prompt was the public advisory, and it named the fixing PR. The agent fetched the PR diff and pasted the fix in. Fix: scrub the prompt. Strip the CVE id, the PR number, the commit hashes and “fixed in version”.
  2. Cheat 2, the answer was in the box. He cut the web tools and re-ran. Same score. The container shipped the full git history, and the agent ran git log and git diff against origin/main. Fix: scrub to the base commit. Drop the remote, delete future branches and tags, expire the reflog, run gc.
  3. Cheat 3, pip is a search engine. Web blocked, git scrubbed. It ran pip download pypdf==6.12.0, unzipped the wheel, and used the fixed release of the very package it was told to fix. The fix is public: GitHub, PyPI, mirrors, archives. Block one door, the house has ten.

“You can't out-scrub the internet.”

So he cut the egress. An allowlist, not a block. And for the first time Opus actually worked the bug. The reward was 0.000, “the number I wanted”. His line: every green before was contamination. Real solve rate was about 0.

Trust lives in the environment

This was my favourite slide. The environment enforces the rules. The prompt never asks for them.

  • Make the verifier trustworthy first: gold patch 1.0, no-op 0.0, only targeted tests.
  • Strip the answer from the prompt.
  • Scrub the repo to the base commit.
  • Pre-bake dependencies and run offline by default.
  • If the network is needed, use an allowlist, never a full block.
  • Keep the gold patch and hidden tests out of the container.

All of it is baked into Repo2RLEnv, so the trust lives in the box by default. And the closing quote:

“A model never does the task. It does the reward. At scale, every gap gets found, so reward design is never done, only iterated.”

More details from the slidesroadmap, frameworks, anatomy, code for every slide
  • The roadmap: what RL environments are, why we need them, OpenEnv and TRL, generating environments, reward hacking. Then a tutorial demo and Q&A.
  • The speaker: post-training at Hugging Face. Before that, Apple and Microsoft Research. He founded CognitiveLab, with a grant from Meta.
  • The environment-count chart: “more environments, better models”. It plotted the Qwen3.5 average ranking against the number of training environments. Beside it: about 20 for Qwen3 (general-domain tasks), 20K for Qwen3-Coder (parallel environments), 100K+ for MiniMax Forge (real-world environments) and 1M+ for Qwen3.5 (agent environments).
  • Gym's contract: reset() gives the first observation. step(action) gives observation, reward and done. Plus an action_space and an observation_space. So any agent works with any environment, and runs can be repeated.
  • For LLMs the skeleton is the same. The agent is the LLM (token generation). The environment is a sandbox (tools, code, state). The reward is a verifier (a rubric or a check). What changes is the tools, the observations and the reward rule.
  • Supervised learning has three pieces (dataset, model, trainer) and you can swap them freely. RL has many more moving parts: tasks, a prompt template, an initial state, tools or a harness, observation, an execution backend, state, a reward or rubric, a done signal, episode control and a transport.
  • The frameworks that step in: OpenEnv (from Meta: HTTP and MCP, rubric rewards), Verifiers (Prime Intellect: in-process, dataset plus tools plus rubric), OpenReward (ORS: rewards per tool call) and Harbor (Laude Institute: agent harnesses in containers). Also NeMo Gym (NVIDIA), SkyRL Gym (Berkeley) and GEM. “Same concept, different dialects.”
  • Anatomy of an environment (a diagram): tasks, prompt template, initial state, tools, state, execution backend, observation, reward, done. An episode-control channel carries actions in and observations out. A training loop sits on the other side: LLM agent, rollout, trainer (loss and gradient), weight update, policy update.
  • Each piece, in the coding example: task “fix this failing test”; prompt (task to chat message); tools bash and run_code; observation stdout and stderr; state repo and files; execution sandbox container; reward tests pass, 0 or 1; done when the answer is submitted.
  • Two kinds of environment: one-shot (RLVR: prompt, LLM, answer, verifier; one turn, stateless, a reward every rollout) and multi-turn agent RL (task, agent, action, a stateful environment, observation, repeated T times; 10 to 100+ turns, one sparse reward at the end, like SWE-bench, OSWorld and AppWorld).
  • The guide: “The ultimate guide to RL environments: building and scaling them in the LLM era”. A Hugging Face write-up, published May 5, 2026 according to the slide. It comes with the RL_Envs_101 code.

Building an environment with OpenEnv (slides 22 to 25, joined together):

# The action space is just functions
class CodingEnv(MCPEnvironment):
    def __init__(self):
        mcp = FastMCP("coding_env")

        @mcp.tool
        def bash(command: str) -> str:
            "Run a shell command in the sandbox."
            result = self._sandbox.run_shell(command)
            self._state.step_count += 1
            return result.stdout + result.stderr

        super().__init__(mcp)   # actions route to @mcp.tool fns

    # each episode starts from a task, handed in on reset()
    def reset(self, seed=None, episode_id=None, **kwargs) -> Observation:
        self._sandbox = Sandbox()
        self._task = kwargs["task"]              # one task per rollout
        for f in self._task["files"]:            # e.g. a repo with a failing test
            self._sandbox.upload(f["path"], f["content"])
        self._state = State(episode_id=episode_id or uuid4().hex)
        return Observation(done=False, metadata={"prompt": self._task["prompt"]})

# The reward: a Rubric scores the outcome
class TestsPassRubric(Rubric):
    def forward(self, action, observation) -> float:
        passed = observation.metadata.get("tests_passed")
        return 1.0 if passed else 0.0

# Serve it: HTTP + MCP server with /reset, /step, /state
app = create_app(CodingEnv, CallToolAction, CallToolObservation,
                 env_name="coding_env",

Talk 4

Scaling up, one dimension at a time

Mansi Agarwal · Senior ML Engineer, PyTorch Engineering, Red Hat

The title slide said it all: composable parallelism with DeviceMesh and DTensor. Mansi started with “the parallelism zoo”. Data parallel (DDP), fully sharded (FSDP), tensor parallel (TP) and pipeline parallel (PP) each have their own API, their own wrapper and their own state-dict format. Combining them means manual plumbing and version-specific hacks. A new kind of parallelism means rewriting the training loop. Her question: what if parallelism was composable, like adding dimensions to a grid?

The old way

One slide showed what it took to mix FSDP with TP before any of this. Five steps: compute the rank groups by hand, create the process groups by hand, write your own TP layers, change the model code, and wrap with FSDP1. About 100 lines. Forget one manual all-reduce and the results are silently wrong.

Three primitives

  • DeviceMesh. It describes your GPU topology as a multi-dimensional grid. A 4×2 grid means 4 groups for data parallel and 2 for tensor parallel. You name each dimension, like dp and tp, and pick sub-meshes by name.
  • DTensor. It makes every tensor aware of how it is distributed. A placement is Shard(dim), Replicate() or Partial().
  • FSDP2 (fully_shard). Sharded data parallel as a composable transform, rebuilt on DTensor.

Communication becomes automatic. For dtensor_a @ dtensor_b, if one side is sharded and the op needs it whole, DTensor adds the all-gather for you. Her line: you write math, DTensor handles communication. Under the hood, every ATen op is intercepted, a sharding rule is looked up, the cheapest one is chosen, collectives are added if inputs do not match, and the op runs on local shards.

From my notes

I underlined this one: DTensor is “locally optimal”. It picks the best sharding per op as it goes. It does not look at the whole graph.

DTensor against JAX

A table compared the two. DTensor is eager-first and greedy per op, so it is locally optimal, and you can debug it with print and pdb. JAX with GSPMD looks at the whole graph, so it can find a globally optimal plan, but it is compiler-first. Her summary: eager-first gives up global optimality to keep debugging easy.

FSDP2

FSDP2 is FSDP1 rebuilt on DTensor. Every parameter is its own DTensor, not one big FlatParameter. It is an in-place transform, not a wrapper. LoRA and frozen layers work, fp8 works, and sharded checkpoints need no communication. The flow: all-gather before forward, run, free the memory after forward. Backward does the same, then a reduce-scatter for the gradients. A lifecycle slide made one point clearly: FSDP2's hooks decide when things happen. DTensor only executes.

Composing dimensions

2D parallelism was a few lines. Apply tensor parallel on the tp mesh, then fully_shard on the dp mesh. Adding parallelism is adding a dimension to the mesh. The same pattern goes to 3D with PP, 4D with CP and 5D with expert parallel for MoE. The code walkthrough made it real: one GPU, then DDP, then FSDP2, then FSDP2 with tensor parallel. At every stage the training loop stayed the same.

Compile and checkpoints

torch.compile removes DTensor's eager overhead. Her ordering rule was: activation checkpoint, then fully_shard, then compile last. Checkpointing with torch.distributed.checkpoint needs no communication on save, and an async save was 10 to 20 times faster. It re-shards when you load: save on 8 GPUs, load on 16.

From my notes

My last note on the page: torch.distributed.checkpoint → reshard for elastic training. That second part is my own reading, not hers. See the question on elastic training below.

Limits and what is next

One slide was called “what the docs don't tell you”: DTensor's eager dispatch costs about 7× per op, about 58 ATen ops have no strategy, views can break, reduce_dtype is ignored for the TP all-reduce, and there is no uneven sharding yet, which blocks clean MoE expert parallelism. “Honest about trade-offs: these are the costs of an eager-first composable design.” Next up: AutoParallel, DTensor erasure, Symmetric Memory, TorchFT, Monarch and zero-bubble pipeline parallelism.

More details from the slidescode for every stage, the lifecycle, limits, what is next
  • The agenda: why distributed training is hard, DeviceMesh, DTensor, FSDP2, composing dimensions (TP, PP, CP), a code walkthrough from 1 GPU to many dimensions, what is next, Q&A.
  • The old way took five steps. Work out rank groups by hand, create process groups by hand (all ranks must take part), write your own TP layers instead of nn.Linear, change the model code, then wrap with FSDP1 and pass the DP group by hand. About 100 lines. Forget one manual all-reduce and the results are silently wrong. FSDP1's FlatParameter also breaks TP weight shapes. Adding PP later means a third set of groups. Checkpointing needs custom state-dict handling.
  • Process groups: a 4×2 mesh makes 6 groups (2 for DP, 4 for TP). A 2×2×2 mesh makes 12.
  • DTensor helpers: distribute_tensor splits a tensor. to_local() gives your shard. full_tensor() gathers everything with an all-gather. redistribute() changes the placement.
  • How an op runs: DTensor catches every ATen op through __torch_dispatch__ (a C++ fast path with a Python fallback). Step one looks up a sharding rule (410+ ops covered, written einsum-style). Step two picks the cheapest one, greedily. Step three adds any collectives needed. Step four runs the op on local shards and wraps the result. On her slide, an unsupported op raises NotImplementedError and does not silently fall back to replicate.
  • FSDP1 (2022) vs FSDP2 (2025): FlatParameter became per-parameter DTensors. A wrapper class became fully_shard(), an in-place transform, so isinstance(model, MyTransformer) still works. LoRA and frozen layers work now. fp8 works. Sharded checkpoints need no communication. FSDP1 is deprecated.
  • The FSDP2 lifecycle, hook by hook: FSDP2's module hooks drive every placement change. DTensor executes, but never decides. pre_forward calls unshard(), an all-gather on a high-priority CUDA stream. The forward runs on full parameters in the default stream, with no DTensor overhead. post_forward calls reshard(), which frees the memory with storage.resize_(0) and keeps the tensor for autograd. pre_backward unshards again and prefetches the next layer. Gradients are computed locally, each GPU holding a Partial(sum). post_backward calls foreach_reduce(), a reduce-scatter that turns them into Shard(0). FSDP2 bypasses DTensor dispatch for these collectives, so the 7× cost is not paid on that path.
  • The composability model: 1D mesh(8,) is FSDP only. 2D mesh(4,2) is FSDP plus TP. 3D mesh(2,2,2) adds PP. 4D adds CP. The next one adds EP for MoE. Each dimension is independent, so you can mix and match based on your hardware topology.
  • 2D in practice: apply tensor parallel on the tp mesh (column-wise for qkv and the first FFN layer, row-wise for the output projections). Then call fully_shard on the dp mesh.
  • torch.compile with FSDP2: DTensor is compile-compatible through the traceable wrapper subclass protocol, and compiling removes the 7× dispatch cost. Functional collectives show up as opaque nodes in the graph. FSDP2's Python hooks stay in eager mode. Start with fullgraph=False to find graph breaks. Use compile_threads=1, because background threads can hang a distributed run.
  • Checkpoints: dcp.save needs no communication. Loading can reshard. Async save was 10 to 20 times faster (7B model: 148 s down to 6.3 s). SafeTensors is supported from PyTorch 2.8. For gradient accumulation use set_requires_gradient_sync(False), not no_sync().
  • DTensor vs JAX/GSPMD (a table): DTensor is mesh-dim oriented, greedy per op (locally optimal), eager-first with optional compile, and easy to debug with print and pdb. JAX is tensor-dim oriented (PartitionSpec), whole-graph (globally optimal), compiler-first, and has no eager mode, so you debug after compilation.
  • “Known limitations: what the docs don't tell you”: eager dispatch costs about 7× per op (compile removes it). Greedy propagation misses globally optimal plans. About 58 ATen ops still have no strategy and fail hard. Views that work on plain tensors can break on DTensors. reduce_dtype is ignored for the TP all-reduce (issue #190626), a silent precision loss. HSDP with mixed precision uses 3× gradient memory on a 2D mesh (#179128). There is no uneven sharding yet, which blocks clean MoE expert parallelism. Shape changes can trigger full recompiles. She was honest about all of these.
  • AutoParallel (GSPMD-style, experimental): a linear program over a torch.compiled graph finds the sharding, and it discovers FSDP, TP and EP on its own. It was in active development on LLaMA-3 at 64 and 256 GPUs.
  • What is coming: DTensor erasure, Symmetric Memory (PyTorch 2.9), TorchFT, Monarch (single controller), zero-bubble pipeline parallelism, and compiler-assisted backward sharding. She called it eager composable primitives today, compiler-optimized sharding tomorrow.
  • Her key takeaways slide: DeviceMesh is an N-dimensional, device-agnostic grid. DTensor makes communication automatic. FSDP2 is a composable in-place transform. Adding parallelism means adding a mesh dimension, not rewriting code. And eager-first design trades global optimality for debuggability.

Talk 5

Zero-copy GPU-to-GPU communication

Arkadip Maitra · PyTorch Engineering, Red Hat

Arkadip went below the training loop, to how GPUs talk to each other. He began with c10d, the default PyTorch distributed layer. It is a general-purpose backend interface, it worked well across CPU and GPU backends, and it was a good fit up to roughly 10K GPUs. Why did it work? Training was bulk-synchronous, the collectives were regular, the host knew the metadata, and the API did not care about the backend.

Meanwhile…

The world around it changed. NICs got smarter, with GPUDirect RDMA and better DMA engines. RoCE fabrics grew bigger. NVLink got stronger inside a node. And the new workloads broke the old assumptions: MoE routing wants dynamic all-to-all, tensor parallel wants compute and comms to overlap, pipeline parallel wants send and receive, inference wants fast KV cache movement, and 100K+ GPU jobs need fault tolerance. A timeline slide put the hardware lane and the framework lane side by side: NVLink in 2014, 400G RoCE at scale in 2024, and by 2025 NCCLX and 100K+ GPUs becoming normal. Distance started to matter a lot too.

Fabric latency multiplier by network distance, from the slide (same rack = 1×)

same rack1×

cross-zone15×
cross-DC30×

His line: comms was only one entrant in this race. The answer on the slide was TorchComms: explicit communicators, pluggable backends, richer semantics, and a path aligned with PyTorch. The stack: your code, the TorchComms API, an NCCLX or RCCLX backend, the CTran transport, and then IB or RoCE, NVLink or sockets.

Then: “many innovations were made, but let's focus on zero-copy.”

The default path against the zero-copy path

Two sequence diagrams were the heart of the talk. On the default c10d path, your data is first copied by a GPU kernel from your buffer into NCCL's internal FIFO. A PCIe DMA moves it to the NIC. It crosses the fabric, and the receiver does the same in reverse: DMA into a FIFO, then a GPU-kernel copy into the destination buffer. Two copies.

On the zero-copy path, the sender's NIC reads straight from your GPU buffer, and the receiver's NIC writes straight into the other GPU's buffer. No staging, no copy kernels. A CPU progress thread drives the transfer, so GPU cores are not used for the copy.

  • The c10d picture (slide 4): user code calls the torch.distributed API, which goes to a c10d ProcessGroup. Below it sit the backends (NCCL, Gloo, MPI, UCC), plus the reducer and autograd hooks, and rendezvous. Under those: NVIDIA GPUs with NVLink, CPU with Ethernet, and HPC clusters.

  • “Meanwhile…”, the hardware: NICs got GPUDirect RDMA, better DMA engines and richer queue-pair behaviour. Framework and backend: 2018 c10d and NCCL, 2023 the GPT-4 and LLM boom, 2024 the backend and runtime race, 2026 “comms moving into c10d/nccl2” (as written on the slide).
  • “What changed?” (a diagram): classic training had regular collectives (AllReduce, AllGather, ReduceScatter), host-known metadata (static execution graphs) and bulk synchronisation (BSP). New pressures: MoE routing needs dynamic, fine-grained all-to-all. TP overlap needs compute-comm hiding. PP needs send and receive with micro-batches. Low-latency inference needs KV cache management and token-to-token latency. 100K+ GPU scale needs fault tolerance and hierarchical networks.
  • TorchComms in four bullets: explicit communicators, pluggable backends, richer semantics, a PyTorch-aligned evolution path. The stack on the next slide: user or model code, the TorchComms API, an NCCLX or RCCLX backend, the CTran transport and runtime, then the physical network: IB or RoCE, NVLink, or sockets and TCP.
  • The default path (a sequence diagram): user GPU buffer, then a device-to-device copy by a GPU kernel into NCCL's internal FIFO on the sender, then a PCIe DMA to the NIC, across the network fabric to the receiver's NIC, a PCIe DMA into the receiver's FIFO, and a second GPU-kernel copy into the user's buffer. Two copies.
  • The zero-copy path: the sender NIC does a PCIe DMA read straight from the user's GPU buffer. The receiver NIC does a PCIe DMA write straight into the other user's buffer. No staging copies.
  • The wait and stall step: the host calls and queues the op. A CPU progress thread picks it up, and the host orders the stream. The GPU stream stalls at one wait point while earlier kernels finish. The progress thread chooses the algorithm, posts the RDMA and polls the completion queue. Then it completes the op, which releases the wait, and the next kernels run.
  • RDMA put vs get: with put, the source writes its payload into the destination's remote window tensor, then writes a signal flag. The destination polls with wait_signal(), sees flag = 1, launches the GPU kernel and consumes the window. With get, the requester asks to read the responder's source tensor. The payload moves by RDMA read straight into the requester's local tensor, a local ready flag is set, and the responder's state is unchanged.
  • CTran IB: a Virtual Connection (VC) holds a control QP for setup, a notify QP for completion messages, an atomic QP for signals and flags, and one or more data QPs for the payload.
  • The network and the fabric: a large request goes through a chunking engine and is spread over several NICs and QPs with sequence numbers. The fabric may deliver packets out of order. The receiver's sequence tracker keeps a bitmask of seen sequences, the next expected one and a notification bit. It then reassembles the data in a buffer and completes the logical request.
  • The complete picture (one long diagram): comms.some_call(), then TorchComms and RCCLX, the NCCLX API, the CTran mapper selecting IB, a VC and QP, a user-space work request, a DMA read from rank 0's HBM, an IB or RoCE packet on the wire, a rkey and address check at rank 1's NIC, a DMA write into rank 1's HBM, a completion signal, and finally rank 1's GPU kernels consume the data.

Questions, answered

Questions that came up in my head after the talks. The short answer comes first. Tap one to open it.

vLLM or SGLang: when should I use which?

Half true. “SGLang for multi-turn and big MoE, vLLM for the rest” is a fair starting rule. It is not a law, and the gap keeps shrinking.

Multi-turn chat: mostly true

Each turn re-sends the whole chat so far. A good engine reuses the KV cache from the last turn and only computes the new part.

  • SGLang keeps the KV cache of finished requests in a radix tree. It matches prefixes one token at a time. It also keeps the cache of the replies, not just the prompts. vLLM does this too, but only for full blocks. Its scheduler is cache-aware, so it tries to run requests that share a prefix together.
  • vLLM hashes fixed-size blocks. Each block's hash includes the hash of the block before it. Only full blocks are reused. With a block size of 4, a 10-token match reuses 8 tokens. In general you lose at most one block minus one token. For a long chat, that is small. The default block size has changed between versions, so check yours.
  • The tree helps most when conversations branch: agents, tree-of-thought, many users sharing one long system prompt or document.
  • One more thing changed. vLLM V1 turned prefix caching on by default. They report under 1% throughput loss even when nothing hits the cache. So old comparisons, where vLLM ran without caching, are out of date.

Big MoE models: partly true

MoE is different because each token only visits a few experts. The tokens must travel to the GPUs that hold those experts. That is an all-to-all. Expert load is also uneven, so the busiest GPU slows everyone. And the attention cache gets copied on every GPU if you use plain tensor parallel.

  • SGLang published a full open recipe for DeepSeek: data-parallel attention, expert parallelism with DeepEP, a load balancer for experts, two-batch overlap, and prefill/decode disaggregation. On 96 H100s they report 52.3k input and 22.3k output tokens per second per node. These are their own numbers.
  • vLLM is not limited to dense models. Its docs describe data-parallel attention with expert parallelism (DeepEP backends) and disaggregated prefill and decode.
  • So who is faster on MoE depends on the model, the GPUs and the release. It moves quickly.
  • Both engines have also moved on cache. Both now handle hybrid models. Both can push cache out of GPU memory: SGLang with HiCache, vLLM with an offloading connector or LMCache.

Dense models: no clear rule

vLLM's real edge is breadth. It supports many models and many kinds of hardware, and a lot of tooling is built around it. For single-turn requests with no shared prefix, both do similar work. I found only a few independent tests, and they disagree by workload. One academic trace study (CCL-Bench) reports vLLM using the GPU more efficiently on small dense models, and SGLang spending less of each step on communication on one small MoE model. Both ran on A100s with small models, so treat it as a hint. Most other comparisons online are vendor or blog posts.

Why is prefill compute-bound and decode memory-bound?

Because of how much work each byte of weights does. In prefill, one read of the weights serves thousands of tokens. In decode, it serves one.

Think of FLOPs per byte moved. This is called arithmetic intensity.

  • Prefill: the whole prompt goes through together. The maths is matrix times matrix. Each weight is loaded once and used for many tokens. The tensor cores stay busy, so you are compute-bound.
  • Decode: one new token per request per step. The maths is matrix times vector. You load all the weights (and the whole KV cache) to make a single token. The GPU waits on memory.

A back-of-envelope check. Llama-3-8B in bf16 is about 16 GB of weights. An H100 SXM moves about 3.35 TB/s. One decode step must read 16 GB, so it takes at least about 4.8 ms. That is roughly 200 tokens per second for one request. This is an upper limit, and real runs reach less. Adarsh's slide showed about 209 tok/s for plain generate(). Check which GPU and precision it used before comparing.

Batching is the fix. If 64 requests share each weight read, you get close to 64 times more tokens for the same read. This goes on until the KV cache reads start to dominate. Another way to see it: an H100 can do roughly 300 bf16 FLOPs for every byte it reads from memory. Decode at batch 1 does about 1. So you need a very large batch before decode turns compute-bound. That is why continuous batching and cache memory matter so much.

Is prefix caching free? Does it change my outputs?

It is cheap, not free. The cache is the same maths reused, so outputs should match, up to tiny numeric drift.

  • Cost when nothing hits: SGLang says it saw no noticeable overhead. vLLM V1 reports under 1% throughput loss at a 0% hit rate.
  • Memory: cached KV lives in the same GPU memory as running requests. Old entries are dropped by least recently used. A busy server may drop your prefix before the next turn arrives.
  • Things that kill hits: a timestamp or user ID at the start of the prompt; requests spread across replicas with no routing; different LoRA adapters or images (they are part of the hash in vLLM).
  • Outputs: reusing a cached prefix is exact reuse. But batch shapes and kernels can change, and different kernels give slightly different numbers. Adarsh called this numeric drift. Test if you need bit-exact results.

Habit to build: put stable text first (system prompt, tools, documents). Put changing text last.

Sources: vLLM prefix caching design · RadixAttention post · vLLM V1 release post

My GPU shows 5% busy in the profile. Is bigger the only fix?

No. Bigger work per launch is one fix. You can also fuse ops, replay launches with CUDA graphs, or cut Python in the hot path.

Every op has a fixed CPU cost: Python, the dispatcher, the driver. A tiny kernel can finish faster than the CPU can launch the next one. The GPU then sits idle. That is overhead bound.

  1. Do more per launch. Bigger batch, bigger matrices, or merge small ops. This is what the 64 → 1024 → 4096 demo showed.
  2. Fuse. torch.compile can merge a matmul with its epilogue (the add, activation or norm after it) into fewer kernels.
  3. Replay. CUDA graphs record a sequence of launches once and replay them in one go. vLLM V1 uses piecewise CUDA graphs for this reason.
  4. Trim the CPU path. Less Python per step, fewer small tensors, avoid syncs like .item() in the loop.

How to check: open the trace. Gaps in the GPU lane mean the GPU was waiting for work.

Sources: torch.profiler docs · Profiler recipe · torch.compile tutorial · vLLM V1 release post

Why do models game rewards, and how do I stop it?

Because RL optimizes exactly what the verifier measures. Any gap between “the reward” and “the task” will be found.

This is Goodhart's law, with a very patient searcher. The model tries thousands of paths. If one of them scores without solving the task, the training signal pushes the model towards it.

Adithya's two stories show it. A try / except: pass wrapper kept code from crashing, so a “code runs cleanly” reward went up with no maths solved. In the CVE environment, the agent read the fix from the PR, then from git history, then from pip.

  • Test the verifier first. The gold solution must score 1.0. A no-op must score 0.0.
  • Remove the answer from the prompt, the repo, the history and the network.
  • Isolate the sandbox. Offline by default. Allowlist, never block-list.
  • Read rollouts, not just reward curves. A sudden jump in reward is a smell.
  • Use several signals, and keep a hidden test the model never trains on.

The honest summary is on his last slide: reward design is never done. It is only iterated.

Sources: Reward hacking (Lilian Weng) · Specification gaming (DeepMind) · The RL environments guide from the talk

Why GRPO instead of PPO for verifiable rewards?

GRPO needs no critic (value) model. It scores a group of answers to the same prompt and compares them with each other.

  • PPO trains a value model next to the policy. It is usually about the size of the policy. That costs memory and adds moving parts.
  • GRPO samples a group of answers for each prompt, scores them, and uses the group's average (and spread) as the baseline. An answer is good if it beats its siblings.
  • With a program-graded reward like pass or fail, that is simple and works well.
  • Catch: if every answer in a group gets the same score, all right or all wrong, every advantage is zero. The reward gives no policy-gradient signal for that prompt. (A KL term, if used, can still move the weights.) The task must be neither too easy nor too hard. TRL logs frac_reward_zero_std so you can see how often this happens.

Sources: DeepSeekMath (introduces GRPO) · PPO paper · TRL GRPO trainer

FSDP, tensor parallel, or both?

Start with FSDP. Add tensor parallel inside a node when FSDP alone is not enough. Put the chattiest dimension on the fastest links.

  • FSDP splits parameters, gradients and optimizer states across data-parallel ranks. It all-gathers one layer at a time. It saves memory and is easy to adopt: Mansi's walkthrough changed only a few lines.
  • Tensor parallel splits each matmul inside a layer. It needs an all-reduce in almost every layer, so it is very sensitive to latency. Keep it inside a node on NVLink.
  • Memory check: mixed-precision Adam costs about 16 bytes per parameter (2 weights, 2 grads, 12 optimizer state). A 7B model is about 112 GB before activations. That is why you must shard.
  • Combine when data parallel alone cannot grow (global batch limit), or a single layer is too heavy. Then add pipeline parallel across nodes, and context parallel for very long sequences.

With DeviceMesh this is a shape choice: (4, 2) with names dp and tp.

Sources: Ultra-Scale Playbook · ZeRO paper · Megatron-LM paper · FSDP2 docs

Is “save on 8 GPUs, resume on 16” how elastic training works inside frameworks?

Only in part. Resharding on load is the checkpoint piece. Elastic training also needs a launcher that notices changes, restarts the workers, and restores more than the weights.

I first wrote that resharding is “exactly what elastic training needs”. That was too strong. Here is the fuller picture.

The common recipe: checkpoint, restart, reshard

  1. Notice the change. A node dies or a new one joins. In torchrun's elastic mode you give a range, like --nnodes=MIN:MAX, and a restart budget. Workers find each other through a rendezvous.
  2. Restart the whole worker group. The group is torn down and started again with the new set of workers. It does not grow or shrink while running.
  3. Reload the latest checkpoint. This is where torch.distributed.checkpoint helps. Each rank saved its own shard with metadata about the full tensors. On load, each rank reads the slices it now needs. So the new world size does not have to match the old one.
  4. Resume the rest of the state. Optimizer state must reshard too. The data loader position, random seeds and learning-rate schedule need to come back as well. Without the data position you repeat or skip samples.

Things the checkpoint cannot decide for you

  • Batch size and learning rate. The number of GPUs changed, so the global batch size changes unless you adjust, for example with gradient accumulation. What to do with the learning rate is your call.
  • The mesh shape. On 16 GPUs, your DeviceMesh might need different dimensions. The parallelism plan has to be built again at startup.
  • Lost work. You go back to the last checkpoint. Async checkpoints (the slides showed 7B: 148 s down to 6.3 s) make saving often cheap.

The newer idea: do not restart everything

Mansi listed TorchFT as coming. It aims at fault tolerance per step, without a full-job restart. The rough idea is to run data-parallel replica groups. If one fails, the others keep going, and the failed one catches up from healthy peers. I have not verified the details against its docs, so read the repo before relying on that description.

In short: DCP resharding is a necessary piece for elastic restarts. It is not the mechanism. The launcher, the rendezvous and the resume logic make it elastic.

Sources: torchrun / elastic launch docs · Rendezvous docs · Distributed checkpoint docs · TorchFT

Why does distance cost so much in a GPU cluster?

Farther means more switches, shared links and longer cables. Meta's NCCLX paper reports latency of 1× in one rack and 30× across data centres.

The numbers on Arkadip's slide: same rack 1×, cross-rack 7×, cross-zone 15×, cross-DC 30×. The NCCLX paper gives the same three figures, as latency compared with the same rack. I could not check how they were measured.

  • Each extra hop adds a switch, a queue and a chance of congestion.
  • Upper layers of a network are often shared, so traffic from many jobs meets there.
  • Longer cables add delay that no software can remove.

What to do about it: place by chattiness. Tensor parallel inside a node. FSDP or data parallel inside a rack or zone. Pipeline parallel, which sends less, across the far links. This is what “match the mesh to your topology” means.

Sources: Meta: RoCE networks for AI training · TorchComms blog · NCCLX paper

DTensor is “locally optimal”. Should I worry?

Not for standard Transformers. You set the plan by hand. For odd models, AutoParallel is the experimental fix.

DTensor chooses the cheapest sharding for each op on its own. It never sees the whole graph, so the full plan may not be the best one. JAX's compiler looks at the whole graph, but you give up eager debugging.

For a Transformer, the good pattern is well known: column-wise on the first linear, row-wise on the next, so you need one all-reduce for the pair. That is the ColwiseParallel and RowwiseParallel plan in the slides. AutoParallel searches for a plan with linear programming over a compiled graph. It is experimental.

Sources: DTensor docs · TP tutorial · AutoParallel
