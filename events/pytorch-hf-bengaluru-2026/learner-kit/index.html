Systems under the model

Modules

0GPU performance basicsabout 5 hours

Every talk that night came back to one question: where does the time go? Compute, memory, or just launching work? Learn this first and the rest is easier.

Core ideas

  • Arithmetic intensity is FLOPs per byte moved. Low means memory-bound. High means compute-bound. This is the roofline idea.
  • Launch overhead. The CPU queues every kernel. Tiny kernels leave the GPU idle.
  • The memory ladder: registers, shared memory, L2, then HBM. Moving data costs more than the maths. Fusing ops avoids trips to HBM.
  • Orders of magnitude: On an H100, HBM moves about 3.35 TB/s. NVLink moves about 900 GB/s in total. A 400 Gb/s NIC moves about 50 GB/s. Each step out is slower.

Learn in this order

  1. Making Deep Learning Go Brrrr From First Principles Start here. Compute, memory and overhead, with fusion. It is long, but worth it.
  2. Transformer Inference Arithmetic Count FLOPs and bytes for a Transformer by hand. It uses A100 numbers.
  3. How to Scale Your Model A free book on rooflines, sharding and communication. Mostly TPUs, so treat it as optional and come back later. Chapter 12 covers GPUs.
  4. NVIDIA: GPU performance background Plain explanations of tensor cores, memory, arithmetic intensity, and math-bound versus memory-bound work.
  5. Modal GPU glossary Short linked definitions of SMs, the memory hierarchy, roofline and arithmetic intensity. Its arithmetic-intensity page says an H100 needs about 295 FLOPs per byte in bf16 to be compute-bound.
  6. GPU MODE lectures Talks on profiling, CUDA, Triton and more. Pick what you need.

Try it

  1. Work out the best-case decode speed for an 8B model on an H100: weights in bf16 are about 16 GB, bandwidth is about 3.35 TB/s.
  2. Time torch.matmul on square matrices of size 64, 256, 1024, 4096 with CUDA events. Plot time against size. Find where the line stops being flat. That is the launch-bound region.
  3. Compute the arithmetic intensity of an element-wise add in fp32 (read 2 numbers, write 1, do 1 FLOP). Then of a big matmul. Compare.

Check yourself

  • Why is decode memory-bound and prefill compute-bound?
  • What does fusing two ops save, and where does the saving come from?
  • The add above has 1 FLOP per 12 bytes. Is it compute-bound or memory-bound on a modern GPU? Why? (Hint: an H100 needs about 295 FLOPs per byte in bf16 to be compute-bound.)
1Profiling PyTorchabout 4 hours

Aritra's rule: what you cannot profile, you cannot optimize. Profiling turns guesses into evidence.

Core ideas

  • Annotate with record_function so your code has a name in the trace.
  • Schedule: wait, warm up, then record a few active steps. Warm-up steps run the profiler but throw the data away.
  • Two outputs: a trace (a timeline) and a table (totals). Sort the table by self CUDA time first. A row you wrapped in record_function can show a bogus total, so read the self times.
  • Overhead bound shows as gaps in the GPU lane and a low CUDA-to-CPU time ratio.
  • Turn on record_shapes (op input sizes), profile_memory (allocations) and with_stack (source line) only when you need them. They add overhead.

Learn in this order

  1. Hugging Face blog: torch profiler (Part 1) A beginner series by Aritra and others. It uses this same matmul plus add example.
  2. Hugging Face blog: profiling Part 2 From nn.Linear to a fused MLP. Compares aten::addmm, eager, torch.compile and a Liger kernel.
  3. Profiler recipe A runnable walk-through on ResNet18. The later parts need a GPU.
  4. Perfetto UI Open a Chrome-format trace and zoom into the lanes.
  5. Hugging Face trace viewer (Space) A Hugging Face Space for looking at traces in the browser.
  6. PyTorch profiler docs The full API. Use it as a reference.
  7. PyTorch performance tuning guide A checklist of easy wins, including avoiding syncs and fusing pointwise ops.
  8. CUDA semantics Streams, async launches and syncs. Explains why the CPU runs ahead.
  9. NVIDIA Nsight Systems When you need a system-wide view beyond PyTorch.

Starter script

import torch
from torch.profiler import profile, record_function, schedule, ProfilerActivity

n = 4096  # try 64, 1024, 4096
x = torch.randn(n, n, device="cuda")
w = torch.randn(n, n, device="cuda")
b = torch.randn(n, device="cuda")

def fn(x, w, b):
    return torch.add(torch.matmul(x, w), b)

def step():
    with record_function("matmul_add"):
        return fn(x, w, b)

sched = schedule(wait=1, warmup=1, active=3, repeat=1)
with profile(activities=[ProfilerActivity.CPU, ProfilerActivity.CUDA],
             schedule=sched, record_shapes=True, profile_memory=True) as prof:
    for _ in range(5):
        step()
        prof.step()

prof.export_chrome_trace("trace.json")
print(prof.key_averages().table(sort_by="self_cuda_time_total", row_limit=15))

Try it

  1. Change n in the script below to 64, 1024 and 4096. Each time, divide the “Self CUDA time total” by the “Self CPU time total” from the table footer. Do not add up the rows, because the record_function row double-counts. Do you get a rising curve? Aritra's slide showed 5% → 26% → 88%. On one H100-class machine we measured about 1%, 8% and 98%. Your numbers will differ. The shape is what matters.
  2. Open the trace in Perfetto. Find the gaps in the GPU lane at size 64.
  3. Wrap the function in torch.compile and compare the tables. In the Hugging Face post, compile turned the matmul and add into one aten::addmm call. But it still launched two GPU kernels and cost about 2× more CPU time per step at this tiny size. Compile does not always help small work.
  4. Turn on with_stack and find the exact line of your biggest op.

Check yourself

  • Why skip the warm-up steps?
  • If one row is on top of the table, what else should you check before blaming it?
  • Name three ways to fix an overhead-bound step.
2torch.compile, Triton and kernelsabout 6 hours

Once you know where the time goes, the next step is to remove work. Fusing ops and shipping good kernels are the two big levers. Hugging Face Kernels makes the second one easier.

Core ideas

  • Graph capture: torch.compile traces your model into a graph and hands it to a compiler (Inductor).
  • Fusion: the compiler merges ops, such as a matmul and the add or activation after it (the epilogue). That means fewer launches and fewer memory trips.
  • Triton lets you write GPU kernels in Python-like code. On GPUs, Inductor generates Triton kernels for you. On CPUs, it generates C++.
  • Kernel distribution is painful: many build tools, many CUDA and PyTorch versions. HF Kernels gives a fixed structure, repeatable Nix builds and a Hub to share them. Builds cover many PyTorch and CUDA versions. Backends are CUDA, ROCm, XPU, Metal and CPU. CUDA and CPU are the best supported.

Learn in this order

  1. torch.compile tutorial Start with the basics and graph breaks.
  2. PyTorch 2 paper How TorchDynamo and TorchInductor work.
  3. TorchInductor design post The compiler's design in the team's words. It is an early 2022 prototype post, so read it for ideas, not details.
  4. Triton tutorials Vector add, softmax, matmul, fused attention. Do them in order.
  5. How to optimize a CUDA matmul Step-by-step from naive to fast. Teaches the memory ladder.
  6. FlashAttention paper The classic fusion story: tile the attention so it avoids reading and writing the big matrix in HBM.
  7. Hugging Face kernels (GitHub) The repo. It has the kernels package, the kernel-builder and the install steps.
  8. Kernels docs Overview. Open Quickstart to load a kernel and Builder to publish one.
  9. Kernels quickstart Load a kernel with get_kernel.
  10. Hello, Hugging Face Kernels June 2025 intro to the Kernel Hub. It covers get_kernel, not the builder or Nix.
  11. Why graph breaks happen .item(), tensor-dependent if, and printing.

Try it

  1. Compile a small MLP with torch.compile. Run it as TORCH_LOGS=graph_breaks python your_script.py. It prints each graph break and why. You can also call torch._logging.set_logs(graph_breaks=True).
  2. Do Triton tutorials 1 to 3. Compare your softmax to PyTorch's.
  3. Install the library with pip install kernels (it needs torch 2.5 or newer, and a CUDA GPU for this example). Then run from kernels import get_kernel, activation = get_kernel("kernels-community/activation", version=1), y = torch.empty_like(x), activation.gelu_fast(y, x). Next try kernelize(model, mode=Mode.INFERENCE) to swap Hub layers into a small model. Use Mode.INFERENCE | Mode.TORCH_COMPILE if you compile too.

Check yourself

  • What is an epilogue, and why is fusing it useful?
  • What is a graph break, and how do you find one?
  • Why do kernel builds break across CUDA and PyTorch versions?
3LLM inference: engines, caches and MoEabout 10 hours

Adarsh's line: one user is easy, a thousand is not. This module follows one request through prefill, decode, batching, the KV cache and the big MoE tricks.

Core ideas

  • Prefill and decode are two different jobs. One is compute-bound, the other memory-bound.
  • KV cache size: for Llama-3-8B (32 layers, 8 KV heads, head size 128, 16-bit), that is 2 × 32 × 8 × 128 × 2 bytes = 128 KiB per token. A 2K-token prompt is about 256 MiB per request. Llama-3-8B shares KV heads (8 instead of 32), so it needs about 4× less per token than a model without grouped-query attention, like Llama 2 7B.
  • Paged KV cache (PagedAttention) stores the cache in small blocks to avoid waste.
  • Continuous batching adds and removes requests at every step instead of waiting for a whole batch.
  • Prefix caching: vLLM hashes each full block together with the tokens before it. Only full blocks are cached. SGLang's RadixAttention keeps a radix tree keyed by tokens. It matches token by token, or page by page if you set a page size above 1. Both engines now also handle hybrid models and can push cache out of GPU memory (SGLang with HiCache, vLLM with an offloading connector or LMCache).
  • Speed tricks: speculative decoding, chunked prefill, quantization, prefill/decode disaggregation.
  • MoE serving: expert parallelism, data-parallel attention, an expert load balancer, and overlapping communication with compute.

  13. FlashInfer (GitHub) Code and docs.
  14. Speculative decoding A small model guesses several tokens. The big model checks them all in one pass. The output is the same as the big model alone.
  15. Sarathi-Serve (chunked prefill) Keep decode smooth while prefill runs.

  17. Mooncake A KV-cache-centred serving system for Kimi. It splits prefill and decode, and uses spare CPU, DRAM and SSD in the GPU cluster as a shared KV cache. The closest paper to the SSD offload note from the talk.

Try it

  1. Compute the KV cache size for a model you like. How many 2K-token requests fit next to the weights on a 80 GB GPU?
  2. Serve a small model with vLLM and with SGLang. Send a 10-turn chat to each and log the time to first token per turn. Then turn prefix caching off and compare. In SGLang, add --disable-radix-cache. In vLLM caching is on by default, so run vllm serve --help to find the off switch for your version, then restart the server.
  3. Make a prompt that starts with a timestamp. Watch the hit rate drop. Move the timestamp to the end. Watch it recover. Read the hit rate from the server logs. The first request is always cold, so compare turns 2 to 10.

4RL environments and reward designabout 8 hours

If a program can grade it, a model can learn it. That makes environments the new datasets. Most of the work, and most of the danger, is in the environment.

Core ideas

  • The arc: pretraining, SFT, RLHF, then RLVR (verifiable rewards) with GRPO.
  • Gym contract: reset() starts an episode. step(action) returns the next observation, a reward and a done flag. OpenEnv adds state(). For LLMs: agent = model, environment = sandbox, reward = verifier.
  • One-shot vs multi-turn: one answer and one grade, or many tool calls and a grade at the end.
  • Parts of an environment: task, prompt, tools, state, observations, execution, reward, done signal.
  • Reward hacking: the model does the reward, not the task. Trust must live in the environment.
  • Frameworks: OpenEnv, Verifiers and OpenReward (ORS) give environments a common shape. Harbor is a task format and agent harness. OpenEnv and Repo2RLEnv build on it.

Learn in this order

  1. Spinning Up in Deep RL Classic RL basics: policies, returns, policy gradients.
  2. Hugging Face Deep RL course Hands-on, with notebooks. It uses Stable Baselines3 and CleanRL, not LLMs. The Unit 7 challenge and leaderboard no longer work.
  3. Andrej Karpathy: Pong from pixels The simplest policy gradient story.
  4. Lilian Weng: policy gradient algorithms A tidy reference.
  5. PPO
  6. InstructGPT (RLHF)
  7. DeepSeekMath (GRPO)
  8. DeepSeek-R1 RL with verifiable rewards at scale.
  9. Tulu 3 (RLVR) Introduces the term RLVR (reinforcement learning with verifiable rewards). A fully open post-training recipe.
  10. The ultimate guide to RL environments (from the talk) Hugging Face article, May 2026. The authors build one environment in six frameworks (OpenEnv, ORS, NeMo Gym, Verifiers, SkyRL Gym, GEM) and compare them. It does not cover reward hacking in depth.
  11. Adithya's RL Envs 101 Open-source RL environments for LLM agents, in numbered projects. Project 01 trains Qwen3-VL-2B to turn math images into LaTeX with a verifiable reward. The repo has been renamed FineEnvs, and the old link redirects.

Try it

  1. Build a tiny environment: ask for a Python function, run the tests in a sandbox, return 1 or 0. Write the reset and step yourself first. Then port it to OpenEnv with openenv init, build (needs Docker), validate and push.
  2. Red-team it. Write three ways to score 1.0 without solving the task. Fix each one. Check that a gold answer gets 1.0 and an empty answer gets 0.0.

  4. Run the LaTeX OCR environment from the talk and compare before and after scores.

  • Why do rewards like “the code ran without errors” fail?

  • In the CVE story, why was blocking the network not enough?
  • What is the difference between a one-shot and a multi-turn environment?
5Distributed training with DeviceMesh, DTensor and FSDP2about 10 hours

Mansi's idea: parallelism should be composable. Adding a kind of parallelism should mean adding a dimension to the mesh, not rewriting the training loop.

Core ideas

  • DeviceMesh names the GPU grid: (4, 2) with dp and tp.
  • DTensor placements: Shard(dim), Replicate(), Partial(). Collectives appear when placements need to change.
  • FSDP2 is fully_shard(), a transform on the model. Each parameter is a DTensor sharded on dim 0, Shard(0). All-gather before forward, free after, reduce-scatter for grads.
  • Tensor parallel: column-wise, then row-wise, so a pair of linears needs one all-reduce. A full transformer layer needs two all-reduces in forward and two in backward. Keep it inside a node: the TP tutorial applies it within each host.
  • Order for compile: Mansi's slide says checkpoint, then fully_shard, then torch.compile last. TorchTitan, as I read a mirror of its Llama 3 code, compiles each transformer block before applying FSDP. Check the current file. The safe habit is to try both on your model.
  • DCP saves each shard without communication and can reshard on load, for example from 8 GPUs to 16.
  • Memory: mixed-precision Adam needs about 16 bytes per parameter. That is 2 for bf16 weights, 2 for bf16 gradients and 12 for fp32 master weights, momentum and variance. Activations are extra.

  1. DeviceMesh recipe Meshes and sub-meshes.
  2. DDP notes The baseline to understand first.
  3. FSDP2 API (fully_shard)
  4. FSDP tutorial
  5. Tensor parallel API parallelize_module, Colwise and Rowwise styles.
  6. FSDP2 design RFC Why FSDP2 shards each parameter.
  7. Tensor parallel tutorial Colwise and Rowwise in practice.
  8. Distributed checkpoint recipe
  9. Accelerate: FSDP1 vs FSDP2 Mansi's slide pointed here.
  10. Ultra-Scale Playbook The best single guide to all the parallelisms.
  11. TorchTitan paper
  12. TorchTitan (GitHub) A reference stack that composes these pieces.
  13. ZeRO The idea behind sharding optimizer state, grads and params.
  14. Megatron-LM (tensor parallel)
  15. Megatron-LM at scale How 3D parallelism is combined.
  16. GPipe (pipeline parallel)
  17. PyTorch FSDP paper

Try it

  1. Follow Mansi's four stages on a toy model: 1 GPU, DDP, FSDP2, FSDP2 + TP. Use the same seed and data order. The loss curves should match to within small numerical noise. The last stage needs at least 4 GPUs. With 2 GPUs you only get a 1×2 mesh.
  2. Print the DTensor placements of a few weights after parallelize_module. Call full_tensor() and compare with the original.
  3. Save a checkpoint with DCP on 2 processes. Load it on 4.
  4. Compute memory per GPU for a 7B model on 8 GPUs with FSDP. Use bf16 compute, fp32 master weights and Adam. Ignore activations. Check: 7B × 16 bytes = 112 GB, divided by 8 is 14 GB per GPU for the sharded state. Then add the short-lived full bf16 copy of one layer that FSDP gathers.

Check yourself

  • What changes in the training loop when you go from DDP to FSDP2? (Almost nothing. Why?)
  • Which dimension of the mesh should sit inside a node, and why?
  • What does DTensor do when an op has no sharding rule? Why is silently falling back to replicate a risky default?
  • Mansi's slide calls DTensor’s sharding choice “locally optimal”. What does that mean?
6GPU communication: NCCL, RoCE and zero-copyabout 6 hours

At scale, how GPUs talk matters as much as how fast they compute. Arkadip's talk went under the training loop to show where copies and distance cost time.

Core ideas

  • Collectives: all-reduce, all-gather, reduce-scatter, all-to-all, broadcast, plus send and receive.
  • Ring all-reduce sends about 2(N−1)/N times the data size per GPU. Bus bandwidth scales the result so you can compare it with the hardware peak. Raw algorithm bandwidth falls as you add GPUs. Bus bandwidth does not.
  • GPUDirect RDMA gives a third-party device, such as a NIC, a direct data path to GPU memory over PCIe.
  • Zero-copy means the NIC reads your buffer directly. It skips the staging copies through internal buffers. In CTran it is also SM-free: a CPU thread drives the whole transfer, so no GPU cores are used for it.
  • TorchComms adds explicit communicators and pluggable backends. NCCLX is a backend. CTran is the host-driven transport inside NCCLX. It supports NVLink, IB/RoCE and sockets. TorchComms was announced in October 2025 as experimental. Its status has been changing, so check the repo and the speaker's article before relying on it.
  • Distance matters. The NCCLX paper reports latency of 7×, 15× and 30× the same-rack latency across racks, zones and data centres.

Learn in this order

  1. NCCL user guide
  2. NCCL collectives Pictures of every collective.
  3. Ring all-reduce explained Gibiansky's classic walk-through.
  4. nccl-tests Measure real bandwidth on your cluster. Read doc/PERFORMANCE.md for how algbw and busbw are defined.
  5. GPUDirect RDMA
  6. Meta: RoCE networks for distributed AI training Why distance and topology matter.
  7. NCCL point-to-point Send, receive and grouped all-to-all.
  8. Demystifying NCCL The ring and tree algorithms and the Simple, LL and LL128 protocols.
  9. PyTorch Distributed is changing, and TorchComms is why (Red Hat, July 2026) Written by the speaker. It says c10d stays the user-facing API.
  10. RCCLX (Meta) CTran moving to AMD through torchcomms.
  11. TorchComms blog

  13. Llama 3 paper Real cluster numbers and failures at scale.
  14. DeepEP A communication library for MoE all-to-all.
  15. NCCL docs: environment and tuning Look for the sections on environment variables and topology.

Try it

  1. Run all_reduce_perf from nccl-tests on 2 GPUs, then on 8. Plot bus bandwidth against message size.
  2. Work out the time for a ring all-reduce of 1 GB across 8 GPUs at 400 GB/s bus bandwidth. Then at 50 GB/s. Check: each GPU moves 2 × 7/8 = 1.75 GB, so 4.4 ms at 400 GB/s and 35 ms at 50 GB/s.
  3. Read the TorchComms post and draw the stack from your code down to the NIC. Mark where the copies are.

Check yourself

  • What does a zero-copy path skip?
  • Why is tensor parallel kept inside a node?
  • Why did c10d fit the first ~10K GPU era, and what changed?

Capstone ideas

Pick one. A small, finished project beats a big one you never ship.

  • Faster step. Take a small Transformer training step. Profile it, fix the top two problems, and write a before and after.
  • Serving shoot-out. Benchmark vLLM and SGLang on your own multi-turn traffic. Report time to first token and throughput. Say what you would pick.
  • An environment I can trust. Build an RL environment, red-team it, train a small model with GRPO, and write up what it tried to cheat.
  • Scale a toy. Train a small LLM with TorchTitan on FSDP2 + TP, then resume the checkpoint on a different GPU count.
  • Map the cluster. Run nccl-tests across two nodes, draw the topology, and explain the numbers.
