PyTorch × Hugging Face meetup, Bengaluru

Hosted by Red Hat and Hugging Face. Five talks on the systems under the model.

This was not a meetup about calling APIs. Every talk was about what runs under the model: profilers, inference engines, RL environments, distributed training and GPU communication.

The evening opened with Sudhir Dharanendraiah. His point was simple. India uses a lot of AI. It should also help build the stack under it.

I took notes by hand all evening. This is the cleaned-up version, with the slides and a few pages of my notes.

Talk 1

Profiling in PyTorch

Aritra Roy Gosthipaty · Hugging Face

“What you cannot profile, you cannot optimize.”

That was the first line. Then Aritra gave a simple recipe.

  1. Mark the code you care about with torch.profiler.record_function.
  2. Wrap it in torch.profiler.profile. Pick the activities, CPU and CUDA. Set a schedule: wait, warmup, then active steps. I wrote down active=3, repeat=1.
  3. Export two things: a trace and a table.

The schedule is easy to miss. Warmup steps are slow and noisy, so you skip them. Only the active steps are recorded. With active=3, every op shows up three times in the table.

To read the table, sort by CUDA time total. The first row is your biggest bottleneck. Then check how many times it was called. Sometimes a row is on top just because it ran a lot.

The idea I liked most: overhead bound

Take a small matrix multiply. The GPU finishes it almost at once. But the CPU spends longer launching the kernel than the GPU spends running it. So CPU time is bigger than CUDA time, and the GPU sits idle. This is called being overhead bound.

The fix is not a faster kernel. It is more work per launch, or fewer launches. If CUDA time is the bigger one, you are compute bound or memory bound instead. That is a different problem.

The trace shows this clearly. Open it in the Hugging Face trace viewer or Perfetto. You get two lanes, one for the CPU and one for the GPU. Gaps in the GPU lane mean the GPU was waiting.

Where torch.compile fits

In eager mode, every op is its own launch: matmul, then add, then activation. torch.compile traces the graph, fuses the ops and caches the result. The work right after a matmul, like an activation or a normalization, is called the epilogue. It can be fused into the same kernel. So one Triton kernel is launched instead of many, and there are fewer trips to memory.

The names in the table, like aten::matmul, are ATen ops. ATen is PyTorch's tensor library.

Talk 2

SGLang, the Transformers backend and kernels

Adarsh · Hugging Face

Adarsh began with a plain point. Serving one user is easy. Serving thousands at once is where the real work starts.

Inference is two jobs

Prefill reads the whole prompt in parallel and builds the model's working context. It is compute bound. The maths is matrix times matrix.

Decode writes one token at a time. It is memory bound. The maths is matrix times vector, and every step reads the KV cache again.

What SGLang is made of

  • Scheduler. Batches requests together.
  • KV cache manager. Stores the cache and reuses it.
  • Model runner. Runs the forward pass.
  • Attention backend. flash-attn or flash-infer.

RadixAttention

Most servers throw the KV cache away when a request ends. SGLang keeps it. It stores the cache of old requests in a radix tree, a memory-efficient prefix tree, and drops the least recently used first. A new request with the same start reuses it. So a shared system prompt is computed only once.

One slide made this real. Llama-3-8B on one H100. The same 1,000 requests, each with a 2K-token shared prompt. Plain generate() gave about 209 tokens per second. SGLang gave about 7,900. That is roughly 38 times more. The run dropped from about 25 minutes to about 40 seconds.

Transformers and SGLang together

Transformers keeps the model definition. SGLang does the fast serving. You switch it on with --model-impl transformers. This helps with models that nobody has ported to a fast runtime yet. The tp_plan in Hugging Face says how the model is split across GPUs. One slide was called “Transformers internals hijacked”. One config line swaps the attention backend.

One warning I wrote down: numeric drift. Different kernels give slightly different numbers. So the same model can behave a little differently on a different backend.

Kernels

Custom kernels are hard to share. Builds break across toolchains and CUDA versions. Hugging Face's kernel-builder uses Nix, so builds can be repeated. It targets ROCm, XPU, CUDA and Metal, and keeps track of the PyTorch and CUDA version matrix.

A small note at the end of my page: the KV cache can be pushed down to SSDs when GPU memory runs out. DeepSeek does this.

Talk 3

RL environments 101

Adithya S Kolavi · Hugging Face

Adithya's idea was short. If a program can grade a task, the task can become an environment where a model learns.

An environment is a few simple parts: a task and a prompt, tools, state, observations, a place to run code, a reward, and a signal for when the episode is done.

OpenEnv gives LLM environments a common shape, a bit like Gym did for classic RL. Other projects work on the same problem. His slide listed OpenEnv, Verifiers, OpenReward and Harbor under “Frameworks step in”.

Repo2RLEnv

This one turns a GitHub repo into an environment. The tests become the reward. Coding is a great fit because the answer can be checked by running it. And there are a lot of repos.

Trust lives in the environment

This was my favourite slide. The environment enforces the rules. The prompt never asks for them. In practice that means:

  • Do not leave the answer in the prompt.
  • Reset the repo to the base commit.
  • Keep the gold patch and hidden tests out of the container.
  • Run offline by default.

My own takeaway: if a reward can be cheated, a model will find out how.

On my reading list now: the “ultimate guide to RL environments” that Adithya pointed us to.

Talk 4

DeviceMesh, DTensor and FSDP2

Mansi Agarwal · Red Hat

Mansi started with the old pain. Mixing FSDP with tensor parallelism took over a hundred lines of manual plumbing. Change one thing and you rewrite the rest.

Newer PyTorch has three building blocks.

  • DeviceMesh. A grid of GPUs. A 4×2 grid means 4 groups for data parallel and 2 for tensor parallel. You name each dimension.
  • DTensor. A tensor that knows how it is split across the mesh. It can be sharded, replicated or partial.
  • FSDP2. Sharded data parallel, rebuilt on DTensor. It is a transform on the model, not a wrapper around it.

So adding a parallelism means adding a dimension to the mesh. It is not a rewrite.

Communication also becomes automatic. You write the maths. If an op needs a different layout, DTensor adds the all-gather or reduce-scatter for you.

“Locally optimal”

I wrote this next to DTensor. DTensor picks the best sharding for each op as it goes. It does not look at the whole graph. So the full plan may not be the best one. Her limits slide had more: eager-mode overhead, ops that are not covered yet, and no support for uneven sharding.

Checkpoints that reshard

torch.distributed.checkpoint can reshard when you load. Save on 8 GPUs, resume on 16. That is exactly what elastic training needs.

Talk 5

Zero-copy GPU-to-GPU communication

Arkadip Maitra · Red Hat

My notes stop before this talk, so I will keep it short.

Arkadip went below the training loop, to how GPUs talk to each other. PyTorch's default layer, c10d, was built for an older world. Networks are faster now. There is GPUDirect RDMA, NVLink and RoCE. In that world, extra copies and extra threads cost real time.

A zero-copy path removes those copies. It uses fewer GPU thread blocks and makes medium-sized messages faster. One slide put hardware and software on two timelines, to show how the fabric and the framework moved together.
