The plan

You have a pretrained vision encoder, a pretrained language model and a projector full of random numbers. What should train first, on which data, and how would you know that one task improved without another getting worse?

In C7 we assembled this model. It runs, and it answers nonsense, because nothing connects what the encoder sees to what the language model reads. This tutorial builds the system that fixes that.

We work in stages. First the projector learns alone on captions. Then the language model joins, on a mixture of six tasks. Along the way we add the parts that a single training loop does not show you: how often each task is drawn, whether the language model forgets plain text, what an image costs in tokens, and which metric each task needs.

All the data is synthetic. We draw every image ourselves, so every caption, count, bounding box and chart value is exact. No label is estimated.

That also means the results here say whether the training system works. They do not say how well a model would do on real photographs.

The runs are also smaller than we planned, and every number is one seed. We planned a 3,000-step Stage 1, an 8,000-step Stage 2 and 2,000-step comparisons. A first 8,000-step attempt reached step 1,400 in 34 minutes on an oversubscribed server, so we stopped it and kept none of its output.

Step 01

Give every task one sample format

Goal Captions, questions, OCR, documents, charts and grounding all become the same dict, so nothing downstream branches on the task.

A real training system reads dozens of datasets. If each one reaches the trainer in its own shape, every later feature has to be written once per dataset. So we fix one format first: a list of images and a list of chat messages.

Two details matter. sample keeps a meta dict that holds whatever the metric for this task will need, such as a bounding box for grounding. And validate runs on every sample, because a wrong sample is far cheaper to catch here than after hours of training.

Each sample is a pure function of its task, split and index. The same index always gives the same pixels, so a run can resume without saving any data, and train and test can never overlap.

Here is sample 0 of every task, rendered by those generators. Pick a task to see its image and its dict.

Real corpora are not the same size. Captions are plentiful, and documents and charts are scarce. We copy that imbalance with nominal corpus sizes, because that is what mixture strategies have to deal with in step 6.

Step 02

Turn a sample into tensors

Goal Expand images into tokens, mark the tokens the model is graded on, and see exactly what one batch contains.

The processor is where most VLM bugs live. It has three jobs. It writes the chat template.

It replaces each image with one <image> token per visual token. And it decides which tokens count towards the loss.

Read the add helper first. Every token goes into ids. Its label is either the token itself or -100, which PyTorch’s cross-entropy skips. Only the assistant’s answer is supervised, along with its closing <|im_end|>. That last token is what teaches the model to stop.

Text replay is the exception. A "text" message has no chat wrapper, and every token is a target, exactly like language-model pretraining.

Now run it on one sample of each task, plus one text passage. The script needs no model weights.

This output is worth reading slowly. These counts come from the tokenizer and the generators, so they do not depend on your hardware.

  • A document costs 245 visual tokens. A chart costs 49. One long sample sets the width of the whole batch, which is why 60.3% of this batch is padding.
  • Only 3.2% of all positions are targets. The rest of the batch is context.
  • There are 12 tiles in pixel_values and 7 samples. The tile tensor has no batch dimension of its own. Tiles are stacked in the order their tokens appear.

Insight

In this batch the text passage is 1 sample of 7, but it holds 34 of the 62 target tokens. A loss averaged over tokens would let that one passage set more than half of the gradient. We come back to this in step 8, where loss_norm decides whether every token or every sample counts once.

Break it

Drop one tile from pixel_values and keep the text the same. The number of slots and the number of visual tokens now disagree.

masked_scatter alone is a poor guard. With too many visual tokens it quietly uses the first ones, and training runs on the wrong images. With too few it raises an error that says nothing about tiles. So the model counts before it scatters.

If you see this error, compare the processor’s tokens per tile with the model’s. A mismatch usually means the image size or the pixel shuffle factor changed on one side only.

Break it

Now grade the model on the prompt and the image slots too, by replacing every -100 with a real id. Nothing crashes. The logged loss is now an average over many positions that have nothing to do with the task, so the two runs can only be compared on one number: the loss on held-out answers, which the script prints for both. A wrong mask gives no error at all, which is why test_loss_mask_ignores_prompt_tokens exists.

The wrong mask grades 604 positions in this batch instead of 96. After 40 steps its logged loss is 8.49, against 0.81 with the correct mask. The two numbers measure different things, so they cannot be compared. The comparable number is the loss on held-out answers, and it is 2.25 with the wrong mask against 0.92 with the right one, from the same start and the same 40 steps.

So the wrong mask costs quality, and it also confuses the log. A likely cause is that part of the effort goes into predicting the 49 identical image slots and the chat template, which no question depends on. This is one short CPU run, so the size of the gap is not a general rule.

Step 03

Choose a metric for every task

Goal Before any training, decide how each task is scored, and write each metric small enough to check by hand.

A mixed model has no single accuracy. A loss curve cannot tell you that charts improved while OCR got worse. So we write the metrics before we train.

Background inMeasuring what a VLM can do

score maps each task to its metrics. Evaluation then greedily decodes held-out samples and averages them. It never touches the training indices, because the split is part of the seed.

A score alone says little. A model can score well on “how many circles?” by always answering “2”. So every score we quote gets two controls. blind=True runs the same model on grey images, so a score that does not drop was never coming from the image. majority_baseline uses no model at all.

Nuance

Two metrics here are softer or harder than their names suggest. An invoice date that is wrong by one digit, 2026-07-16 against 2026-07-15, scores 0.9 on ANLS and 0 on exact match. For documents where one digit changes the meaning, read both.

And our chart values are integers from 1 to 9. Two different values differ by at least 11%, so the 5% tolerance never helps. On these charts, relaxed accuracy only asks whether the model read the exact integer.

Step 04

Decide what trains, and how fast

Goal Name the freezing choices as presets, count what each one trains, and give each module its own learning rate.

The three modules are in very different states. The vision encoder and the language model are pretrained and fragile. The projector is new and has nothing to lose. So each needs its own treatment, and that treatment changes between stages.

Learning rates follow from the same reasoning. Each module gets its own AdamW parameter group, so the ratios between modules are a deliberate choice.

AdamW inWhat an optimizer actually does

The comment on _no_decay hides a real trap. Decoupled weight decay shrinks every weight it touches, however small its gradient is. Most of the vocabulary never appears in our synthetic tasks, so decay would slowly erode words the model already knew. We exclude embeddings from decay. Every run in this post sets weight_decay to 0.0, so the exclusion changes nothing in them. It matters once you turn decay on.

The schedule is a linear warmup and then a cosine decay. It multiplies each group’s own base rate by the same factor, so the ratios between modules hold for the whole run.

Now count what each preset trains. The numbers below are for C7’s model: SigLIP base, an MLP projector and SmolLM2-135M.

The script prints one block like this for each of eight settings: four freeze presets and four LoRA placements. The saved log lost the headings that name the blocks, so the other blocks are read from results/param_report.json.

Stage 1 trains 0.9% of the model. Parameter counts are hardware independent, and they add up by hand. The projector is 3072 × 576 + 576 weights in its first layer and 576 × 576 + 576 in its second, which gives 2,102,400. Four vision blocks at 7,087,872 each, plus 1,536 for the final norm, give the 28,353,024 of the partial top 4 entry in that file.

Insight

The language model’s embedding matrix has 28,348,416 weights, more than thirteen times the whole projector. The totals also show that it is the output layer: 30 blocks at 3,540,096, this matrix and a 576-weight norm already make 134,551,872, so there is no separate output matrix. A softmax sends a gradient to every output row, so the lm preset can move words our tasks never use. That is one route by which a model can drift away from language, and it is why step 8 measures forgetting.

Test

The test that matters most in a staged recipe checks that frozen weights did not move.

Step 05

Stage 1: align the projector

Goal Write the training loop once, then use it to teach the projector alone to speak the language model’s embedding space.

This is the simplest version of the recipe, in the style of LLaVA. Both towers are frozen. Only the projector moves, and we train it on captions only. If this cannot work, nothing later will.

Why alignment comes firstTeaching language models to see

The whole recipe uses one loop. A stage is only a configuration of it.

We compute the loss ourselves rather than asking the model for it. We want a loss per sample, so we can log each task on its own, and later so that packed rows can be split back into samples.

The step itself is short. Draw samples, build the batch, run forward, take the per-sample loss, then backward, clip and step.

Nuance

Frozen does not mean out of the graph. requires_grad_(False) stops the language model’s weights from collecting gradients, but activations still carry gradients through every one of its layers back to the projector. So Stage 1 pays for a full backward pass through the language model. That is also why a torch.no_grad() around the language model would be a bug here, while one around the vision encoder would be safe.

Break it

A high learning rate is safe for the projector only up to a point. Multiply it by 1,000 and run the same 40 steps on the CPU. Nothing crashes here either.

The loss does not blow up. It stalls at 1.99, and the held-out answer loss is 2.02 against 0.92 at the configured rate. A stalled loss is harder to notice than a NaN, because every number in the log still looks like a number. This is one 40-step CPU run.

Goal Implement four ways to decide how often each task is drawn, and record what actually got drawn.

Proportional mixing gives documents 1.3% of the draws. At that rate, the 1,000-step Stage 2 run with a batch of 16 would draw about 213 documents in 16,000 samples. Uniform fixes that, but it asks a scarce corpus to supply as many samples as an abundant one. Temperature is the usual compromise, and the config uses T = 2.

Move the sliders. Besides the probabilities, the figure shows how many passes the run makes over each corpus, because repeating a small corpus too often is how it gets memorised.

The sampler records every draw. Each task walks its own fixed permutation, so repeats start only after a full epoch, and the state fits in a small dict, so resuming is exact.

Nuance

Most of our runs draw less than one epoch from any corpus, but not all. The 16,000 samples of the main Stage 2 run, at T = 2 with 10% replay, make at most 0.8 epochs, over documents, and fewer over every other corpus. The 250-step six-task runs stay near one epoch of documents or below: 0.67 for uniform mixing, 1.0 for the manual weights, and 1.04 for the two resolution runs. The training log prints these numbers.

There are two exceptions. Stage 1 makes 2.4 epochs over the captions. The long grounding runs make 6.0 epochs over the 4,000 grounding samples, so a falling training loss there may be memorisation.

The corpus sizes are nominal anyway. So in this tutorial the mixture mostly decides how updates are shared between tasks. On real data, where a corpus of 1,000 documents can be repeated dozens of times, memorisation becomes the bigger risk. The figure lets you see that by raising the sample count.

The clearest difference between these four runs is VQA, and it follows the share of draws. VQA scores 0.906 with proportional mixing, where it is 26.7% of draws. It scores 0.844 at T = 2 (24.8%), 0.773 with uniform mixing (16.7%) and 0.680 with the manual weights (8.3%).

We read this as a statement about draws: with the budget fixed, more draws of a task gave a higher score on it. It is not a ranking of mixtures. A mixture that wins on VQA loses draws on something else.

The other tasks do not show the same pattern. Caption stays between 0.930 and 0.961. Chart stays between 0.109 and 0.133, and one test sample is 0.008.

Step 07

Stage 2: train on the full mixture

Goal Start from the aligned projector, unfreeze the language model, and track each task separately while comparing how much of the vision encoder should train.

Stage 2 loads the Stage 1 checkpoint and adds the language model to the trainable set. The main run keeps vision frozen. Then we ask how far to unfreeze: keep vision frozen, unfreeze its top blocks, or train everything. LoRA is a fourth answer, which step 11 builds.

Step 08

Goal Add text-only samples to the batches, and measure whether the language model got worse at language.

When a pretrained language model trains on short visual answers, its weights drift towards those answers. Nothing in a multimodal loss notices that it can no longer write a paragraph. So we need two things: replay to resist the drift, and a measurement to see it.

Replay needs almost no new code. A text passage is one more task in the mixture, and with_replay fixes its share before the rest is split.

Train and test passages come from different WikiText-2 splits, so the check never sees a replayed passage. It does see the same kind of text, and the results below come back to that.

Break it

Allow far too many tiles. Each tile and the thumbnail take 49 visual tokens. By arithmetic, a grid of 20 tiles plus a thumbnail would take 21 × 49 = 1,029, already over the processor’s limit of 1,024.

If you hit this, lower max_tiles or raise max_length, and remember that doubling the token count roughly quadruples attention cost for that row.

Step 10

Stop paying for padding

Goal Fit several samples into one row of a fixed token budget, in a way that computes exactly what separate samples would.

Tiling made lengths vary a lot. Our batch had rows from 34 to 274 tokens, and 60.3% of its positions were padding. Sorting by length helps. Packing goes further: it concatenates short samples into one row.

The first part is bin packing. First-fit decreasing is a simple and well-known heuristic: take the longest sample first and put it in the first row with room.

Placing samples in one row is the easy part. Three things must hold, or the row computes something different from the separate samples.

  1. A token may only attend to earlier tokens of its own sample. That needs a block-diagonal causal mask.
  2. Position ids restart at 0 for each sample.
  3. The first token of a sample is not a target for the last token of the previous one.

Build the mask yourself. Change the lengths, then turn the block mask off to see which pairs would leak.

The trainer turns seg_ids into a sample index, so per_sample_loss works unchanged.

Samples with more than one image need nothing new. The processor expands each image slot in order and records tiles_per_image, and the tiles go into the same tensor. No training task in this tutorial uses more than one image, so this script only shows that the path works and what it costs, with real forward passes through C7’s model.

Test

This is the contract of packing: the same loss per sample as running each sample alone.

Break it

Keep the packed row and replace the block mask with a plain causal one. Nothing crashes. The first sample cannot tell the difference, because it has nothing before it.

The second sample now reads the first, and its logits move. A leak like this gives a clean-looking loss curve while training on a task that does not exist.

To debug a suspected leak, change a token in one sample and check that the logits of every other sample in the row stay identical.

Packing removes wasted positions, not necessarily wasted attention. Our batch drops from 1,918 positions to 1,024 with a budget of 512. Step 12

Teach the model to point

Goal Turn points, boxes and masks into text a language model can write, and parse them back without losing track of the error.

A language model can only point by writing tokens. So grounding needs an encoding from pixel geometry to text, and a decoder for the metric. We quantise coordinates into 32 bins across each side, which makes one bin 7 pixels on a 224-pixel image.

Theory inWhen language must point

Two text formats carry exactly the same bins. The tokens format uses one new vocabulary item per coordinate, such as <loc_3>. The text format writes digits the language model already knows, such as [3, 10, 8, 15].

Nuance

Quantisation caps the metric before the model does anything, because the decoded box grows outward to whole bins. With 32 bins, a 28-pixel square can decode to 35 by 35 pixels, so a perfect answer scores an IoU of 0.64.

One more wrong bin outward on one side gives 0.53, and a second wrong bin takes it below 0.5. So on the smallest objects, accuracy at IoU 0.5 allows about one wrong bin, and accuracy at 0.75 can fail on a perfect answer. Raise the bin count when objects are small.

Points use the same bins, and they are scored by whether the decoded point lands inside the true box. Masks have no natural token form, so the model writes an outline: a flat list of quantised vertices. The true mask is stored as a COCO run-length encoding. In the grounding task, 60% of the samples ask for a box, 20% for a point and 20% for an outline.

Nuance

Outlines cost far more tokens than boxes. A box takes 4 location tokens. A square outline takes 8, and a circle, drawn with 12 vertices, takes 24.

In the text format the same circle takes up to 96 tokens, because every digit, comma and space is a token of its own. A generation limit that is too small would cut a text-format outline off by the limit rather than by the model. So the grounding task has its own limit for each format.

What these runs do not show

The runs are smaller than the plan, and several things were never measured. This is the list, so that the tables above are not read as more than they are.

  • A full-scale Stage 2. The plan was 8,000 steps. The numbers here are for 1,000 steps, and the OCR error was still falling at the end.
  • bf16 or fp16. Every run is float32, and the trainer has no mixed precision.
  • More than one seed. Every difference between two runs is a single-run difference, so it can be noise.
  • Real data. Everything is rendered shapes, words, invoices and bar charts. The scores do not predict how a model would do on photographs or scans.
  • A speed comparison. Both machines were shared with other jobs. Only the quality numbers compare across rows.

The real runs also exposed bugs that the tests on tiny models had missed. A lrs.vision=1e-5 override was read as a string, which crashed the first freeze_partial run, and parse_value now returns a float. The standalone model loaded SigLIP with an argument the class rejects, and loaded the language model in bfloat16 while the rest ran in float32.

On the CPU, grounding never produced a coordinate with the default <loc_k> initialisation, which led to the opt-in loc_init=spread. A single generation limit of 24 tokens would have capped text-format outlines, so each grounding format now has its own limit. And mask outlines gained a decoder, a scorer and a training task, because they had an encoder and nothing else.

Key insights and nuances

  • One text passage can outweigh six visual samples. In our batch of 7, it holds 34 of the 62 target tokens, so how you average the loss is a choice about tasks. Step 2
  • A soft metric can hide a wrong answer. One wrong digit in a date scores 0.9 on ANLS and 0 on exact match. On our integer charts, the 5% tolerance of relaxed accuracy never applies. Step 3
  • The embedding matrix is also the output layer. Its 28.3M weights are shared, so the softmax sends a gradient to every row, including words our tasks never use. Step 4
  • Frozen does not mean out of the graph. Stage 1 trains 0.9% of the weights, and it still pays for a backward pass through the whole language model. Step 5
  • A mixture is a choice about updates and about repeats. The Stage 2 main run stays below one epoch of every corpus (at most 0.8), but Stage 1 makes 2.4 epochs over its captions and the long grounding runs make 6.0 over 4,000 samples, so memorisation was possible there and we did not measure it. In the 250-step runs, the VQA score followed the share of VQA draws, from 0.906 at 26.7% to 0.680 at 8.3%. Step 6
  • A score above zero is not a learned task. On the H100 run, documents score 0.191 with real images and 0.197 with grey images, and charts score 0.148 against 0.125 for a fixed answer. The grey-image and no-model controls found both failures. Step 7
  • Replay flatters the forgetting number. With replay, perplexity falls from 35.32 to 23.19, partly because the replay text and the test text are the same kind of writing. The run without replay (35.32 to 49.85) is the real forgetting measure. Step 8
  • Tiling also distorts. A 336 by 224 image is stretched 33% to fit a 1 by 2 grid. Step 9
  • Packing removes positions, not attention pairs. Our batch drops from 1,918 positions to 1,024, while pairs stay near 525,000. Step 10
  • LoRA only on the vision tower, or only on the projector, did not learn the tasks in 250 steps. With the language model blocks frozen, VQA was 0.445 and 0.461 against 0.812 for LoRA on the language model. Step 11
  • A perfect grounding answer does not score 1. With 32 bins, a perfect answer on a 28-pixel square can score an IoU of 0.64. Step 12
  • Grounding is not shown to work. After 1,500 steps, 2 to 4 of 70 boxes are correct, and a fixed box with no model gets 1 to 5 of 70. The data cannot separate undertrained from no skill yet. The 32 new location rows start 3.2e-6 apart, a plausible cause that we did not isolate. Step 12
