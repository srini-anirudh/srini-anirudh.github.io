The plan

A model can write a tool call. What else has to exist before it can fix a failing test on its own, without hurting anything?

That extra code is the harness. We build it the way this series builds everything. We write the simplest version, run it, watch it fail, and add the piece that fixes the failure. We start with an eight-line loop and end with about 3,300 lines of small modules.

The theory post explains why harnesses look the way they do. Here we write one and measure it.

The design reasoning inInside an AI agent harness

Most of the tutorial uses a scripted model. It replies from a fixed list, so every run is the same. That is not a shortcut around the hard part, because the tools, the tests, the edits and the permission checks all run for real. It lets us test the harness without needing a model that behaves. Step 19 connects a real model and reports what happened.

Clone the repo once.

That install is for the whole series, so it pulls PyTorch, Transformers, Datasets and more. For this tutorial alone, .venv/bin/pip install pytest is enough until the real model in step 19 and the real tokenizer in step 2. We checked that lighter install with minimal_loop.py, demo_fix_test.py and two test files.

Commands run from the repo root. A terminal that needs the tutorial folder starts with cd c10-agent-harness and ends with cd ... Where no script exists for a check, the terminal holds a short Python snippet to paste, and the output below it comes from that snippet.

A note on the numbers. Token counts and pass or fail counts below come from scripted runs and do not depend on the machine. Timings do, so each one names its hardware. Most saved files in results/ end with a hardware: line that the script does not print. We move it to the label on the output block.

Step 01

Write the minimal loop

Goal An agent in eight lines, and a clear list of the ways it fails.

An agent is a loop. Call the model. If it asks for a tool, run the tool, add the result to the context, and call the model again. If it does not ask for a tool, stop.

Read it line by line. The context is a plain list of messages, and it starts with the task. model.complete takes the list and returns a response. We append that response at once, because the model must see its own past calls on the next turn. If the response is final we stop. Otherwise we run each call and append each result.

Nothing here is a tensor. The object that flows around this loop is a list of dictionaries, so this table does the job a shape table does in other tutorials.

The messages in the context, in the format Hugging Face chat templates accept
RoleFieldsMeaning
userrole, contentThe task.
assistantrole, content, tool_callsWhat the model said, and zero or more calls.
tool_calls[i]id, type, function.name, function.argumentsOne requested call. We keep the arguments as a dict.
toolrole, content, tool_call_idA result, tied to the call it answers by id.

OpenAI-compatible servers want function.arguments as a JSON string, not a dict. to_wire in openai_compat.py converts them on the way out.

The model is a ScriptedModel. It takes a list of raw replies and returns them in order. It parses each one with the same parser a real model's text goes through, so a badly formed reply breaks the same way.

Run the script. It does one good run and then breaks the loop in three ways.

Break it

The first two breaks crash loudly, which is the better case. The third is quiet. The model writes one trailing comma, the parser records an error, and the loop has nothing to run and nothing to say. It calls the model again. A real model given the same context tends to repeat itself, so this loop would spend money until you stopped it.

The debugging lesson is about where the error goes. All three failures are facts the model could act on, and in this loop none of them reach it.

Test

We keep these failures as tests, so the reference stays honest: test_minimal_loop_crashes_on_unknown_tool and test_minimal_loop_spins_on_malformed_call.

Checkpoint

  • The good run ends with four messages: user, assistant, tool, assistant.
  • You can say why the third break does not raise anything.
Step 02

Generate tool schemas from functions

Goal Write a Python function once, and get the schema the model reads from it.

The minimal loop passes tools=[], so the model knows nothing about what it can call. A model learns its tools from a JSON schema: a name, a description and the arguments. We could write those by hand. Then the schema and the function would drift apart, and the model would read a description of code that no longer exists.

So we generate the schema. The function's signature gives the types and the docstring gives the words.

How the schema reaches the model inHow language models learn to use tools

A parameter annotated ToolContext is skipped. That is how a tool gets the workspace and the sandbox without the model ever seeing them. A parameter with no default is required. A default of None means optional, with nothing written into the schema.

The types go through one small function.

Now look at the real output and at what it costs. A schema is not free. It goes into the prompt on every turn.

The estimate column is our cheap token counter from step 10. The tokenizer column is a real tokenizer. Prose matches almost exactly. JSON is overcounted by 1.89 times, because the estimate treats every brace and quote as its own token. We will come back to that.

Insight

Twenty tools cost 1,676 real tokens before the model has read the task. The five-tool preset costs 537. Our estimate says the tool list is over 90% of the first prompt in the demo run. So the size of the toolset is a design decision with a price on every turn, and a small model should get a small preset. That is why coding_tools("small-model") exists.

Test

test_schema_from_signature_and_docstring checks the required list, the hidden context, defaults and enums. test_full_registry_exposes_twenty_valid_schemas checks every tool in the default set.

Checkpoint

  • show_schemas.py prints the schema for read_file, with no ctx in it.
  • You can predict the schema of a new function before you run it.
Step 03

Parse and validate tool calls

Goal Turn all three failures from step 1 into messages the model can act on.

A tool call is text until we parse it. Models trained on the Hermes format write it inside a tag.

Two jobs follow. Parsing asks whether this is a well-formed call. Validation asks whether this call fits a tool we have. They fail differently, so they are separate.

The parser is strict about structure and forgiving about small things. Some models write parameters instead of arguments, and some encode the arguments as a JSON string. Both are safe to repair. A broken string is not, so it becomes an error with the position and a snippet of the text around it.

Validation runs after parsing, against the schema we generated in step 2.

The small helper _coerce accepts a quoted number such as "12" for an integer field, because small models often write that. You can turn it off with coerce=False.

Break it

Send the registry three bad calls.

Each message tells the model what to do next. The typo lists the real names. That is the whole debugging interface a model has, so these strings are worth writing with care.

A call can pass both checks and still fail, because the tool itself can have a bug. So execution catches everything.

In the full loop, an error of either kind goes back to the model. format_call_errors writes the message, and the loop counts consecutive failures. After four in a row it stops with the status protocol_errors. That closes the third break from step 1: the model hears about the problem, and the retries have a limit.

Test

test_malformed_call_gets_feedback_then_recovers sends the same trailing comma that broke step 1. test_too_many_protocol_errors_stops_the_run checks the limit.

Checkpoint

  • A malformed call is not a final answer, and the model gets told why.
  • A wrong tool name returns a list of the right names. It does not raise.
Step 04

Add filesystem tools

Goal Read, list, search, write and patch, with every path held inside the workspace.

A coding agent needs five operations on files. They live in different modules, because search and patching are big enough to deserve their own steps.

The five filesystem operations
OperationToolWhere
readread_fileThis step
listlist_dirThis step
writewrite_fileThis step
searchsearch, find_files, find_symbolStep 11
patchedit_file, apply_patchStep 6

Two small pieces of code do the safety work.

The tracker needs a reason. A model edits from memory. If the file changed since it read it, or it never read it at all, then the edit is based on a view of the file that is out of date. That is a silent way to lose someone's work. The check costs the model one more read, and it prevents that loss.

read_file returns numbered lines. Models refer to line numbers, and a real file has no line numbers to quote. It also stops at 400 lines unless asked for more, and it says so in the output.

Break it

Try to edit without reading, change the file behind the model's back, and walk out of the workspace.

The harness writes each of these for a reader who can fix the problem with one more tool call.

Nuance

The path check protects the file tools only. A shell command is free to name any path. We test that in step 8, and the result is not comfortable.

Checkpoint

  • test_paths_cannot_escape_the_workspace and test_symlink_escape_is_blocked pass.
  • test_write_requires_a_fresh_read passes.
Step 05

Add the shell tool

Goal Run a command, and report exit code, stdout and stderr, with a timeout that actually kills everything.

The obvious version is subprocess.run(command, shell=True, capture_output=True, timeout=60). It looks finished. We tried it with a command that starts a background child, the way a test server or a build tool does.

That shows two real bugs. When the timeout fires, Python kills only the process it started, and the background child lives on. In a loop that runs for hours, those children add up. In the normal path, the shell exits at once but the background child still holds the output pipe, so the call waits for that child. A model that runs server & would block the agent.

The fix is to give each command its own process group, and to act on the whole group.

Read the highlighted lines in order. start_new_session=True makes the child the leader of a new group, so its pid is also the group id. The loop checks the clock on each tick and checks memory on every fifth tick, because calling ps is slow. After the leader exits, a final kill_group removes anything it left behind. That line is what fixes the second bug.

Output needs the same care. If a command prints for a long time, we cannot hold it all in memory. _Capture keeps the first and last half of its budget and counts what it dropped.

Capture has a cost that step 16 comes back to: past 1 MB, the middle of the output is gone. The tool itself is short. It turns a result into text for the model.

Try it. This is what the model sees.

Nuance

A 1 second timeout took 1.7 seconds here, and between 1.5 and 1.7 across our runs. kill_group always waits its 0.5 second grace between SIGTERM and SIGKILL, even after a plain sleep has died. A test runner needs that wait to flush its output. Treat a timeout as a limit on when the kill starts, not on when the call returns.

Checkpoint

  • test_timeout_kills_the_whole_process_group checks that the background child is really gone.
  • test_background_orphans_do_not_hang_the_call returns in under 5 seconds.
  • test_capture_is_bounded_and_counts_everything passes.
Step 06

Compare edit formats and build the applier

Goal Measure what each edit format does when the model makes a mistake, then build an applier that fails loudly.

There are four common ways for a model to express an edit. It can rewrite the whole file. It can quote a block and give its replacement. It can write a unified diff with exact line numbers, or a unified diff where the numbers are only hints.

Why editing is a protocol inInside an AI agent harness

Search and replace is the simplest of the careful formats. The applier tries an exact match, then ignores trailing spaces, then ignores indentation.

The last line is the most useful one in this file. When the quote is not found, the error shows the region of the file that is closest. The model does not have to guess what it got wrong.

Diffs go through a parser and then apply_hunks. In strict mode the old lines must sit exactly where the header says. In anchored mode the number is only a hint: we search for the old lines and take the match nearest the hint.

What each format does under a slip

Now the measurement. The benchmark takes real lines of real Python and asks for a one-line edit, 200 times per cell. It writes the edit in each format, applies one kind of slip, and sorts the outcome into three groups. Correct means the file is right. Refused means the applier raised a clear error, so the model can retry. Corrupted means the applier succeeded and the file is wrong, and nobody was told.

Edit formats, along the aspects the benchmark measures
FormatTokens per editCorrect, of 1,400Refused, of 1,400Corrupted, of 1,400Stale line numbersNon-unique quote
Whole file1,6678000600OverwritesNot affected
Search/replace778775230Not affectedRefuses
Strict diff1186257750RefusesNot affected
Anchored diff1221,0363640Not affectedNot affected

Read it this way. Whole file never refuses, which sounds good and is not. It gives the model no signal when a slip happens. Search/replace is about 20 times cheaper, and every slip it could not handle became a refusal. Anchored diff gets the most edits right. We use search/replace as the default tool because it is the smallest, with apply_patch for changes that span several places.

Insight

A refusal costs one more turn. A silent corruption costs whatever happens until someone notices. So count them separately. Strict diff refuses more than anything else and corrupts nothing, which makes it safe but slow. Anchored diff refused 364 edits against 775 for strict, and also corrupted nothing. Its context lines do the work that strict mode asks the line numbers to do.

Break it

Those zeros were not there at first. The first version of reindent shifted only the lines that start with the first quoted line's indent, and it left the rest alone. It looked fine until we quoted two lines where the second is shallower. Swap this version back in by hand and rerun the benchmark.

That is 66 and 93 silent corruptions, in the two formats that repair indentation. Here is one by hand. The file has z = 2 at four spaces, outside the if. The buggy version returned it at eight spaces, inside the if.

The first result still parses, and its behaviour has changed. The fixed version shifts every line by the same signed amount, and raises if a line would go past column zero. When you debug an applier, check the strategy field: indentation marks every edit that took this path.

Nuance

The slips are simulated. The table shows what each format does when a slip happens, not how often a real model slips. That rate would change the totals a lot, and the zeros cover only these seven slips.

The benchmark also calls the appliers directly. In the real tools the file tracker from step 4 catches stale files first, so a model that rewrites a whole file from an old read gets a refusal. The lazy rewrite and the misremembered line get past it, because the file on disk has not changed.

Check against git

We compare the diff applier with an implementation we did not write. The same diff goes to our applier and to git apply, on the same file, 200 times. The output is from an AMD EPYC 7R13 CPU.

On clean input all three agree on all 200. The second row taught us something. Git accepts a diff whose line numbers are off by three, because it searches for an offset. So our anchored mode behaves like git apply here, and our strict mode is stricter than git. Anchored mode and git gave the same result on all 400 diffs.

The same script compares our schemas with transformers.utils.get_json_schema, on one sample function. The types, descriptions and required lists all match. Ours also writes defaults and additionalProperties: false. Theirs marks an optional argument as nullable, and adds a return type.

Checkpoint

  • test_flattened_structure_is_refused_not_guessed and test_apply_patch_is_atomic_across_files pass.
  • You can say which row of the table made you choose your default format.
Step 07

Add verification tools with one result shape

Goal Tests, lint, type check and build all answer the same question in the same format.

An agent that cannot check its work is guessing. We could tell the model to run pytest through the shell tool. Then it has to read pytest's output, and ruff's, and mypy's, each in its own dialect. All of them answer one question: what is broken, and where?

Real ruff and real mypy never ran for this tutorial, because neither is installed on the machine behind these numbers. Their parsers have tests on hand-written output only, so a real version may format things differently. The pytest path, the built-in lint check and build all ran for real.

The pytest parser reads the summary line for the counts and the short report for the failures. The exit code decides the status, because the text alone cannot tell a failure from a crash.

Run it on a copy of the toy repo. This is the text the model gets.

The second and third lines give the file, the line, the test and the assertion, before any of pytest's own formatting. The passing tests are gone. The result is also a structured event, so the log can say when the suite went from red to green without parsing text again.

Step 08

Run commands in a sandbox

Goal Two backends behind one interface, with workspace mount, limits, network policy, timeout and cleanup.

The model chooses the commands, so they must not run with our full rights. Both backends implement one method: run(command, timeout, cwd) returns an ExecResult. Both use run_process from step 5. The limits live in one small dataclass.

The local backend

LocalSandbox is a guard rail for laptops and CI. It clears the environment so API keys do not reach commands the model writes, sets resource limits, and removes network access where the operating system allows it.

A test tries to open a connection through the sandbox. On our Linux machine, using unshare, it passes because the connection is refused.

Break it

The class docstring says this backend is not a security boundary. Here is what that means. We put a file next to the workspace, not inside it, and run two commands through LocalSandbox.

Both ran with no prompt. read_file refuses this path, and the shell does not. The same user and the same kernel means no real wall. If that matters to you, the fix is a real boundary, which is the next backend.

The Docker backend

DockerSandbox runs each command in a fresh container. The workspace is bind-mounted at /workspace, and nothing else from the host is visible.

The CPU limit sets a soft and a hard value on purpose. That makes a CPU kill exit with 152, so it is not mistaken for the memory kill, which exits with 137.

Break it

The --user flag is there because the first real run failed without it. The container ran as the image's root with --cap-drop ALL, which removes the capability that lets root ignore file permissions. Root became a stranger to the host user's files. In a mode-700 workspace it could not read.

A mode-755 workspace was readable but not writable. Running as the host uid fixes both, and files the command writes stay owned by that user. To see it fail, delete the --user line and run test_docker_runs_for_real with Docker present.

We ran this backend for real, on an AMD EPYC 7R13 with Docker 29.1.4 and image python:3.12-slim. The demo starts a fresh throwaway container for each row, checks one limit from inside it, then lets the agent fix the toy repo with every test run in a container.

Nuance

Only commands run in the container. read_file, edit_file and the git tools run in the harness process on the host, and they rely on the path check from step 4. python:3.12-slim also has no pytest and the container has no network, so the demo copies pytest's packages into the workspace and sets PYTHONPATH. A real setup would build its own image.

This demo checks our flags and limits on one Linux kernel, with cgroup v2. It is not a security audit of container isolation. We did not run a container with Limits(network=True), a first-time pull through DockerSandbox, macOS or Docker Desktop.

Checkpoint

  • test_env_is_scrubbed, test_network_is_denied_by_default and test_cpu_limit_kills_a_busy_loop pass with no Docker at all.
  • With Docker and the image present, 19 tests run inside real containers: 18 in test_docker_sandbox.py and 1 in test_fs_shell_sandbox.py. Without them, those 19 skip and say why.
Step 09

Add the permission layer

Goal Classify every action by how much damage it can do, and ask a person only when it matters.

A sandbox limits what a command can reach. Permissions decide whether it runs at all. There are four levels, ordered by how bad a wrong call can be.

Most tools have a fixed risk. read_file is READ and edit_file is WORKSPACE_WRITE. The shell tool has a risk that depends on the command, so a classifier reads the string.

The default is the important part. An unknown program is WORKSPACE_WRITE, never READ. A false alarm costs one prompt, and a false read can cost a home directory.

In the loop, the check runs after validation and before execution. A denial becomes an observation, so the model can choose another way.

Now try the real classifier on strings built to fool it.

Nuance

Reading a string cannot tell you what a program will do. The first two run with no prompt, and one of them deletes the filesystem. The last two are DANGEROUS, though they harm nothing. The classifier filters accidents, and the sandbox limits the damage when it is wrong, so you need both.

Checkpoint

  • test_denied_call_never_executes_and_is_logged shows the tool never ran.
  • test_hard_ceiling_cannot_be_approved shows an approver cannot lift the ceiling.
Step 10

Build the context from named parts

Goal Assemble what the model sees each turn from sections, and count the tokens of each one.

In the minimal loop the context was one growing list. A real prompt has parts that change at different rates. The instructions never change. The repository state changes after an edit. The task never changes, but the plan and the step counter do. Only the history grows.

So the system message is rendered fresh each turn, and the history is kept apart from it.

Step 11

Add repository search

Goal Find text, find files and find definitions, without reading the whole repository.

The model cannot read every file. Search lets it pull in only what it needs. We write the reference first, in pure Python, because it has no dependencies and is easy to trust.

Then we pick the fastest backend that exists on the machine.

Text search answers where a string appears. A model usually wants to know where a function is defined and who uses it. Python's ast module gives us that for free.

find_files is the third tool. It matches paths with a glob, for when the model knows a file's shape and not its contents. Here are all three on the toy repo.

Nuance

Pure Python is only 1.3 times slower than git grep here, because this repo is small and its files are already cached. Do not expect that ratio on a large repository. find_symbol rebuilds the index on every call, at over half a second here. Caching it is the first thing to fix on a large repository.

Two gaps, stated plainly. The ripgrep backend is written, but ripgrep is not installed on the machine that ran these numbers, and no test covers that path. The plan lists embedding search as optional, and we did not build it. Exercise 1 asks you to add it and to find out whether it helps.

Step 12

Build a repository map

Goal Show the shape of the whole codebase in a few hundred tokens.

Search needs the model to know what to look for. A map tells it what exists. We use the symbol index to render each file as an outline, rank the files, and stop when the budget is spent.

On a larger codebase the budget is what makes this useful. This is the map of this repository's Python code, from the same benchmark.

Step 13

Keep a plan outside the history

Goal A checklist the model maintains, and the harness shows on every turn.

Long tasks lose their thread. A plan helps only if the model keeps seeing it. If the plan sat in the chat history, it would scroll away and later get compacted. So it lives in the agent's state, and the context builder renders it into the system message each turn.

The tool that changes it is one line of real work: update_plan replaces the whole list. Replacing is simpler than editing items by index, and it makes a model restate where it is.

Checkpoint

  • test_plan_tool_round_trip passes, including both refusals.
  • test_compaction_triggers_preserves_task_and_replays shows the task surviving compaction. We build that in step 15.
Step 14

Write every action to an event log

Goal An append-only JSONL file from which the whole chat history can be rebuilt.

When a run goes wrong, you need to know what happened, in order. So every action becomes one JSON line, written at once. A crash loses at most one line.

Step 15

Compact the context when it gets too large

Goal Keep the prompt inside a budget, and keep the facts that are expensive to rediscover.

Every model call sends the whole history again. A run of N steps sends about N squared tokens in total. The benchmark shows it in the table below: doubling from 80 to 160 steps with no budget multiplies total prompt tokens by 3.9.

When the history gets too large we summarise the older part. The rules, in order: task state survives because it is not in the history. Important failures from the dropped turns are kept word for word. Older turns become one line each. Recent turns stay whole, and a cut never separates a call from its result.

This is the real summary from the demo run. It replaced 16 messages, and the context went from 4,609 to 4,087 estimated tokens.

Now measure it. The benchmark runs a scripted session of N tool calls, each returning the same file-sized text.

Insight

While it holds, a budget changes the growth as well as the peak. With no budget, doubling from 80 to 160 steps multiplies the total by 3.9, which is quadratic. With a budget of 4,000 the same doubling multiplies it by 2.1. At 160 steps that saves 89%.

Nuance

A budget holds only while the summary fits inside it. Our summary keeps one line per call and is never dropped, so it grew to 7,687 tokens at 640 steps. There the prompt peaks at 8,273 under both budgets, 4,000 and 8,000.

So the limit depends on the budget. In these runs the summary costs about 12 tokens per call, and the rest of the prompt about 590. A budget B therefore holds up to about (B − 590) / 12 steps: near 120 steps for 2,000, 280 for 4,000 and 620 for 8,000. That rough fit agrees with every row above. A budget of 2,000 holds at 80 steps and fails at 160, 4,000 holds at 160 and fails at 320, and 8,000 holds at 320 and fails at 640.

Past that point every turn compacts and the growth returns. From 320 to 640 steps the total grows 2.9 times at a budget of 4,000 and 2.3 times at 8,000. Those runs also compact 448 and 133 times.

All of this measures token counts only. It says nothing about whether a model would still solve the task after compaction this hard. That needs a real model and an evaluation.

Checkpoint

  • test_compaction_keeps_recent_turns_whole_and_pairs_intact checks that no result is cut off from its call.
  • test_second_compaction_extends_the_first shows summaries do not nest.

Step 16

Truncate giant outputs safely

Goal A 20,000 line log becomes about 90 lines and keeps its failing assertion, as long as the log fits in capture.

A test run can print 20,000 lines. Pasted into the context, that costs about 300,000 estimated tokens and hides the task. The usual fixes are to keep the start or keep the end. So we test them: one failing assertion at a random place in a synthetic log, 200 times.

Every simple policy lost the assertion almost every time. So we add a third source of lines: anything in the middle that looks like an error, with one line of context on each side.

Nuance

The 100% has an easy condition: this log holds one failure. Rescue has a budget of 30 lines and spends it from the top. So 200 earlier FAILED lines use it up and the assertion is lost. Tick the box in the figure to see it, or run the snippet below.

Break it

The benchmark calls truncate_output directly. Through the real run_command, capture from step 5 runs first and keeps at most 1 MB per stream. A longer log loses its middle before rescue ever sees it, and no pattern can bring that back.

At 960 KB everything works. At 2 MB the assertion is gone from the observation and from the saved file. The footer says so: it reports the dropped bytes and says kept text, not full text, and the saved file's first line says it is incomplete. run_tests goes through the same capture, so its details can lose an assertion too, and it adds the same note.

Truncation happens twice. The shell tool truncates each stream as it formats the result. The loop then applies a limit to every observation, whatever tool produced it, because one forgotten tool should not be able to fill the context.

Checkpoint

  • test_truncation_keeps_head_tail_and_rescues_errors passes.
  • test_giant_output_stays_in_budget runs a 50,000 line command through the shell tool.
  • test_footer_and_spill_tell_the_truth_when_capture_dropped_bytes checks the footer and the saved file.
Step 17

Add git status, diff, log, revert and checkpoint

Goal Let the agent save and restore the working tree as often as it likes, without touching the user's branch.

Status, diff and log are thin wrappers around git. Checkpoints need more thought. The agent needs an undo button, and a commit on the user's branch is the wrong way to get one. It would move HEAD and show up in their history. So we write a commit object using a temporary index, and store it under a private ref.

The agent also saves a checkpoint by itself at the start of each run, so even a bad run has a way back. That event is the second line of the demo log.

Nuance

revert_to_checkpoint is marked WORKSPACE_WRITE, so it runs with no prompt, and it discards every later edit. That is fine for an agent's own work in a temporary copy. In a user's real checkout with uncommitted changes, you may want to raise its risk. The checkpoint at the start of the run is what keeps those changes recoverable.

Checkpoint

  • test_checkpoint_does_not_touch_head_or_index passes.
  • test_restore_undoes_edits_and_new_files covers edits, deletions and new files.
Step 18

Trace time, tokens and failures

Goal Answer the questions you ask after a bad run: how many calls, how many tokens, which tool was slow, how many retries.

The event log says what happened. A trace says what it cost. There is one span per model call and one per tool call.

This is the table at the end of the demo run. It covers model calls, tool calls, tokens, latency, failures and retries.

The model latency is close to zero because the model is a script. That makes this useful as a measure of the harness itself. bench_overheads.py runs 200 steps with a no-op tool.

Insight

The harness costs about a millisecond per step. A real model call takes seconds: about 6.7 seconds per call in our CPU run in step 19. So you do not need to optimise the loop. In the table above, almost all of the tool time is run_tests. A slow agent is a slow model or a slow test suite, and the trace tells you which.

Step 19

Assemble the agent and fix a real bug

Goal Inspect, search, edit, test, see the failure, repair and verify, with every piece from the earlier steps in the loop.

Here is the loop again. Compare it with Listing 1.

The eight-line loop had one exit. This one has four. The run can finish, run out of steps, hit too many protocol errors, or hit a permanent model error. Transient model errors, such as a rate limit, retry with backoff inside _call_model.

The demo

The toy repo has one real bug: median returns the upper middle value for an even-length list. The demo gives the scripted model a task and a script with three mistakes in it. It tries a forbidden install, writes broken JSON and quotes a line from memory. The script decides what the model says. The harness decides what happens next.

Every mistake was handled in its own way. The install became a denial, the JSON became a parse error, and the stale quote became a helpful refusal. None of them stopped the run, and the task finished in 13 steps.

Nuance

This demo shows that the harness handles these failures correctly. It does not show that a model would make good choices. The model is a script, and we wrote the script to make those mistakes and recover from them.

A real model

So we ran a real one. HFLocalModel follows the same interface. The chat template renders the tool schemas into the prompt. It generates greedily, and the same parser reads the text. This is the only part of the tutorial with tensors.

What generate does inThe mechanics of LLM inference

This is the honest result. The model did not fix the bug. It tried an edit on its first move, without reading the file, and with a search string that does not exist. The harness refused it for being unread. The model replied in plain text that it would try again, and plain text means the run is over. The status says done, and the bug is still there.

Nuance

done means the model stopped calling tools. It does not mean the task succeeded. This is why the script checks the file and the test runs by itself, and prints bug fixed: False. A harness reports what happened. Deciding whether it worked is a separate job, and it should not rely on the model's word. This is a single run of a 0.5B parameter model, so it says little about what larger models do.

Any server that speaks the OpenAI chat format also works, through OpenAICompatModel. It uses only the standard library, and reads its settings from the environment so that keys stay out of code and logs.

We have not run this client against a real model, so we have no numbers for it. The tests run it against a small fake HTTP server in the same process. They cover the request format, the mapping of errors to retries, and bad JSON in the arguments. results/openai_stub_output.txt is a full run against a local stub that replays scripted replies. It tests the client and the loop, and it says nothing about any real model.

Key insights and nuances

  • The first failure of a naive loop is silence. In the eight-line loop, none of the three failures reach the model. Telling it what went wrong is most of what the first few steps add. Step 1
  • Tools have a price on every turn. Twenty schemas cost 1,676 real tokens before the task is read. The toolset is a design decision. Step 2
  • The dangerous edit format is the one that never refuses. Whole-file rewrite had 600 silent corruptions of 1,400. Search/replace had none, at about a twentieth of the tokens. Step 6
  • Tolerance is where corruption enters. The first reindent added 66 and 93 silent corruptions to the two formats that repair indentation, and fixing it took both to zero. Each repair needs its own test. Step 6
  • A local sandbox is not a wall. read_file refuses a path outside the workspace, and cat through the shell reads it with no prompt. Docker fixes this at a cost of about 412 ms per command against 13 ms. Step 8
  • Reading a command string cannot tell you what it does. An rmtree('/') inside python -c classifies as a workspace write, and grep sudo as dangerous. You need the sandbox as well. Step 9
  • A budget changes the growth while it holds. Doubling from 80 to 160 steps multiplies total tokens by 3.9 with no budget and 2.1 with a budget of 4,000, a saving of 89%. Step 15
  • The budget's limit depends on the budget. The summary keeps one line per call and is never dropped, about 12 tokens per call here. A budget of 2,000 fails by 160 steps, 4,000 by 320 and 8,000 by 640. Step 15
  • Rescue is only as good as its budget. It kept the assertion 100% of the time with one failure in the log, and lost it when 200 other failures came first. Step 16
  • Capture runs before truncation. Past 1 MB per stream the middle of the output is gone, from the observation and from the saved file. The footer reports the lost bytes. Step 16
  • done is not success. The real model's run ended with status done and the bug still there. Check the outcome separately. Step 19
