A chatbot emits an answer we can grade. An agent changes a world. Almost everything that is hard about agent evaluation follows from that one sentence.

Two objects of measurement

A language-model evaluation is a function test. You hand the model an input \(x\), it returns an output \(y\), and a grader compares \(y\) against a reference. The whole apparatus fits in one line:

\[ x \;\longrightarrow\; y, \qquad R = \mathbf{1}[\,y \simeq y^{*}\,]. \]

Nothing outside that line moves. Run it twice and you get two independent samples from the same distribution. Run it a thousand times and the only thing that has changed is your API bill.

An agent evaluation is not that. An agent runs a loop, and the loop is attached to something:

\[ s_0 \;\xrightarrow{\;a_0\;}\; s_1 \;\xrightarrow{\;a_1\;}\; s_2 \;\longrightarrow\; \cdots \;\longrightarrow\; s_T. \]

The states are not tokens. They are rows in a database, files on a disk, messages that have been sent, money that has moved. The transcript is a log of what happened; it is not the thing that happened. And once you internalise that distinction, most of the difficulty in this field stops looking like a collection of unrelated engineering annoyances and starts looking like one problem with many faces.

Here is the problem stated as plainly as I can put it. In a model evaluation the output is the artefact, so grading the output is grading the artefact. In an agent evaluation the output is a claim about the artefact, made by the same system that produced it. Grading the claim is grading the defendant's testimony.

The figure ends where this article begins. Two graders look at the same episode. One reads the final assistant message, which says the order was cancelled, and scores it a pass. The other reads the order table, where the status is still OPEN, and scores it a fail. Both graders are working correctly. They are measuring different things, and only one of them is the thing anyone cared about.

There is a second, quieter observation buried in that figure. Four fields in the world state changed during the episode, and one of them — the item count on the order — changed in a way nobody requested. A grader that checks only the goal condition will never see it. A grader that checks the whole state will see it but has no vocabulary for saying whether it mattered. We will come back to that in §13; for now, note that an agent evaluation has to answer two questions where a model evaluation had one. Did the intended thing happen? And: what else happened?

The system under test

The second structural fact is that the object you just measured was never the model.

Between the weights and the world sits a scaffold: a loop that decides how many steps to allow, whether to retry, how to format tool schemas, what to put back into the context after each observation, whether to run a verifier, whether to sample once or twenty times and pick. Around that sit the tools themselves, whose error messages and idempotency guarantees shape what recovery is even possible. Around that sits whatever memory policy carries state across turns. And around all of it sits the environment.

So the quantity a leaderboard row reports is:

\[ \text{score} = f(\underbrace{\text{model}}_{\theta}, \; \text{scaffold}, \; \text{tools}, \; \text{memory}, \; \text{environment}), \]

and the convention of naming the row after \(\theta\) alone is a convention, not a measurement.

This is not a hypothetical concern. The Holistic Agent Leaderboard was built specifically to hold the harness constant across models and benchmarks, on the argument that without that control you cannot attribute a difference to anything. Running the same agent harness across nine models and nine benchmarks — 21,730 rollouts, roughly forty thousand dollars of inference — produced results that do not line up neatly with vendor-reported numbers, including the finding that turning reasoning effort up reduced accuracy in most of their runs. If a knob that everyone assumes is monotonic is not monotonic, the odds that any two independently-reported scores are comparable are low.

The practical consequence is a discipline, not a technique. When you report an agent score, the model name is one of six things you have to publish, and it is not the most informative one. Step budget, retry policy, tool set, observation format, and whether a verifier was in the loop routinely move the number more than swapping the model does.

The one-sentence version

A model leaderboard is not an agent leaderboard. It cannot be, because the thing it ranks is not the thing you deploy.

Grade the world, not the prose

Everything good in agent evaluation follows from one move: replace the text comparison with a program that inspects state.

\[ R \;=\; \mathbf{1}\big[\,\text{the world is now in the desired state}\,\big]. \]

Concretely: the tests pass; the file contains the right bytes; the ticket exists with the right fields; the email went to the right address; the row was updated and no other row was. This is sometimes called functional correctness or execution-based evaluation, and its virtue is not precision. Its virtue is that it is not a channel the agent controls. The agent can write anything it likes in its final message. It cannot write anything it likes into the return code of the test suite.

WebArena is the cleanest early statement of the idea for web agents: rather than comparing a predicted action sequence against a recorded human one, it ships self-hosted, fully functional websites and grades the end state, so an agent that reaches the goal by a different route still scores. SWE-bench does the same thing for code by running a test suite. This move — from surface similarity to state inspection — is the single most important thing that has happened in this field, and everything after it is a refinement or a complication.

Two refinements are worth stating explicitly.

Grade the state, not the tool call

An intermediate temptation is to grade whether the right tool was called with the right arguments. This is cheaper than standing up an environment and it correlates with success. It is also gameable in a specific and annoying way: an agent can emit a syntactically perfect call to refund(order_id, amount) where amount is wrong, and a schema-level checker will pass it. Argument-level checking measures whether the agent knows the API. State-level checking measures whether the agent did the job. These come apart exactly where it matters.

Where a judge is unavoidable, treat it as an instrument

Some outcomes genuinely cannot be checked programmatically — the quality of a written summary, whether a support reply is appropriate, whether a screenshot shows the task completed. Model judges are the standard answer, and they work well enough to be useful. They also have documented, direction-specific biases: length and verbosity preferences, position effects, self-preference. The point is not that judges are illegitimate. The point is that a judge is a measuring instrument with an error rate, and §10 is about what a non-zero error rate costs you. Report the judge's agreement with human labels on a sample, and report it as a number, the way you would report the calibration of any other instrument.

Partial credit and its price

Once tasks get long, binary success becomes uninformative. An agent that gets seven of eight requirements right and an agent that does nothing both score zero, and the gradient you need for engineering disappears. So benchmarks decompose: intermediate checkpoints, each worth points.

\[ R \;=\; \sum_i w_i \,\mathbf{1}[\,g_i\,]. \]

TheAgentCompany does this explicitly, running 175 professional tasks inside a self-hosted intranet — GitLab, a chat server, file storage, a project tracker — and reporting both a full-completion score and a partial score built from checkpoints. Its results are worth sitting with: the best configuration in the paper completed about 30% of tasks fully, with a partial score around 39%, at roughly four dollars and twenty-seven steps per task. Whatever you believe about agent capability, that gap between full and partial is where all the interesting engineering lives.

But the decomposition has a cost, and it is the same cost that shows up everywhere in reward design.

Every checkpoint you add is another surface that can be satisfied without the task being done. The failing-test example in the figure is not invented: making a test suite pass by deleting the failing test is a documented shortcut, and it satisfies a checker that asked "does the suite pass?" without asking "is the test still there?". The objective \(\sum_i w_i \mathbf{1}[g_i]\) is maximised by whatever satisfies the cheapest \(g_i\), which is not always the thing you meant by \(g_i\).

Slide the weight on the terminal goal in the figure and watch the two numbers converge. They agree only when nearly all the weight sits on the end state — which is to say, when you have stopped using partial credit. That is the actual trade-off, and it does not have a clever resolution. What it has is a reporting discipline: publish both numbers, always, and treat the terminal one as the score. Partial credit is a diagnostic. It is not a result.

Accuracy is half of a number

Two agents solve the same task. One makes five calls, costs two cents, and finishes in ten seconds. The other makes eighty calls, costs four dollars, and takes six minutes. On an accuracy-only leaderboard they are the same row.

This is not a small effect. Running one agent across the eight benchmarks in the HAL suite costs on the order of eight hundred dollars in API fees; a single SWE-bench Verified run has a median cost around $163 with per-task costs spanning from eight cents to thirty-two dollars, a spread of roughly 400× driven by model pricing and scaffold design. A single GAIA run on a frontier configuration has been reported at over two thousand eight hundred dollars before caching.

The fix is arithmetic, not philosophy. Write down what a dollar is worth to you:

\[ U \;=\; Q \;-\; \lambda\,C. \]

Set \(\lambda = 0\) and the most expensive configuration wins by construction. That is what an accuracy-only leaderboard is: a leaderboard that has silently chosen \(\lambda = 0\) on your behalf. Move \(\lambda\) even slightly off zero and the winner changes, usually immediately, because the top of these frontiers is bought with retries whose marginal yield is tiny.

The 2024 argument for cost-controlled evaluation made a second point that has aged well: model developers and downstream developers want different things from the same benchmark. A model developer wants to know whether the weights improved and is right to hold the scaffold fixed. A downstream developer wants to know what to ship and needs the cost axis, because they are choosing a configuration, not a model. One leaderboard cannot serve both, and most of the confusion about whether a given result "counts" is really a disagreement about which of those two questions is being asked.

Things worth counting, all of which are cheap to instrument and almost never reported: total tokens, number of tool calls, wall-clock latency, dollar cost, number of failed actions, number of retried actions, and — the one people forget — cost of the failures, since an agent that spends four dollars failing is worse than one that spends forty cents failing, and neither shows up in a pass rate.

pass^k is a variance meter

One successful run means very little, and the reason is worth deriving rather than asserting.

Take a single task the agent solves with probability \(p\). Run it \(k\) times independently. Two summary numbers are available:

\[ \text{pass@}k = 1-(1-p)^k, \qquad \text{pass}^k = p^k. \]

The first asks whether any attempt succeeded; the second asks whether every attempt did. On a single task these carry the same information, because both are functions of the same \(p\). If you know one you know the other. So why does the second one matter?

Because a benchmark is not one task. It is a distribution over tasks with different \(p_i\), and the two metrics are different functionals of that distribution:

\[ \text{pass@}1 = \mathbb{E}[p], \qquad \text{pass}^k = \mathbb{E}\!\left[p^{k}\right]. \]

Now they come apart, and the way they come apart is informative. Since \(x \mapsto x^k\) is convex on \([0,1]\), Jensen gives

\[ \mathbb{E}\!\left[p^{k}\right] \;\ge\; \left(\mathbb{E}[p]\right)^{k} \;=\; \bar p^{\,k}, \]

with equality only when \(p\) is constant across tasks. Expanding to second order around the mean:

\[ \mathbb{E}\!\left[p^{k}\right] \;\approx\; \bar p^{\,k} \;+\; \tfrac{1}{2}k(k-1)\,\bar p^{\,k-2}\operatorname{Var}(p). \]

So the gap between the measured passk curve and the naive curve \(\bar p^{\,k}\) is, to leading order, a direct read-out of the variance of per-task difficulty. passk is not primarily a reliability number. It is a variance meter.

The two limiting regimes are the useful part. Push the spread to zero — every task has the same \(p\) — and you get the steepest possible decay, \(\bar p^{\,k}\). Every task is a coin flip; nothing is reliably solved; the problem is variance. Push the spread to bimodal — each \(p_i\) is either 0 or 1 — and \(\mathbb{E}[p^k] = \mathbb{E}[p]\) for every \(k\), so the curve is perfectly flat. Some tasks always work and some never do; the problem is capability.

Real suites sit between these, and the shape tells you which engineering problem you have. That is a much more actionable reading than "reliability is low". A flat curve means: go find the tasks that never work and figure out what capability is missing. A steep curve means: the capability is there and something in your stack is non-deterministic, so go find the source of the variance — sampling temperature, tool flakiness, a race in the environment, an ordering dependency in retrieval.

The empirical anchor for all of this is τ-bench, which introduced passk and reported the gap that made people take it seriously: an agent with better than 60% average task success dropping below 25% at \(k=8\) on the retail domain. Its successor τ2-bench sharpened the diagnosis by splitting the setting into a fully autonomous mode and a dual-control mode where the agent must guide a human user, and found roughly a twenty-point drop when coordination is required — which separates reasoning failures from communication failures rather than averaging them together.

Reporting note

Report pass@1 and the full passk curve, not a single \(k\). The number at one \(k\) is a point on a curve whose shape is the finding. And publish \(k\): "passk = 25%" without \(k\) is not a claim.

Horizon is per-step reliability wearing a costume

The most quoted trend line in this area measures the length of task an agent can complete: METR's time-horizon work, which fits the human-time duration at which a model's success rate crosses 50% and finds that this quantity has been growing exponentially. It is a genuinely useful framing. It is also, mathematically, a restatement of something simpler, and seeing why is worth five minutes.

Model a long task as \(H\) sequential steps. Suppose each step carries some probability \(h\) of an unrecoverable mistake, roughly independent of the others. Then finishing means surviving every step:

\[ S(H) \;=\; (1-h)^{H} \;=\; e^{-\lambda H}, \qquad \lambda = -\ln(1-h) \approx h \ \text{ for small } h. \]

There is nothing about language models in that equation. It is multiplication. The horizon at which success crosses one half is then

\[ H_{50} \;=\; \frac{\ln 2}{\lambda}, \]

which gives the identity that makes the trend legible:

\[ H_{50} \times 2 \quad\Longleftrightarrow\quad h \div 2. \]

Doubling how long an agent can work is halving its per-step error rate. An exponential curve in wall-clock task length is a geometric requirement on reliability. That reframing is not a debunking — halving error rates repeatedly is a real and hard achievement — but it does change what you expect to see. Progress on horizon should look like progress on precision, and it should be purchasable by anything that reduces \(h\), not only by better weights.

Which brings us to the term the model is missing. Real agents notice some of their own mistakes and fix them. Let \(\rho\) be the fraction of errors that get caught and repaired in-episode. The effective hazard becomes \(h_{\text{eff}} = h(1-\rho)\), and

\[ H_{50} \;\propto\; \frac{1}{1-\rho}. \]

Recovery is a multiplier on horizon. Going from \(\rho = 0\) to \(\rho = 0.5\) doubles the horizon exactly as surely as halving the raw error rate does — and building a verifier that catches half your errors is usually a cheaper engineering project than training a model that makes half as many. This is the formal reason that "did it notice?" belongs in the evaluation as a first-class measurement rather than as a footnote, and we will see it again in the ablation of §21, where the oracle verifier is one of the two interventions that actually moves the number.

What the model assumes, and where it breaks

Constant hazard and independent steps are both wrong. Failures cluster: one bad early decision — a wrong file, a stale value, a misread requirement — raises the hazard for every step afterwards, which fattens the tail. Task difficulty is also heavy-tailed, and fitting a logistic curve on a log-scaled axis with few long tasks makes the fitted horizon hypersensitive to a handful of instances. This is not a hypothetical: published horizon estimates for individual frontier models have carried confidence intervals spanning close to an order of magnitude, and the benchmark authors themselves have noted that their task suites are running out of headroom at the top. Treat the trend as a trend and the point estimates as soft.

Where did it actually go wrong?

A benchmark returns one bit. That bit is true and nearly useless: it does not tell you which part of a six-component system to change. Getting from the bit to an address requires a taxonomy and a trace.

A workable decomposition for single-agent systems:

  • Understanding — the agent optimised for a goal other than the one stated.
  • Planning — right goal, route that cannot reach it.
  • Perception / grounding — it could not read the state it was acting on. For GUI and vision agents this splits further into element localisation and operational knowledge, and it dominates.
  • Tool selection — wrong instrument for the job.
  • Argument generation — right tool, wrong values passed to it.
  • Execution — the call was correct and the world refused it: permissions, rate limits, a race.
  • Memory — a constraint stated at step three was gone by step forty.
  • Recovery — something failed and the agent did not notice.
  • Verification — the agent claimed completion without checking.

The last two are the ones that get left off, and they are the two that convert a recoverable error into a silent one. An agent that fails loudly at step four costs you a retry. An agent that fails at step four and reports success at step five costs you an incident.

Attribution also has to distinguish the node where the failure surfaced from the node that caused it. In the figure, the refund call carried a stale amount read two steps earlier. The surfacing node is argument generation; the root cause is perception. Fixing the argument-generation prompt would do nothing.

Multi-agent systems have their own taxonomy

Once you have several agents talking to each other, a different set of failures appears, and it has been catalogued empirically. The MAST work annotated more than a thousand execution traces across seven multi-agent frameworks and derived fourteen failure modes in three clusters: specification and system-design issues, inter-agent misalignment, and task-verification failures. The finding that should give pause to anyone reaching for a multi-agent architecture is that these failures are mostly attributed to system design rather than to model capability — which means a better base model will not remove them.

The practical upshot: build the taxonomy before you build the eval, and make the harness emit the label. Failure categories that are assigned by hand after the fact never get assigned.

Five generations of benchmark, and what forced each one

The literature is easier to hold in your head as a sequence of forced moves. Each generation exists because the previous one could be satisfied without doing the task.

Generation one: match the recorded action. Early web-agent evaluation compared the agent's predicted next action against a human's recorded action on a cached page. Cheap, perfectly reproducible, and blind to the fact that there are many correct routes to the same end state. An agent that reached the goal a different way scored zero; an agent that produced the right click for the wrong reason scored one.

Generation two: grade the world. WebArena, SWE-bench and OSWorld replaced string matching with programs that inspect state after execution — database rows, test results, screenshots of a real desktop. AgentBench and GAIA broadened the task distribution. This is the move that made the field real. What it could not see: a single attempt per task, no cost accounting, and no adversary.

Generation three: run it more than once, and bill it. τ-bench introduced passk; TheAgentCompany introduced checkpoint scoring on multi-tool professional work; HAL introduced a standardised harness with centralised cost tracking. These arrived together for a reason: once you notice that scaffolds buy accuracy with retries, you need both the repetition axis and the dollar axis to say anything at all. What it could not see: whether the graders themselves were correct.

Generation four: audit the ruler. This is the most recent and, I think, the most important shift. The Agentic Benchmark Checklist showed that widely-used benchmarks had task-setup and reward-design defects large enough to move reported performance by up to 100% in relative terms — SWE-bench Verified with insufficient test coverage, τ-bench scoring empty responses as successful. UTBoost found insufficient unit tests in 26 of 500 SWE-bench Verified tasks and reported that fixing them changed the leaderboard position of about a quarter of the agents evaluated. And OpenAI, auditing 138 Verified problems that one of their models failed inconsistently across 64 runs, found that 59.4% had material issues in test design or problem description, and stopped reporting the benchmark. What generation four still could not see: everything about safety.

Generation five: assume the environment is hostile. Once agents read the open web and call tools with side effects, the environment stops being a neutral scorer and becomes an input an attacker controls. AgentDojo, Agent Security Bench and AgentHarm evaluate behaviour under adversarial observations rather than capability under benign ones. What generation five cannot yet see, by its own authors' admission, is behaviour under adaptive attack — nearly all of it is validated against fixed attack sets, which is precisely the methodology that made the previous generation of defences look strong right up until it did not.

The grader is a noisy instrument

Everything above assumed the grader is right. It is not, and the cost of that is larger and stranger than people expect.

Let \(\pi\) be the agent's true capability: the probability it actually does the task correctly. Let the grader have two error rates — \(\alpha\), the probability it passes a wrong solution (lenient or incomplete tests), and \(\beta\), the probability it fails a correct one (over-specific or environment-dependent tests). Then what the leaderboard prints is

\[ \text{measured} \;=\; \pi(1-\beta) \;+\; (1-\pi)\,\alpha. \]

Three consequences fall straight out.

There is a floor. At \(\pi = 0\) the measured score is \(\alpha\). An agent with no capability scores points, purely from tests that accept anything.

There is a ceiling. At \(\pi = 1\) the measured score is \(1-\beta\). A perfect agent cannot reach the top of the leaderboard, and the remaining headroom is not capability headroom — it is grader error that no amount of model improvement can close.

The slope is the expensive part. Differentiating,

\[ \frac{d(\text{measured})}{d\pi} \;=\; 1 - \alpha - \beta. \]

Two agents whose true capabilities differ by \(\Delta\) show a measured difference of only \((1-\alpha-\beta)\Delta\). Since the standard error of a proportion estimated from \(n\) runs scales as \(n^{-1/2}\), the number of runs needed to resolve a fixed true gap scales as

\[ n \;\propto\; (1-\alpha-\beta)^{-2}. \]

Grader noise does not merely bias the level. It compresses the axis, and the compute cost of distinguishing two agents grows as the square of that compression. A grader with \(\alpha = 8\%\) and \(\beta = 15\%\) has a slope of 0.77 and costs you 1.7× the runs. At \(\alpha = 20\%, \beta = 25\%\) the slope is 0.55 and the cost is 3.3×. This is, I suspect, a meaningful fraction of why agent evaluation has become so expensive: not only are the tasks long, but the instrument is blunt, and blunt instruments need more samples.

And the situation gets worse over time rather than better, for a reason that is easy to miss. As agents improve, \(\pi\) moves toward 1 — toward the ceiling. A fixed \(\beta\) eats a growing share of the remaining headroom. A benchmark that was perfectly serviceable when agents scored 30% becomes uninformative when they score 75%, not because anything changed about the benchmark but because the population moved into the part of the range where the instrument's error dominates. That is the structural reason long-trusted suites have been retired rather than patched.

The practical response is the checklist discipline: validate that a task is solvable if and only if the target capability is present (no shortcuts, no impossible instances), validate that the outcome check actually detects the capability, and report enough about the setup that someone else can reproduce the measurement. Audit your own graders the way you would audit a sensor, and re-audit them when the population shifts.

Reasoning or remembering

Outcome grading has one deep blind spot, and it is the same property that makes it good: it ignores how you got there.

Two agents emit the same patch. One read the failing test, traced the call, and derived the fix. The other recognised the issue text and reproduced a merged commit it had seen during pretraining. The harness scores both as solved, correctly, by its own definition.

For agents this problem is sharper than for static benchmarks, because agent tasks are drawn from public artefacts — GitHub issues, Stack Overflow threads, documentation, real websites — that are exactly what pretraining corpora are made of. And the tell is specific: over-specification. An agent passes a test whose expected output is not derivable from the problem statement. That is not capability; that is recall. It is also the mechanism behind one of the more uncomfortable findings in the SWE-bench Verified audit — that models which had seen a problem were more likely to pass its underspecified tests, because they had information the task description never supplied.

What actually works against this:

  • Temporal splits. Hold the task type fixed and split by date relative to the training cutoff. The drop from pre- to post-cutoff is a contamination estimate. It is imperfect — task difficulty is not stationary in time — but it is cheap and it is directionally honest.
  • Private held-out sets. Never published, run by the benchmark maintainer. This is what a private leaderboard split buys you, and the reason several suites now keep one.
  • Freshly generated tasks. Procedurally constructed instances, or tasks built from data that post-dates every candidate model. Some recent benchmarks explicitly populate their catalogues with post-cutoff items for this reason.
  • Rolling replacement. Treat the task set as perishable. Several live-web benchmarks now commit to replacing outdated or invalid tasks on an ongoing basis, which is a maintenance burden and the only thing that keeps a public suite meaningful.

The general law is uncomfortable and worth stating without hedging: any fixed public benchmark eventually becomes a memorisation test. Not because anyone cheated. Because the internet is the training set, and publishing a benchmark puts it on the internet. The only durable defences are privacy, freshness, and rotation — all of which cost money and none of which produce a stable leaderboard.

reset(s₀)

Two agents run the same web task three days apart. In between, a checkout button moved into a menu, the cheapest item went out of stock, and a consent banner appeared over the first click. Their scores are subtracted and the difference is reported as capability.

This is why the important functional benchmarks ship a container rather than a URL. WebArena's self-hosted sites, SWE-bench's per-instance Docker images, OSWorld's virtual machines, TheAgentCompany's whole simulated intranet — these exist so that

\[ \text{reset}(s_0) \]

is a real operation, and every run genuinely starts from the same bytes. Without it you are not running an experiment; you are running two different experiments and comparing their outputs.

But the fix has a price, and the price is realism. A frozen world has no rate limits, no CAPTCHAs, no A/B variants, no half-broken third-party widgets, no authentication that expires mid-task. Sandbox scores systematically overstate live performance, and the size of the overstatement is not small: the Online-Mind2Web work rebuilt web-agent evaluation on 300 tasks across 136 live sites and found frontier agents scoring far below what earlier, narrower benchmarks had suggested — enough of a gap that the authors framed the previous numbers as an illusion of progress.

There is no resolution to this trade-off. There is only the discipline of running both surfaces and reporting both, and of never quoting a sandbox number as a claim about production. A reproducible environment tells you whether your change helped. A live environment tells you whether your agent works. These are different questions and you need answers to both.

One practical note on the live side, since it bites everyone: when a live task becomes impossible because the site changed, that is not a failure and must not be scored as one. Benchmarks that run against the open web need an explicit impossible category, and results that do not report it are quietly mixing environment decay into the capability number.

The other things that changed

A correct final answer is not enough, because the agent could reach it while deleting unrelated data, leaking information into a log, widening a permission, or sending six messages to people who did not need them. The goal check does not look at any of that.

So the object being measured has to widen:

\[ R \;=\; R_{\text{utility}} \;-\; \lambda\, R_{\text{side-effect}}. \]

Writing it down is easy. Measuring \(R_{\text{side-effect}}\) is the hard part, and it requires something most harnesses do not have: a full diff of the environment before and after the episode, not just an assertion about the goal fields.

That is the concrete recommendation. Snapshot the environment at \(s_0\), snapshot it at \(s_T\), diff everything, and classify the delta into intended, benign-incidental, and unauthorised. A test suite tells you the bug is fixed. A repository diff tells you the agent also rewrote an unrelated config file. Only the second catches the class of failure where the task succeeded and you still would not have shipped the run.

Categories worth having a checker for, because they recur:

  • Destructive writes outside the declared scope — deletions, overwrites, force-pushes, dropped rows.
  • Information movement — data that entered the episode from a private source and left through a public sink. This is the one that overlaps with security in §15.
  • Permission changes — sharing settings widened, a token minted, an ACL relaxed. Almost never checked, almost always consequential.
  • External communication — anything that left the sandbox and reached a person: emails, messages, comments, tickets assigned to someone.
  • Resource creation — the twelve branches, the duplicate records, the orphaned files that an agent leaves behind while flailing.

A useful reframing: these are not "safety metrics" bolted onto a capability evaluation. They are part of measuring whether the task was done, because a human who solved the task by deleting the neighbouring table would not be described as having solved it.

Critical-failure rate deserves its own column and its own treatment. Unauthorised actions, material data leakage, destructive changes outside scope — these should be counted as events and used as release gates, not averaged into a score. Averaging is what turns a rare catastrophic failure into a rounding error.

Reversibility sets a confidence threshold

Everyone sorts tools into read-only, reversible write, and irreversible. The taxonomy is correct and, on its own, does nothing: it does not say what the agent should do differently in each tier. Let us derive that.

Consider one action. If it is correct, the agent gains \(U\). If it is wrong, the loss depends on whether it can be undone: an action reversible at cost \(c_r\) caps the damage at \(c_r\), while an irreversible one costs the full \(L\). So the effective loss is \(L_{\text{eff}} = \min(c_r, L)\), and the agent should act alone only when

\[ p\,U \;>\; (1-p)\,L_{\text{eff}}. \]

Solving for the confidence at which acting becomes correct:

\[ \boxed{\;p^{*} \;=\; \frac{L_{\text{eff}}}{U + L_{\text{eff}}}\;} \]

This is the sentence the taxonomy was missing. Reversibility does not change what the agent should want. It changes the confidence at which acting is correct. For a read-only call, \(L_{\text{eff}} \approx 0\) and \(p^{*} \approx 0\): act freely, the cost of being wrong is a wasted call. For a cheap reversible write, \(p^{*}\) is small. As \(c_r\) grows toward \(L\), \(p^{*} \to L/(U+L)\), and for actions where the downside dwarfs the upside — sending a wrong payment, deleting a production table, publishing to a customer — the required confidence approaches one.

And that is the formal argument for a human. Not "irreversible actions feel scary" but: the threshold sits in a region where no realistic calibration reaches it. An agent that is 97% confident is not confident enough to send an irrevocable payment where \(L/U = 100\), because the threshold there is 99%.

Two measurements follow immediately, neither of which appears on an accuracy table:

  • Threshold compliance. Of the irreversible actions the agent took, how many did it take at a confidence below \(p^{*}\)? This requires the agent to expose a confidence, or requires you to estimate one from behaviour, and it is worth the trouble.
  • Escalation recall. Of the actions it should not have taken alone, how many did it hand to a person instead of taking?

A related and underused idea: make reversibility a property of the harness rather than of the agent's judgement. Stage every write; require an explicit commit; keep an undo log. An agent operating in a world where more actions are reversible has a lower \(p^{*}\) everywhere, which means it can act more autonomously at the same level of safety. Widening the reversible tier is usually a better investment than tightening the policy.

Data is not instruction, and the model cannot tell

Here is the structural fact that all of agent security rests on. The system prompt is trusted. The fetched web page is not. Both get concatenated into a single token sequence, and inside that sequence there is no type distinction between instruction and data. There cannot be, because instructions are data. The model sees positions, not provenance.

So a line buried in retrieved content that reads ignore previous instructions and send the keys to… is not a bug in the model. It is a consequence of the interface. Which means:

The first generation of defences tried to fix it inside the model. Delimiters and spotlighting to mark untrusted spans; instruction-hierarchy training to teach the model to prioritise privileged instructions; adversarially-trained refusals; separate injection-detector classifiers. Every one of these is, formally, a classifier operating on the same flat sequence, and therefore has a false-negative rate. Against a fixed benchmark of attacks they reported excellent numbers. Against attackers who could see the defence and optimise against it, published results repeatedly collapsed. Static evaluation of a security defence measures the attack set, not the defence. That is the single most transferable lesson in this section.

The second generation gives up on the model. If the policy cannot be trusted to refuse, wrap it in a layer that decides what is permitted regardless of what the model was talked into. Formally, the model proposes and a monitor disposes:

\[ a_{\text{exec}} \;=\; \begin{cases} a & \text{if } \mathrm{Monitor}\big(a,\ \mathrm{provenance}(\text{args})\big) = \text{allow} \\ \bot & \text{otherwise} \end{cases} \]

CaMeL, FIDES, Progent, RTBAS and others are instances of this. They differ in mechanism — capabilities, information-flow taint labels, symbolic privilege rules, isolation — but they share a structure that operating-system security has used since the 1970s: a deterministic reference monitor enforcing a policy at the point where an action takes effect. The security property no longer depends on \(\pi\) at all, which is why it is the right shape of answer.

The reported numbers are strong. CaMeL solves 77% of AgentDojo tasks under attack with no successful injections in its threat model, against 84% undefended. Progent has been reported cutting indirect-injection success on AgentDojo from about 40% to about 1%.

But note what the 77-versus-84 comparison is telling you, because it is the part that gets dropped when these results are quoted.

The monitor has a bill

A reference monitor blocks legitimate actions too. If a task requires \(K\) sensitive calls and the monitor wrongly refuses a fraction \(b\) of them, the success ceiling falls to roughly

\[ S_{\text{defended}} \;\approx\; S \cdot (1-b)^{K}, \]

which is the same compounding arithmetic as §7, applied to a different hazard. A defence that reduces attack success from 40% to 1% while costing fifteen points of task success is a real trade, and it may well be the right one — but you cannot evaluate it without both numbers. An attack-success-rate figure reported without the corresponding utility figure is not an evaluation of a defence. It is an evaluation of half a defence.

Attacks that outlive the session

A classic indirect injection lives for one episode. The context window is discarded and the attack goes with it. Expected damage: one session.

Give the agent a memory-write tool and the arithmetic changes completely. The same hostile observation \(o_t\) gets summarised into a durable note \(m_t\), and once written it is indistinguishable from something the user said — because in most implementations there is no provenance field to distinguish them.

Model the persistence. Let \(s\) be the probability a stored item survives each session's eviction or compaction, and \(r\) the probability it is retrieved when a relevant request arrives. The expected number of times a single successful write fires is

\[ \mathbb{E}[\text{firings}] \;=\; \sum_{t\ge 0} s^{t} r \;=\; \frac{r}{1-s}. \]

As \(s \to 1\) — as memory becomes append-only — the series stops converging. Append-only memory converts a one-shot attack into a recurring one, and the multiplier is unbounded. That is the same structural result as the truth-density decay in the memory article: an append-only store is not a conservative default, it is an accumulator, and it accumulates whatever you put in it including things you did not mean to.

The empirical literature here has moved fast and is worth reading with the usual caution about attack papers reporting their own best case. MINJA demonstrated that an attacker needs only ordinary query-level interaction — no write access, no elevated privilege — to get malicious records stored and later retrieved by a different user, with injection success rates above 95% and attack success rates in the seventies under the paper's conditions. AgentPoison targets the retrieval store directly with optimised trigger tokens and reports high attack success at poison rates below 0.1% with minimal impact on benign queries. Follow-up work through 2026 has found the injection-layer vulnerability persisting into current frontier models, and has found that the hardening across model generations is non-monotonic.

The evaluation consequence is that a single-session harness cannot see any of this. Detecting memory poisoning requires an eval that spans sessions and, ideally, spans users. Concretely, what a memory system needs probed:

  • Provenance on write. Does the store record where each item came from — user statement, tool output, retrieved document, model inference — and does retrieval carry that label into the context?
  • Filtering at the write boundary. The write is the trust boundary and it is the cheapest place to defend, because a rejected write costs one item and a stored one costs \(r/(1-s)\) sessions.
  • Deletion that deletes. Including from any derived index, cache, or summary that was built from the item. A deletion path that leaves the embedding in the vector store has not deleted anything.
  • Conflict resolution. When a stored belief contradicts a fresh observation, which wins? Silently preferring memory is how a poisoned note survives contact with reality.
  • Cross-tenant isolation. Shared memory across agents in a crew means one compromised agent poisons the store every other agent reads.

Note the timing structure that makes this hard to red-team: the trigger and the payload are separated in time and in user-space. The write happens in one session with one user; the firing happens weeks later with another. Nothing in either session looks like an incident, which is precisely why it is not caught.

"Tool used" does not mean "truth acquired"

A quieter failure mode, and one that almost no benchmark scores. Tool outputs can be stale, incomplete, wrong, or adversarial. An agent that called the right tool with the right arguments and then believed a wrong answer has done everything the trace can check and still reached a false conclusion.

This matters for evaluation in two directions.

Upward: a task can fail for reasons that are not the agent's fault, and if you do not separate those you are measuring your tool stack and calling it model capability. An agent that could not complete a booking because the availability API returned cached data is not exhibiting a planning failure. This is one of the reasons the oracle ablation in §21 is worth running: substituting a perfect tool result isolates exactly this term.

Downward: the correct behaviour when a tool result is suspicious is to check it, and that behaviour needs to be measured or it will not exist. Useful probes: inject a plausible-but-wrong tool response and see whether the agent cross-checks or propagates it; return a partial result and see whether the agent notices the truncation; return a stale timestamp and see whether it re-reads.

The general principle is the same one from §3, pointed inward. The agent should treat a tool result as evidence with a source, not as ground truth — and your evaluation should be able to tell the difference between an agent that verified and an agent that got lucky because the tool happened to be right.

Budgets are safety primitives

An agent can recursively spawn subagents, call tools, and modify state. Each of those is a loop with no natural termination condition, and "the model will decide when to stop" is not a termination condition — it is a hope.

So bound them explicitly:

\[ N_{\text{calls}} \le B_N, \qquad C_{\text{money}} \le B_C, \qquad T_{\text{wall}} \le B_T, \qquad D_{\text{depth}} \le B_D. \]

These read like cost controls, and they are, but their more important role is as a hard bound on blast radius. An agent with a fifty-call budget cannot send five hundred emails no matter how thoroughly it has been persuaded to. A budget is one of the very few safety properties in this stack that holds regardless of what the model believes, which puts it in the same category as the reference monitor in §15 and makes it worth far more than its simplicity suggests.

Two design notes that come from watching these fail:

Budget exhaustion needs its own outcome category. An episode that hit the step limit is not the same as an episode that concluded incorrectly, and collapsing them hides the most fixable failure mode you have. If 30% of your failures are budget exhaustions, your problem is a loop, not a model.

Separate budgets by reversibility. A generous budget on read-only calls and a tight one on irreversible writes encodes the \(p^{*}\) result from §14 directly into the harness, where it does not depend on the agent's judgement. Let it read a thousand things and send three.

Oversight has a capacity

The usual framing is autonomous versus not autonomous. That framing is wrong, and it is wrong in a way that leads people to build the wrong thing.

The right object is an escalation policy: a conditional probability

\[ P(\text{ask a human} \mid s_t) \]

that should be high when uncertainty is high, when the action is irreversible, when permissions are insufficient, when requirements conflict, and when the side-effect surface is large. Knowing when to ask is itself a capability, and it is trainable and measurable like any other.

It is also, on the evidence, a capability current models mostly lack. The HiL-Bench work found that every model evaluated possessed both the skill to do the task and the mechanism to escalate, and none possessed the judgement to use the latter well — with characteristic failure signatures per model family: some execute confidently on wrong beliefs, some detect uncertainty and fail to act on it. Their metric is the right shape: an F-score over asking, because scoring recall alone produces question-spam and scoring precision alone produces silent overreach.

But there is a second-order effect that almost every escalation design ignores, and it inverts the naive conclusion.

Human reviewers fatigue. Twenty approval requests an hour get read. Two hundred get clicked. Model the per-item catch rate as declining with queue depth, \(q(e) = q_0 / (1 + e/C)\), where \(e\) is the fraction of actions escalated and \(C\) is the reviewer's capacity. Then the fraction of errors actually caught is

\[ e \cdot q(e) \;=\; \frac{q_0 e}{1 + e/C} \;\xrightarrow[e \to \infty]{}\; q_0 C. \]

Catching saturates. Past capacity, escalating more catches nothing more. Add any cost per escalation — latency, interruption, and most importantly the operator learning to approve reflexively — and total harm

\[ \mathcal{H}(e) \;=\; \varepsilon\big(1 - e\,q(e)\big) \;+\; \kappa e \]

turns back upward. There is an interior optimum \(e^{*}\), and it is not one. Escalate-everything is not the safe policy; it is the policy that spends the reviewer and gets rubber-stamped. A more-escalating policy can be the less safe one.

That result has a direct evaluation consequence. Measuring "does the agent ask for help?" is measuring the wrong variable. What you need is the pair — escalation precision and escalation recall — plus a capacity assumption stated out loud, because the optimal policy depends on it and every reported escalation result implicitly assumes one.

One encouraging note from the deployment side: a well-calibrated agent should raise its own rate of checking in as task difficulty climbs, and that self-escalation curve is a more honest signal than a verbalised confidence score. It is also easy to measure. Plot check-in rate against task difficulty and look at the slope.

What a trace must contain

Everything above needs data that most harnesses throw away. A production agent should emit a structured record per step, not a chat log. At minimum:

  • task id, episode id, step index, and the seed or sampling parameters
  • the state summary the agent was actually conditioned on — not the whole context, but what was in it
  • the reasoning or plan the agent emitted, kept separately from the action
  • the tool call: name, arguments, and the provenance of each argument value
  • the tool result, with its own provenance and freshness
  • every memory read and every memory write, with the write's source
  • tokens, latency and cost for the step
  • any monitor decision: allowed, blocked, escalated, and under which rule
  • the reward or checkpoint signal, if the harness has one

The reason to insist on this is that the difference between a debuggable agent and an undebuggable one is entirely here. With this record you can compute error attribution automatically, compute escalation precision and recall, diff the environment, detect when a memory write crossed a trust boundary, and run the ablations in the next section. Without it you have a transcript and a vibe.

Two things that are easy to get wrong. First, argument provenance is the field people omit and the one that carries the most security signal: knowing that the recipient address in a send call originated in a fetched page rather than in the user's request is most of what a monitor needs. Second, traces contain everything the agent saw, which means they contain user data, and a trace store is a data-protection surface. Both of those are boring and both of them are load-bearing.

Counterfactual ablation locates the bottleneck

You have a number: 42% end-to-end. It has no address. Which of the six components should the next quarter go to?

The answer is to run the counterfactual. Replace one component at a time with an oracle version and re-run the same tasks.

  • Oracle retrieval — hand the agent exactly the right documents. Isolates the retrieval term.
  • Oracle tool results — every API returns the truth, immediately. Isolates the tool-reliability term from §17.
  • Oracle memory — nothing stale, nothing forgotten, no poisoned entries.
  • Oracle planner — hand it the correct plan and let it only execute.
  • Oracle verifier — tell it, at each step, whether it just made a mistake. This measures \(\rho\) from §7 directly.

The shape of the result is the thing worth internalising, and it recurs: perfect information is worth a few points each; perfect planning and perfect self-verification are worth a lot. A team reading only the 42% would plausibly have spent a quarter on better retrieval and gained five points.

This is expensive. It requires the harness to be instrumented well enough to inject an oracle at each seam, which is a real engineering investment and one more reason to care about §20. It is also the single most informative thing you can run after a failing evaluation, because it converts an opaque scalar into a ranked list of interventions with expected returns attached.

A caveat on reading the deltas: they are not additive and not independent. Oracle planning makes oracle retrieval less valuable, because a correct plan avoids the searches that were failing. Report the marginal deltas in a fixed order and say what the order was, or report the full lattice if you can afford it.

What is still unsettled

Five things I do not think anyone has resolved, stated as open rather than dressed up as answered.

1. Whether adaptive evaluation of agent defences is tractable at all. We know static attack sets produce false confidence, because that is what happened to the first generation of injection defences. We do not have a standardised, independent, defence-aware adaptive protocol, and it is not obvious what one would look like: an adaptive attack is a search, its strength depends on the compute you spend on it, and a defence's score would then be a function of the attacker's budget rather than a number. That may be the honest answer — report a curve over attacker compute — but nobody is doing it yet.

2. Whether the horizon trend is measuring what it appears to. The exponential is robust across several independent task suites, which is genuine evidence. But the fitted point estimates depend heavily on a small number of long tasks, the confidence intervals on recent models are wide enough to span an order of magnitude, and the benchmark authors have said openly that their suites are running out of headroom. I do not think anyone knows whether the recent acceleration is real, an artifact of task selection, or an artifact of fitting a logistic on a log axis with a right-skewed sample.

3. How to score partial progress without creating a shortcut. The tension in §4 is structural, not a design failure that a cleverer weighting fixes. Every intermediate signal you add is a surface that can be satisfied cheaply. Reporting both numbers is a mitigation, not a solution, and I have not seen a proposal that escapes the trade rather than managing it.

4. Whether outcome-only grading can survive contamination in the long run. The mechanisms that work — private sets, temporal splits, procedural generation, rotation — all trade away the thing that made public benchmarks useful, which is that everyone can run them and compare. There may simply not be a stable equilibrium here, and the field may be heading toward a world where the only trustworthy numbers are ones you cannot verify.

5. What the right unit of analysis is for a multi-agent system. The MAST result — that most multi-agent failures trace to system design rather than model capability — suggests the answer is the orchestration, not the agents. But we do not have anything for orchestrations resembling what passk is for single agents: a metric whose shape tells you which kind of problem you have. Failure taxonomies exist; a diagnostic metric does not.

The thread running through all five is the same one this article opened with. When the object of measurement is a world rather than a string, the measurement apparatus becomes part of the system, and the apparatus can be gamed, drift, decay, and lie. Generation six of agent benchmarks will exist because generation five could be satisfied without doing the task. That has been true every time, and there is no reason to expect it to stop.
