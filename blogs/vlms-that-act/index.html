From answering to acting

Most of this series has treated a vision-language model as a function. You give it an image and a question. It gives back text. The image is the same before and after the answer.

This post asks one question. What changes when the image is no longer a fixed input, but the current state of an environment that the model can change?

Start with the static case. Call the image I, the prompt x and the answer y. The model is a conditional distribution over answers.

y ∼ pθ(y ∣ I, x)a static VLM: one image, one prompt, one answer, and the episode ends

Now give the same model a computer. The image is a screenshot. The prompt is a task, such as "file a 42.50 travel expense and submit it". The output is no longer an answer. It is an action, such as a click at a point on the screen.

The click changes the screen. A field fills in, a menu opens, a page loads. The next screenshot depends on what the model just did. So the model is now a policy: a rule that picks an action from what it sees and what it has done so far.

at ∼ πθ(at ∣ It, x, ht)   st+1 = T(st, at)   It+1 = render(st+1)a visual policy: the action changes the hidden state s, and the next screenshot is a picture of that state

Here ht is the history: earlier screenshots and actions, often compressed. The symbol st is the full state of the computer. It includes things no screenshot shows, such as a record saved on a server or a tab in the background. The screenshot It is only a picture of part of that state.

Figure 1 runs this loop on a small expense app. Watch the order of events. The harness takes a screenshot. The model decides what to do. It turns a phrase such as "the Submit button" into a point. The harness clicks there. Then the screen changes, and the loop starts again.

Three things change when we move from answering to acting. Each one gets its own part of this post.

  • The output must execute. An answer can be roughly right. A click either lands on the button or it does not. Grounding, which When Language Must Point treated as an output format, becomes the action itself.
  • The input depends on the output. Each action decides the next screenshot. A small mistake leads to a screen the model has never seen in training. Errors compound over a long task.
  • Success is a fact about the world. We cannot grade a computer-use agent by reading its text. We have to check whether the report was actually saved. That needs a live environment, not a fixed test set.

Figure 2 puts the two cases side by side. The static model maps an image to an answer once. The policy is applied again and again, and its own outputs come back as inputs.

The text-agent version of this loop is covered in The Making of an AI Agent. The formal view, a partially observed decision process, is set out in Reinforcement Learning for Agents From First Principles. This post focuses on what the image adds: what the agent sees, how it points, and how it learns to do both.

Nuance

The screenshot is not the state. Two screenshots can be identical while the world differs. For example, an expense report submitted once and submitted twice can leave the same confirmation on screen. This is why interactive benchmarks such as OSWorld and AndroidWorld grade tasks by inspecting files, databases or system state, not by looking at the final picture. In practice, keep an action log and verify outcomes through state, not through pixels alone.

Early visual-tool systems

The first systems that "acted" on images did not click anything. They called tools. In early 2023 language models were strong planners but weak at seeing. So researchers let a language model plan, and let separate vision models do the seeing.

Take a question: "How many mugs are to the left of the laptop?" A language model cannot answer from the question alone. But it can write a short plan. Find the laptop. Find the mugs. Keep the mugs whose position is left of the laptop. Count them. Each step can be handed to a vision model, such as an object detector.

Figure 3 shows this pattern step by step.

Several systems from this period share the pattern. They differ in how the plan is written and in which experts they can call.

  • VisProg (Gupta and Kembhavi) prompts a large language model with a few examples. It writes a Python-like modular program. Each line may call an off-the-shelf vision model, an image-processing routine or a Python function. Running the program gives the answer plus an interpretable rationale. It needs no task-specific training.
  • ViperGPT (Surís, Menon and Vondrick) gives a code-generation model an API of vision modules. The model writes real Python against that API. The Python is then executed. It also needs no further training.
  • Visual ChatGPT (Wu et al.) connects ChatGPT to visual foundation models for drawing and editing images inside a conversation.
  • MM-REACT (Yang et al.) prompts ChatGPT in the ReAct style. Images reach ChatGPT only as text: descriptions, coordinates written as text, and file names. ChatGPT decides which vision expert to call next.
  • HuggingGPT (Shen et al.) uses a language model as a controller over models hosted on Hugging Face. It plans the task, selects models, runs them and writes the final response.

All of them follow the loop from ReAct (Yao et al.): reason, call a tool, observe the result, reason again. That is the same loop as Figure 1. Only the environment is different. Here the tools read the image but do not change it. The loop moves the model's knowledge forward, not the world.

Two lessons from this period carry over to GUI agents. First, decomposing a visual task into calls is a strong idea. It makes the reasoning inspectable. Second, everything passes through text. The planner sees what the expert reports, nothing more. If the detector misses the third mug, the planner has no way to notice.

Later VLMs moved perception inside the model. Tools came back in a new role: as ways for a model that can already see to look more closely. Cropping and zooming are the main examples. They are covered in Thinking With Images. How a language model learns to call tools at all is covered in How Language Models Learn to Use Tools.

Nuance

In MM-REACT the planner receives images only as text: descriptions, coordinates and file names. VisProg and ViperGPT likewise pass detector outputs to code, not to a model that can inspect pixels. So an expert's mistake is invisible to the planner. When you build a tool loop today, return visual evidence, such as a crop or an overlay, to a model that can see it. Do not return only a text summary of what the tool found.

What a screen looks like to a model

A computer-use agent must first decide what to read. A human reads pixels. A program can often read much more. The operating system and the browser keep structured descriptions of every window, and an agent can ask for them.

There are five common ways to present a screen to a model.

  • Screenshot. The raw pixels, resized to fit the model's visual budget. It shows exactly what a person sees. It contains no names, roles or hidden elements.
  • Accessibility tree. The tree of interface elements that the operating system exposes for screen readers. Each node has a role (button, text box, link), a name ("Submit") and a state (focused, disabled). It exists on desktop and mobile platforms, but its quality depends on how well each app was built.
  • DOM or HTML. The page structure of a website. It is detailed and exact. It also includes scripts, styles and invisible elements, so it is often far longer than what is on screen. It exists only for web pages.
  • Set-of-Mark overlay. A screenshot with numbered marks drawn on candidate regions. The model answers with a number instead of a coordinate. The original Set-of-Mark work (Yang et al.) used segmentation models such as SAM to find regions in natural images. For screens, the marks usually come from the accessibility tree or from a detector.
  • Hybrid. A screenshot plus a compact list of interactive elements, often with marks. OmniParser (Lu et al.) builds such a list from pixels alone. It combines a detector for clickable regions, a model that describes icons, and OCR.

Beyond these, a harness may expose application state directly: an API, a file system or a database. That is the most precise source of all. It is also the least general, because it exists only where someone built it.

Which representation works best? The first large interactive benchmark to test this was OSWorld (Xie et al.). It ran 369 real computer tasks in virtual machines and tried four input settings: accessibility tree only, screenshot only, screenshot plus accessibility tree, and Set-of-Mark.

The results were clear for the models of that time. The best score, 12.24%, came from GPT-4 reading only the accessibility tree. GPT-4V with screenshot plus tree was close, at 12.17%. Screenshot-only agents scored lowest, between 5.26% and 5.80%. Humans completed over 72% of the tasks.

Yet the authors wrote that screenshot-only input "should be the ultimate configuration in the long run". The reason is coverage. Many apps have poor accessibility trees. Canvas apps, remote desktops and games may have none. A DOM exists only on the web. Pixels exist everywhere, and they are what the interface was designed for.

The field followed that argument. Pure-vision agents such as Aguvis, UI-TARS and OpenCUA read only screenshots. UI-TARS reported 24.6% on OSWorld with a 50-step budget, about twice the best score in the original OSWorld paper. Its successor, UI-TARS-2, reported 47.5%. Anthropic's computer-use model also works from screenshots, and so does OpenAI's Computer-Using Agent. Anthropic wrote that "training Claude to count pixels accurately was critical".

Insight

In OSWorld, text-only accessibility input beat screenshot-only input by about two to one (12.24% against at most 5.80%). Within eighteen months, screenshot-only models trained for grounding passed both (24.6% for UI-TARS, 47.5% for UI-TARS-2). The ranking of observation types is not fixed. It depends on whether the model has been trained to ground. If you use a general VLM without GUI training, give it structure. If you train for grounding, pixels give you coverage that structure cannot.

Nuance

Set-of-Mark is not a free win on screens. SeeAct (Zheng et al.) found that Set-of-Mark prompting "turns out to be not effective for web agents", and its best grounding strategy combined HTML with visuals. OSWorld also reports that the value of the accessibility tree and of Set-of-Mark "varies by models". Measure the representation with your model before you commit to it.

Grounding becomes action

Suppose the model has decided: "Click Submit." Four things must now happen. The model must find the Submit button in the screenshot. It must express that location as numbers. The harness must convert those numbers to screen coordinates. Then it must send a click event to the operating system.

The second step is ordinary visual grounding. When Language Must Point explains how VLMs output points and boxes: as text numbers, as special tokens, or through a dedicated head. Here we look at what makes grounding on screens different from grounding in photos.

What is different about screens

  • Targets are small. A toolbar icon may be 16 to 24 pixels wide on a screen that is thousands of pixels wide. In a photo, objects usually cover a larger share of the image.
  • Screens are dense with text. Many elements are identified by their labels. Reading them is an OCR problem, which How VLMs Read Documents covers in depth.
  • Icons carry function, not appearance. A gear means "settings". A floppy disk means "save". The model must know conventions, not only shapes.
  • The tolerance is the element box. A click is correct if it lands anywhere inside the target element. This is how the ScreenSpot benchmark scores grounding. It is more forgiving than an IoU threshold on a box, but a miss by a few pixels can still hit the neighbouring button.
  • The model sees a resized image. The screenshot is scaled to fit the visual-token budget. The model's coordinates must be mapped back to real screen pixels.

Models handle the coordinate format in different ways. SeeClick writes decimal coordinates between 0 and 1 as plain text, for example click (0.49, 0.40). CogAgent writes boxes normalised to the range 000 to 999. UGround writes raw pixel coordinates "without any normalization". UI-TARS uses coordinates relative to the screen size. GUI-Actor avoids writing coordinates at all. It adds an attention-based action head that links a special token to the matching image patches.

Resolution decides what can be pointed at

The tolerance argument has a simple arithmetic core. A model has a budget of N visual tokens. A screen of width W and height H is resized to fit that budget. Each token then covers a square of side

p = √W · H / Nscreen pixels covered by one visual token, along each side

On a 3840 by 2160 screen with 1,024 tokens, p is about 90 screen pixels. A 24-pixel icon is then about a quarter of one token wide. Three or four toolbar icons share a single token. The model cannot point between them without more resolution. Figure 6 lets you try this.

ScreenSpot-Pro (Li et al.) measured this effect. It collected high-resolution screenshots from 23 professional applications across five industries and three operating systems. The targets are small, and the screens are large. When the benchmark was released, the best existing grounding model scored 18.9%.

The authors also proposed ScreenSeekeR, a search method that uses a planner to guide zooming into likely regions. Without any extra training it reached 48.1%. Zooming at inference time is exactly the kind of tool use covered in Thinking With Images. The cost side of resolution, and how to cut visual tokens without losing small targets, is the subject of The Cost of a Picture.

Insight

On ScreenSpot-Pro, a zoom-in search procedure took accuracy from 18.9% (best existing model) to 48.1% with no training. Much of the failure on professional screens is therefore a resolution problem, not a knowledge problem. If your agent works on large or dense screens, give it a zoom or crop action before you collect more grounding data.

Choosing the action space

Grounding produces a location. The action space decides what the agent can do with it. There are three main levels, and the choice changes how hard the task is.

  • Pixel level. The agent emits operating-system events: click(x, y), double_click, drag(x1, y1, x2, y2), scroll(dx, dy), type("text") and key("ctrl+s"). This works on any interface. Every pointing action needs exact grounding.
  • Element level. The harness gives each element an id, from the accessibility tree, the DOM or Set-of-Mark. The agent writes click(element_42). The harness clicks the centre of that element. Grounding becomes a choice from a list. AppAgent (Zhang et al.) labels elements with numbers so that a tap "avoids the need for precise screen coordinates". WebArena's baseline agents also act on element ids.
  • API level. The agent calls a function such as submit_expense(amount=42.50, category="Travel"). No perception is needed at all. But the function must exist, and it covers only the tasks someone planned for.

A fourth option sits between pixel level and API level: code as the action. Aguvis adopts the pyautogui library "as our universal interaction interface". The model writes calls such as pyautogui.click(x, y). Code can combine several low-level events in one step, and it adds loops and conditions when needed. OpenCUA and Jedi use the same style.

Cross-platform models also need a shared vocabulary. A tap on a phone and a click on a desktop are the same idea. UI-TARS "standardizes actions into a unified space across platforms". OS-Atlas uses a unified set of basic actions (click, type, scroll) plus custom actions for each platform.

The level matters because errors multiply over steps. If each pointing action succeeds with probability 0.98, four pointing actions succeed together with probability 0.984, about 0.92. One API call has no pointing to get wrong. The same lesson appears for text agents as the agent-computer interface. In Inside an AI Agent Harness, the shape of the tools changes success rates as much as the model does. SWE-agent (Yang et al.) made the same argument for software engineering.

In practice the levels are mixed. A sensible agent calls an API when one exists, acts on elements when the tree is reliable, and falls back to pixels for everything else.

Insight

WebRL trained text-only language models that read simplified HTML and act on element ids. Its 8B model rose from 4.8% to 42.4% on WebArena-Lite through reinforcement learning, with no pixels at all. On the web, a good element-level interface removes most of the perception problem, and the remaining difficulty is the policy. Pure vision pays for itself when you need apps that have no usable structure.

Trajectories are the training data

We now know what the agent sees and what it can do. The next question is how it learns. The unit of data is a trajectory: the task, then screenshots and actions in turn, from the first screen until the task ends.

τ = (x; I0, a0, I1, a1, …, IT)one episode; many datasets also store a short thought before each action

Every step of a trajectory is one training example. The input is the task, the current screenshot and the history. The target is the action. A 30-step demonstration gives 30 examples, all correlated with each other.

Trajectories are expensive. Someone has to perform the task, and every step has to be recorded with the exact action and the screen it was taken on. The field has found six ways to get them. Figure 8 shows what each one provides and what it lacks.

Human demonstrations

People perform tasks while a recorder logs screenshots and actions. Android in the Wild (Rawles et al.) contains 715,000 episodes over 30,000 unique instructions. AndroidControl (Li et al.) has 15,283 demonstrations of 14,548 unique tasks across 833 Android apps. Each of its tasks has both a high-level instruction ("book a table for two") and low-level step instructions ("tap the date field"). Mind2Web (Deng et al.) has over 2,000 tasks from 137 websites in 31 domains. OpenCUA's AgentNet has 22,625 human-annotated computer tasks across Windows, macOS and Ubuntu. WebLINX adds web navigation with multi-turn dialogue.

Human data is the most trusted source. But people rarely make and then fix mistakes while being recorded. So demonstrations are thin on exactly the situations where an agent struggles most.

Tutorials and logs

The web holds many written and video tutorials for software. They describe tasks step by step, but they rarely give exact coordinates. UI-TARS used "6M GUI tutorials" mainly to teach reasoning patterns, not exact actions.

Accessibility and DOM traces

Every rendered web page comes with its own labels. The DOM says where each button is and what text it carries. A crawler can screenshot the page and pair each element's box with its text. This gives grounding data for free, at web scale. It teaches where things are. It does not teach what to do next. The next section covers how far this idea has been pushed.

Teacher agents

A strong model can generate or annotate data for a smaller one. Aguvis used GPT-4o to write an "inner monologue" (a short reasoning trace) for each step of existing trajectories. OS-Atlas used GPT-4o to write grounding instructions. UI-TARS ran its own agent on "hundreds of virtual machines" and filtered and refined the new traces. Teacher data scales well, but it inherits the teacher's errors unless it is filtered carefully.

Synthetic interfaces

Instead of crawling interfaces, one can build them. Jedi (Xie et al.) generated 4 million grounding examples. It collected icons, rendered interface components from React libraries in code, and used layouts from Figma templates. Synthesis gives control over rare widgets and exact labels. The risk is a gap between synthetic and real apps.

Exploration and reverse task synthesis

The last source turns the usual order around. An agent first explores an app by interacting with elements. Then a model looks at what happened and writes a task that the actions would complete. OS-Genesis (Sun et al.) converts observed states and actions into low-level instructions, then derives high-level tasks from them, and filters the results with a trajectory reward model. The data is cheap and matches the real app. The tasks may be less natural than the ones people actually want.

Nuance

Demonstrations show the right action in states the expert visited. They almost never show a mistake followed by a fix. UI-TARS addressed this directly: annotators label the corrected action at an error step and also the step after it, and these "reflective" pairs train the model with DPO. If your agent rarely recovers, the cause may be the data, not the model. Add error-and-correction examples on purpose.

How GUI models learn to find elements

Before a model can plan a task, it must know where the actionable elements are. A general VLM trained on photos and documents is not good at this. The ideas below are different answers to one question: where does the grounding signal come from?

Pixels only, from the start

Pix2Act (Shaw et al., 2023) showed early that pixels can be enough. It used a 282M-parameter Pix2Struct model that "relies solely on pixel-based screenshots". It acted with raw mouse and keyboard events, with coordinates as discrete bins. It was trained by behavioural cloning and improved with Monte Carlo tree search. On MiniWob++, a suite of small web tasks that grew out of World of Bits (Shi et al.), it outperformed human crowdworkers. Auto-GUI (Zhang et al.) applied a similar screen-only idea to Android in the Wild. WebGUM (Furuta et al.) combined HTML with screenshots and an instruction-tuned model.

Harvest labels from the web's own structure

The DOM is the largest free source of grounding labels. Four models built on it.

  • SeeClick (Cheng et al.) continued pretraining Qwen-VL (9.6B) on about 300,000 web pages from Common Crawl, pairing element text with locations. With mobile and general data the set reached about 1M examples. It also introduced ScreenSpot: about 600 screenshots and 1,272 instructions from iOS, Android, macOS, Windows and the web.
  • CogAgent (Hong et al.) is an 18B model built on CogVLM-17B. It adds a small high-resolution cross-module so that it can read 1120 by 1120 inputs. Its CCS400K set has 400,000 web screenshots and 140 million question-answer pairs about elements, all taken from the DOM.
  • UGround (Gou et al.) scaled the idea to 10 million elements over 1.3 million screenshots. It paired HTML attributes with descriptions written by a VLM. UGround is a pure grounder. A separate planner, such as GPT-4o, decides what to click, and UGround finds it. The authors call this setup SeeAct-V.
  • OS-Atlas (Wu et al.) went cross-platform. Its corpus has over 2.3 million screenshots and more than 13 million elements from Windows, Linux, macOS, Android and the web. On desktop and mobile it used accessibility trees instead of HTML. While doing this, the authors found that 11.32% of ScreenSpot samples were wrongly labelled, and released a corrected ScreenSpot-v2.

Detect and describe from pixels

Another route trains a perception model on screenshots and hands its output to a planner. Ferret-UI (You et al.) extended the Ferret model with an "any resolution" input that splits each screen into two sub-images. Its 250,000 training samples came from a UI detection model run on Android and iPhone screens, plus tasks generated by GPT models. Ferret-UI is a screen-understanding model, evaluated on referring and grounding tasks rather than on full agent tasks.

OmniParser (Lu et al.) is a parsing pipeline rather than one model. A YOLOv8 detector, fine-tuned on 67,000 screenshots with boxes taken from the DOM, finds clickable regions. A BLIP-2 model describes each icon. OCR reads the text. The output is a structured list plus a screenshot with boxes, given to GPT-4V. With screenshot-only input it improved GPT-4V on ScreenSpot, Mind2Web and Android in the Wild.

Synthesise the interfaces

Jedi, described above, generated 4 million examples from rendered components and templates. With it the authors released OSWorld-G, a grounding benchmark of 564 finely annotated samples. They used Jedi as the grounder under GPT-4o or o3 as the planner.

Separate grounding from planning in training

A full agent needs both skills, but they can be taught in order. Aguvis (Xu et al.) uses a two-stage pipeline "that separates GUI grounding from planning and reasoning". Stage one trains grounding. Stage two trains planning on trajectories annotated with inner monologue. It works only from screenshots, acts through pyautogui, and was built on Qwen2-VL at 7B and 72B.

UI-TARS (Qin et al.) continued training Qwen2-VL at 7B and 72B on about 50 billion tokens. It has three phases: continual pretraining, an annealing phase, and DPO on reflective pairs. Its data covers perception (captions and element descriptions), grounding, unified action traces and tutorials. OpenCUA (Wang et al.) trained Qwen2.5-VL models up to 72B on AgentNet, with reflective long chain-of-thought and 189,000 boxes parsed from accessibility trees. Its 72B model reported 45.0% on OSWorld-Verified.

Change what the model outputs

Writing coordinates as text has a weakness. The model must turn a spatial judgement into digits, one token at a time. GUI-Actor (Wu et al.) replaces this with an attention-based action head. A special <ACTOR> token attends to the visual patches, and the most attended patches give the target. Its 7B version on Qwen2.5-VL reported 44.6 on ScreenSpot-Pro. The output-format trade-offs are discussed in When Language Must Point.

Spend fewer tokens on empty space

Screens have large flat areas. ShowUI (Lin et al.) treats patches with identical colour as connected components and skips part of each component during training. This removes 33% of visual tokens and speeds training by 1.4 times. Built on Qwen2-VL-2B with 256,000 training examples, it reached 75.1% on ScreenSpot zero-shot. Token reduction more broadly is the topic of The Cost of a Picture.

Insight

SeeAct showed that GPT-4V could complete 51.1% of tasks on live websites when a human grounded its text plans into actions. With automatic grounding the gap stayed "substantial". Planning was ahead of pointing. This is why a planner-plus-grounder split (SeeAct-V with UGround, Jedi under GPT-4o or o3, OS-Atlas as a grounder in OSWorld) became a common design. If your agent fails, test it with oracle grounding first. That one experiment tells you which half to fix.

Nuance

Grounding benchmarks such as ScreenSpot are single-step and static. A high score does not mean the agent finishes tasks. The OSWorld authors found that agents struggle "primarily" with "GUI grounding and operational knowledge". Operational knowledge means knowing how an application works, for example which menu holds a setting. No grounding benchmark measures it. Report a grounding score next to an interactive task score, never instead of one.

Behavioural cloning and compounding error

With trajectories in hand, the simplest training method is to copy them. This is behavioural cloning. At each step of each demonstration, raise the probability of the action the expert took.

ℒBC(θ) = − ∑τ ∑t log πθ(at* ∣ st),   st = (It, x, ht)supervised fine-tuning on actions; the loss is computed only on action (and thought) tokens

This is the same loss as supervised fine-tuning of a language model, with the action written as text. The details of loss masking are in Teaching a Language Model to Follow Instructions. Most models in Table 3 were trained only this way.

Behavioural cloning has a known flaw. The training states come from the expert. The test states come from the model. These are not the same.

Follow one step of reasoning. The expert never makes a mistake, so the data contains only screens that a correct agent would see. Now the model makes one small mistake, such as opening the wrong menu. The next screen is one that never appeared in training. The model has no data for it, so it is more likely to make a second mistake. That leads to an even stranger screen.

Ross, Gordon and Bagnell analysed this for imitation learning. With a per-step error rate ε, the expected number of mistakes of a cloned policy can grow with the square of the horizon T, not linearly. Their fix, DAgger, runs the learner, asks the expert to label the states the learner actually visits, and retrains. That makes the training distribution match the test distribution.

Even without the quadratic effect, long tasks are hard. Suppose every step succeeds independently with probability 1 − ε and there is no recovery. Then

P(success) = (1 − ε)Ta pessimistic baseline: no recovery, independent errors

With ε = 2% and 30 steps, that is 0.9830, about 0.55. With ε = 5%, it is about 0.21. Per-step accuracy that sounds high gives task success that is low. The Agent Evaluation Playbook develops this point for text agents. Figure 9 shows both effects.

For GUI agents, the off-distribution screens are concrete. A wrong click opens a dialog that no demonstration contains. A slow page shows a spinner instead of a form. A pop-up covers the button. The agent must notice the unexpected state and recover. Pure cloning teaches neither skill well.

There are three practical remedies. One is to add recovery data, as UI-TARS did with reflective pairs. Another is DAgger-style relabelling, where an expert labels the states the model reaches. Human labelling at that scale is expensive, so a strong model can act as the labeller. The third is to let the model learn from outcomes in a live environment. That is reinforcement learning, the subject of the next section. Why cloning is not enough covers the general argument.

Reinforcement learning from task outcomes

Reinforcement learning replaces the expert with a reward. The agent attempts the task in a live environment. At the end, a checker inspects the state and returns a reward.

R(τ) = 1[task completed],   J(θ) = 𝔼τ ∼ πθ [R(τ)]maximise the probability that the task is actually done

"Task completed" must be a fact about the world. The form was submitted, so a new row exists in the database. The spreadsheet was edited, so the cells hold the expected values. The file was downloaded, so it exists in the downloads folder with the right contents. The policy-gradient machinery that turns this reward into updates is the same as for text agents. It is derived in Reinforcement Learning from First Principles and adapted to agents in Reinforcement Learning for Agents From First Principles.

Because the agent learns from states it reaches itself, RL addresses compounding error directly. It sees its own mistakes and the outcomes that follow them. What is specific to GUIs is the cost and the noise of the loop.

  • Environments are heavy. Each rollout needs a virtual machine or an emulator, reset to a known state. ARPO ran 256 parallel virtual environments. UI-TARS-2 built a unified sandbox platform for large-scale rollouts.
  • Rewards are not always checkable. Where no script can verify the outcome, a model judges it. DigiRL used Gemini 1.5 Pro as an autonomous evaluator. WebRL trained an outcome-supervised reward model. UI-TARS-2 uses verifiers where possible and otherwise uses itself as a generative outcome reward model. A model judge can be fooled, which is a form of the reward hacking described in the agent RL post.
  • Rewards are sparse and late. A 30-step task returns one bit at the end. Assigning credit to the right steps is hard, as covered under credit over fifty steps.
  • The world changes. Live websites and apps update. A policy cloned from last year's screens may meet different screens today.

Four lines of work

Single-step RL for grounding. The cheapest form of RL treats each step alone. The reward checks the action type and whether the predicted point falls inside the target box. UI-R1 trained Qwen2.5-VL-3B with GRPO on 136 tasks. GUI-R1 used 3,000 samples and compared itself against models trained on millions. These are evaluated on static benchmarks. Rewards for points and boxes are discussed in Rewarding What the Model Sees.

Offline-to-online RL on devices. DigiRL (Bai et al.) started from a 1.3B AutoUI model. It used offline RL first, then continued with online RL in Android emulators, using advantage-weighted regression. On Android in the Wild tasks, success rose from 17.7% with supervised training on static demonstrations to 67.2%. It also beat AppAgent with GPT-4V (8.3%), the 17B CogAgent (38.5%) and the best earlier filtered behavioural-cloning approach (57.8%).

Curricula from failures. WebRL (Qi et al.) generates new tasks from the agent's unsuccessful attempts, so the task set follows the agent's ability. It uses an outcome reward model and a KL-constrained update. Its agents read HTML rather than pixels.

Multi-turn RL at scale. ARPO (Lu et al.) adds a replay buffer to GRPO so that rare successful trajectories are reused, training UI-TARS-1.5 7B on OSWorld tasks with a binary success reward. UI-TARS-2 (Wang et al.) is the largest reported effort. It combines a data flywheel, a stabilised multi-turn RL framework, and a hybrid environment with file systems and terminals. It reported 47.5 on OSWorld, 50.6 on WindowsAgentArena and 73.3 on AndroidWorld.

Insight

In DigiRL, the same 1.3B model went from 17.7% (supervised on static human demonstrations) to 67.2% after offline-to-online RL. It also beat a filtered behavioural-cloning baseline that learned from its own successful rollouts (57.8%). Learning from its own failures and their outcomes, in the live environment, was worth more than more copies of good behaviour. If you have a resettable environment and a reliable success check, spend it on online RL before you buy more demonstrations.

Nuance

For single-turn reasoning, GRPO has largely replaced PPO because it needs no value model. UI-TARS-2 reports the opposite for long multi-turn GUI episodes: "PPO consistently outperforms GRPO" in its setup, with value pretraining and length-adaptive advantage estimation. This is one report, but the reason is plausible: a learned value function helps credit assignment over many steps. Do not assume that the best algorithm for maths transfers to agents.

Evaluating in interactive environments

How do we know an agent works? The first GUI benchmarks were static. They recorded human trajectories and checked the agent's action at each step against the recorded one. Mind2Web, Android in the Wild and AndroidControl are mainly used this way. The model sees the expert's history, predicts the next action, and is scored on whether it matches.

Static evaluation is cheap and repeatable. But it cannot measure three things that matter. It cannot credit a different but valid path. It cannot test recovery, because the history is always the expert's, never the model's own mistakes. And it cannot measure long-horizon success, because the model never has to live with its earlier choices.

Interactive benchmarks fix this by running the agent in a real environment and checking the final state with a script. Figure 10 contrasts the two.

  • WebArena (Zhou et al.) hosts realistic websites locally and defines 812 long-horizon tasks. Its best GPT-4 agent succeeded on 14.41% of tasks, against 78.24% for humans.
  • VisualWebArena (Koh et al.) adds 910 tasks across Classifieds, Shopping and Reddit sites that require understanding images on the page.
  • OSWorld (Xie et al.) runs 369 tasks on real desktop applications inside virtual machines, with checker scripts for each task.
  • AndroidWorld (Rawles et al.) provides reward signals for 116 programmatic tasks across 20 real Android apps. Tasks are parameterised, so each run can use new values.
  • Windows Agent Arena (Bonatti et al.) offers 150+ Windows tasks. Its Navi agent reached 19.5%, against 74.5% for an unassisted human.
  • Online-Mind2Web (Xue et al.) runs 300 tasks on 136 live websites. Its authors found "over-optimism in previously reported results" on easier or static benchmarks.

Nuance

Interactive scores depend on the step budget. UI-TARS reported 24.6 on OSWorld with 50 steps and 22.7 with 15 steps. The Claude baseline in the same comparison moved from 14.9 to 22.0. One model gained about two points from the larger budget. The other gained about seven. Rankings at one budget do not hold at another. Always report the step budget, and compare models at the same one.

What a computer-use agent must remember

A screenshot shows the present. A task spans the past. The agent must carry information that no single screen holds. Five kinds of memory matter.

  • The current task and plan. The goal, the sub-goals already done, and the next one. Without this, long tasks lose their thread.
  • Previous actions. A log of what the agent did. This prevents repeated actions. Recall the nuance from the first section: a report submitted twice may look the same on screen as one submitted once.
  • Interface state that is not visible. Content scrolled out of view, values copied from another window, a tab in the background. The agent saw these earlier and must remember them.
  • Discovered app structure. Where things live in an app. AppAgent explores an app first and compiles "a document that records the effects of actions applied to different elements". Agent Workflow Memory (Wang et al.) induces reusable routines, which it calls workflows, from past trajectories and adds them to the agent's memory.
  • Persistent user state. Preferences, accounts and earlier decisions that should carry across sessions. This kind of memory raises privacy and governance questions, covered in Memory Is More Than Context.

Images make memory expensive. Each screenshot costs many visual tokens. Keeping every past screenshot in context quickly fills it. A common design keeps the most recent few screenshots as images and summarises older steps as text: the action taken and what changed. This is the compaction trade-off from Inside an AI Agent Harness, with a much higher price per observation. The general taxonomy of agent memory is in Memory Is More Than Context.

The harness around the model

The model chooses actions. The harness makes them happen and keeps them safe. For computer use, the harness has more parts than for a text agent.

  • Screenshot capture. Capture the screen, resize it to the model's budget, and record the scale factor so that coordinates can be mapped back.
  • Input injection. Turn click(x, y) into a real operating-system event, through a library such as pyautogui on desktops or the platform's input tools on mobile.
  • Sandbox. Run the agent in a virtual machine or container, so that a mistake cannot touch the user's real files. See containment and blast radius.
  • Permissions. Decide which apps, sites and actions are allowed without asking. See permissions and the arithmetic of fatigue.
  • Action validation. Reject coordinates outside the screen, element ids that do not exist, and actions outside the allowed set before they run.
  • Waiting and retries. Wait for the page to settle before taking the next screenshot. A screenshot taken during loading shows a screen that will not exist a moment later.
  • State and logging. Keep the action log, the task plan and the verification results outside the model's context, as the source of truth.
  • Observation compression. Decide how many past screenshots to keep, at what resolution, and what to replace with text.

The screen is an attack surface

A computer-use agent reads everything on the screen. That includes text written by strangers: web pages, emails, documents, pop-ups. If any of that text looks like an instruction, the model may follow it. This is indirect prompt injection (Greshake et al.). For a text agent the injected text arrives through a tool result. For a computer-use agent it arrives as pixels.

The evidence is direct. Zhang et al. inserted adversarial pop-ups into existing agent test environments. Agents clicked the pop-ups 86% of the time on average, and task success fell by 47%. Asking the agent to ignore pop-ups was "ineffective against the attack". The EIA attack (Liao et al.) injected content adapted to each website. It reached up to 70% attack success at stealing specific personal information. Wu et al. dissected the adversarial robustness of multimodal agents more broadly.

Figure 11 walks through one injection and the harness defences that stop it.

No model-level fix fully separates instructions from data on a screen, so the defences sit in the harness. Treat on-screen text as data. Keep a list of allowed sites and actions. Classify actions by reversibility: reading is safe, sending, deleting, paying and publishing are not. Require a human confirmation before any irreversible step. Give the agent the least privilege the task needs. The Agent Evaluation Playbook treats injection testing in detail, and Aligning Vision-Language Models covers model-side safety training.

Insight

In the pop-up study, an instruction to "ignore pop-ups" did not stop agents from clicking them, and they clicked 86% of the time. A defence written in the prompt is just more text on the same channel as the attack. Put the defence where the model cannot be talked out of it: in the harness, as allow-lists, reversibility checks and confirmation gates.

Where computer-use agents fail

When an agent fails a task, the score says only that it failed. To improve it, we need to know why. A useful method is to find the first step where the trajectory went wrong and assign it to one cause. Seven causes cover most failures.

  • Perception. The model misread the screen. It saw "4250" where the field says "42.50".
  • Grounding. The model knew what to click but pointed at the wrong place.
  • Planning. The model chose a wrong or premature step, such as submitting before a required field was filled.
  • Memory. The model forgot what it had done and repeated an action.
  • Action execution. The action was right but had the wrong effect, such as typing into a field that did not have focus.
  • Changed environment. The screen changed between the screenshot and the action, for example when a pop-up appeared.
  • Recovery. After an error, the agent failed to notice it or kept repeating the same failed action.

Figure 12 lets you click each cause and see an example on the same form.

Two techniques make attribution reliable. First, counterfactual substitution: replace one component with an oracle and see whether the task succeeds. SeeAct did this with grounding and found the gap between its best automatic grounding and oracle grounding. Second, replay: rerun the trajectory from a saved snapshot up to the failing step and try alternatives there. Both are developed in The Agent Evaluation Playbook.

What comes next

We started with a static function from an image to an answer. We ended with a policy acting in a world. Along the way, each part of a VLM took on a new job. The vision encoder must resolve 20-pixel icons on large screens. The output format must produce executable coordinates. Training must cover states that experts never visit. Evaluation must check the world, not the words.

You should now be able to reason about a computer-use system from its parts. What does it observe, and what does that cost? At what level does it act? Where does its grounding data come from? Was it trained only by copying, or also from outcomes? Is it evaluated on single screenshots or in a live environment? And what in its harness stops an on-screen instruction from becoming an irreversible action?

The same loop applies when the actions move a robot instead of a cursor. RT-2 expressed robot actions as text tokens, and later models such as OpenVLA and π0 built dedicated action outputs on top of VLMs. From VLMs to VLAs picks up that story. The backbones that recur in Table 3, and how each open family was built, are surveyed in How the Open VLM Families Were Built.

Key insights and nuances

  • The screenshot is not the state. Identical screens can hide different worlds, so grade tasks by checking state and keep an action log. Section 1.
  • Tool loops that pass only text hide expert errors. Return crops or overlays to a model that can see. Section 2.
  • The best observation depends on grounding training. In OSWorld, accessibility text beat screenshots two to one for general models. Grounding-trained pure-vision models later passed both. Section 3.
  • Set-of-Mark is model-dependent. SeeAct found it ineffective for web agents. Measure before adopting. Section 3.
  • Resolution is often the real grounding problem. Zoom-in search raised ScreenSpot-Pro accuracy from 18.9% to 48.1% without training. Section 4.
  • On the web, element ids remove most perception. WebRL reached 42.4% on WebArena-Lite from text and ids alone. Section 5.
  • Demonstrations lack recoveries. Add error-and-correction data on purpose. Section 6.
  • Planning ran ahead of pointing. Oracle grounding let GPT-4V complete 51.1% of live web tasks. Test with an oracle grounder to find which half to fix. Section 7.
  • Grounding scores are not task scores. Operational knowledge of apps is a separate bottleneck. Section 7.
  • Per-step accuracy hides task failure. At 2% error per step, a 30-step task succeeds about 55% of the time without recovery. Section 8.
  • Online RL beat more demonstrations. DigiRL went from 17.7% to 67.2% on the same 1.3B model. Section 9.
  • The best RL algorithm may differ for agents. UI-TARS-2 found PPO beat GRPO on long GUI episodes. Section 9.
  • Step budgets change rankings. Compare interactive scores at the same budget. Section 10.
  • Prompt-level defences do not stop on-screen injection. Put defences in the harness. Section 12.
