Rebuilding the Page and Grounding It

A one-page tour of my research: rebuild a document page, then ground, reason over, and segment it.

The idea in one paragraph

A document page is a picture that was written down. A model that only sees pixels can read it, but it cannot easily say where an answer came from, and a model that only sees extracted text loses the layout that gave the words their meaning. My work over the last two years has been about closing that gap: make the page representable in a form a machine can use, then make it queryable in a way that points back at the page.

The four papers below are one story told in four steps. The first rebuilds a page as structured HTML. The next three train vision-language models to answer questions, show their evidence, and understand layout, using that representation as the common language.

Rebuild the page: REPLICA

Most document pipelines throw something away. OCR keeps the characters but drops position and style. Markdown keeps reading order but drops everything visual. If you want to ask a question later, or draw a box around the answer, you need a representation that keeps text, hierarchy, position and appearance together.

REPLICA is an agentic workflow that rebuilds a page as FID-HTML, a web-native format that records every element together with its bounding box and visual style. The pipeline has four stages: segment the page, localize and route each region to a specialist agent, assemble the pieces in reading order, and refine the result with a reflection agent that compares the rebuilt page against the original.

Rebuilding is only useful if you can measure how faithful the rebuild is. We built VFDR-Bench, a set of 5,000 expert-annotated documents, with three metrics for visual fidelity. REPLICA reaches 93% visual fidelity on it, and was presented as an oral at ICDAR 2026.

What matters for the rest of this story is the output. FID-HTML is a page that can be read by a model and mapped back onto the image. That is the bridge to grounding.

Ground the answer: M3Grounder

A grounded answer is one that points back at the page. Many models can output a bounding box, but boxes break down quickly: a sentence that wraps, a curved line of text, a legend entry in a chart, or an answer that spans two columns does not fit in a rectangle.

M3Grounder answers document questions with interleaved grounding tokens and pixel-level masks. It supports multiple spans per answer, multiple granularities (a word, a line, a table cell) and multiple element types across text and graphics. To train it we built a data engine that scales to 200K-325K documents and 1.5M-2M grounded question-answer pairs, using the structured representation from the previous step to generate accurate supervision.

The lesson here was that grounding is a data problem as much as a modeling problem. Once the page is described precisely, you can generate evidence labels at a scale that hand annotation could never reach.

Reason with evidence: DoCoG

Grounding the final answer is useful. Grounding every step of the reasoning is better. Consider a chart-heavy page and the question “by how much did net sales grow?” The model has to find two numbers, subtract them, and report the result. If it gets the answer wrong, you want to know which number it misread.

DoCoG is a mask-based grounded chain-of-thought framework. Each reasoning step carries its own segmentation mask over the evidence it uses, across text and visual elements such as charts, tables and flowcharts. Training runs in two stages: supervised fine-tuning to learn the format, then preference optimization with an anchor loss so the model improves its reasoning without drifting away from what it already grounds well.

This was presented as a spotlight at ECCV 2026.

Segment the structure: DocLayout-VL

Before you can ground anything, you need to know what the page is made of. Classic layout models predict a flat list of boxes from a fixed label set. Real documents are nested: a column contains a section, a section contains a table, a table contains cells. They also contain things the label set never anticipated.

DocLayout-VL reframes layout as promptable, open-set, hierarchical segmentation. A vision-language model produces a layout tree, a segmentation model turns it into dense masks, and a hierarchy-aware grounding step keeps the two consistent. It is trained on 2.5M documents with more than 400K labels and 80M masks, and evaluated on a new benchmark, HOPLay-Docs-Bench.

You can ask it for “the footnotes” or “every seal on the page” and get masks back, which is the layout counterpart of what M3Grounder does for answers.

One recipe, four papers

Looking back, the four projects share a recipe.

  • Represent first. Pick a representation that keeps text, structure and appearance together, then build everything else on it.
  • Make evidence a first-class output. Masks, not just boxes, and at every step, not just the last.
  • Generate supervision from structure. A precise page description turns labeling into a data engine.
  • Measure what you claim. Each paper comes with a benchmark designed for the property it argues for.

The same team and the same infrastructure, from pre-training data to large-scale generation, sit behind all four. The systems side is a story of its own, and the talks page has the slides.
