The plan

What exactly happens between loss.backward() and optimizer.step()? Which tensors change, which stay the same, and how would you check?

Those two lines sit inside every framework in this series. Trainer and the distributed and fine-tuning libraries later in the series all wrap them. If you can read those two lines at the level of tensors, the wrappers stop being mysterious.

To answer the question we need the parts underneath it. So we start with one tensor and build upward. A tensor leads to views, views to broadcasting, and broadcasting to matrix multiplication. Then come autograd, a layer, a model, a loss, an optimizer, a data pipeline and a training loop. The last step traces one real training step and prints every piece of state.

The derivations live in the theory posts, so we only point to them. Here we write the code and look at what it does.

Step 01

Look inside a tensor

Goal Read every piece of metadata a tensor carries, and compute its memory footprint by hand.

Start with the simplest tensor we can make: x = torch.randn(4, 8). It looks like a 4 by 8 table of random numbers. It is really a flat block of memory plus a small record that says how to read that block. Here is every field of the record for x.

What x = torch.randn(4, 8) carries
FieldValueMeaning
shape(4, 8)The size along each dimension.
rank2The number of dimensions. x.dim() returns it.
dimension0 and 1One axis of the tensor. Dimension 0 has size 4. Dimension 1 has size 8.
dtypetorch.float32How to decode the bytes of one element.
devicecpuWhich memory holds the bytes.
storage32 floatsThe flat block itself. It has no shape.
element size4 bytesThe size of one float32.

We collect these in one record, so that a later script can print any tensor the same way.

Two fields look alike and are not. nbytes is what this tensor’s own elements occupy. storage_bytes is the size of the whole block it points into. They are equal here. Step 2 shows a case where they differ by a factor of 1000.

The memory footprint has a one-line formula.

M = numel(x) × bytes per element = 32 × 4 = 128 bytes

Run the first script. It prints the metadata and repeats the sum for two other dtypes.

The shape is the same in all three lines. Only the bytes per element change. This is why half precision matters at scale: the same model in bfloat16 needs half the memory for its weights.

Step 02

Storage, strides and views

Goal Turn a logical index into a memory address by hand, and see why transpose moves no data.

The storage is flat, but a tensor has rows and columns. Two more numbers connect them. The stride of a dimension says how many slots to move in storage when that index goes up by one. The storage offset says which slot holds element zero.

Together they give the one rule that every view in PyTorch follows:

slot = offset + index[0] × stride[0] + index[1] × stride[1] + …

Take m = torch.arange(12).view(3, 4). Its stride is (4, 1). Moving down one row skips 4 slots. Moving right one column skips 1 slot. So m[2, 3] reads slot 0 + 2 × 4 + 3 × 1 = 11.

Now we write the rule as code. storage_indices applies it to every element, in pure Python, because it is a definition and not a fast path.

If the rule is right, we can build a transpose without touching any data. We swap two entries of the shape and the same two entries of the stride. Then as_strided makes a new view on the same storage. view_manual does a similar thing: it keeps the storage and computes fresh row-major strides for the new shape.

The script prints the layout of several views of one storage. Run it again and read the second block.

Read a few rows. m.t() has stride (1, 4), the swap we predicted, and it still shares storage. m[:, 1:3] has offset 1, because its first element is in slot 1. m[:, ::2] has column stride 2, because it skips every other column. m.t().contiguous() is the only row with shares=False. That call copied the data into a new storage in row-major order.

The next block applies our rule. Since base = torch.arange(12), each value equals its slot, so we can check by eye.

The table sums up the operations. Read it by asking one question: does this call move any bytes?

Break it

Transpose a matrix and flatten it with view. The slots of one logical row are no longer next to each other, so no single stride can describe the flat result. PyTorch refuses.

To debug this, print t.stride() and t.is_contiguous(). Then choose. Use t.contiguous().view(12) if you want the copy to be visible in the code. Use t.reshape(12) if you do not mind which one you get.

Insight

reshape hides a behaviour change. On a contiguous tensor it returns a view, and writes reach the original. On a non-contiguous tensor it returns a copy, and writes do not reach the original. The output above shows it: t.reshape(12) shares storage with m: False. Code that writes through a reshape can change meaning when an earlier line adds a transpose. Use view when you depend on sharing, because it fails loudly.

Views have one more cost. A slice keeps its whole storage alive.

One 4000-byte row holds a 4 MB block in memory. If you keep small pieces of big tensors, such as a few rows of a batch in a list, call clone() first. Otherwise each piece keeps the big block alive.

Test

Each hand-written function is compared with PyTorch: strides, slots, transpose, permute, and the failure of view.

Step 03

Broadcasting

Goal Write the broadcasting rule yourself, see that it copies nothing, and catch the bug it can hide.

Later tutorials add a vector to every token and a per-head vector to every position. We do not want Python loops for that. Broadcasting lets two tensors of different shapes combine, as if the smaller one had been repeated. The rule is short:

  1. Line the shapes up from the right.
  2. Treat a missing dimension as size 1.
  3. In each column, the sizes must be equal, or one of them must be 1.
  4. A size-1 dimension is stretched to match.

Stretching costs no memory, and Step 2 tells us why. If a dimension has stride 0, then moving along it never moves in storage. Every index reads the same element. So an expanded tensor is one more view.

The script tries the two shapes that attention needs.

Shapes in this step (B = 2, H = 4, N = 5, D = 8)
TensorShapeMeaning
x[B, N, D]One D-number vector per token and batch element.
bias[D]One vector. It is added to every token.
q[B, H, N, D]One vector per batch element, head and token.
per_head[1, H, 1, D]One vector per head. It is shared across batch and tokens.
per_head, expanded[B, H, N, D], stride (0, 8, 0, 1)Still 4 × 8 = 32 numbers in memory.

Break it

The last block of the output is the most useful one. A regression head returns [B, 1]. Labels often come as [B]. These shapes broadcast without complaint, to [B, B]. Every prediction is compared with every label.

The loss is 1.0290 when it should be 0.6618. Training still runs, and the curve still falls, so nothing tells you it is wrong. To debug it, print the shape of pred - target. If it has more dimensions than you expected, a broadcast has happened.

Our mse_loss in Step 9 raises an error on this mismatch. F.mse_loss only emits a warning.

Test

Step 04

CPU and GPU tensors

Goal Know where a tensor lives, what a copy costs, and how to time GPU code without fooling yourself.

So far the storage has been in host memory, the RAM the CPU uses. A discrete GPU has its own memory. A tensor lives in one or the other, and x.device tells you which. x.to(device) returns a new tensor on that device, with a new storage. x.cuda() is short for x.to("cuda"). If the tensor is already there, no copy happens.

We pick the device in one place, with a helper that every script uses.

The second function exists because GPU work is queued. When torch.mm(a, b) returns on a GPU, Python has only put a command in a queue. The multiply has not finished. If you read the clock at that point, you measure the time to queue the work.

The matmul benchmark measures this mistake directly. It needs a device with a real queue, so this one is from the Apple M5 GPU.

The clock read before the sync says 0.285 ms. The real time is 53.6 ms, which is 188 times longer. Figure 3 shows the two timelines.

Break it

Time the same 4096 by 4096 matmul on CUDA and leave out synchronize(). This is one run on an NVIDIA H100 80GB HBM3.

Without the sync, the multiply appears to take 0.037 ms. The real time is 2.695 ms, about 73 times longer. Report the first number and you would claim a speed the GPU never reached. Every GPU timing in this post calls synchronize() before it reads the clock.

Anything that needs the value forces the same wait. .item(), .cpu() and print(x) all block until the device catches up. This is why GradNormMonitor in Step 13 stores a tensor and not a float.

Pinned memory and asynchronous copies

On a discrete GPU, a copy is done by a DMA engine, a hardware unit that reads RAM directly. It needs the source pages to stay in place. The operating system can normally move or swap ordinary pages, which are called pageable. pin_memory() makes a copy of the tensor in pages that are locked in place. Without it, the driver first copies your data to a pinned buffer of its own.

With a pinned source, x.to(device, non_blocking=True) can return at once while the copy runs in the background. The CPU can use that time to prepare the next batch. The benchmark times all three directions and shows what non_blocking returns.

Tensors in the transfer benchmark, for size S in MB

Nuance

These numbers do not tell you what a CUDA machine does, for two reasons. First, an Apple GPU shares its memory with the CPU, so there is no PCIe link to cross. Second, the laptop was shared with other jobs.

A second run gave very different numbers: 8.11 and 47.60 GB/s at 256 MB, against 15.23 and 21.71 above. It also reported 41.2 seconds for one 64 MB copy to finish. We do not know the cause of that outlier. The two runs disagree by a factor of two or more, so they do not support any claim that pinning is faster here. Treat this as a working benchmark to run on your own hardware.

Here is the same benchmark on CUDA. It is one run on an NVIDIA H100 80GB HBM3.

The non_blocking line behaves as described above. The call returned after 0.036 ms, and the 64 MB copy finished after 4.741 ms.

Step 05

Matrix multiplication

Goal Write matmul from its definition, add the batch dimension, and measure what a real kernel buys you.

Almost all the compute in a neural network is matrix multiplication. Linear layers use it now. Attention uses it in Build Attention From Scratch. Its shape rule is worth learning early. The inner dimension K must match, and it disappears:

[B, M, K] @ [B, K, N] → [B, M, N]

We start from the definition, with three loops. Then we remove one loop with broadcasting from Step 3. Then we add a batch dimension.

The line in mm_rows is worth reading slowly. a[i, :, None] has shape [K, 1]. b has shape [K, N]. Their product broadcasts to [K, N], where row p of b is scaled by a[i, p]. Summing over dimension 0 gives one output row, of shape [N].

torch.matmul adds one more idea on top of torch.bmm: the leading dimensions broadcast. The last two dimensions never do. They follow the matmul rule. We can write that with the tools we already have.

Which call takes which shapes
CallInput shapesOutputNotes
torch.mm[M, K], [K, N][M, N]Exactly two dimensions.
torch.bmm[B, M, K], [B, K, N][B, M, N]Exactly three dimensions, same B.
torch.matmul, @[..., M, K], [..., K, N][..., M, N]Leading dimensions broadcast.
Attention, in Build Attention From Scratch[B, H, N, d], [B, H, d, N][B, H, N, N]One score per pair of tokens, per head.

Now the bottleneck. We run all versions and report milliseconds and GFLOP/s, billions of floating-point operations per second. A multiply and an add count as two.

Insight

The Python loops reach 0.0004 GFLOP/s. torch.mm on 8 threads of the same CPU reaches 186 to 635 GFLOP/s in this run, and 138 to 438 across three reruns. Either way that is a factor of roughly a million per operation, for the same arithmetic. Replacing the two inner Python loops with broadcasting gets to 3.1 GFLOP/s. So most of the gap is the cost of Python and .item(). The rest is the gap between one tensor operation per row and a tuned kernel. Write the loops to understand the operation, and never ship them.

That machine has no accelerator we can use. For the GPU rows we use the earlier run on the Apple M5.

Nuance

The GPU does not always win. On the M5 at n = 256, the CPU took 0.192 ms and the GPU took 0.400 ms. The GPU only pulls ahead at n = 1024.

Both tables are noisy. The M5 table reports 217.7 ms at n = 4096, while the single timed call in Step 4 took 53.6 ms. On the EPYC server this table shows 8.0 ms at n = 1024, and three reruns took 4.9, 11.0 and 11.7 ms. Both machines were busy with other jobs, and we did not track down these gaps. Treat the numbers as ratios and orders of magnitude.

Here is the same benchmark on CUDA, one run on an NVIDIA H100 80GB HBM3. The CPU rows come from that machine’s own host CPU. It is a different machine from the EPYC server above, so compare its CPU rows only with its GPU rows.

On the H100 the GPU wins at every size we ran, even n = 256: 0.049 ms against 0.079 ms on its host CPU. At n = 2048 it takes 0.369 ms against 22.7 ms. At n = 4096 it reaches 51,001 GFLOP/s, about 51 TFLOP/s, in float32 with the default precision. These are single runs.

Test

Step 06

Autograd

Goal See the graph that PyTorch records, walk it yourself, and learn when gradients add up and when the graph disappears.

Set requires_grad=True on a tensor and PyTorch starts recording. Each operation on it creates a backward node, and the output tensor points to that node through grad_fn. The maths is in the theory post. Here we inspect the objects.

Derivation inWhat autograd actually does

format_graph prints the recorded graph. It is a short recursion over next_functions, the list of inputs each node holds.

The tensors of the graph, with values
TensorShapeValueKindgrad_fn
x[3][1, 2, 3]LeafNone
w[3][0.5, -1, 2]LeafNone
y = x * w[3][0.5, -2, 6]Non-leafMulBackward0
z = y.sum()[]4.5Non-leafSumBackward0

A leaf is a tensor you created, not the result of a recorded operation. Weights are leaves. By default, backward() fills .grad only on leaves. y.grad exists here only because we asked for it with y.retain_grad().

The nodes run in the reverse order of the forward pass. SumBackward0 sends a gradient of 1 to each element of y. MulBackward0 multiplies by the other input, so x receives w and w receives x. Then the two AccumulateGrad nodes write into .grad.

Gradients accumulate

AccumulateGrad means what it says. It adds to .grad. It does not overwrite.

This is why every training step starts with zero_grad. It is also useful on purpose: gradient accumulation over several small batches is exactly this behaviour. Step 13 shows what happens when you forget to clear them.

The graph is freed, unless you ask

Backward nodes hold tensors they saved for the backward pass. To save memory, backward() frees those tensors as it goes. A second call then has nothing to work with.

Break it

Call backward() twice on the same graph.

The fix depends on what you meant. If you need both passes, use retain_graph=True on the first one. Note that the gradient then doubles: 8.9634 is 2 × e1.5. In most training code the fix is different. This error usually means a tensor from an earlier step is still in the graph, for example a running total of the loss. Use loss.item() or loss.detach() when you store it.

detach and no_grad both stop recording, at different scopes
ToolScopeShares storageTypical use
x.detach()One tensorYes, writes reach xKeep a value without its graph. Treat a term as a constant.
torch.no_grad()Every operation in the blockNot applicableEvaluation, and the optimizer update.

Step 07

A Linear layer by hand

Goal Build y = xW + b from two parameters, and match nn.Linear exactly.

We now have what a layer needs: a matmul, broadcasting and gradients. A linear layer is two tensors and one line of algebra.

y = x W + b

We start with the two tensors and no class at all. nn.Parameter marks a tensor as something to train. The rest is the matmul from Step 5 and the broadcast from Step 3.

Shapes of the layer
TensorShapeMeaning
x[..., in_features]Input. Any number of leading dimensions.
W[in_features, out_features]The weight. Row i says how input i feeds each output.
b[out_features]The bias. It broadcasts over all leading dimensions of x.
y[..., out_features]Output.

Now we wrap those two tensors in a class. nn.Parameter is a tensor with requires_grad=True that a module registers when you assign it to an attribute. That single behaviour is why the next step works.

Read forward with the earlier steps in mind. x @ self.weight is the matmul from Step 5. y + self.bias is the [B, N, D] + [D] broadcast from Step 3. The initial values come from a uniform range of plus or minus 1 / sqrt(in_features), the same range nn.Linear uses. It keeps the output variance roughly independent of the input width.

There is one trap when you compare with PyTorch. We store W as [in, out], which matches the algebra. nn.Linear stores its weight transposed, as [out, in]. The test copies our weight across with a transpose, then requires equal outputs.

Autograd sees the layer as ordinary tensor operations, so we can print its graph. This is the Linear layer plus .pow(2).mean() as a loss.

Read it from the bottom. The weight [3, 2] enters MmBackward0, the matmul. Its result and the bias [2] enter AddBackward0. Then come the square and the mean. The two leaves are the only tensors that will get a .grad.

Test

gradcheck compares the gradient from autograd with a numerical estimate from small changes to the input. It needs float64, which is why the test calls .double().

Step 08

nn.Module and an MLP

Goal Understand what nn.Module keeps track of, by building an MLP that uses all of it.

We borrow one thing from PyTorch: nn.Module. It is bookkeeping. When you assign an attribute, it looks at the type and files it in the right place. That filing is what lets .parameters(), .to(device) and .state_dict() work on a whole tree of layers.

A stack of linear layers alone is still one linear map, so we need a nonlinearity between them. We also add two small modules that show the other things nn.Module handles: dropout depends on the training mode, and Standardize holds buffers.

Theory inWhy neural networks need nonlinearity

Now ask the module tree what it found. named_parameters() walks the tree and gives each parameter a dotted name. state_dict() holds the parameters plus the buffers.

Check the sum by hand: (2 × 16 + 16) + (16 × 16 + 16) + (16 × 3 + 3) = 371. The buffers appear in state_dict but are not returned by .parameters(), so the optimizer never sees them.

What nn.Module does with each kind of attribute
KindExampleIn parameters()In state_dict()Moved by .to()Updated by the optimizer
Parameterself.weightYesYesYesYes
Bufferself.meanNoYesYesNo
Submoduleself.headIts parametersIts entries, prefixedYesIts parameters
Plain tensorself.t = torch.ones(2)NoNoNoNo

Read down the columns. A buffer is state that must be saved and moved, but never trained. The last two rows are bugs. Nothing warns you about them. The model runs, and those tensors never learn.

train() and eval() do one thing: they set self.training on every module in the tree. They do not turn gradients on or off. That is what no_grad is for. Dropout reads the flag. In training mode it zeros elements and scales the rest by 1 / (1 - p), so the expected activation is the same in both modes.

Step 09

Loss functions

Goal Build cross entropy from log_softmax and gather, make it stable, and match F.cross_entropy exactly.

A loss turns the model’s output into one number. That number is the root of the graph, the place where backward() starts. MSE comes first, because it is one line plus the shape check that Step 3 taught us to want.

Cross entropy is the loss for choosing one of C classes. The model outputs a score per class, called a logit. Softmax turns scores into probabilities. The loss is the negative log probability of the right class. The direct way to write that overflows.

The stable version uses one trick. Subtract the row maximum m first. The numerator and the denominator of softmax both get divided by exp(m), so the result does not change. But now every exp() argument is zero or negative, so it cannot overflow.

With log_softmax in hand, cross entropy is a lookup. gather picks one element from each row, at the column the target names.

Shapes in cross entropy (N = 4, C = 3)
TensorShapeMeaning
logits[N, C]A score per class. [B, T, C] is flattened to this.
target[N]The right class id per row. Integers, not one-hot.
logp[N, C]Log probabilities. Each row sums to 1 after exp.
safe[:, None][N, 1]The index for gather. It must have the same rank as logp.
picked[N]log p(target) for each row.
loss[]A scalar, the root of the graph.

Look at two rows in the output. The third row has its largest logit on class 2 but its target is class 1, so it contributes 3.0038. The fourth row has all-zero logits, so its probability is one third and it contributes ln 3 = 1.0986. That is the loss of a model that has learned nothing. For three classes, expect a first loss near 1.1. The 8-example batch in Step 14 has a loss of 1.1375. With the same initial weights, 200 shuffled batches of 64 averaged 1.107. That is what a good initial state looks like.

Break it

Feed large logits to the naive version. exp(100) overflows float32, which tops out near e88.

If your loss is nan and your logits are large, this is the kind of line to look for. The fix is to use a stable form. Do not clip the logits.

ignore_index needs care. Ignored rows must add nothing to the sum, and they must also leave the count. Dividing by valid.sum() does both, so padding does not shrink the loss.

Test

The value and the gradient must both match F.cross_entropy, including ignored positions and [B, T, C] input. A second test checks the closed form of the gradient, softmax minus one-hot.

Checkpoint

  • ours and torch print the same digits in every block.
  • You know that a useless three-class model starts near a loss of 1.1, and you check for it.
Step 10

Optimizers

Goal Write SGD and AdamW as the update rules they are, and match torch.optim to the last printed digit.

An optimizer is less than its name suggests. It holds references to parameters and some state per parameter. step() reads each p.grad and changes p in place. The simplest possible version is the four highlighted lines in this training loop:

The loop recovers the true W and b with an error near 1e-06. The first output line shows what happens without no_grad: PyTorch refuses an in-place write to a leaf that requires a gradient.

no_grad is required. The update must not be recorded, or the next backward pass would try to differentiate through it. Everything else in an optimizer class is state and bookkeeping. Here is the shared part.

SGD adds optional momentum and weight decay on top of the two-line update.

AdamW keeps two running averages per parameter. The first is of the gradient. The second is of its square. The update divides one by the square root of the other, so each element gets its own step size. The theory post derives why.

Now the check. We train the same model with the same seed four times, with our optimizers and with PyTorch’s.

The largest gap in epoch loss over 60 epochs is exactly zero, for both pairs. Our optimizers follow the same trajectory as PyTorch’s, to every digit that gets averaged into that loss.

The time column needs a warning. Torch SGD looks slow: 5.03 s against 1.85 s here, and 1.7 to 3.1 times manual SGD in four reruns. That is not the price of SGD. It looks like a one-time cost, and --compare always runs torch SGD first.

Test

This test compares final weights after 25 steps, for plain SGD, SGD with momentum and weight decay, and AdamW.

How much does readable code cost? torch.optim.AdamW has three implementations: a for-loop, a foreach version that batches operations, and a fused kernel. We time one step on 6.3 million parameters.

The last block is one run on an NVIDIA H100 80GB HBM3. Its cpu ms column is that machine’s host CPU, not the EPYC server above. On CUDA, foreach goes from slowest to second fastest, at 0.55 ms. Fused takes 0.23 ms. Ours takes 3.24 ms and the for-loop 3.78 ms.

Nuance

Only one result holds across every column, CUDA included: the fused kernel is fastest, at about half the for-loop time or better. The other orderings change. Ours beats the for-loop on the EPYC server, 5.37 against 7.59 ms. It loses on the M5 CPU, 11.73 against 8.34 ms. It wins again on MPS, 8.58 against 11.20 ms.

The EPYC numbers also move between runs. Three reruns gave 6.75 to 8.83 ms for ours and 7.16 to 11.33 ms for the for-loop, and the two tied once. foreach was the slowest every time, at 8.97 to 16.90 ms against 18.12 ms above. Do not read much into a gap that changes sign. The readable version is fine for learning. Reach for fused=True when the optimizer shows up in a profile.

Step 11

Dataset and DataLoader

Goal Write a dataset and two collate functions, then measure what workers and prefetching really change.

A Dataset answers two questions: how many examples are there, and what is example i? We use interleaved spirals in 2D. They are small, they are exact, and no linear model can separate them. So if we reach high accuracy, the hidden layers are doing real work.

A DataLoader does four jobs for each batch. It picks indices, with shuffling if you ask. Workers fetch those examples. A collate function turns a list of examples into one batch. Optionally, the batch is pinned. We will write each job ourselves.

Collate is the part you write most often. For equal-shape examples it is one torch.stack.

Language data does not have equal shapes. Every sequence has its own length, so torch.stack fails. We pad to the longest sequence in the batch and return a mask that says which positions are real.

Shapes through the data pipeline

Collate was one job. Here are the other three, in SimpleDataLoader. It covers batching, shuffling, workers, prefetching and pinning, in about 90 lines.

The first three tabs are short. _index_batches makes one order per epoch and cuts it into lists of indices. Shuffling changes only that order. __iter__ fetches and collates in the main process when there are no workers. _worker_loop does the same job in a separate process: it takes a batch id and its indices, and sends the batch back.

_iter_workers holds two ideas. Workers finish in any order, so finished batches wait in the ready dict until their turn. That keeps the batch order fixed. And in_flight starts at num_workers * prefetch_factor and stays at that level, because a new task goes out only when a batch comes back. So that bound is the prefetch. It is also what stops workers from filling all of memory.

Pinning is the one line in _finish. Note a limit: our workers start fresh every epoch. PyTorch’s loader also watches for workers that die and seeds each worker, so random augmentation differs between them.

Now we measure workers. Our spirals are too cheap to need any, so SlowDataset burns 2 ms of CPU per example. That stands in for decoding an image or tokenizing text.

The benchmark adds a pin_memory row only when CUDA is present. On the H100 machine, in one run, four persistent workers gave 1813 examples per second without pinning and 1771 with it. That is no difference. This benchmark pins each batch but never copies it to the GPU, so it shows only that pinning did not slow the loader down.

Insight

Worker startup has a measurable price. This epoch holds 1.2 seconds of work, so four perfect workers would need 0.30 s. Four persistent workers come close, at 0.34 s in epoch 2. Four fresh workers take 0.55 s. So starting and stopping the processes costs about 0.2 s per epoch.

On this short dataset that is about a third of the epoch time. On an hour-long epoch it would be nothing. Use persistent_workers=True when epochs are short. Workers also have to be started differently on macOS and Windows, by importing your script again, so expect this price to differ there.

Nuance

Raising prefetch_factor from its default of 2 to 4 changed nothing here: 1778 against 1750 examples per second. This loop does no work between batches, so it never waits on a batch that was fetched early. Prefetching should matter when training steps and data costs vary from batch to batch, but this benchmark does not test that. Also, do not read the SimpleDataLoader rows as a win over PyTorch. It shows 1508 against 1089 here, but three reruns gave 1096 to 1208 against 1138 to 1226. The result is too noisy to rank the two.

Notice where p changes: in one row only. The forward pass, the loss and the backward pass do not change any weights. Only step() does.

Next come the parts that surround the step. to_device moves a batch, and evaluate measures the model without recording a graph.

evaluate uses both tools from earlier steps. @torch.no_grad() stops recording, which saves memory. model.eval() turns dropout off, which changes the answer. They do different jobs, and you need both.

Finally, fit runs the epochs, and saves and resumes checkpoints.

A checkpoint holds the model, the optimizer and the random state. Without the optimizer state, AdamW would restart with empty averages, and the resumed run would differ from the original. The test checks this: it trains 2 epochs, resumes to 4, and compares with 4 uninterrupted epochs.

Validation accuracy reaches 0.998 in a few seconds. The validation set uses the same spirals with fresh noise. Now drag through the run and watch the regions form.

The training curve is not smooth. AdamW’s epoch loss jumps from 0.038 at epoch 18 to 0.224 at epoch 19, and back to 0.059 at epoch 20. At this learning rate that is ordinary. It is also why we look at the whole curve, and not only the last row.

Step 13

Debugging

Goal Break the loop in five ways, and find each bug with hooks and checks, without editing the model.

A training bug rarely raises an error. Usually the loss just looks wrong. So we need ways to look inside a running model without editing it. PyTorch gives us hooks: functions that run at fixed points. A forward hook runs after a module’s forward and sees its output. A post-accumulate-grad hook runs during backward, right after a parameter’s .grad has been written.

We build three tools on these two hooks. Each one removes its hooks on exit, so it is safe to use in a with block.

Break 1: a learning rate of 10

Break it

Plain SGD with momentum 0.9 and lr=10, on the Step 12 model.

Read the log top to bottom. The loss climbs to 3.9e20 by step 9. The next logged rows show about 4. Why would an exploding model recover? It has not. The script logs only every third step, and unlogged step 22 has a loss of 5.55e15. The gradient column gives the next clue. From step 12 on, the largest logged gradient is on head.bias.

Insight

A logged loss of 4 here means a dead model, not a recovered one. We added ActivationStats to this same run and printed every step. From step 11 on, the second ReLU outputs zero for all of its values on almost every step. The head then sees only zeros, so head.weight gets no gradient.

Its weights still move. Momentum 0.9 keeps pushing them with the velocity saved earlier. They move by a norm of 2.42e18 at step 12, and their norm grows from 5.67e18 at step 11 to 1.83e19 at step 18. The loss of 4 is not stable either. At step 22, one value out of 4096 gets through the ReLU, and the loss jumps to 5.55e15.

At step 24 the detector fires on one -inf among the 4096 values of the blocks.1.0 output. The ReLU clamps that value to 0, so the model output is still finite and the loss on that step is a normal-looking 2.31. A check on the loss alone would never have seen it. Watch activations and gradients per layer, not only the loss.

Nuance

The last two lines try two fixes, and one of them fails. Gradient clipping at 1.0 keeps lr=10 and ends at train loss 9.7995 with validation accuracy 0.333, which is chance for three classes. Clipping bounds the size of the gradient, but a clipped gradient of norm 1 still moves the weights by a distance of 10, and momentum adds to that. Only the learning-rate fix works: at lr=0.1 the run ends at validation accuracy 0.998. Clipping guards against rare spikes. It does not repair a learning rate that is too high.

Break 2: forgetting zero_grad

Break it

Delete one line. Gradients from all earlier steps stay in .grad, as Step 6 showed.

The loss ends at 351.68 against 0.0136. The gradient norm gives it away: 8.43 against 0.0106 after 30 epochs. A gradient norm that does not shrink while the loss is high points to this bug.

Break 3: evaluating in training mode

Break it

Train with dropout 0.3 and forget model.eval() before you evaluate.

The quickest test is to run the same batch twice. A model in eval mode gives the same answer both times. Here, 14.1% of the predictions change between two passes, and the accuracy reads 0.900 when the true value is 0.969.

Break 4: a shape mismatch

Break it

Pass a batch with 3 features to a layer that expects 2.

Read the numbers in the message as the Step 5 rule. 8x3 is [B, K] and 2x16 is [K, N]. The inner dimensions, 3 and 2, differ. The 2 is in_features, so the fault is in the input width or the layer setting.

Break 5: a device mismatch

Break it

Keep the model on the accelerator and the batch on the CPU. This is the real error on the Apple M5 GPU.

PyTorch’s error names two devices. Ours names the tensor and says what to do. On a large model that saves time, because the failure no longer lands deep inside a matmul. On a machine with no accelerator, the script uses the meta device as a stand-in, so the PyTorch message differs.

Step 14

From backward to step

Goal Answer the question we started with, on one real step, with every piece of state printed.

Now we have every part we need. This script runs one training step of a small MLP on 8 spiral points. It stops after each line and prints what changed. We follow one parameter closely: head.weight, of shape [16, 3].

Walk through the output with the figure.

After the forward pass, the loss exists and the graph has 26 nodes, 6 of which are leaves. There is one leaf for each parameter tensor. Every .grad is still None. No weight has changed.

During loss.backward(), autograd walks those nodes from the loss down. The order is real, and our hook recorded it: head first, then blocks.1, then blocks.0. The graph is then freed, so a second backward() fails. Weights have still not changed.

Between the two lines, the gradients sit in .grad. Nothing is running. The optimizer has no state yet, because it creates state on the first step. This gap is where other tools do their work. Gradient clipping scales .grad here. Mixed precision unscales it here. In training across several machines, the gradients have already been averaged by now. Manual accumulation skips the step here. All of these are edits to the same tensors.

During optimizer.step(), AdamW allocates exp_avg and exp_avg_sq for each parameter, reads .grad, and writes to p in place. It never looks at the graph or the loss. It only sees p, p.grad and its own state.

The script also proves the update by hand, for the element with the largest gradient. On the first step, the bias correction cancels the (1 - beta) factors, so the update reduces to almost exactly lr × sign(g).

The tracked element, head.weight[10, 0]
QuantityValueSource
Before-0.087641Saved before the step

Insight

On AdamW’s first step, the size of the gradient does not matter. Only its sign does. Among the entries of head.weight with a nonzero gradient, the mean update is 0.01000, which is the learning rate. test_adamw_first_step_is_lr_sized makes the point sharply: gradients of 0.0001, -5 and 300 all move their weights by the same 0.01. So with AdamW, the learning rate is a distance in weight units. Our weights start within plus or minus 0.25, so lr=0.01 moves each live weight by 4% of that 0.25 bound on the first step, even if its gradient is tiny.

Insight

Half of this gradient is zero, and the ReLUs are the reason. 24 of the 48 entries have an exactly zero gradient. They form 8 complete rows out of 16. Those rows connect to the 8 hidden units that output zero for all 8 examples in this batch. No signal flows through them, so no gradient flows back. Their weights still moved by up to 2.5e-05. That movement is weight decay alone, which is lr × wd × p and does not depend on the gradient.

This batch is an extreme case, not a typical training batch. The script takes ds.x[:8] with no shuffle, so all 8 examples are class 0 and sit near the origin. Their radius is at most 0.12, and the dataset reaches 1.0.

A shuffled batch has fewer zeros. With the same initial weights, 200 shuffled batches of 8 averaged 32% zeros in this gradient, from 12.5% to 50%. Batches of 64 averaged 17%.

Nuance

The optimizer costs memory. Here the parameters take 1484 bytes and the AdamW state takes 2968 bytes, a ratio of exactly 2. So a model under AdamW needs at least three times its weight memory before you count gradients, which add a fourth copy until zero_grad drops them. This is why large trainings care about optimizer state as much as weights.

After zero_grad, .grad is None again. The optimizer state survives, with one step recorded. The weights keep their new values. The loop is ready to run again.

So here is the answer. loss.backward() walks the recorded graph from the loss to the leaves and writes one gradient tensor per parameter. It changes no weights. optimizer.step() reads those gradient tensors and its own state, and changes the weights in place. It knows nothing of the graph. Between the two lines there is only data in .grad, waiting, and you can read or edit it.

Checkpoint

  • The after and by hand values print the same six decimals.
  • You can list what is alive at each of the five stages: graph, .grad, optimizer state.

Key insights and nuances

  • A tensor is a view: storage plus shape, stride and offset. transpose, permute, slicing and expand only change the metadata. Step 2
  • reshape may return a view or a copy, depending on an earlier line. If you depend on writes reaching the original, use view, because it fails loudly. Step 2
  • A 4000-byte slice can hold a 4 MB block in memory. clone() the small pieces you keep. Step 2
  • [B, 1] - [B] broadcasts to [B, B], and training still runs. The loss was 1.0290 where 0.6618 was correct. Step 3
  • A GPU timing without a sync measures the queue. 0.285 ms against a real 53.6 ms on the Apple M5 GPU, and 0.037 ms against 2.695 ms on an H100. Step 4
  • Measure copies on your own machine. The MPS numbers were noisy. One H100 run gave 11.7 GB/s pageable and 14.3 GB/s pinned to the GPU, and 1.35 GB/s back, far below the link’s rating, for reasons we do not know. Step 4
  • Python loops are about a million times slower per operation than torch.mm on the same CPU. On the Apple M5, the GPU only wins from about n = 1024. Step 5
  • Starting workers has a measurable price on short epochs. Four workers took 0.55 s per epoch when started fresh, and 0.34 s when persistent. Step 11
  • A small model gains nothing from an accelerator, as far as we measured. On an H100 it took 4.91 s for 60 epochs, against 5.79 s on the EPYC CPU. The Apple M5 GPU took about 0.88 s per epoch. All of these are different machines. Step 12
  • A finite loss does not prove a healthy model. At lr=10 the logged loss dropped to about 4 while the second ReLU layer output zeros. An unlogged step still hit 5.55e15, and momentum kept moving weights that had no gradient. Step 13
  • Clipping does not repair a learning rate that is too high. lr=10 with clipping stayed at chance. Step 13
  • AdamW’s first step is about lr × sign(g). Gradient size does not matter on that step. Step 14
  • AdamW state takes twice the memory of the parameters. 2968 bytes against 1484 in our run. Step 14

  1. Complete view_manualHard PyTorch’s view also works on some non-contiguous tensors, when the dimensions you split or merge have strides that line up. Extend view_manual to cover those cases. Write a test that compares it with Tensor.view on random slices and permutes, including the error cases.
    Hint

    Group old and new dimensions into chunks with equal products. A chunk of old dimensions can be merged only if each stride equals the next stride times the next size.

  2. Measure a real GPUEasy Run benchmarks/transfer.py, matmul.py and optimizers.py on your own CUDA machine, a few times each. Compare them with the single H100 run here. At what size does pinned memory start to matter? Where does the GPU stop winning at matmul? Then run the six GPU-only tests.
  3. Compare Adam with L2 and AdamWMedium Add an AdamL2 class that adds wd * p to the gradient, as our SGD does. Match it against torch.optim.Adam. Then train the spiral model with both at a high weight decay and compare the parameter norms.
    Hint

    Use param_norms from debug.py at each epoch. The theory post on optimizers says what to expect.

  4. Add BatchNormMedium Write a BatchNorm1d module with running statistics as buffers. Match nn.BatchNorm1d in both modes. Then repeat Break 3 and see how much worse a forgotten eval() becomes.
  5. Find dead units automaticallyMedium Extend ActivationStats to count units that are zero for every example in a batch. Run it on the lr=10 scenario. At which step does the first layer stop being useful? Can a warmup schedule keep the units alive?
    Hint

    For an output of shape [B, D], use (out == 0).all(dim=0).
