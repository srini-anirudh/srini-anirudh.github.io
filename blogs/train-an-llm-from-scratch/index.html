pretrain, a small and complete LLM pretraining system. It turns raw stories into token shards and trains a Llama-style decoder with AdamW, accumulation and bf16. The plan

A training loop fits in ten lines. What does it take to stop that loop at any step, restart it on another day, and get the same numbers to the last bit?

The answer is most of a pretraining system. The ten-line loop has no epochs, no saved position, no schedule and no way to run on two machines. We write that loop first and run it. Then we fix what it lacks, one module at a time, and test each fix.

A few short forms appear below, and each is explained again where it first matters. BPE is byte-pair encoding, the way our tokenizer builds its vocabulary. EOS is the end-of-sequence token that closes a story. ZeRO is the Zero Redundancy Optimizer, which splits optimiser state across processes. MAD is the median absolute deviation, a spread that one outlier cannot move.

The order follows the data. Stories become tokens, tokens become windows, and windows become batches. Then come the optimiser, the step, the checkpoint and the loop. Last come the parts that only matter at scale: utilisation, several processes, and things going wrong.

Why each stage existsHow LLMs are pretrained

We train the architecture from Build a Modern LLM From Scratch. By default this folder builds it with Hugging Face’s LlamaForCausalLM, so the folder runs on its own. C4 showed that the two give the same logits. A flag swaps in C4’s TinyLLM. The trainer only needs model(input_ids).logits.

Every output below comes from a saved file in results/, unless the text says it is a separate run. Each output block names the hardware that ran it. The GPU outputs are single runs on NVIDIA H100 80GB HBM3 GPUs, labelled as such, and they are kept apart from the CPU numbers. Where a run has not happened, the post says “not yet measured” and gives the command. Commands run from the repo root.

The last command downloads the data and builds what steps 1 to 6 explain. Here is that whole path on real tokens. Press Next to walk it, or read on and come back.

Step 01

The simplest loop that learns

Goal Watch the loss fall with almost no code, then list exactly what this loop cannot do.

We start at the end state of C1 and C4: a model, a flat file of tokens and a loop. Each row of the batch starts at a random offset. There is no dataset class and no schedule.

The slice has L + 1 tokens because L inputs need L targets, and the last target sits one place past the last input. The model returns one score per vocabulary entry at every position. So logits is three-dimensional, and cross_entropy wants it flat.

Shapes in the naive loop (B = 8, L = 64, V = 4096)
TensorShapeMeaning
tokens(n,)The memory-mapped file of uint16 ids. Nothing is read until it is sliced.
chunk(8, 65)Eight slices of L + 1 tokens.
x, y(8, 64)Inputs and the same tokens moved along by one.
logits(8, 64, 4096)A score for every vocabulary entry at every position.
loss()The mean over 512 target tokens.

The first loss is the number to check. An untrained model is close to uniform over 4,096 tokens, and ln(4096) is 8.318. The first printed loss is 8.319. If your first loss is far from ln(V), stop and look for a bug before you train.

The loop learns. Now look at what it cannot do:

  • It samples with replacement, so it has no epochs and it cannot say what it has seen.
  • It has no position to save, so it cannot resume.
  • Each row can start in the middle of a word and can run across two stories.
  • The learning rate never changes, and a single bad gradient is applied in full.
  • Two processes running this loop would train on overlapping data and drift apart.

The next 18 steps fix these, and each one adds a module and a check.

Checkpoint

  • The first loss is close to ln(4096) = 8.318.
  • The loss falls by more than 3 in 200 steps.
Step 02

The raw corpus

Goal Turn one large text file into a clean list of whole documents.

The corpus is TinyStories, a set of short stories generated by larger language models so that small models have something simple to learn from. We use its V2 GPT-4 file. It is plain text, with the literal string <|endoftext|> between stories. The small vocabulary is why a 5.4M-parameter model can make visible progress in minutes.

The train file is 2.2 GB, and we only need part of it. So download asks for the first 128 MiB with an HTTP Range request. That creates a problem. The cut lands in the middle of a story.

The 128 MiB slice holds 163,746 training documents and 33,284,335 tokens. That is far less than a real model trains on, and it is enough to show every mechanism here. Note the median document: 180 tokens, not far below the window length of 256. That fact drives the packing choice in step 5.

Test

The test feeds a string with a cut-off tail and checks that the tail is kept or dropped as asked. It runs with the other data tests in this group.

Checkpoint

  • split_documents returns stripped, non-empty stories.
  • test_split_documents_drops_partial_tail passes.
Step 03

Use a tokenizer, then train a small one

Goal Compare an existing tokenizer with one trained on our corpus, and see what the choice costs in parameters.

We start with an existing tokenizer, GPT-2’s, loaded from the Hub. Then we train a byte-level BPE on our own stories. Both sit behind one small interface, so the rest of the code does not care which it gets.

BPE starts from single bytes and repeatedly merges the most frequent adjacent pair into a new token. It stops when the vocabulary reaches 4,096 entries. Common words become one token. Rare words stay in pieces.

The output shows the two tokenizers one after the other. On this simple sentence they make the same 12 pieces. Their ids differ, and so do their sizes. The difference shows up in the model.

The embedding table has one row per token. With tied embeddings that same table is also the output layer. At 256 dimensions, the GPT-2 vocabulary would take 12.87M parameters, which is 75% of the model. Our 4,096-token vocabulary takes 1.05M, which is 19%. On a corpus of children’s stories, most of GPT-2’s entries would never earn their place.

Nuance

This is a choice about small models and a narrow corpus. A tokenizer trained on one corpus will split text from another corpus into many pieces, and it cannot be swapped later without retraining the model. A pretraining run that may later see code, tables or other languages should spend its vocabulary differently.

Checkpoint

  • EOS is id 0 in our BPE and id 50256 in GPT-2.
  • test_bpe_roundtrip_and_eos passes: decoding the ids returns the original text.
Step 04

Document boundaries and token shards

Goal Put an EOS after every document, and store the corpus as flat files a loader can slice.

Why not join the documents and tokenize the result? Two things go wrong. The tokenizer can merge across the join, and the model never sees a signal that a story has ended. We measure both.

The first pair ends in a full stop, and joining changes nothing except the missing boundary. The second pair is a document cut mid-sentence. Here the join creates a word that was never written: sun and day become the pieces _su nd ay.

The last line is the surprise. Only 2 of 1,999 real neighbouring pairs tokenize differently when joined, because complete stories end in punctuation.

Insight

On this corpus, token corruption at the join is rare: 2 pairs in 1,999. The stronger reason for EOS is the stop signal. A model only learns to end a story if the end of a story is a token it can predict. Our sampler in step 15 stops at EOS for exactly this reason. So check for EOS in your shards even when your tokenizer looks clean at the joins.

The encoding step appends EOS to each document and stores it as uint16. Two bytes are enough for any vocabulary up to 65,536, and they halve the disk use compared with int32.

What is on disk for the training split
FileShape and typeMeaning

train_doc_lens.npy(163746,) int32Length of each document, including its EOS.

The first EOS sits at position 176, so the first story has 177 tokens. Position 177 starts the next story. Already the first window holds parts of two documents. Step 5 asks whether that is acceptable.

Checkpoint

  • y[:8] is x[:8] moved along by one.
  • test_every_document_ends_in_eos passes: every document ends in EOS, and EOS appears nowhere else.
Step 05

Padding or packing

Goal Build fixed-length sequences both ways, then measure how much of each batch is real data.

The model wants a rectangle. Documents are not rectangles. There are two simple ways to get one.

Padding puts one document in each row. Long documents are cut at L. Short ones are filled with a padding token, which the loss must skip. Packing joins everything into one stream and cuts it every L tokens.

Here are both on three tiny documents, where 0 is EOS and 99 is the padding token. This is a short run of ours, not a saved result, and you can paste it into a Python shell from inside the folder.

Padding lost the 6 and the 0 of the third document, and the second row is 40% filler. Packing kept every token, and windows of L + 1 overlap by one. The overlap is what gives each window its full set of targets. But the first window now runs from one document into the next.

Try the two strategies on 40 real document lengths from our corpus. Move L and watch the filler and the cuts trade places.

Now the same measurement on all 163,746 documents. This benchmark works from document lengths alone, so it builds no tensors and the numbers do not depend on the hardware.

Utilisation is the share of the rectangle that holds real tokens. Tokens cut is the share of the corpus that never reaches the model. Multi-doc windows are windows with a document boundary inside. Split docs are documents that do not fit whole in one window.

Insight

Utilisation alone can mislead. At L = 128, padding reports 99.6% utilisation, which looks perfect, and it throws away 37.3% of all tokens. The rows are full only because most documents were cut. At L = 512, padding keeps nearly everything and only 39.3% of the rectangle is real. Always read utilisation next to tokens cut.

Nuance

Best-fit packing, from Ding et al., splits far fewer documents: 12.7% against 72.7% at L = 256. It is not free. At L = 256 its utilisation is only 78.6%, because the median document has 180 tokens and two of those do not fit in one window. At L = 512 it reaches 95.1%, because two do fit. The cost depends on how L relates to your document lengths, so measure it on your corpus.

We use greedy packing because the loader becomes simple: window i is a fixed slice. The price is that 91.9% of windows at L = 256 contain a boundary, and attention can read across it. packing.py has the tools to stop that.

Nuance

The trainer in this tutorial does not use this mask. It calls model(x) with the default causal mask, so a token can read the end of the previous story. EOS tells the model where the break is, and many packed pretraining runs accept this. We have not measured whether the block mask improves our small model. Exercise 1 asks you to measure it.

Checkpoint

  • Greedy packing has 100.0% utilisation and cuts no tokens at every L.
  • test_pad_and_pack_shapes and test_document_ids_positions_and_mask pass.
Step 06

A loader that can say where it is

Goal Shuffle, share out data across ranks and workers, prefetch, and save the exact data position in three numbers.

The naive loop sampled at random. That gave it nothing to save. We replace it with three small pieces. The first gives each window a fixed address.

The second decides the order. It builds one permutation from seed + epoch, and the order depends on nothing else.

Here is the real output for 12 windows and two ranks. This is a short run of ours, and skip=2 is what a resume after two samples would do.

The third piece counts. The important detail is where it counts.

Shapes through the loader (B = 16, L = 256)
TensorShape and typeMeaning
shard slice(257,) uint16L + 1 tokens, read from the memory map.
chunk(257,) int64Cast up, because nn.Embedding needs a long tensor.
x, y from the dataset(256,) int64One sample: inputs and targets.
x, y from the loader(16, 256) int64One micro-batch.

The loader passes num_workers, prefetch_factor and pin_memory to PyTorch’s DataLoader. Workers prepare batches in other processes while the model is busy. Prefetch sets how many batches each worker keeps ready. Pinned memory lets a batch reach a GPU without an extra copy, so the trainer turns it on only for CUDA.

Workers made it slower here. With none, the loader delivers 1,910 batches per second. Two workers give 718, and four give 1,161. A memory-mapped slice is cheap to read, so the likely cost is sending finished batches between processes, which is more than the work the workers take over. We did not profile this further.

Insight

More workers is not always faster. Workers pay off when a sample takes real work, such as decoding an image or tokenizing text on the fly. Our tokens are already on disk, and one process delivers 15.6M tokens per second, far more than this model can use. So the main config keeps num_workers: 0. Measure before you add workers.

A map-style dataset gets its worker split for free, because the sampler hands out indices. A stream does not. Every worker runs the same __iter__, so without a split each of N workers yields the whole stream.

Test

These tests read a stream of 40 batches across an epoch boundary, stop after 17, and rebuild the loader in a new object. The batches must match exactly, with and without workers. Another test checks that two ranks with two workers each see every window once.

Checkpoint

  • Rank 0 and rank 1 lists share no index.
  • test_resume_mid_epoch_reproduces_batches passes across an epoch boundary.
Step 07

AdamW and its parameter groups

Goal Configure each number of the optimiser on purpose, and keep weight decay away from the parameters it would harm.

The derivation lives in the theory post. Here we set five numbers and decide which parameters get decay.

Derivation inWhat an optimizer actually does
The AdamW settings in TrainConfig and the main run
SettingValueWhat it does here
lr2e-3 peakSet in tinystories.yaml. It scales every step, and step 8 changes it over time.
beta10.9Averaging for the first moment, the running gradient.
beta20.95Averaging for the second moment. This is lower than the common 0.999, so the estimate follows recent gradients faster.
eps1e-8Keeps the denominator away from zero.
weight_decay0.1Pulls the weights in the decay group toward zero, separately from the gradient.

RMSNorm gains have a natural value of 1. Decay would pull them toward 0, which fights their purpose. So how many parameters does this rule touch? We ran it on the main model.

The 13 vectors are two gains per block across 6 blocks, plus one final norm. They hold 0.06% of the parameters. We have not measured what happens if they do decay on this small run, so we make no claim about its size. The rule is standard, and exercise 5 asks you to measure it.

AdamW keeps state for each weight. After one step, the optimiser holds this for the embedding matrix.

Optimiser state for one parameter, model.embed_tokens.weight
StateShapeMeaning
step()Number of updates, used for bias correction.
exp_avg(4096, 256)First moment. One number per weight.
exp_avg_sq(4096, 256)Second moment. One more number per weight.

So the optimiser holds twice the model, and that fact returns twice. In step 13 it is why a resume-ready checkpoint is three times the size of the weights. In step 18 it is what ZeRO removes first.

Test

Every parameter must land in exactly one group. A tied weight must not appear twice.

Checkpoint

  • Decay and no-decay tensors add up to all 56 named tensors.
  • test_param_groups_cover_every_parameter_once passes.
Step 08

Warmup, cosine decay and a floor

Goal Write the schedule as one small function, plot it, and match it against the Transformers version.

At the start the second moment has seen almost nothing, and steps can be large. Warmup raises the learning rate slowly while that estimate settles. After the peak, cosine decay lowers it smoothly. A floor keeps some learning going at the end.

Change the shape yourself. The default values are the main run. The output above is the same curve at seven points.

Compare with a trusted implementation

test_schedule_matches_transformers compares every step with get_cosine_with_min_lr_schedule_with_warmup from Transformers, to 1e-9. It allows for two deliberate differences. Their warmup starts at 0 on step 0, so that step does nothing, while ours starts at 1 / warmup. Past the last step their cosine turns back up, while ours holds the floor.

Checkpoint

  • Step 39 and step 40 both print 2.000e-03. Step 799 prints 2.000e-04.
  • test_schedule_matches_transformers passes.
Step 09

Gradient accumulation that is really equal

Goal Split one large batch into micro-batches, get the same gradient, and catch the common bug.

One optimiser step can see more sequences than fit in memory at once. We run several forward and backward passes, let the gradients add up, and then step once. The size that matters to the optimiser is the global batch:

B_global = B_micro × N_accum × N_GPU

The main run has 16 × 2 × 1, which is 32 sequences, or 8,192 tokens per step. The question is what to divide by. A mean loss over a big batch weights every target token the same. To get the same gradient, each micro-batch must add its sum of per-token losses, divided by the token count of the whole step.

Shapes in one micro-batch of the main run (B = 16, L = 256, V = 4096)
TensorShapeMeaning
x, y(16, 256)Inputs and targets.
logits(16, 256, 4096)Scores at every position, about 16.8M numbers.
flat logits(4096, 4096)16 × 256 = 4,096 positions by 4,096 tokens. The two numbers are equal by coincidence.
flat targets(4096,)One target per position.
loss_sum()The sum over non-ignored targets.

A common version averages each micro-batch’s mean loss. We call it mean of means. It looks right, and on our packed data it is right. So we test both, on real tokens, against one big batch.

The first group uses packed data. Both methods agree with the big batch to float32 noise. In the second group, one micro-batch keeps only 16 of its 128 targets, as padding would cause. Our method stays at 3.73e-09, and mean of means moves to 8.25e-03. That is more than a million times larger. Figure 4 shows why.

Insight

Packed data hides this bug completely. Both methods give the same 3.73e-09 until the target counts differ. So a pipeline can run mean of means for a long time without a visible problem, then change when you add padding or an ignore mask. Post-training labels in C6 ignore many tokens, so that is where it would appear. Normalise by the step’s token count from the start.

Test

Both behaviours are tests. One asserts that our method equals a big batch. The other asserts that mean of means does not.

Checkpoint

  • Token-weighted accumulation stays at float32 noise in both groups.
  • test_mean_of_means_is_wrong_with_unequal_token_counts passes.
Step 10

bf16 training compared with fp32

Goal Run the forward pass in bf16 with autocast, and measure what changes against fp32.

bf16 has the same exponent range as fp32 and far fewer mantissa bits. It rarely needs a loss scaler, and matmuls on it are faster on hardware that supports it. Autocast runs chosen operations in bf16 while the weights stay fp32.

The memory ledger and four precisions inInside a training step

Look back at lm_loss_sum in step 9. It calls logits.float() before the cross-entropy. A softmax over 4,096 entries in bf16 has only about three decimal digits of precision to work with, and the loss is the number we most want to trust. So the loss is computed in fp32.

What each tensor uses under bf16 autocast
TensorTypeWhy
Weightsfp32Small updates would vanish if stored in bf16.
Activations in forwardbf16This is where the speed and memory gains are.
Logits at the lossfp32Cast up by lm_loss_sum.
Gradientsfp32They have the type of the weights.

The benchmark starts both runs from the same weights and the same batches, so any difference in loss comes from numerics alone.

The numerics hold up. After 30 steps the final losses are 5.9233 and 5.9239, and the largest gap anywhere in the run is 0.0010. The speed is the surprise. On this CPU, bf16 takes 460.8 ms per step against 41.9 ms for fp32, so it is about 11 times slower.

Nuance

bf16 is not automatically faster. This CPU has no fast bf16 matmul, so PyTorch emulates it, and each operation costs far more. That is why this benchmark uses the small smoke config. The usual speed gain comes from hardware with native bf16 support, so this result says nothing about GPUs. The next block shows one GPU run, which does not follow that rule either. So check your hardware before you set precision: bf16.

Here is the same benchmark on one NVIDIA H100, with the main config and 8,192 tokens per step.

On the H100, bf16 is slower than fp32 too: 60.5 ms against 45.8 ms per step. The loss gap is 0.0079, larger than on the CPU run. This model is far too small for the GPU. Each step is a few short kernels, so the time is probably spent launching them, and the cheaper bf16 matmuls save little. A larger model would keep the GPU busy, and we expect the usual gain there. That has not been measured.

Checkpoint

  • The maximum loss difference between fp32 and bf16 is about 0.001.
  • Weights are still torch.float32 after a bf16 step.
Step 11

Clip the gradient and record its norm

Goal Limit the size of a bad step, and turn the gradient norm into a number we can watch.

Clipping scales the whole gradient down when its total length is above a limit. Its direction does not change. So it limits the damage from one bad batch while leaving normal steps alone.

Why it works inWhy transformers do not explode

The norm that goes in the log is ‖∇θ L‖ before clipping. On the main run it starts at 2.83 and falls to 0.92 by step 20. After that, only one logged value goes above the limit of 1.0: 1.30 at step 140. So clipping matters early and then mostly does nothing. You can scrub through it in Figure 7.

The scheduler still advances on a skipped step. If it did not, the learning rate and step would no longer agree.

Test

One test compares the returned norm with one computed by hand, on a copy of the model. Another places a NaN in the embedding and checks that no weight moves.

Checkpoint

  • grad_norm appears on every log line, unclipped.
  • test_nonfinite_gradient_skips_update passes.
Step 12

Activation checkpointing

Goal Trade compute for memory, and measure both sides of the trade.

The name is close to “checkpoint”, and the idea is unrelated to saving a file. Backward needs the intermediate tensors of forward, so autograd keeps them alive. For a deep model that memory is large. We can drop them and recompute them when backward arrives.

The saved tensors fall from 571.7 MiB to 104.1 MiB, which is 0.18 times. The step takes 1.10 times as long. The theory says about one extra forward pass, and forward is only part of a step, so a small rise is what we should expect.

Now the same benchmark on C4’s TinyLLM, which has the same architecture and the same parameter count.

Insight

Saved tensors are not peak memory. Both models save 0.18 times as much under autograd, but process peak growth only falls to 0.70 times on the Llama path and 0.48 times on TinyLLM. Step time differs too, at 1.10 and 1.28 times. These come from one 6-step run on a CPU that other jobs also used, so treat the differences as rough. Same architecture, different implementation, different result. So measure the peak of your own code, and do not estimate it from the saved-tensor count.

The same benchmark on one NVIDIA H100, with the Llama model:

Saved tensors fall by the same 0.18 times. Peak growth falls to 0.30 times, a better result than on the CPU. The step takes 1.71 times as long, more than the 1.10 times on the CPU. On this small model the recompute is not hidden by anything.

Test

The trade must change memory and nothing else. The test checks that saved bytes fall, and that every gradient matches the plain model within tolerance.

Checkpoint

  • Saved bytes fall with the wrapper on.
  • test_activation_checkpointing_same_grads_less_saved_memory passes.
Step 13

Checkpoints that hold the whole run

Goal Save everything a run depends on, write it safely, and detect a damaged file.

A checkpoint with only weights restarts training. To resume it we need every piece of state that affects the next step. There are more than you might expect.

Inside a checkpoint
KeyContentsIf you leave it out
modelWeights, 5.4M numbersNothing to resume.
optimizerBoth moments and step counts, 10.8M numbersAdam restarts with empty moments, and early steps are too large.
schedulerPosition on the LR curveThe LR goes back to warmup.
stepOptimiser steps takenLogging and stopping both go wrong.
rngPython, NumPy, torch CPU, and the acceleratorDropout and sampling differ from the original run.
dataSeed, epoch, batches consumedThe run replays batches it has already seen.
configThe whole run definitionA resume can silently change the run.
extraLoop state, such as the spike detectorIts statistics restart.

The final checkpoint of the main run is 61.9 MiB on disk. The weights alone are 5,401,856 × 4 bytes, which is 20.6 MiB. Three times that is 61.8 MiB, so the two Adam moments really do make the file three times the size of the model.

The restore mirrors this, with one safety check in the trainer. If the config in the checkpoint differs from the config of this run, the trainer refuses to continue.

Nuance

load_checkpoint uses weights_only=True, so a checkpoint cannot run code when it is loaded. It is also why the NumPy state had to become a tensor. Checksums catch damage, and this setting limits what a hostile file can do. They solve different problems, so keep both.

Checkpoint

  • A checkpoint has all eight keys, and a .json manifest with a checksum sits next to it.

Step 14

Prove that a resume is exact

Goal Compare an uninterrupted run with one stopped and restarted, down to the last bit.

We run the same config three ways on real data. Straight runs 40 steps. Resumed stops at step 20, builds a new model, optimiser and loader from the checkpoint, and continues. Weights only is the usual mistake: it reloads the weights and restarts everything else.

The resumed column equals the straight column at every step, and the largest gap is exactly 0. That is the claim we set out to prove in the plan. results/resume_test_tinyllm.txt shows the same result on C4’s model.

Insight

The wrong resume looks better. At step 40 the weights-only run shows a loss of 5.749 and the correct run shows 6.126. Two things changed in that run. Its data position restarted, so its next batches are the same ones the model trained on in steps 1 to 20. Its schedule and Adam moments also restarted, so it runs a fresh warmup with empty moments. We did not separate the causes. The loss in the log is measured on the batch before the update, so replayed data can look like progress. If a restarted run suddenly improves, suspect the resume and check validation loss before you celebrate.

Nuance

The run above is on a CPU with a single process. We also ran the same script on one NVIDIA H100, in results/gpu_resume_test.txt. It printed bitwise equal: True with a gap of 0.00e+00. That is one GPU and one run. GPU kernels are not guaranteed to be deterministic in general, so on other hardware expect a close match with a small tolerance, and read any gap carefully. The test asserts exact equality only on CPU.

Test

first + second == full compares Python floats, with no tolerance. The group also damages a checkpoint and changes a config, and checks that both are handled.

Step 16

Model FLOPs utilisation

Goal Turn tokens per second into one honest number: the share of the hardware peak doing useful work.

A tokens-per-second number means little without the model size. MFU fixes that. It divides the useful FLOPs per second by the peak FLOPs per second of the hardware.

What to do with the number inHow to find what is slowing your model

Plug in the main model. N is 5,401,856, with n = 6 layers, d = 256 and T = 256.

6 × 5,401,856 + 12 × 6 × 256 × 256 = 32,411,136 + 4,718,592 = 37,129,728

That matches flops_per_token in the first line of the log. Nearly all of it comes from the weights. The attention term is 13% here because the context is short.

We also need a peak. Vendors publish one for datacenter GPUs. For other hardware we measure the best FLOP rate of a large square matmul, which is the friendliest workload the machine can run.

Three checks are in that output. The formula gives 37,129,728 FLOPs per token and FlopCounterMode counts 37,896,192, a ratio of 0.98. The best matmul on this CPU reached 0.731 TFLOP/s in fp32. The training run had a median of 6,972 tokens per second, and 6,972 × 37,129,728 is 0.259 TFLOP/s. That is 35.4% of the peak. One caution: the peak and the throughput were measured at different times on a shared CPU. A second run of the benchmark on the same CPU measured the peak at 0.595 TFLOP/s, which would make the same throughput 43.5%. Read the MFU as a range of about 35% to 44%, not as one exact value.

MFU tells you there is a gap between what the hardware can do and what the run uses. It does not say why. The theory post covers how to find the cause. On one H100 the same benchmark gives a different picture.

The run reached 5.487 TFLOP/s against a measured bf16 peak of 687.7 TFLOP/s. That is an MFU of 0.8%. The model is too small to use the GPU, so most of the time goes to launching small kernels. A real run would aim far higher. This number is only for this model and says nothing about large ones.

Nuance

Our peak is measured, so this MFU is not comparable with one computed from a vendor datasheet. A matmul of size 4096 is a best case and a real step is not, so a low value on a small model is expected. The peak also moves between measurements. The training log measured 0.62 TFLOP/s at its own start, so its mfu column reads higher than 35.4% for the same throughput. Use MFU to compare runs on the same machine, against the same peak. Recomputed work from activation checkpointing also does not count as useful, so turning that on lowers MFU even if the hardware is just as busy.

Compare with a trusted implementation

The formula is checked against PyTorch’s FlopCounterMode over a real forward and backward pass. It must land within 15%.

  • test_flop_formula_close_to_flop_counter passes.
Step 17

Data parallelism with DDP

Goal Train with several processes, and prove that the result equals one big batch.

DDP keeps one full model per process. Each process gets different data, computes its own gradients, and averages them with all the others. All processes then apply the same step, so the replicas stay identical. torchrun starts the processes and sets RANK, WORLD_SIZE and LOCAL_RANK in the environment of each.

Derivation inThe parallelism playbook

The data split is already done. EpochSampler from step 6 takes every world_size-th entry. The other half is the all-reduce, and it is short enough to write by hand.

In train_step we saw one more line for this. Under DDP, the all-reduce runs only on the last micro-batch, because an all-reduce on each one would be wasted communication.

To check it, one script runs three versions on the same global batch of (8, 32). The first is one process with the whole batch. The second is two processes with DDP. The third is two processes with our all-reduce by hand.

Shapes in the DDP check (2 ranks)
TensorShapeMeaning
x, global(8, 32)The same batch on every rank, built from one seed.
xl, local(4, 32)x[rank::world_size], this rank’s half.
w_ddp(P,)All weights in one vector, gathered from each rank to compare.

DDP matches a single process to float32 noise. Our by-hand version matches DDP exactly. The weights are identical on every rank.

Insight

DDP is averaging, and it behaves exactly like one larger batch only because the local batches are the same size. A mean over two equal halves equals the mean over the whole. If ranks ever had unequal numbers of target tokens, as with padded data, a plain average would have the mean-of-means bug from step 9, now across machines. Our EpochSampler gives every rank an equal share, and packing gives every window the same count, so the two choices protect each other.

The full loop runs under torchrun with the same train.py. This config uses a smaller 1.25M-parameter model for 200 steps, so two processes fit on the CPU.

It ends at a validation loss of 3.9259, and the same run on TinyLLM ends at 3.7687. Multi-GPU DDP uses the same code on NCCL.

On two NVIDIA H100 GPUs the equivalence script gives the same answer as on gloo.

DDP on NCCL matches one process with the whole batch to 3.73e-09, the same gap as on the CPU, and the ranks stay identical. The throughput of the full runs is in the table in step 15. The multi-GPU runs used two GPUs. Larger counts have not been measured.

Checkpoint

  • The script prints weights identical on every rank: True.
  • test_ddp_two_processes_match_one_big_batch passes. It starts two real processes.
Step 18

Sharded training with FSDP and ZeRO

Goal Stop keeping redundant copies, starting with the optimiser state, and measure what each rank stores.

DDP has one weakness: memory. Each rank stores all the weights, all the gradients and both Adam moments. That is four times the model, on every rank, and most of it is a copy of what another rank already holds. ZeRO removes these copies in stages.

Stage 1 is the simplest. Each parameter gets one owner rank, and only that rank keeps its moments. The owner computes the update and broadcasts the new weight. PyTorch ships this, and it runs on gloo.

Optimiser state falls from 9.54 MiB to 4.76 MiB and 4.78 MiB, so about half per rank. The two shares differ a little because whole parameters are assigned to owners. The weights stay identical to DDP, with a gap of 0. So this memory saving costs no accuracy, and it costs an extra broadcast each step.

FSDP goes further and shards the weights too. A rank holds one shard of each block. Just before a block runs, its weights are gathered with an all-gather. Just after, they are freed.

Move the controls to see the arithmetic for models of several sizes. This is calculation, not measurement. The two runs in this step are the measured part.

The script trains the same seeded steps under DDP and under FSDP on gloo, gathers the shards back, and compares them.

Each rank stores half of the weights, 2.38 MiB and 2.37 MiB against 4.75 MiB, and half of the optimiser state. The final losses match to all printed digits, and the largest weight gap is 3.70e-07. This run proves that the shards are right. It says nothing about speed or GPU memory.

The GPU memory is on a larger model, with 141M parameters, 100 steps and two NVIDIA H100 GPUs.

Per GPU, parameters fall from 544 to 272 MiB and optimiser state from 1,088 to 544 MiB. Peak memory falls from 2,769 to 1,854 MiB, which is a smaller drop than the parameters and optimiser state, because activations and the temporary full copy of each block remain. The weight gap against DDP is 9.52e-04, larger than the 3.70e-07 on the CPU. We did not investigate the cause. DeepSpeed was not run, so ZeRO-2 and ZeRO-3 remain not yet measured.

Stages 2 and 3 of ZeRO need DeepSpeed. Its config for the same kind of run is short. It uses a learning rate of 3e-3 and no schedule, so it is a sketch and not a copy of the main run.

Nuance

This tiny model has no memory problem, so sharding it only shows that the mechanism works. On a real model, FSDP also needs a sharded checkpoint, and our save_checkpoint does not write one. Resume under FSDP is not implemented in this folder. To use it for long runs, you would add that, for example with torch.distributed.checkpoint.

Checkpoint

  • ZeRO-1 and FSDP each store about half of the optimiser state per rank at 2 ranks. FSDP also stores about half of the weights.
  • test_fsdp_on_gpus_halves_local_params is marked gpu. It passed on two H100 GPUs: 1 passed in results/gpu_pytest.txt.
Step 19

Break it on purpose

Goal Cause each failure for real, see what the guard does, and find where the guard is weak.

A long run will hit these failures eventually. Each one gets a detector and a planned response. We wrote the guards earlier in the loop, and now we test them by causing each failure. These runs are on CPU with the small config.

Break it: a token id past the vocabulary

A common real cause is a shard written with a different tokenizer. We set one id to 5000 in a model with 4,096 entries.

Without the guard, a CPU gives IndexError: index out of range in self. It is correct, and it tells you nothing about where the id came from. The guard names the range and the vocabulary, so you can see at once that the tokenizer and the model disagree. On GPUs this kind of failure can be far less clear, which is a good reason to check the batch before it leaves the CPU.

Break it: NaN gradients

A forward hook turns the output into NaN on step 5, and again from step 10 on. One bad step should be noise. Three in a row should stop the run.

At step 5 the update is skipped and weights moved is False. Training continues normally at step 6. Steps 10 to 12 are three in a row, and the guard raises. The message says the loop would now reload the last good checkpoint and lower the learning rate. The trainer does not do that yet. It only stops, and exercise 4 asks you to add the rest. To debug a NaN, look at the step in the log where skipped first appears, and save that batch.

Break it: a learning rate far too high

We hold the rate constant for 150 steps with no scheduler, so no decay can rescue a bad choice. We try 3e-3, which is close to the normal peak, then 100 and 1,000 times that. The last rate runs with clipping and without it.

At 3e-3 the loss falls to 4.394. At 3e-1 it jumps to 19.425 at step 3, then stalls near 5.9 and stays there. At 3 it reaches 171.355 on step 2 and never recovers. Clipping does not save that run. Adam divides each gradient by its own running size, so scaling the gradient down barely changes the step. The learning rate sets the step size, so clipping is no protection against a bad one.

Break it: a loss spike at step 100

At step 100 we feed a batch of uniform random tokens. The loss really jumps. Does the detector fire?

It does. But our first detector did not, and the reason is worth knowing. That version kept an exponential moving average of the mean and variance. On the same run, during development, it printed step 100 loss 10.586 running mean 6.237 std 1.157 spike False. That output is not in results/, because the old code is gone. The variance still remembered the fast fall from 8.3 early in training. So the threshold, mean plus six standard deviations, was 6.237 + 6 × 1.157, which is 13.2. That is above the spike.

The current version uses the median and the MAD of the last 50 steps. The window forgets the early fall, and one outlier cannot move either statistic. The printed spread is 1.4826 times the MAD, which makes it comparable with a standard deviation. The threshold at step 100 is 5.660 + 6 × 0.153, about 6.6.

Break it: a corrupt checkpoint

We cut the newest checkpoint in half, which is what a crash during a non-atomic write can leave behind, and then resume.

A plain torch.load gives failed finding central directory, which does not tell you what to do next. The checksum finds the damage before loading. The run falls back to step 10, trains forward and writes a new step 20 checkpoint. The validation loss at step 20 is 6.6114, the same as before the damage, so the fallback lost only time.

Out of memory needs one more idea. When a step fails, we free memory, split each micro-batch in two and retry. The token-weighted rule from step 9 makes this safe, because the split step has the same gradient.

To cause a real failure on the CPU, the script caps the process memory at 1,024 MiB above its current use. Then it asks for one micro-batch of 128 sequences.

The step succeeds at 16 micro-batches of 8 sequences. All 32,768 tokens were used, so this is still the same global batch.

Read the listing and this output together. step_with_oom_retry defaults to max_splits=3, which stops at 8 micro-batches. The demo passes max_splits=5 to reach 16, because at 8 the CPU cap still fails. With the default, this batch of 128 would raise instead of recovering. The test uses a fake out-of-memory error raised before any backward pass. So the path where a real failure leaves partial gradients is exercised only by this demo.

The same demo ran on a GPU. With the process capped at 1 GiB of GPU memory, a real CUDA out-of-memory error was recovered with 8 micro-batches of 16. Every one of the 32,768 tokens was used.

Test

Each guard has a test. The OOM test asserts the micro-batch counts go 1, 2, 4 and that the update matches.

The last failure is a process that dies. torchrun --max-restarts 1 restarts the whole group, and the same train call finds the newest checkpoint.

Rank 1 dies at step 15. Rank 0 sees the broken connection and fails too, so torchrun starts attempt 1 with both ranks. Both load the newest checkpoint, from step 10, repeat five steps and finish at step 30. The demo shows that the run recovers. It does not compare the final weights with an unbroken run. Step 14 made that comparison in one process.

Break it: the restart that could not connect

Our first version of this demo did not recover. The crash and the restart both happened, and then gloo logged connectFullMesh failed and the whole job exited with code 1. The cause is in how torchrun restarts. With its default static rendezvous, attempt 1 reuses the same key-value store, so the new rank 1 read the address that the dead rank 0 had published.

The fix is the PrefixStore branch of init_distributed in step 17. Each attempt writes its keys under its own prefix, so no rank can read an old address. To debug a hang or a refused connection after a restart, first ask where each rank learned its peers’ addresses. This was measured on gloo. A restart on NCCL has not yet been measured.

Checkpoint

  • You can cause each failure with one command, and you know what its output means.
  • All tests in the guards group pass.

Key insights and nuances

  • Read utilisation next to tokens cut. At L = 128, padding shows 99.6% utilisation and discards 37.3% of all tokens. Step 5
  • EOS matters more as a stop signal than as a tokenizer boundary. Only 2 of 1,999 real neighbouring pairs tokenize differently when joined. Step 4
  • Best-fit packing depends on how L relates to your documents. Its utilisation is 78.6% at L = 256 and 95.1% at L = 512 on the same corpus. Step 5
  • Packed data hides the mean-of-means bug. The error is at float32 noise until target counts differ, then it reaches 8.25e-03. Step 9
  • A wrong resume can look like an improvement. The weights-only restart reports a lower training loss. It replays batches the model has already seen, and it also restarts warmup and the Adam moments. Step 14
  • Exact resume is a testable claim. The stopped and restarted run matches the straight run with a gap of exactly 0, on a CPU and on one H100. Other GPUs and multi-GPU runs have not been measured. Step 14
  • The optimiser is twice the model. That is why the two Adam moments are the first thing ZeRO shards. Step 7 and step 18
  • An MFU from a measured peak is for comparing runs on one machine. It is not comparable with a value computed from a datasheet. Step 16
  • Equal shares make DDP equal to one batch. Packing and an equal-share sampler are what keep a plain average correct. Step 17
  • A guard needs testing as well. Our first spike detector missed a jump to 10.586, because its variance still held the early fall in loss. A median over a short window catches it. Step 19
  • More workers can be slower. On memory-mapped tokens, one process gave 1,910 batches per second and two workers gave 718. Step 6
  • bf16 is not automatically faster. On a CPU that emulates it, a step takes about 11 times as long, with a loss gap of only 0.0010. Step 10
  • Saved tensors are not peak memory. Activation checkpointing cut saved tensors to 0.18 times, and process peak growth to only 0.70 times. Step 12
  • The same architecture can train differently. TinyLLM ends at 2.2611 and HF Llama at 2.6135. Scaling the residual projections at init brings Llama to 2.2529, on one seed, which is consistent with the start being the cause. Step 15
  • An independent implementation checks the step. Our train_step and Hugging Face Trainer, given the same optimiser, schedule and loss, end 20 steps with a weight gap of exactly 0. It does not cover the loader or the guards. Step 15

    Hint

    Count samples consumed in the shared permutation, across all ranks, instead of batches on one rank.

  4. Make recovery automaticMedium TrainingDiverged stops the run today. Catch it in the trainer, reload the newest valid checkpoint, halve the learning rate and continue. Test it with the NaN hook from break_it.py, and record the rollback in the log. Decide what the config check should do, since the LR has now changed.
  5. Let the gains decayEasy Move the RMSNorm gains into the decay group. Log the mean gain during training, and compare the final validation loss with the normal run. Use a larger weight_decay to make any effect easier to see.
