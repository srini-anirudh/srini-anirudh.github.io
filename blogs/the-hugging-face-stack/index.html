The plan

We know how to train a model in raw PyTorch. What does the Hugging Face stack do for us, and how do we check that it does it correctly?

The stack is easy to use and hard to see into. One call to Trainer(...).train() makes dozens of choices. If you cannot name those choices, you cannot debug them.

So every step below follows one rule. We write the thing the library does, run both versions, and compare the numbers. When they agree, we know what the library does. When they disagree, we have found a choice we did not know about.

Two small models carry the post. The first is SmolLM2-135M, a real 134.5 M parameter checkpoint, small enough to run on a CPU. The second is a tiny random Llama with 106,816 parameters, which trains in seconds. Both are LlamaForCausalLM, so they run the same code.

The task is synthetic arithmetic, for example "What is 49 - 97?". The right answer is always known, so labels and rewards never need a judge.

Clone the repo once. Every command below runs from its root.

Nuance

Hugging Face APIs change between major versions. This code runs on transformers 5.22, datasets 5.1, accelerate 1.15, peft 0.21, trl 1.17 and torch 2.15. Some details below are specific to transformers 5: configs are dataclasses, rope_theta moved into rope_parameters, and apply_chat_template(tokenize=True) returns a BatchEncoding. The ideas carry over. Check the exact names against your version.

Every output here came from an AMD EPYC 7R13 CPU limited to 8 threads, with no GPU. The Accelerate comparison in step 9 uses 1 thread per process. Steps 10 and 11 also show one GPU run each, on one NVIDIA H100 80GB HBM3 (torch 2.15.0, CUDA 13.2), always labelled and kept apart from the CPU numbers. Most outputs are shapes and equalities, which do not depend on hardware. Timings do. Each timing is a single run on a busy shared machine, with the load average above 70 and no variance estimate. Read them as rough guides only, and do not read a ranking into small gaps.

Step 01

Read the config, and let the Auto classes pick a model

GoalSee that a small JSON file decides every tensor shape, and follow how from_pretrained finds the right class.

A checkpoint has two parts: a description of the architecture and the weights. Transformers keeps them apart. The description is config.json, which is 905 bytes for SmolLM2. The weights are model.safetensors, which is 538 MB in float32.

That split pays off in three ways. You can read an architecture without downloading its weights. You can build the same architecture with new weights. You can catch a shape mismatch before any bytes move.

AutoConfig downloads only the JSON and returns a LlamaConfig. config_fields is a small helper that prints the fields we care about. The next line shows the dispatch: the string model_type indexes a table of class names.

Dispatch has three stages. config.json holds "model_type": "llama". AutoConfig maps that string to LlamaConfig. Then each Auto model class holds its own table from config class to model class. That is why the same config gives a different class for each Auto class.

Same config and same input (B = 2, T = 7, vocabulary 512, D = 64, 3 labels)
Auto classTop fieldShapeMeaning
AutoModellast_hidden_state(2, 7, 64)One vector per token. No head.
AutoModelForCausalLMlogits(2, 7, 512)One score per vocabulary entry, per token.
AutoModelForSequenceClassificationlogits(2, 3)One score per class, per sequence.

Insight

AutoModel and AutoModelForCausalLM report the same 106,816 parameters, even though one has a head. The head is tied to the input embedding, so it adds no new tensor. The classification head does add one: 64 × 3 = 192 parameters, which gives the 107,008 above. When you count parameters by hand, check tie_word_embeddings first.

The config fields are enough to compute the whole parameter count. Try it below. The two presets reproduce the real counts from the output above, which confirms the formula.

Test

Compare the formula with the library on your own config. Change one field in tiny_llama_config, build the model, and check that count_parameters equals the figure.

Step 02

Turn text into tensors with a tokenizer

GoalInspect input_ids and attention_mask, and find each special-token default that can surprise you.

A tokenizer maps text to integer IDs and back. It also owns the rules for padding and truncation, and those rules decide what a batch looks like.

The Ġ in Ġbackward stands for a leading space. The space belongs to the token, so "backward" at the start of a sentence would be a different ID from " backward" in the middle.

The table in the output holds three things worth checking on any new checkpoint.

  • BOS. This tokenizer adds no BOS automatically. The first ID is 504, the token "The". Many other tokenizers do add one.
  • PAD. The base checkpoint has no pad token. The Instruct checkpoint of the same model uses <|im_end|>, so its pad token equals its EOS token. We will pay for that in step 6.
  • Padding side. It decides whether real tokens sit at the end or the start of the row. The attention mask follows them. Training can use either. Generation needs the left, as step 10 shows.
A batch of two texts with padding (B = 2, N = 6)
TensorShapeMeaning
input_ids(B, N)Token IDs. N is the longest row in the batch.
attention_mask(B, N)1 on real tokens and 0 on padding.

Added tokens are the last trap. Adding a token grows the tokenizer at once, but it does nothing to the model. The embedding table still has the old number of rows.

Break it

Add the two tokens and run the model before resizing. The new token ID has no row in the embedding table.

The error index out of range in self comes from nn.Embedding, and the message names no token. When you see it, compare len(tokenizer) with config.vocab_size first. resize_token_embeddings fixes both the input table and the tied head, and it updates the config too.

Checkpoint

  • You know the BOS, EOS and PAD tokens of your checkpoint, and whether BOS is added for you.
  • test_encode_decode_round_trip and test_smollm2_tokenizer_adds_no_bos pass.
Step 03

Turn a conversation into token IDs and labels

GoalFollow a list of messages down to the exact tokens the model sees, then keep labels only on what the assistant wrote.

A chat model does not read messages. It reads one long token sequence. A chat template is a small Jinja program, stored with the tokenizer, that turns the message list into that sequence. The reason for training this way is in the theory post.

Theory inTeaching a language model to follow instructions

The template renders plain text first. add_generation_prompt=True stops right after the assistant header, where the model should begin writing. In transformers 5, tokenize=True returns a BatchEncoding and not a list, so our helper asks for a dict and takes input_ids.

Now the labels. In supervised fine-tuning, the model should learn to write the reply. It should not learn to predict the system prompt. So we set every other label to -100, the value cross_entropy skips. The hard part is finding which tokens are the reply.

Read the loop slowly. prefix renders everything before this reply, including the assistant header. through renders everything up to and including the reply. The reply is the tokens between those two lengths.

The while loop trims the newline the template adds after <|im_end|>. The end-of-turn token stays labelled, because the model must learn to stop. The newline is not labelled, because the model never writes it.

The check on the two prefixes matters. Some templates change earlier text when a new message arrives. Prefix diffing would label the wrong tokens there, so the function raises an error and does not guess.

There is a second way to find the reply. A training template can wrap assistant text in {% generation %} markers, and then return_assistant_tokens_mask=True returns the mask directly. Our assistant_labels_by_template does that. The script confirms that both methods give the same labels.

Nuance

The last line above is a conversation with no system message. The template added one by itself: "You are a helpful AI assistant named SmolLM, trained by Hugging Face". Your prompts may hold text you never wrote. Print the rendered text once for each new checkpoint before you train or evaluate on it.

Checkpoint

  • Only two positions carry labels: the reply token and the end-of-turn token.
  • test_two_assistant_mask_methods_agree and test_only_assistant_text_and_end_of_turn_are_labelled pass.
Step 04

Add images with a processor

GoalSee that a VLM processor is a tokenizer plus an image processor, and that the image decides how long the text is.

AutoProcessor bundles a tokenizer with an image processor, and with a video processor when the model has one. Its job is more than two calls side by side. The prompt holds one <image> placeholder. The processor must expand it into exactly as many tokens as the vision encoder will produce.

Its full AutoProcessor also loads a video processor, which needs torchvision, and torchvision is not installed. So the video side is not covered.

Nuance

Prompt length depends on the image. The same prompt takes 875 tokens by default and 80 with do_image_splitting=False. Batch a 640 × 480 image with a 300 × 300 one, and the tile axis pads to 17, so the first image carries 4 empty tiles. The square image gets more tiles because SmolVLM scales each image until its long edge is 2,048 pixels. Measure tokens per image on your data before you pick a batch size. Step 05

Store and transform examples with Datasets

GoalUnderstand why a Dataset is not a list[dict], how the cache decides to skip work, and when to stream.

We start with the data itself. Each row is a sum with a known answer. Synthetic data keeps every later label exact.

Now load it the way any dataset is loaded. load_dataset reads local files too, so the Hub is one source among several.

Your fingerprints will not match the ones printed here. Two runs of this script on the same machine gave different values. Within one run they behave as described below, so compare fingerprints inside one run and not against this page.

Arrow stores data by column, as flat typed arrays. Here that is 74,000 bytes for 2,000 rows, or 37 bytes per row: four 8-byte integers, one character and a 4-byte string offset. The Python list costs 384,184 bytes before counting any integer object.

The table is also memory-mapped. MemoryMappedTable means the bytes stay in a file and the operating system pages them in when needed. Several worker processes can share them, and a dataset can be larger than RAM.

Look at what shuffle did: indices mapping: True. It moved no rows. It wrote a separate list of row numbers and left the table alone.

Next comes tokenizing with map. We use the labels from step 3, drop the old columns, and run it twice.

Insight

A cache hit is not free. The second map computed nothing, yet it took 0.55 s. To build the cache key, Datasets must hash the function, and this function reaches a whole tokenizer. Change anything it reaches and the fingerprint changes, so the cache misses.

scripts/16_side_checks.py times that hash alone, 9 times in each of 3 runs.

The median was 0.46 to 0.52 s across the 3 runs. That suggests the hash is most of the 0.55 s.

The benchmark compares ways of running the same tokenization.

In this run, batching was about 3 times faster. A likely reason is that a fast tokenizer handles a whole batch in one call into Rust, but we did not test that. A second process gained nothing here: 18,596 rows/s against 18,626. This is one run on a busy machine, so a rerun may differ. Starting workers and moving results back has its own cost, and this is a small job, so measure before you raise num_proc. A batched function receives a dict of lists and may also return a different number of rows, as the explode function in the script does.

Streaming

A Dataset needs the whole corpus on disk. Pretraining corpora are often too big for that, so they are read as a stream, a point the theory post covers in How LLMs are pretrained. With streaming=True you get an IterableDataset: it has an order but no length and no random access.

The last two lines show why streaming matters. FineWeb-Edu on the Hub is 3,038 files and 5.84 TB, far more than this tutorial wants on disk. The script reads the first rows of a Hub dataset without a full download.

Step 06

Build a batch with a data collator

GoalWrite the function that turns a list of examples into one batch of tensors, and find a bug in the library default.

A dataset yields one example at a time, with its own length. A model needs a rectangle. The collator is the step between them. It has three jobs: pad to a common length, build the attention mask, and set every label that should not be trained on to -100.

The three torch.full and zeros lines make rectangles of shape (B, N). The loop writes each example over the first n positions. Anything not written keeps its fill value, so padding is decided by position. Keep that in mind for the Break it below.

What a collator returns (B examples, longest length N)
TensorShapeFill valueMeaning
input_ids(B, N)pad_token_idTokens the model reads.
attention_mask(B, N)01 on real positions.
labels(B, N)-100Targets. The model shifts them by one inside the loss.

Break it

Use the library's DataCollatorForLanguageModeling on this tokenizer. It copies input_ids to labels, then runs labels[labels == pad_token_id] = -100. That masks by value. In this checkpoint the pad token is the EOS token, so every real end-of-turn token loses its label.

Nothing crashes. The model never practises stopping, and you notice much later when replies run on. To check any collator, count the real EOS tokens that keep a label. There is no error message for this bug, so the count is the only signal.

The vision collator has the same three jobs, plus one. The processor already pads, so we only build labels. Labels are -100 on padding, on image tokens and on the prompt. Because prompt length depends on the image, we run the processor on the prompts alone and read their real lengths.

Checkpoint

  • All 9 real end-of-turn tokens keep their labels with our collator, and 0 keep them with the library's.
  • test_pad_equal_to_eos_keeps_real_eos_labels and test_library_collator_drops_real_eos_when_pad_is_eos pass.
Step 07

Match a raw loop to Trainer, number by number

GoalWrite a plain PyTorch loop whose loss and gradient norm equal Trainer's at every step, so that every hidden choice has to appear as a line of code.

This is the centre of the post. Trainer is a training loop that someone else wrote. To learn what it does, we write the same loop and require equal numbers. Any choice we miss shows up as a difference.

Theory inInside a training step

Start with the loss. Language models predict the next token, so logits and labels are offset by one. The loss is a sum over tokens, not a mean over a batch. The reason appears in a moment.

Then the optimizer. Trainer puts weight decay on matrices but not on biases or norm weights. If we decayed everything, the runs would drift apart.

Now the loop.

The highlighted lines hold the important decision. Gradient accumulation splits one step into several micro-batches. Each micro-batch has a different number of label tokens. n_tokens counts them across all micro-batches first, so every token has the same weight, whichever micro-batch it landed in.

Here is the same run through Trainer. The arguments are grouped by what they control, which is the useful way to read them. There are many more options, and you rarely need them.

Over 60 steps, the largest loss difference is 1.43e-06, which is float32 rounding when losses near 10 are summed. The gradient norms print as equal.

Break it

Average each micro-batch, then divide by the number of micro-batches. This is what most hand-written loops do. Run train_raw(..., normalize="micro_mean").

Nothing fails. The final loss even looks close, at 1.7021 against 1.7046. The direct effect shows at step 0, where both runs start from the same weights. There the losses differ by 0.012 and the gradient norms by 0.0034, because tokens in a short micro-batch now count for more than tokens in a long one.

After that the runs drift apart. The largest gaps come later, once each: 3.39 in gradient norm at step 30, and 0.116 in loss at step 38. The median gradient-norm gap over the 60 steps is 0.047. These numbers come from results/raw_vs_trainer.json. So a small error at every step turns into a different run. To catch it, compare the two runs step by step from step 0, in loss or in gradient norm. The final loss will not show it.

Nuance

Treat these timings as rough. Here Trainer took about 3 ms more per step than the raw loop, and Accelerate took 2.6 ms less, which is not a plausible real gain. In the 60-step run above, Trainer finished first. Each is a single run at a load average above 70, with no variance estimate, so the order means nothing. No large overhead showed up on this CPU. We have not measured a GPU.

What the raw loop did not have

Equal numbers cover the training step. Trainer also gives you evaluation, checkpoints, callbacks and resume, which our raw loop never had. Callbacks are how each of these reports what it does. Logging, early stopping and tracker integrations all listen to the same events.

A checkpoint holds more than weights. optimizer.pt, scheduler.pt and rng_state.pth are what make resume exact: the run restarted from step 20 in a new Trainer ended with the same weights as a run with no stop. To match that with the raw loop, you would have to save and restore all of them yourself.

Nuance

The held-out loss rises from 6.27 to 6.30 as training continues. This is expected. The data is random tokens, so nothing learned from it carries over to other random tokens. The run exercises the plumbing and says nothing about generalisation.

Test

test_raw_loop_equals_trainer requires equal loss, gradient norm and learning rate at every step. test_resume_from_checkpoint_matches_uninterrupted stops at step 6, resumes in a new Trainer, and requires the same final weights as a run with no stop.

Checkpoint

  • The raw and Trainer curves agree to about 1e-6 at every step.
  • You can name the five choices that make them agree: data order, token-level normalisation, decay groups, schedule and clipping.
Step 08

Change one thing by subclassing Trainer

GoalOverride compute_loss to add a loss term and new metrics, and prove that the override changes nothing when the new term is off.

Often you want the whole of Trainer except one thing. A subclass is the right tool for that. As our example we add z-loss, a small penalty on the squared log of the softmax normaliser. PaLM used it with a weight of 10-4 to stop logits drifting large.

We pop the labels so the model does not compute a loss of its own. Then we compute the summed cross-entropy and the z term, and divide both by num_items_in_batch. Trainer computes that number across the whole accumulated batch, which is the same n_tokens as our raw loop.

The first highlighted line makes one choice explicit. Trainer divides the loss by gradient_accumulation_steps unless it believes the loss is already scaled. When the flag is unset, it decides from the model: a model whose forward accepts **kwargs is assumed to scale its own loss. Ours does, so removing the line changes nothing here. We checked: the gap to the default stays at 9.54e-07. Setting the flag to False makes Trainer divide again, and the first logged loss halves, from 6.24 to 3.12. The documentation asks a subclass that computes its own loss to set the flag, so we set it.

With the weight at zero, the subclass equals the default to 9.54e-07. That is the test that lets us trust the override. Only then do we turn the new term on.

Nuance

The z-loss term shows up in the loss, and we can check it by hand: at step 0, 1e-3 × 6.256² = 0.039, which is the gap between 6.2801 and 6.2409. But mean log Z barely moves in 40 steps: 6.214 against 6.217. A weight this small on a run this short changes the loss we report far more than the logits. This run proves the plumbing. It says nothing about whether z-loss helps.

Step 09

Run the raw loop on several processes with Accelerate

GoalKeep our own loop and hand over only devices and processes. Then check that two processes equal one.

The two libraries are easy to mix up, so state the difference plainly. Trainer is a training-loop abstraction: it owns the loop. Accelerate is an execution abstraction: you keep the loop, and it decides where the tensors live. Trainer itself uses Accelerate underneath.

Theory inThe parallelism playbook

Walk through the changes. prepare moves the model to the device, wraps it in DDP when there are several processes, and gives each process its own shard of the data.

Token counting now needs a network call. Each process only sees its own tokens, so reduce sums the counts across processes. Then comes a factor that looks odd: scale = num_processes / n_tokens. DDP averages gradients across processes, and we want a sum over tokens. Multiplying by the process count cancels that average.

no_sync skips the gradient all-reduce on every micro-batch but the last. An all-reduce sums a tensor across processes and gives every process the result. The gradients stay in local memory until the final one, which saves a round of communication.

Insight

Two CPU processes with batch 4 match one process with batch 8 to 9.54e-07 in loss and 5.96e-08 in gradient norm. So DDP is not an approximation. With correct token weighting and the same global batch, it computes the same gradient, and you can test that on a CPU before you rent a cluster. The scheduler is left unprepared for the same reason: a prepared scheduler steps once per process per optimizer step, which would change the schedule with the process count.

Nuance

This run is CPU with gloo, the PyTorch backend that carries messages between CPU processes. Multi-GPU DDP, FSDP (fully sharded data parallel) and DeepSpeed are not yet measured in this tutorial. The same prepare call is meant to cover them through accelerate launch, but strategies that change how the model is wrapped add their own constraints, such as saving sharded state. The agreement above says nothing about those paths.

Checkpoint

  • Rank 0 and rank 1 both report processes=2.
  • test_accelerate_equals_raw passes, and test_two_processes_equal_one passes under the slow marker.
Step 10

Read model outputs, then write generate() as a loop

GoalLearn the shape of every field a forward pass returns, and reproduce model.generate token for token with a plain loop.

A Transformers forward pass returns a ModelOutput, a dataclass that also behaves like a dict. Empty fields are skipped when you iterate. We ask for everything and print its shape, using one small helper.

The last row shows grouped-query attention from the config: 9 query heads share 3 key-value heads. The cache stores only key-value heads, so its size follows num_key_value_heads. C3 builds this from scratch.

generate() is a loop

Generating has five parts: a forward pass, a KV cache, logits processors, a sampler and a stopping rule. We write them in order. The first version is the simplest: run the whole sequence again at each step.

The cost per step grows with the length, since every step reprocesses the history. A KV cache removes that repeated work. The first forward pass, called prefill, runs the whole prompt and fills the cache. Each later pass, called decode, sends only the newest token.

positions_from_mask needs a word. With left padding, a position ID cannot be the column number, because the real tokens would start at 2. So we count real tokens instead: the mask [0, 0, 1, 1, 1] gives positions [0, 0, 0, 1, 2].

The processors are small. They reshape the last-position logits before sampling. Their theory is in the sampling post, so we only check that ours equal the library's TemperatureLogitsWarper, TopKLogitsWarper and TopPLogitsWarper.

Theory inChoosing the next token

Our loop matches model.generate token for token. Sampling matches as well once both start from the same seed, because torch.multinomial draws from the same random stream. That also confirms that generate uses the processors in the same order as ours.

All three produced the same tokens. The cached loop took 3.79 s and the no-cache loop took 5.39 s. A cache should win, because it does not recompute the history, and the gap should grow with length, because the no-cache cost per step keeps growing. We did not measure longer runs, and this single run on a busy machine does not pin down the ratio.

Our loop also finished ahead of model.generate, at 16.9 against 14.3 tokens/s. We draw no conclusion from that order. There are no repeats, so it may be noise.

We ran the same benchmark once on one NVIDIA H100 80GB HBM3 (torch 2.15.0, CUDA 13.2).

On the H100 the tokens were again identical. The cache helped far less than on the CPU: 29.7 against 26.9 tokens/s. model.generate was the slowest of the three, at 20.3 tokens/s. With batch 1 and a 135 M model, each new token is one small forward pass, so the time likely goes to launching kernels and to Python, not to arithmetic. We did not profile it. This is one run, and a larger batch or model would change the picture.

Break it

Pad on the right when generating. The last position of the shorter row is now padding, and the model predicts the next token from there. The text changes.

Again there is no error from the model. The library logs a warning in this case, but it is easy to lose in a busy log. A batched generation that gives different text from a one-prompt generation is the signature of this bug, so that comparison is the test to run.

Checkpoint

  • greedy, tokens identical: True and sampling with the same seed, tokens identical: True.
  • test_cache_equals_no_cache, test_greedy_equals_generate_with_left_padding, test_sampling_equals_generate_with_same_seed and test_processors_equal_library pass.
Step 11

Wrap a model with PEFT

GoalAdd LoRA adapters, see exactly what became trainable, check PEFT's arithmetic by hand, and merge the result.

PEFT (parameter-efficient fine-tuning) edits a model in place. It replaces chosen linear layers with wrappers that hold a small trainable update, and it freezes everything else. Why a low-rank update is enough is the subject of the theory post.

Theory inHow LoRA changes a model without rewriting it

target_modules matches module names by suffix. That is all PEFT needs to know about your model. manual_lora_forward is the check. It recomputes a wrapped layer from its parts: the frozen output, plus alpha / r times the two small matrices.

Read the output from the top. Only 0.68% of the model is trainable, and 240 tensors carry it: 30 layers, 4 projections, and 2 matrices each. PEFT and our hand-written formula agree exactly at 0.00e+00. With seed 0, training took 180 s for 150 steps on the CPU, at 1.20 s per step. The loss fell from 2.52 to 0.295.

One run could be luck, so a second script repeats it for seeds 0, 1 and 2. The held-out sums stay the same in every run. Only the adapter's starting values and the batch order change.

Exact-match accuracy on 182 held-out sums went from 0.000 to between 0.560 and 0.593, with a mean of 0.573. None of these sums appear in training. Three seeds give a range, not a confidence interval. A repeat of seed 0 gave the same result, down to the adapter's hash, so a fixed seed is reproducible on this machine.

Do not read the whole jump as arithmetic the adapter learned. The 0.000 is mostly a format effect. The base model opens with To add 86 and, and the script cuts each reply at 6 tokens. So the base model fails even on sums it might get right with more room. We did not measure that. After training, the model replies with a bare number.

So a small adapter can change what a model does. It does not make a good calculator: 41% to 44% of the answers are still wrong after this short run.

We repeated the three seeds once on one NVIDIA H100 80GB HBM3 (torch 2.15.0, CUDA 13.2).

On the H100 a step took 0.22 to 0.29 s, against 1.08 to 1.30 s on the CPU. Accuracy and final loss match the CPU runs to the printed digits for each seed. The adapter hashes differ, so the weights agree only up to float rounding.

The adapter file ties to the shapes too: 921,600 × 4 = 3,686,400 bytes of weights, plus a header, gives the 3,717,656 bytes on disk. That is 0.69% of the full model in float32.

An adapter saves only the small matrices. To load it you need the base model too, which is why PeftModel.from_pretrained takes two arguments. merge_and_unload folds the update into W and removes the wrappers. You get a plain LlamaForCausalLM back, with no PEFT dependency at inference.

The merge is not exact. On the CPU, logits moved by up to 1.03e-04 for seed 0, and by 7.82e-05 to 1.03e-04 over the three seeds, so about 1e-4. On the H100 the gaps were 4.72e-05 to 8.20e-05. The likely cause is rounding: the merged path rounds W + 2 B A to float32 once, where the adapter path rounds two terms separately. We did not test that explanation.

Test

Four tests pin this down. test_only_lora_tensors_are_trainable checks what trains. test_fresh_adapter_changes_nothing checks that B starts at zero. test_manual_formula_equals_peft checks the arithmetic. test_merge_preserves_logits checks that merging keeps the logits within 1e-4. That test runs on the tiny model. On SmolLM2, seed 0 on the CPU landed just above that bound, so the bound does not carry over to larger models.

Checkpoint

  • Every trainable name contains lora_.
  • The adapter reloads with no change in logits. Merging moves them by about 1e-4 on SmolLM2 (CPU), and by up to 8.20e-05 on the H100.
Step 12

Learn the data contract of each TRL trainer

GoalSee that TRL trainers are Trainer subclasses told apart by the shape of their data, and run each one for three steps.

TRL (Transformer Reinforcement Learning) holds post-training losses: SFT (supervised fine-tuning), DPO (direct preference optimization), reward models and GRPO (group relative policy optimization). The most useful thing to learn first is the dataset format, because each trainer expects a different one. Our arithmetic rows convert to all of them.

TRL trainers in this tutorial
TrainerDataset columnsWhat the loss needsTheory
SFTTrainermessagesAssistant tokens as labelsSFT

RewardTrainerchosen, rejected, prompt optionalA model with one score per sequencePreferences

The SFT run closes a loop with step 3. assistant_only_loss=True uses the {% generation %} markers we met there, and TRL labels == our assistant_labels_by_prefix: True confirms that the library and our function mark the same tokens.

The DPO number is a check we can do in our head. At step 0 the model equals the reference, so its preference margin is zero, and the loss is -log(sigmoid(0)) = ln 2 = 0.693. The run prints exactly that. RewardTrainer starts close to the same value, 0.69, because a random scorer gives chosen and rejected almost equal scores. It needs a different model class, LlamaForSequenceClassification with one label, and its batch stacks the chosen rows and then the rejected rows. Both losses stay near ln 2 over the three steps, so neither run shows learning.

Nuance

The GRPO run printed a loss of 0.0, a gradient norm of 0.0 and frac_reward_zero_std of 1.0. It ran and learned nothing. The random model never answers correctly, so every completion in a group gets reward 0. GRPO weights each completion by its reward relative to its group, so equal rewards give zero gradient. Before a real RL run, check that the base model sometimes earns a reward. These runs prove the data contract only. C6 trains real models.

Nuance

TRL changes some Trainer defaults. In SFTConfig, gradient_checkpointing and bf16 default to True. Our script sets both to False so that it runs on a CPU. A setting that looks like a standard TrainingArguments field may not have the standard default.

Checkpoint

  • The DPO loss starts at 0.693.
  • test_sft_trainer_labels_equal_ours and test_reward_is_exact pass.

A safetensors file has a simple layout: 8 bytes for the header length, a JSON header, then raw tensor bytes. Nothing is pickled, so loading never runs code. Because the format is this simple, we can read it with the standard library.

The sizes add up exactly: 8 + 30,368 + 538,060,032 = 538,090,408 bytes, the file size above. And 538,060,032 / 4 = 134,515,008, the parameter count from step 1. Each number ties to the others, so nothing is hidden in this file.

Large models are split. max_shard_size writes several files and one index, which maps each tensor name to its file.

Insight

Loading is really two jobs, and the second can wait. The config took 1.6 ms. A skeleton of all 134.5 M parameters took 28 ms, and every parameter sat on the meta device, so no weights were read or stored. Together with the shard index and seek, this is how a loader can place a model across devices before it reads any tensor, one shard at a time. That is what makes loading a model bigger than RAM possible.

Now compare with the same model's repo on the Hub. The script lists its files through the Hub API.

The weights file is 269,060,552 bytes on the Hub, about half of ours, because the checkpoint is stored in bfloat16 and we loaded it as float32. The other extra files come from the original training run or an older tokenizer format. README.md is the model card, and save_pretrained does not write one.

Step 14

Plug our own model into the stack

GoalWrite a config and model class, register them, and get saving, loading, generate, Trainer and PEFT without further work.

So far we have used Llama. Every library above worked because the model follows a contract. Now we write a model of our own that follows it. First the config.

model_type is the string that gets written into config.json. It is what the Auto classes read back. The block itself is a small pre-norm decoder and it is not the point here, so we skip to the plumbing. C3 and C4 build a modern block properly.

Now the top-level class with its head. The whole integration lives in a few lines: the two parent classes, the tied weights map, and a forward that accepts the standard arguments and returns a standard output.

Two details in this listing are easy to miss. GenerationMixin is what gives us generate(); a PreTrainedModel alone no longer has it. And **kwargs in forward is not decoration. Trainer checks for it, and only then passes num_items_in_batch, which is what makes token-weighted accumulation exact.

Break it

The script next saves the model and calls AutoConfig.from_pretrained before register(). The file is fine, but nothing maps the string backward_pass to a class.

You will see this error in any process that loads the model without importing your code first. Call register() at import time of your package.

Insight

A few lines of contract buy the whole stack. The raw loop and Trainer agree to 7.15e-07 on a model that did not exist in the library, generate equals a no-cache greedy loop, and PEFT needed nothing beyond two module names. So a from-scratch model does not need to give up the tooling. The C4 model should join the same way, through the same contract. How much work that takes is not yet measured.

Step 15

Add vision to the custom model

GoalSee the pieces a VLM needs on top of a language model: nested configs, an image token, a processor step, and a forward that mixes the two.

A VLM is a vision encoder feeding a language model. The new code is small, but each piece has to agree with the others. The processor from step 4 has its own half of this contract.

Theory inTeaching language models to see

Nested configs save as nested dicts in one config.json, and each one is rebuilt as its own class. expand_image_tokens does what SmolVLM's processor did in step 4, without the tiles.

Generation has one wrinkle. Images are encoded once, during prefill. After that the KV cache holds what the text attended to, so prepare_inputs_for_generation passes pixel_values only on the first iteration. test_generate_with_cache_matches_full_recompute checks this.

Break it

Pass the text with its single placeholder, before expansion. The encoder makes 16 features, and the text has one slot.

We raise this error ourselves, and that was a deliberate choice. Without the check, masked_scatter takes just as many values as there are slots and ignores the rest, so a mismatch where the text has too few slots would pass silently and leave image features out. Whenever your processor and encoder disagree, you want this line to fail early.

Checkpoint

  • The Auto class returns our VLM after a round trip, and the logits match.
  • test_forward_shapes, test_image_changes_the_prediction, test_misaligned_image_tokens_raise and test_round_trip pass.

The layers compared

Rows are the ways we ran a training loop. Columns are the aspects we measured or built. Read down the agreement column first. The first four rows compute the same thing, so among them the choice is about who owns the code and not about the result. The TRL row is different. Those trainers add new losses, and here we only checked that the SFT labels match ours.

The pattern to notice: across the first four rows, moving down the table does not change the mathematics. It moves one decision at a time between you and the library. That is why equivalence tests are possible at all, and why they are the best way to learn a new layer.

That is the idea behind this whole tutorial. Hugging Face should automate mechanics you already understand, not hide them from you.

Key insights and nuances

  • Trainer can be matched to float precision, and doing so names its choices. Over 60 steps the raw loop stays within 1.43e-06 in loss. That took sequential data, token-level normalisation, decay groups, a linear schedule and clipping. Step 7
  • The most damaging bugs here raise no error. Masking labels by value removes all 9 real end-of-turn labels when pad equals EOS. Averaging micro-batches moves the step-0 loss by 0.012, then the runs drift apart while the final loss barely moves. Right padding changes generated text. Each needs a count or comparison to catch. Step 6, Step 7, Step 10
  • A tied head adds no parameters and no bytes. AutoModel and AutoModelForCausalLM both report 106,816 parameters, and lm_head.weight is not in the file. Step 1, Step 13
  • DDP computes the same gradient as one process. Two CPU processes with batch 4 match one with batch 8 to 9.54e-07 in loss, given correct token weighting. You can test this before you have a cluster. Multi-GPU paths are not yet measured here. Step 9
  • A cache hit still costs the hash. A cached map took 0.55 s. Hashing the mapped function alone took about 0.5 s, which suggests the hash is most of that time. Step 5
  • An image decides the length of the text. The same prompt takes 875 tokens by default and 80 without tile splitting, and the batch tile axis pads to the largest image. Step 4
  • GRPO with equal rewards has zero gradient. The random model earned no reward, so the loss and gradient norm were 0.0. A real run needs a base model that sometimes succeeds. Step 12
  • Timings here are single runs and can flip. Trainer was slower in one benchmark and faster in another, and Accelerate beat the raw loop it wraps. These ran at a load average above 70 with no repeats, so do not build on any such order. Agreement checks are solid, while the overhead numbers are only rough. Step 7
  • A model joins the stack through a small contract. A config with model_type, the right base classes, a standard forward and register() give save, load, generate, Trainer and PEFT. Step 14
