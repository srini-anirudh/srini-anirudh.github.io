The plan

Can an agent that imitates successful runs be taught to handle what those runs never showed it? We build the system that answers this, and measure the answer.

Here is the answer, so you can read the rest with it in mind. Cloning works on the expert's path and breaks one step off it. Plain GRPO with an outcome reward did not fix that in our runs. Over 120 iterations, clean success went from 78% to 80%, perturbed from 13% to 3%, and failures from 21% to 19%. A likely cause: the clone rarely succeeds on the hardest levels, so most groups have no reward variance and there is little to reinforce. We have a probe that fits this, but it is unsaved, and one run below argues against it as the whole story. Two other runs did lift perturbed success: a variant with one on-policy step per iteration on a larger batch, which also changed the learning rate, minibatch and run length (13% to 31%) and filtered BC on the policy's own successes (27%). Every learning result here is a single seed, so read them as leads. The code is the main deliverable, and the runs show how to read it.

The task is small. An agent must find the right config file, change one value, and submit. Five tools are available: list, read, search, edit, submit. The reward is 1 if the final files are correct, and 0 otherwise.

This toy has the same shape as real agent training. There is a task, a stateful world, tool output the model cannot predict, and a verifier. Because it is small, a policy can be trained and scored end to end on a CPU. So we can measure each idea instead of sketching what should happen.

We go from imitating demonstrations to learning from consequences. The derivations live in the theory posts. Here we implement each idea and look at what it does.

Step 01

Build the filesystem environment

Goal A small world with state, five tools and an exact reward, driven entirely by text.

Start with what a task is. A task has some config files, a sentence that says what to change, and the files that a correct agent leaves behind. Each file holds three key = value lines.

The kind field is the difficulty. A direct task names the file. A search task names only the key, so the agent must find the file. A dependent task also hides the value: the agent must look up one key to learn what to write into another.

Now the environment. It has the five methods every RL environment has. Notice the types: strings go in and strings come out. A tiny word-level policy and a pretrained language model can both drive this, with no adapter inside the environment.

Three details matter. reset deep-copies the files, so no episode can leak into the next. step never raises on a bad action: a malformed call becomes the observation error invalid input, because the model has to read that message and react. And reward is a pure function of the final files.

Here are the tools. Only edit and submit change anything.

Before any model exists, we need something that can solve every task. Otherwise a low score could mean the task is impossible. So we write a scripted expert. It is a generator: it yields an action and receives the tool's answer.

Run it across the five curriculum levels.

Test

Tests pin the reward and the budget. An extra edit anywhere must make the reward 0. The expert must solve every level, which proves the tasks are solvable.

Checkpoint

  • demo_env.py prints a successful episode for each level.
  • The expert's step count equals optimal_steps on the clean levels.
Step 02

Record the trajectory as text and as tokens

Goal One sequence that holds the whole episode, with a mask that says which tokens the policy produced.

A trajectory is τ = (s0, a0, r0, ..., sT). We store it two ways. The text view is for reading and for the verifier. The tensor view is for training.

Nuance

Why store ids rather than re-tokenise the text later? With a word tokenizer it makes no difference, and a test confirms that. With a BPE tokenizer, decoding and re-encoding does not always give back the same ids. The log-probabilities in the update would then no longer describe what was sampled. So keep the sampled ids whenever the tokenizer is not this simple.

The tensor layout is one line. Task, then action, then tool output, then the next action. This is one multi-turn conversation.

Look inside the tensors for one level 2 episode.

Step 03

Choose a policy that can learn on this machine

Goal A language-model-shaped policy that is fast enough to train and score many times on a CPU, with an interface a larger LM can fill.

The obvious choice is a pretrained LM with LoRA, as in C6 and C9. So we measure it first. The benchmark runs one GRPO iteration through each candidate: 16 episodes, then one update.

This settles it. One iteration through SmolLM2-135M with LoRA took 33 seconds on the AMD EPYC 7R13 CPU, 8 threads. The tiny policy took 0.43 seconds, about 76 times faster. Our main run has 120 iterations at 12 times this batch size. At the SmolLM2 rate that one run would take about 13 hours, and this post has eight experiments with many runs. So learning curves on a CPU have to come from a small model, and that is what we use. Nothing about the algorithm depends on the size. These timings ran once on a shared machine, so read the ratio, not the absolute numbers.

The policy is a small decoder-only transformer: 686,465 parameters. It reads one token sequence and predicts the next token. It generates an action token by token until <eos>. So everything that follows is the code that would also train a larger LM. Step 16 checks that by swapping one in.

One log-probability helper does the alignment that causes most bugs in this kind of code. out[:, t] scores tokens[:, t], computed from the logits at position t - 1.

Insight

Right-padded batches need no attention mask. With causal attention, position t cannot see padding that comes after the sequence ends, so the logits at real positions are exact. The test test_right_padding_needs_no_mask checks this for our block, and test_tiny_policy_right_padding_contract_matches_llama checks it for Hugging Face Llama. In practice this removes a whole class of padding bugs from the rollout.

Checkpoint

  • Changing a future token leaves earlier logits unchanged (test_causality_future_tokens_do_not_change_past_logits).
  • The checkpoint saves and loads with equal outputs.
Step 04

Clone the expert

Goal Teach the action syntax and the procedure from clean demonstrations, then measure how far that gets.

Behaviour cloning minimises L = −∑t log π(a*t | st). In code, this is cross-entropy with a loss mask. If you did C6, you have written this already. The only change is that the assistant turn is now many turns.

Read the last line carefully. On 300 fresh tasks per suite, the policy succeeds 80% of the time. From perturbed starts it succeeds 14%. With failures injected it succeeds 20%. On long tasks it succeeds 0%. It never saw an error message or an and in a task, and it shows.

This is the cloned policy that the rest of the post starts from. A strong start is not the aim. It knows the action syntax and the procedure, which gives RL something to work with.

Break it

Train a smaller clone, with 4,000 demonstrations and two layers. Then compare its training loss with its score on fresh tasks.

The loss is 0.0004. The larger run above ended at 0.0436, and it scores no worse on fresh tasks. So the loss says little here. The suites do not say why either, so split the clean suite by level, with run_suite from evaluate.py and Episode(level, seed, []) for 300 seeds per level.

Levels 1 and 2 are perfect. Level 3 is at 30%. Print a failing level 3 episode.

The policy found the right file and read it. Then it copied the wrong number. Level 3 needs the value of a second key, read from the file it just opened. One plausible reason is that 4,000 demonstrations are too few to learn that copy, but we looked at one failing episode and did not test it. To debug a score like this, evaluate on fresh tasks, split by difficulty, and read the failing episodes. The training loss would not have told you.

Checkpoint

  • Loss falls below about 0.05, and the clean suite is well above the other three on unseen tasks.
  • test_bc_loss_drops_and_save_load_roundtrip passes.
Step 05

Break the clone with one small mistake

Goal Put the policy one harmless step off the expert's path, and measure what happens.

A cloned policy has seen only the expert's states. The expert never errs. So the moment the policy makes any mistake, or the world behaves differently, it is somewhere it has never been. This is the compounding-error argument from the DAgger paper. We can measure it directly.

Derivation inWhy cloning is not enough

A perturbed start plays k wrong actions before the policy takes over: a search for an unrelated key, a read of a missing file, a malformed call. Each is harmless. The files do not change, and the budget still leaves room to finish. To make "a state no demonstration contains" a number, we abstract each state into its history of action types and outcome types.

One harmless step takes success from 80% to 17%. Three steps take it to 4%. The expert stays at 100% from the same starts, so the task never became harder. Look at the first trajectory. After one correct-looking read, the policy emits edit edit db/dev ttl 30. No demonstration contains that action. It is what a next-token model does outside its data.

Insight

From clean starts, 0% of the policy's decisions fall in states the demonstrations never visited. After a single forced mistake, 95% do. Our 9 abstract states cover 5,000 demonstrations, so a procedure's state space is narrow. That makes the first mistake the expensive one. In practice, measure success from perturbed starts, not only from clean ones. A clean evaluation hides this completely.

Nuance

The abstract signature under-counts novelty. The second trajectory above has a forced search host for the wrong key, and every state it visits has a signature seen in demos. The policy then reads the wrong file and edits with the wrong value. The signature says the state is familiar, while the tokens that matter are not. So treat the unseen rate as a lower bound.

Checkpoint

  • The expert stays at or near 100% at every k. The drop belongs to the policy.
  • The unseen-state rate rises as success falls.
Step 06

Let the policy act in the environment

Goal Generate whole episodes with the current policy, write a slow version first, then make it fast and prove the two agree.

DAgger would ask an expert to label the new states. For agents, that expert rarely exists. So the policy learns from its own consequences instead, and that starts with letting it act. Here is the naive rollout. It handles one episode and one token at a time.

It works. It is also slow, so we profile it.

The naive rollout runs 54.6 episodes per second with 777 forward passes. Batching 64 episodes runs 248.8 per second with 43 forwards. The policy forward takes 94% of the naive run and 91% of the batched run. So the model is the bottleneck, and batching is the fix.

Slow tools change this. At 20 ms per call, 64 episodes take 5.1 seconds with no workers and 0.6 seconds with 32 workers. Real tools can take far longer than 20 ms, in which case a real system spends its time waiting on them.

A GPU only pays off at a large batch for a policy this small. On an NVIDIA H100 80GB HBM3, torch 2.15.0+cu132, batch 64 ran at 147.9 episodes per second, against 223.6 on the CPU rows of the same file, and the GPU figure includes the first CUDA call. At batch 256 the GPU ran at 822.7 episodes per second, against 277.7 on the CPU. Both are single runs from results/bench_rollout_gpu.txt.

Test

Two equivalence tests hold this together. Greedy naive and greedy batched rollouts must give identical tokens. And the log-probabilities recorded during sampling must equal those from a training forward over the finished sequence, which means the GRPO ratio starts at exactly 1.

Break it

Move the shift by one in token_logprobs. Change logits[:, :-1] to logits[:, 1:]. The code still runs and every shape still matches, so nothing crashes during training. Then run the test above.

Each position now scores a token with the logits from the wrong step. The recorded log-probabilities no longer describe what was sampled, so the GRPO ratio does not start at 1, and the update trains on noise. To debug it, print (logp - batch.old_logprobs) at the action positions before any update. On a healthy policy every entry is 0 up to float error. Any larger value points at the alignment.

Step 07

Outcome reward and group-relative advantages

Goal Turn one bit of feedback per episode into a signed signal, with no critic.

We start with the honest reward: 1 if the files are right, 0 otherwise. It cannot be gamed by looking busy. It also says nothing about which action helped. To get a gradient from it, GRPO samples G trajectories for the same task and compares them with each other.

Derivation inGRPO from first principles

Try it. Click a trajectory to change its reward. Notice what happens when every reward is the same.

Insight

Dividing by the std makes rare events loud in both directions. A lone winner gets +2.47. A lone loser gets −2.47, seven times the size of each winner beside it. So one lucky success on a hard task gets +2.47, against +0.35 for each of seven ordinary wins in the group. A flat group gets exactly 0. In practice, log the fraction of flat groups on every iteration. Those rollouts cost time and taught nothing.

Nuance

Group members share the task, but their failure seeds differ. A member can win only because it drew no timeout. So the group's spread mixes the policy's choices with the environment's luck. Dropping the std is the other knob here, and it is one half of what Dr. GRPO changes (the other half removes length normalisation). It keeps the sign and drops the amplification: a lone winner gets +0.875. Set scale_std=False in GRPOConfig to try it. We did not run that comparison in this post.

Test

We compare the implementation against a separate NumPy reference, and pin the properties: advantages sum to zero, a flat group gives zero everywhere, and one winner of eight gets a larger push than each of seven winners of eight.

Checkpoint

  • test_group_relative_matches_numpy_reference and test_group_relative_properties pass.
  • test_zero_variance_batch_produces_zero_policy_gradient passes.
Step 08

Write the GRPO update and train

Goal A clipped surrogate over action tokens of whole episodes, and a first RL run that we read honestly.

The update is the same as in C6, applied to multi-turn sequences. Environment tokens stay out of the loss because of the mask. Everything else is PPO's clip and an optional KL to a reference policy.

The online loop is short. It samples tasks, rolls out G episodes per task, and updates.

Read the eval columns first. Over 120 iterations and 8 minutes, greedy success went clean from 78% to 80%, perturbed from 13% to 3%, failures from 21% to 19%, long from 0% to 0%. So this run did not improve the policy, and perturbed success ended lower. These RL runs evaluate on 150 tasks per suite, so their starting values differ slightly from the 300-task numbers in step 4. The run is a single seed.

The sampled columns tell the same story. Sampled success averaged 0.21 over the first 10 iterations and 0.20 over the last 10, so it did not move. What did move is the shape of the episodes. The share that submitted fell from 0.93 to 0.35 (the same two means), and episodes grew from 4.5 to 7.9 steps. Greedy decoding still picks the cloned behaviour, so the eval columns hide most of this drift.

Why so little learning? We have a likely cause, and a probe that supports part of it. We sampled the cloned policy at temperature 1, as training does, on 800 training seeds at each of the two hardest levels.

On level 4, 159 of 800 episodes succeeded (20%), 586 hit an error, and only 9 of those succeeded. On level 5, 0 of 800 succeeded. A group of eight is flat whenever all its members fail or all succeed, and a flat group gives no gradient. The zero-var column averaged 0.80 over the first 10 iterations and 0.80 over the last 10. Levels 1 and 2, which the clone already solves, add flat groups of the all-win kind, so the probe covers only part of the flat share. The probe is a scratch script and is not saved in results/. A second run of it with another seed, also unsaved, gave 563 errors and 13 recoveries on level 4. Read these counts as roughly 570 and 10. Short 30-iteration checks with a lower learning rate, a KL penalty, the mean-only advantage and temperature 0.7 looked the same, and those are unsaved too.

Insight

Outcome-only GRPO can only reinforce behaviour that the policy already produces by chance, and on the hard levels it rarely does. Flat groups are a likely cause of the flat result, not a proven one. The on-policy run below had the same flat share (0.76 over its last 10 iterations) and still gained on perturbed starts. One untested idea is that trajectory-level advantages push down the submit token in failed episodes, which fits the fall in the submit share. We did not test it. In practice, measure the sampled success rate on each task type before you train. If it is near 0 or near 1, those groups will be flat.

One variant gave a gain on one suite. The default update reuses each batch for two epochs of minibatch steps. After the first step the ratios move away from 1, and the main run had 0.00 to 0.33 of its action tokens per iteration outside the clip range of 0.8 to 1.2. The variant below takes one gradient step per iteration on a batch four times larger, so every update is exactly on-policy. It also changes the learning rate (3e-4 instead of 2e-4), the minibatch size (768 instead of 64) and the length of the run (60 iterations instead of 120). It sees 46,080 episodes in total, against 23,040.

The perturbed suite rose from 13% to 31%. Failures went from 21% to 22%, and clean stayed at 79%. Long stayed at 0%. Perturbed success rose at every evaluation: 15%, 27%, 31%. The clip fraction is 0 on every iteration, as it must be when the old and new policy are the same at the only step. This run took 13 minutes. Sampled success averaged 0.24 over its first 10 iterations and 0.27 over its last 10, with 7.2 steps per episode at the end, so the gain shows only in the greedy perturbed suite. With 150 tasks the standard error of one score is about 3 to 4 points. It is one seed, so treat it as a lead, not a result.

Nuance

This is not a general claim that more epochs hurt. PPO-style reuse works in many settings. We changed five things at once: one epoch instead of two, four times more episodes per iteration, a larger minibatch, a higher learning rate, and half as many iterations. We did not separate them, so we cannot say which one mattered. The sampled episodes in this run also grew long, so the drift from the main run is not gone. Separating the changes is a good exercise.

Checkpoint

  • Compare every greedy suite with its cloned value before you believe a run. Also watch the sampled success and steps columns, because greedy evaluation can hide drift.
  • Read the zero-var column. If it is near 1, the update has no signal. In our main run it averaged 0.78.
Step 09

Trajectory-level or action-level credit

Goal Compare one advantage per episode against one advantage per action, on the long-horizon tasks.

Trajectory-level credit gives every action of an episode the same advantage. A winning episode with a pointless retry rewards the retry. Over many episodes the noise averages out, but it costs samples. The horizon makes this worse.

The alternative is a critic. The value head estimates V(st), the expected final reward from a state. The difference V(st+1) − V(st) then says whether one action helped. GAE blends these one-step differences.

On the evaluation suites the three runs are the same. Failures ended at 22%, 21% and 23%, against 21% at the start, and long stayed at 0% in each. Sampled success stayed low (0.04 to 0.06, 0.06 to 0.05 and 0.05 to 0.05 as 10-iteration means), and 0.84 to 0.90 of the groups were flat at the end. There was little signal for any credit scheme to divide up.

One difference did show up in the sampled episodes. Under trajectory credit, the share that submitted fell from 1.00 to 0.14 and episodes grew from 3.1 to 10.3 steps. Under action credit they stayed at 3.9 steps with 1.00 submitted. That is one seed, and the greedy suites do not show it. The comparison is also not clean: action credit adds a critic, and it whitens advantages over the whole batch instead of within each group, so it can give a gradient on a group where every reward is equal. Treat the difference as a lead, not as evidence about credit alone.

Step 10

Shape the reward, then hack it on purpose

Goal Add intermediate rewards, see what a reasonable-looking one pays for, and fix it with a form that cannot be farmed.

Outcome rewards are sparse. Step 8 showed how sparse: most groups were flat. So people add milestones. Here are two ways, in the same file.

Think about what the highest-scoring behaviour is. Solving a level 2 task gives 0.2 + 0.2 + 1 = 1.4. Looping read until the step budget ends gives 0.2 per call, for nine calls: 1.8. The reward prefers not solving the task. We wrote it that way on purpose, in one line.

Check that claim against the real reward functions. These episodes were played in the real environment. Choose a behaviour and a reward.

The result is consistent with a hack, and one seed cannot separate it from noise. Averaged over 10 iterations, the activity run's return went from 1.18 to 1.16, so the trainer saw no gain. Its sampled success went from 0.68 to 0.61, and the outcome run's from 0.68 to 0.64. Single iterations swing between 0.44 and 0.82, so these two are not clearly different. The submit share fell from 1.00 to 0.89 and episodes grew from 3.5 to 4.2 steps, against 0.96 and 3.8 under the outcome reward. Clean greedy success ended at 73%, against 81% with the outcome reward and 78% at the start. That gap is about 1.6 standard errors.

The figure's box shows one trace. It is the sampled episode with the most steps, picked by us, so it is the clearest case and not a typical one. Before training, the policy copied a wrong value and submitted. After training, on the same task, it read the same file again and again until the budget ran out. That earns more under this reward than an honest failure, so it is the behaviour a hack would produce. One trace does not show that the reward caused it.

The potential run ended at exactly the outcome run's numbers: 81% clean and 0.64 sampled success over the last 10 iterations. That is what the Insight below predicts.

The fix is potential-based shaping (Ng, Harada and Russell, 1999). Define Φ(s), the fraction of milestones reached. Pay Φ(st+1) − Φ(st) on each step. Credit arrives early, but losing progress costs what gaining it paid.

Insight

Because Φ is 0 at both ends, the shaping terms cancel over an episode: the total shaped return equals the outcome, exactly. test_potential_shaping_telescopes_to_the_outcome checks this. So under trajectory-level GRPO, which only sees the sum, potential shaping changes nothing at all. It only matters with action-level credit, where the per-step rewards enter GAE. In practice, adding milestone potentials to a pure GRPO trainer is a no-op, and you should not expect it to help.

Checkpoint

  • test_activity_reward_pays_more_for_looping_than_for_solving passes.
  • Always log true success beside the training reward. The gap between them is your reward-hack alarm.
Step 11

Exploration: temperature, group size, diverse starts

Goal Measure what controls how much signal each batch of rollouts carries.

GRPO learns only from groups that disagree. So exploration has a concrete meaning here: it is whatever makes a group's outcomes differ. We measure the fraction of zero-variance groups, because each one is a batch of rollouts that taught nothing.

Three levers are in the code, and we measure two of them. Sampling temperature changes how often a group tries something else. Group size G changes how likely one member is to get lucky. The task sampler supplies diverse tasks and diverse starts, which we did not vary here. The temperature must also enter the training log-probabilities, otherwise the ratio no longer describes the sampling distribution. token_logprobs takes it as an argument for that reason.

Averaged over each run, the share of flat groups was 0.82 at T=0.5, 0.78 at T=1.0, 0.70 at T=1.5. Temperature changed that share a little and changed nothing that mattered. Every temperature ended with perturbed success at 1% to 3%, down from 13%, and failures at 19% to 21%. A likely reason is that almost no sampled episode on the hard levels succeeds, so wider sampling finds nothing new to reinforce. We did not test that. We also did not vary the starts: every run here uses the same task sampler, with half of the level 1 to 3 starts perturbed.

Group size shows one exception. At 192 rollouts per iteration, the flat share averaged 0.90 at G=2, 0.84 at G=4, 0.78 at G=8, 0.68 at G=16. G = 2, 4 and 8 ended with perturbed success at 0%, 5% and 1%. G = 16, with only 12 tasks per iteration, ended at 19%. It is one seed on 150 tasks, and the other three runs went the opposite way, so we do not read it as a result. The G = 8 row is the same run as the T = 1.0 row, so it appears twice.

Checkpoint

  • Your training log reports zero-variance groups on every iteration.
Step 12

Curriculum: from one tool to long horizons

Goal Raise the difficulty only when the policy is ready, and compare that against starting at the hardest level.

The chance that a sampled episode solves a long task shrinks with its length. Below some point, whole groups fail and the update has nothing to work on. A curriculum keeps the policy where it sometimes succeeds. The ladder has five rungs.

None of the three schedules improved anything. On the long suite they ended at 0%, 0% and 0%.

  • Hardest first trained on level 5 only. Not one group ever had a win (the flat share was 1.00 over the last 10 iterations), so the policy never changed. Every suite stayed at its start value.
  • The final mix is levels 2 to 5 at weights 1, 1, 2 and 4, so half of the tasks are level 5. It lowered clean success from 78% to 47%. Its submit share fell from 0.62 to 0.22 and episodes grew to 9.3 steps. That is the same mix the staged run was meant to reach, and a heavy level 5 share gives the update mostly failed episodes.
  • The staged curriculum never left stage 1 of 3. Its first stage is level 3 with half the starts perturbed, and its sampled success averaged 0.16 over the last 10 iterations, far below the 0.75 threshold. So it trained on that one mix for 100 iterations, and the promotion rule never fired.

So this run does not test whether a curriculum helps. It shows that the ladder only works if the first rung can be climbed. Here the cloned policy fails half-perturbed level 3 starts too often to get past the threshold. A lower threshold, or a first stage with clean starts only, would be the next thing to try.

Checkpoint

  • test_curriculum_advances_on_threshold_only passes.
Step 13

Failure recovery: timeouts, bad input, missing files

Goal Inject the ways tools really fail, reward finishing anyway, and look at the behaviour that appears.

Real tools can hang, crash, reject arguments and point at files that have moved. Demonstrations from clean runs show none of this. So we inject the failures in the environment, seeded per episode. A failed call costs a step, so a policy that panics runs out of budget.

No recovery bonus is in the reward. The outcome reward already pays only the episodes that finish. So the question is whether GRPO learns recovery from that signal alone. Here is the failure suite for the cloned policy and for the policy from the main run.

GRPO did not learn recovery from the outcome reward alone. The cloned policy recovered in 5 of 218 episodes that hit an error. The policy from the main run recovered in 0 of 221. Look at the rows. The clone's few recoveries all came after error invalid input or error internal. It never recovered from a timeout (0 of 63) or a no such file error (0 of 133). Two cautions on the rows. The no such file row includes stale paths from the task and also files that the policy mistyped itself, and an episode with several errors is counted in several rows. The scripted expert recovers from all four, because it retries and searches. The clone never saw it do so, since the demonstrations come from clean levels.

Nuance

The failure-injection code works: the expert solves every level 4 task in the tests. What is missing is a policy that ever produces a recovery to reinforce. The fix in practice is to put recoveries into the data first, for example by cloning the expert on level 4, or with the DAgger exercise below. Then RL has something to sharpen.

Checkpoint

  • test_failure_injection_is_seeded_and_recoverable passes.
  • Count recoveries per failure type, not only overall success. Our run shows why: the totals hide which errors never get fixed.
Step 14

Offline against online

Goal Give offline and online training the same data budget and the same gradient steps, and compare.

Online rollouts cost environment time. Offline training reuses a stored dataset for free. So the question is what the free data can teach. We collect one buffer from the cloned policy, with as many trajectories as the online run will generate. Then we train two offline methods on it.

The simplest method scored highest. Filtered BC trains only on the 25% of stored episodes that succeeded, and it took perturbed from 13% to 27% and failures from 21% to 25%. With 150 tasks per suite one score has a standard error of about 3 to 4 points, and this is one seed. Online GRPO with the default update ended at 2% perturbed, and offline GRPO at 5%.

The clip fraction shows why offline GRPO struggles. Online it stayed between 0.01 and 0.33. Offline it climbed from 0.17 to about 0.45: the clip fraction counts tokens whose ratio is more than 0.2 away from 1, so nearly half the tokens are far from the stored policy. Tokens past the bound in the direction their advantage favours stop giving gradient, which is some of them and not all. The stored log-probabilities describe the cloned policy, and the policy has moved away from it.

Insight

Filtered BC and the on-policy GRPO run of step 8 ended within a few points of each other on perturbed starts, at 27% and 31%, each from one seed. The two runs also differ in learning rate, epochs and rollouts, so the comparison is loose. Filtered BC trains only on the policy's own successes, without advantages, ratios or a critic. GRPO also pushes failures down. We did not test why the two land close. In practice, filtered BC on your own rollouts is cheap, so run it early as a baseline.

Checkpoint

  • Offline GRPO's clip_frac climbs through the run. Online stays lower, because its old log-probs refresh every iteration.
Step 15

The full agent-RL system

Goal Separate the loop into the components a production trainer has, each timed and each testable.

The loop in step 8 mixes everything together. A real system separates it, because each part scales and fails differently. Task sampler, env workers, rollouts, trajectory store, verifier, batches, update, new policy.

Why grade the state, not the claimThe agent evaluation playbook

The output above is the last of three runs, each 10 iterations. This tests the pipeline and its timings, not training: the policy did not improve over these iterations either. Sampled success went from 0.28 to 0.12, and after the run the evaluation read 78% clean and 1% perturbed. With instant tools the whole run took 40 seconds. With 20 ms per tool call and no workers it took 318 seconds. With 32 workers it took 45 seconds. The verifier checked 1920 trajectories in each run and found 0 mismatches. The store holds 5.9 MB for 1920 episodes.

Test

A run must survive a restart. test_resume_gives_the_same_weights_as_an_uninterrupted_run saves after one iteration, loads into a fresh system, and checks that the next iteration gives the same weights as an uninterrupted run. Weights, optimizer, sampler state, and both random generators are in the checkpoint. Forget any one of them and this test fails.

Checkpoint

  • Verifier mismatches stay at 0 on a healthy run. Any other value means a bug or a tampered record.
  • test_system_iteration_runs_all_stages and the resume test pass.
Step 16

Drop in a Hugging Face model

Goal Prove the interfaces hold: the same rollout and update code runs a trusted Llama and SmolLM2 with LoRA.

All of this claims to be LM-shaped. Here is the check. An adapter gives any causal LM the same PolicyOutput, and nothing in rollout.py, grpo.py or online.py changes.

Both tests pass with no change to rollout.py, grpo.py or online.py. The benchmark in step 3 used the same adapter: a 832,001-parameter Llama took 0.66 seconds per iteration, against 0.43 seconds for our 686,465-parameter policy. SmolLM2 with LoRA has 1,843,777 trainable parameters out of 136,358,785. It ran one iteration in that benchmark.

The test that loads SmolLM2-135M-Instruct with LoRA and plays one episode needs the model in your cache. Run with -m network, it gave: 1 passed (AMD EPYC 7R13 CPU, 8 threads).

We did not train SmolLM2 here. On a CPU the experiments in this post would take days, as step 3 showed. So this step shows that the interfaces hold. It says nothing about how well a real LM learns this task. Exercise 5 is that experiment.

One GPU number puts this in scale. On an NVIDIA H100 80GB HBM3, torch 2.15.0+cu132, the same SmolLM2 iteration from step 3 took 3.5 seconds, against 33 seconds on the CPU. That is results/bench_policy_gpu.txt, measured once. Training SmolLM2 on this task on a GPU has not been measured.

Nuance

Marker tokens need care with a pretrained LM. A token added for this task gets a random output row in lm_head, and LoRA does not train lm_head. So the policy would have no trained way to end an action. HFCodec reuses the chat delimiters the model already knows for this reason. We reasoned this from the code. We did not run the failing version.

Checkpoint

  • test_tiny_llama_drops_in_for_rollout_and_update passes offline.
  • test_smollm_lora_runs_one_episode passes with the model in your cache (marked network).

Key insights and nuances

  • One harmless mistake takes the cloned policy from 80% to 17%, while the expert stays at 100%. A clean evaluation hides this completely. Step 5.
  • If the recorded log-probabilities do not equal a training forward over the same tokens, the GRPO ratio does not start at 1. An off-by-one here does not crash. Only the test catches it. Step 6.
  • Dividing by the group std makes a lone winner +2.47 and a lone loser −2.47, against ±0.35 for the majority. A flat group gives exactly 0, so log how many groups are flat. Step 7.
  • Outcome-only GRPO with the default update did not improve held-out success here. A likely cause is that most groups were flat: the clone recovered in 9 of 586 sampled level 4 episodes that hit an error and solved 0 of 800 on level 5. The probe is unsaved, flat groups also come from all-win groups, and the on-policy run had the same flat share and still gained, so the cause is not established. Step 8.
  • Greedy evaluation can hide drift. Sampled episodes got longer and submitted less often while the greedy suites barely moved. Log the submit share and the episode length as well as success. Step 8.
  • A variant with one on-policy step per iteration on a larger batch (and a higher learning rate, a larger minibatch and half the iterations) lifted perturbed success from 13% to 31% on one seed. We did not separate the changes. Step 8.
  • With under 10% sampled success and 84 to 90% of groups flat, trajectory and action credit scored the same on the suites. The comparison also changes normalisation and adds a critic, so it says little about credit alone. Step 9.
  • The activity run is consistent with a hack but not separated from noise. Its submit share fell to 0.89 and clean success ended at 73%, against 81% with the outcome reward, about 1.6 standard errors apart. One seed. Step 10.
  • Potential-based shaping cancels over an episode, so under trajectory-level GRPO it changes nothing. Our potential run matched the outcome run exactly. Step 10.
  • A curriculum only helps if its first rung can be climbed. Ours never left stage 1, so it tested nothing. Log which stage the run is in. Step 12.
  • Filtered BC on the clone's own successes (27% perturbed) ended within a few points of the on-policy run (31%) and above every other GRPO variant, with far less machinery and no new rollouts. Both are single seeds, and the two runs differ in several settings. It is a cheap baseline to run early. Step 14.
  • The verifier replays recorded actions on a fresh copy of the task and decides the reward from the files. The rollout worker's claim never counts. Step 15.
