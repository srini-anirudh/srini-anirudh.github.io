The plan

Can an agent that imitates successful runs be taught to handle what those runs never showed it? We build the system that answers this, and measure the answer.

The task is small. An agent must find the right config file, change one value, and submit. Five tools are available: list, read, search, edit, submit. The reward is 1 if the final files are correct, and 0 otherwise.

This toy has the same shape as real agent training. There is a task, a stateful world, tool output the model cannot predict, and a verifier. Because it is small, a policy can go through a real learning curve in minutes on a laptop. So every number in this post is measured. None is a sketch of what should happen.

We go from imitating demonstrations to learning from consequences. The derivations live in the theory posts. Here we implement each idea and look at what it does.

Step 01

Build the filesystem environment

Goal A small world with state, five tools and an exact reward, driven entirely by text.

Start with what a task is. A task has some config files, a sentence that says what to change, and the files that a correct agent leaves behind. Each file holds three key = value lines.

The kind field is the difficulty. A direct task names the file. A search task names only the key, so the agent must find the file. A dependent task also hides the value: the agent must look up one key to learn what to write into another.

Now the environment. It has the five methods every RL environment has. Notice the types: strings go in and strings come out. A tiny word-level policy and a pretrained language model can both drive this, with no adapter inside the environment.

Three details matter. reset deep-copies the files, so no episode can leak into the next. step never raises on a bad action: a malformed call becomes the observation error invalid input, because the model has to read that message and react. And reward is a pure function of the final files.

Here are the tools. Only edit and submit change anything.

Before any model exists, we need something that can solve every task. Otherwise a low score could mean the task is impossible. So we write a scripted expert. It is a generator: it yields an action and receives the tool's answer.

Run it across the five curriculum levels.

Test

Tests pin the reward and the budget. An extra edit anywhere must make the reward 0. The expert must solve every level, which proves the tasks are solvable.

Checkpoint

  • demo_env.py prints a successful episode for each level.
  • The expert's step count equals optimal_steps on the clean levels.
Step 02

Record the trajectory as text and as tokens

Goal One sequence that holds the whole episode, with a mask that says which tokens the policy produced.

A trajectory is τ = (s0, a0, r0, ..., sT). We store it two ways. The text view is for reading and for the verifier. The tensor view is for training.

Nuance

Why store ids rather than re-tokenise the text later? With a word tokenizer it makes no difference, and a test confirms that. With a BPE tokenizer, decoding and re-encoding does not always give back the same ids. The log-probabilities in the update would then no longer describe what was sampled. Serving stacks that train agents keep token ids for this reason.

The tensor layout is one line. Task, then action, then tool output, then the next action. This is one multi-turn conversation.

Look inside the tensors for one level 2 episode.

Step 03

Choose a policy that can learn on this machine

Goal A language-model-shaped policy that is fast enough to produce real learning curves, with an interface a larger LM can fill.

The obvious choice is a pretrained LM with LoRA, as in C6 and C9. So we measure it first. The benchmark runs one GRPO iteration through each candidate: 16 episodes, then one update.

This settles it. One iteration through SmolLM2-135M with LoRA took 298 seconds on the CPU. The tiny policy took 1.1 seconds. Our main run has 120 iterations at 12 times this batch size. At the SmolLM2 rate that would take days on this laptop, while other jobs compete for it. A real learning curve on this machine has to come from a small model, so that is what we use. Nothing about the algorithm depends on the size. The machine was busy during these timings, so read the ratio, not the absolute numbers.

The policy is a small decoder-only transformer: 686,465 parameters. It reads one token sequence and predicts the next token. It generates an action token by token until <eos>. So everything that follows is the code that would also train a larger LM. Step 16 proves that by swapping one in.

One log-probability helper does the alignment that causes most bugs in this kind of code. out[:, t] scores tokens[:, t], computed from the logits at position t - 1.

Insight

Right-padded batches need no attention mask. With causal attention, position t cannot see padding that comes after the sequence ends, so the logits at real positions are exact. The test test_right_padding_needs_no_mask checks this for our block, and test_tiny_policy_right_padding_contract_matches_llama checks it for Hugging Face Llama. In practice this removes a whole class of padding bugs from the rollout.

Checkpoint

  • Changing a future token leaves earlier logits unchanged (test_causality_future_tokens_do_not_change_past_logits).
  • The checkpoint saves and loads with equal outputs.
Step 04

Clone the expert

Goal Teach the action syntax and the procedure from clean demonstrations, then measure how far that gets.

Behaviour cloning minimises L = −∑t log π(a*t | st). In code, this is cross-entropy with a loss mask. If you did C6, you have written this already. The only change is that the assistant turn is now many turns.

Read the last line carefully. On clean tasks the policy succeeds 80% of the time. The misses are mostly level 3, where the value must be looked up in a read result. From perturbed starts it succeeds 14%. With failures injected it succeeds 20%. On long tasks it succeeds 0%. It never saw an error message or an and in a task, and it shows.

This is the cloned policy that the rest of the post starts from. A strong start is not the aim. It knows the action syntax and the procedure, which gives RL something to work with.

Break it

Train on 4,000 demonstrations instead of 30,000. An early version of this tutorial did that, with two layers. The training loss reached 0.0016, and yet greedy success on level 3 was far below levels 1 and 2. The failing episodes all look like this:

The policy read the right file and copied the wrong value. Level 3 needs a two-hop lookup: find the key from the task in the observation, then take the number after it. With few demonstrations the model memorises instead. A small loss on the training set says little here, so always evaluate on fresh tasks.

Checkpoint

  • Loss falls below 0.01 and the clean suite passes on unseen tasks.
  • test_bc_loss_drops_and_save_load_roundtrip passes.
Step 05

Break the clone with one small mistake

Goal Put the policy one harmless step off the expert's path, and measure what happens.

A cloned policy has seen only the expert's states. The expert never errs. So the moment the policy makes any mistake, or the world behaves differently, it is somewhere it has never been. This is the compounding-error argument from the DAgger paper. We can measure it directly.

Derivation inWhy cloning is not enough

A perturbed start plays k wrong actions before the policy takes over: a search for an unrelated key, a read of a missing file, a malformed call. Each is harmless. The files do not change, and the budget still leaves room to finish. To make "a state no demonstration contains" a number, we abstract each state into its history of action types and outcome types.

One harmless step takes success from 80% to 18%. Three steps take it to 4%. The expert stays at 100% from the same starts, so the task never became harder. Look at the first trajectory: after one correct-looking read, the policy emits edit edit db/dev ttl 30. That is not a syntax it was taught. It is what a next-token model does outside its data.

Insight

Only 0% of decisions are in unseen states from clean starts, and 95% after a single forced mistake. The state space of a procedure is narrow, and demonstrations cover exactly one path through it. So the first mistake is the expensive one. In practice, measure success from perturbed starts, not only from clean ones. A clean evaluation hides this completely.

Nuance

The abstract signature under-counts novelty. The second trajectory printed by the script has a forced search for the wrong key, and every state it visits has a signature seen in demos. The policy then reads the wrong file and edits with the wrong value. The signature says the state is familiar, while the tokens that matter are not. So treat the unseen rate as a lower bound.

Checkpoint

  • The expert stays at or near 100% at every k. The drop belongs to the policy.
  • The unseen-state rate rises as success falls.

Step 07

Outcome reward and group-relative advantages

Goal Turn one bit of feedback per episode into a signed signal, with no critic.

We start with the honest reward: 1 if the files are right, 0 otherwise. It cannot be gamed by looking busy. It also says nothing about which action helped. To get a gradient from it, GRPO samples G trajectories for the same task and compares them with each other.

Step 08

Write the GRPO update and train

Goal A clipped surrogate over action tokens of whole episodes, and the first real RL learning curve.

The update is the same as in C6, applied to multi-turn sequences. Environment tokens stay out of the loss because of the mask. Everything else is PPO's clip and an optional KL to a reference policy.

The online loop is short. It samples tasks, rolls out G episodes per task, and updates.

Step 09

Trajectory-level or action-level credit

Goal Compare one advantage per episode against one advantage per action, on the long-horizon tasks.

Trajectory-level credit gives every action of an episode the same advantage. A winning episode with a pointless retry rewards the retry. Over many episodes the noise averages out, but it costs samples. The horizon makes this worse.

The alternative is a critic. The value head estimates V(st), the expected final reward from a state. The difference V(st+1) − V(st) then says whether one action helped. GAE blends these one-step differences.

Step 10

Shape the reward, then hack it on purpose

Goal Add intermediate rewards, watch a reasonable-looking one destroy the policy, and fix it with a form that cannot be farmed.

Outcome rewards are sparse. So people add milestones. Here are two ways, in the same file.

Think about what the highest-scoring behaviour is. Solving a level 2 task gives 0.2 + 0.2 + 1 = 1.4. Looping read until the step budget ends gives 0.2 per call, for nine calls: 1.8. The reward prefers not solving the task. We wrote that, by accident, in one line.

(pending)

The fix is potential-based shaping (Ng, Harada and Russell, 1999). Define Φ(s), the fraction of milestones reached. Pay Φ(st+1) − Φ(st) on each step. Credit arrives early, but losing progress costs what gaining it paid.

Insight

Because Φ is 0 at both ends, the shaping terms cancel over an episode: the total shaped return equals the outcome, exactly. test_potential_shaping_telescopes_to_the_outcome checks this. So under trajectory-level GRPO, which only sees the sum, potential shaping changes nothing at all. It only matters with action-level credit, where the per-step rewards enter GAE. In practice, adding milestone potentials to a pure GRPO trainer is a no-op, and you should not expect it to help.

Checkpoint

  • test_activity_reward_pays_more_for_looping_than_for_solving passes.
  • Always log true success beside the training reward. The gap between them is your reward-hack alarm.
Step 11

Exploration: temperature, group size, diverse starts

Goal Measure what controls how much signal each batch of rollouts carries.

GRPO learns only from groups that disagree. So exploration has a concrete meaning here: it is whatever makes a group's outcomes differ. We measure the fraction of zero-variance groups, because each one is a batch of rollouts that taught nothing.

Three levers are in the code. Sampling temperature changes how often a group tries something else. Group size G changes how likely one member is to get lucky. The task sampler supplies diverse tasks and diverse starts. The temperature must also enter the training log-probabilities, otherwise the ratio no longer describes the sampling distribution. token_logprobs takes it as an argument for that reason.

Step 12

Curriculum: from one tool to long horizons

Goal Raise the difficulty only when the policy is ready, and compare that against starting at the hardest level.

The chance that a sampled episode solves a long task shrinks with its length. Below some point, whole groups fail and the update has nothing to work on. A curriculum keeps the policy where it sometimes succeeds. The ladder has five rungs.

Step 13

Failure recovery: timeouts, bad input, missing files

Goal Inject the ways tools really fail, reward finishing anyway, and look at the behaviour that appears.

Real tools hang, crash, reject arguments and point at files that have moved. Demonstrations from clean runs show none of this. So we inject the failures in the environment, seeded per episode. A failed call costs a step, so a policy that panics runs out of budget.

No recovery bonus is needed. The outcome reward already pays only the episodes that finish. Here is the same task before and after training.

Step 14

Offline against online

Goal Give offline and online training the same data budget and the same gradient steps, and compare.

Online rollouts cost environment time. Offline training reuses a stored dataset for free. So the question is what the free data can teach. We collect one buffer from the cloned policy, with as many trajectories as the online run will generate. Then we train two offline methods on it.

Step 15

The full agent-RL system

Goal Separate the loop into the components a production trainer has, each timed and each testable.

The loop in step 8 mixes everything together. A real system separates it, because each part scales and fails differently. Task sampler, env workers, rollouts, trajectory store, verifier, batches, update, new policy.

Exercises

  1. Add DAggerMedium The scripted expert plans from the task text, so it can label any state. Roll out the cloned policy, ask the expert for the right action at each state it visits, add those to the demos and retrain. Compare the perturbed suite with step 5.
    Hint

    Replay the actions so far through a fresh ScriptedExpert plan to get the next expert action. Forced steps stay masked.

  2. Try anchor-state groupsHard Trajectory groups compare whole episodes. Group-in-Group Policy Optimization compares actions taken from the same abstract state. Use signature from shift.py as the anchor, and compare against group_relative on the long suite.
    Hint

    Compute one advantage per step: the step's return minus the mean return of all steps with the same signature in the batch.

  3. Add demotion and an automatic curriculumMedium Give Curriculum a demotion rule, then replace the fixed stages with sampling weights set by each level's zero-variance rate. Does it beat the fixed ladder?
  4. Break the verifierEasy Change FileSystemEnv.reward so it checks only the first subtask. Find which suite and which log line reveals the change first, and how long the policy takes to exploit it on level 5.
  5. Train the real LMHard Use smollm_policy and the same train_online. First do SFT on the expert demos with LoRA, then GRPO. On a CUDA GPU, measure how many iterations per hour you get, and note what you had to change. Keep a small G at first.

You should be able to go from a tensor operation all the way to a foundation model and agent system without any layer feeling magical. The GRPO loss in this post is a log_softmax and a gather from C1. It runs over a model from C4, with a loss mask from C6, in a loop whose environment has the shape of the harness from C10. There is no separate magic for the last step.

The toy here is small on purpose. To scale it, swap the environment for a sandboxed repository, swap the policy for a real LM, and put the rollouts on an inference server. The theory posts cover what changes then.
