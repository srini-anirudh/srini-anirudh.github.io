The plan

The agent from C10 forgets everything when its process ends. What do we have to add so that it uses what it learned yesterday, and how do we prove that the memory is the reason it does better?

Start with the failure. The script below runs one task twice. The model is scripted: it deploys to whatever region it can find in its system prompt, so the output shows exactly what reached the prompt.

The first run has no memory, so the region is missing. The second run has one extra call, attach_memory. A 15-token memory section appears, and the agent deploys to the right region. It also uses us-east-2, the value the user moved to, and not the older eu-west-1. By the end of this post you will have built every piece of that.

The theory post explains why memory has three separate problems: writing, managing and reading. We do not repeat that here. We implement each one and look at what it does.

Why context is not memoryMemory is more than context

We build in twelve steps, one per item in the plan. Steps 1 to 4 create the stores. Step 5 decides what enters them. Steps 6 and 7 find things in them.

Step 8 turns many episodes into one rule. Steps 9 and 10 fit the result into a token budget. Step 11 connects it to the harness. Step 12 asks whether any of it helps.

Nuance

Most evaluation numbers in this post come from a deterministic rule-based reader, not a language model. That is a deliberate choice: the reader is perfect given the right lines, so any error it makes is an error in what the context contained. It also means these numbers are not the accuracy a real model would reach. So step 12 ends with two separate measurements on a real model. They are small, and we state their limits there.

Clone the repo once. Every command below runs from its root.

Step 01

Count tokens and hold the task state

Goal A unit of account for every later decision, and an explicit record of what the agent is doing right now.

Every choice in this package costs tokens: what to store, what to retrieve, what to drop. So we need a counter first. It does not need to be exact. It needs to be fast, deterministic and close enough.

The regex splits text into words and punctuation marks. Long words cost more, because a real tokenizer splits them too. lru_cache matters because the packer in step 9 asks for the same costs many times.

How close is it? The benchmark compares it with the real SmolLM2 tokenizer on three samples: English, a build log and Python code.

The estimate is exact on the English sample and undercounts the log by about 22%, 29 tokens against 37. So keep some headroom when the budget is a hard model limit, or pass the exact HFTokenCounter instead.

Now the first memory. Working memory is what the agent is doing right now. It is not retrieved. It is always in context, it is small, and the agent rewrites it as the task moves.

Why not leave this to the transcript? Because in step 10 we throw parts of the transcript away. If the goal and the plan live only in old turns, compaction deletes them. As a separate object, they survive.

Step 02

Log what happened as episodes

Goal A cheap, append-only record of every action, in the form (s, a, o, r, t).

An episode is one transition: what the agent was trying to do, what it did, what came back, whether that was good, and when. Writing one needs no judgement, so nothing is lost at this stage. It is too verbose to put in context directly. Later steps read from it.

Step 03

Extract stable facts from what people say

Goal Turn a sentence into a structured claim about a subject and an attribute.

Episodes record events. Semantic memory records what is true. The difference matters. "The owner for atlas is priya" should become one fact that later statements can correct, not one more line in a log.

So a fact has a key: (subject, attribute). An extractor turns text into a Claim. The store then judges the claim and may turn it into a Fact. Keeping those two types separate is what makes step 4 possible.

Real systems ask a model to do the extraction. We provide both. The rule extractor keeps the benchmark exact, because every extraction error can be seen and repeated. The model extractor shows the part that is easy to forget: nothing a model returns is trusted until every field is checked.

Two details carry a lot of weight in the rule extractor. A hedge ("I think", "might") lowers confidence from 0.9 to 0.4. A transient phrase ("just for today") sets the scope to session. Steps 4 and 5 use both signals.

Nuance

The rule extractor understands the phrasings of our benchmark world and very little else. That is why the benchmark in step 12 shows near-perfect extraction. In a real system extraction would be the weakest link, and you should expect it to miss facts and invent some. The model extractor is tested only on canned replies. Its accuracy on real text is not measured here.

Test

  • A malformed model reply costs one memory and never corrupts the store.
Step 04

Update and supersede instead of appending forever

Goal Every claim causes exactly one operation, and an old value stops being returned without being erased.

The naive store appends every statement. After a move it holds both eu-west-1 and us-east-2, and the model has to guess which is current. We make the store decide instead.

Read decide from the top. A retraction deletes if there is something to delete. A new key adds. The same value updates. A different value supersedes, unless the claim is much weaker than the current fact.

The margin test is the interesting line. With a margin of 0.3, a confident statement (0.9) can replace another confident statement (0.9). A hedge (0.4) cannot, since 0.4 + 0.3 is below 0.9.

The update branch combines confidence with a noisy-OR: 1 - (1 - a)(1 - b). Two independent statements at 0.9 give 0.99. That is why the history below shows conf=0.99 for a fact that was stated twice.

Superseding closes the old fact by setting valid_to. It stays in the store, so we can ask what we believed at any time:

Note conflicts logged: []. The hedge at t = 4.2 never reached the store. The writer from the next step stopped it first, because its confidence was too low. So a weak claim has two lines of defence, and the margin is the second one.

Break it

Turn each protection off. First, make the store append-only. Second, remove the writer and open the margin to 1.0, so any claim can replace any fact.

Neither failure raises an error. The symptom is a stale or wrong value in the retrieved memories, so the agent acts confidently on bad data. To debug it, print the retrieved block and the fact history for that key. If two versions are both active, the store is not superseding. If the wrong value is active, look at the margin.

Insight

Stale facts hurt more than missing ones here. In the ablation in step 12, the append-only store still recalls every stated fact (1.00), but accuracy on updated facts falls from 1.00 to 0.66. The information is present and retrieved, and it misleads the reader anyway. So a memory system needs an edit path as much as it needs a write path.

This operation set is close to the one Mem0 describes (ADD, UPDATE, DELETE, NOOP). The validity intervals are the idea Zep uses on the edges of its temporal knowledge graph. Our version adds a separate SUPERSEDE so that the operation log says whether a value was refreshed or replaced.

Checkpoint

  • as_of(t=2.0) returns eu-west-1 and as_of(t=4.5) returns us-east-2.
  • test_add_update_supersede_delete_noop passes.
Step 05

Decide what deserves to be stored

Goal Implement should_store(event) from novelty, stability, importance, confidence and scope.

If we store everything, retrieval has to dig through chit-chat and log lines, and some of what it finds will be wrong. The write decision is the first place to protect quality.

Take the signals one at a time.

  • Novelty is 1 minus the highest cosine with anything stored. Do we know this already?
  • Stability starts from the source and moves with word patterns. "always" and "uses" raise it. Timestamps, process ids and "for today" lower it.
  • Importance rises for explicit requests ("remember", "must"), for error names, and for a large reward in either direction.
  • Confidence depends on the source (user 0.9, tool 0.85, model 0.5), and a hedge halves it.
  • Scope is session for transient statements, which never persist.
Shapes in the novelty check (M stored memories, D = 512)
TensorShapeMeaning
v(D)The new event, as a unit vector.
self.stored(M, D)One unit vector per stored memory.
self.stored @ v(M)Cosine with each stored memory.
noveltyscalar1 minus the largest cosine, clamped at 0.

The demo runs twelve events through the writer. Step through them and watch which gate stops each one.

The event at t = 3.1 is worth a look. It repeats a known fact in different words. Novelty is low at 0.30 but above the gate of 0.1, so it passes. The fact store then sees the same value and records an UPDATE, not a second fact.

The method also has an edits_memory flag. A retraction that repeats an earlier retraction word for word would otherwise fail the novelty gate. An edit is never "not novel", because what matters is what it would change in the store.

Nuance

The weights (0.4, 0.35, 0.25) and the threshold (0.5) are hand-set, not learned. The tests pin the decisions on a fixed set of events, so a change in weights is visible, but no search shows that these values are the best ones. Generative Agents asks a model to rate importance instead. You can do the same here through importance_fn.

Insight

The writer does its most visible work on things that are true today and false tomorrow. Remove the writer and the scope gate. Then accuracy on the day after a "just for today" override falls from 1.00 to 0.00. Stated facts barely change, from 1.00 to 0.98. So scope is a separate decision from recall: a store can recall everything and still be wrong the next day.

Checkpoint

  • Chit-chat, log lines and hedges are rejected, each with its own reason.
  • The tests below pass.
Step 06

Find memories with embeddings and a vector index

Goal Text to unit vector, then the most similar memories, first with a loop and then with one matrix multiplication (a matmul).

We need text as vectors so that similar text is close. Start with the simplest embedder that works: signed feature hashing. It uses no model and no download, and it gives the same bits on every machine.

The result is a sparse vector. Every word and word pair lands in one of 512 buckets, and the row is normalised to length 1. Now cosine similarity is a plain dot product.

Now the index. The reference version is a Python list and a loop. It exists to be obviously correct.

The fast version stores all the vectors as one matrix. Search is one matmul and a top-k. Removed rows get minus infinity, so they can never win.

Shapes in one search
TensorShapeMeaning
matrix(C, D)Capacity C doubles when full. Real example: (1024, 512).
alive(C)Boolean. False for removed or unused rows.
queries(Q, D)One unit vector per query.
sims(Q, size)Cosine with every used slot. Dead slots are minus infinity.
top.indices(Q, k)The slots of the k best memories, best first.

Here is what is inside those tensors for one real query. The query has five non-zero buckets out of 512, so nothing else in the matrix can affect the result.

Now measure. The benchmark uses random unit vectors with D = 384, the size of the MiniLM embeddings. MiniLM here is all-MiniLM-L6-v2, a small pretrained sentence-embedding model. It maps a sentence to 384 numbers, so that sentences with similar meaning land close together.

On this CPU the matrix version is more than 150 times faster than the loop. It also scales far enough: a million memories take 155 ms and 1.5 GB. This is still exact search, so it returns the true top-k.

Nuance

Hashing matches shared words, not meaning. The paraphrase check shows the gap, measured on the same CPU. The rule-reader evaluation in step 12 uses the hashing embedder, and that world repeats its own words, so it does not reward MiniLM. The real-model run at the end of step 12 does. Swapping is one argument: AgentMemory(embedder=TransformerEmbedder()).

Break it

Replace blake2b with Python's hash(). Python salts string hashes per process, so a memory stored in one run lands in a different bucket in the next. Nothing crashes, and tests in one process still pass.

The symptom is a memory that was fine yesterday and now retrieves nothing, with cosines near zero. If retrieval quality falls after a restart, encode one known string in two processes and compare the vectors.

Checkpoint

  • Both indexes return the same ids and the same scores to within 1e-5.
  • A removed slot is reused and never returned.
Step 07

Rank by meaning, age and importance together

Goal Implement S = α Ssemantic + β Srecency + γ Simportance, and see what each term contributes.

Similarity alone has no sense of time or stakes. A rule the user asked us to remember should not lose to a slightly better word match from last month. So we score on three terms, as Generative Agents does.

Shapes in hybrid scoring (N live memories)
TensorShapeMeaning
sims(size)Cosine for each used slot.
semantic(N)The live rows, with negatives clamped to 0.
recency(N)0.5age / half_life, in (0, 1].
importance(N)Written by the writer, in [0, 1].
comp(N, 3)The three terms for each memory.
total(N)comp @ w, the final score.

The clamp is there because of what Figure 4 showed: a hash collision can make a cosine slightly negative, and that should not count as evidence against a memory.

Insight

On our benchmark, semantic-only retrieval ties the full hybrid at 0.999, and recency-only falls to 0.686. So the recency and importance terms earn nothing here. The reason is step 4: superseding already removes stale values, and that is the problem recency is usually asked to solve. Fix staleness at write time, and retrieval has less to do.

Nuance

That tie is a statement about this benchmark, not a proof that recency is useless. Our world has exact keys and no important memory that lacks shared words with the query. Also, Generative Agents min-max normalises each term over the candidates. We keep fixed ranges instead, so a score means the same thing from one query to the next, at the cost of letting a narrow-range term matter less.

The search also takes an optional mmr_lambda. Maximal marginal relevance trades score against similarity to what is already picked, so three near-duplicates do not fill the memory section. It is tested but off by default, and the evaluation does not use it.

Checkpoint

  • Each weight alone ranks by its own term.
  • The score equals the weighted sum of its terms to within 1e-5.
Step 08

Turn many episodes into one rule

Goal Procedural memory: find repeated recoveries in the episode log and promote them to a reusable, templated strategy.

A fact says what is true. A procedure says what to do. It is written with a placeholder, so one procedure covers every project, and it keeps its own track record.

Where do procedures come from? We look for one pattern inside each trajectory: an action fails with an error, some fix runs, and the same action then succeeds.

The inner loop is worth reading slowly. Start at a failed step and scan forward for the same action. If the retry succeeded, the steps in between are the fix. If the retry failed, stop: this span did not recover, and the next failed step starts its own span. That is how clear_cache drops out in the trajectories below. It sits in a span whose retry failed.

The last condition in consolidate needs at least two different entities. Two episodes on the same project could be a quirk of that project. Two projects are evidence of a pattern.

Insight

Whether a rule helps depends on the reader. In step 12, a reader that can generalise from another project's episode gets nothing from rules: 2.92 steps with them and 2.92 without. A literal reader gains: 3.59 steps fall to 3.30, and on new projects 6.13 fall to 5.37. Consolidation pays when the model would not make the analogy by itself.

Checkpoint

  • Two episodes on one project give no rule. A third on another project gives one with support == 3.
  • proc.instantiate("dune") returns ["login dune"].
Step 09

Pack the context under a token budget

Goal Given a budget B, choose among instructions, task state, memories, recent events and tool observations.

We now have more candidate text than fits. Choosing is a knapsack problem: each block has a cost and a value, and we want the most value under B. The packer uses the standard greedy approximation, by value per token, with three additions.

The three passes do this:

  1. Required blocks first. Instructions, task state and the request go in, or the packer raises BudgetError.
  2. Section floors. Recent events reserve 60 tokens, so memories cannot push them out completely.
  3. Global greedy. Everything else is taken in order of value per token. A block that does not fit may be compressed into the space left, if at least 16 tokens remain.

The output is rendered in a fixed section order, with stable text first. It is not sorted by score. That keeps the prompt prefix steady, which helps with prompt caching, and it is the order a reader expects.

Move the budget and watch the packer choose. Every state below is a real run of pack on the same 14 candidates, from scripts/export_figures.py.

Insight

Set B to 160 in Figure 7. The agent has just failed with AuthError, and the rule that fixes it is the most valuable memory (value 0.996). It is dropped anyway, while cobalt owner: chen, a fact about another project, is kept.

The rule costs 35 tokens, so its density is 0.028 against 0.068. Greedy by density prefers many small blocks. If one long block is essential, give it a higher value or a section floor. It returns in compressed form at B = 200 and whole at B = 224.

Break it

The baseline most people start with is to send the transcript and cut the oldest text when it overflows. truncate_left implements exactly that, and it removes the instructions first. The second failure below is the opposite one: a budget too small for what is required. We make that case loud, because a silent failure would send the model a prompt with no instructions.

Read the last two lines again. In this world, at a small budget, truncating the transcript is worse than having no memory at all. Step 12 confirms this with 20 seeds and explains why.

The packer is cheap: 1.67 ms for 1,000 candidate blocks under B = 800 on the AMD EPYC 7R13 CPU. It adds nothing you would notice next to a model call.

Nuance

The pipeline demo below shows a rule for MigrationError while the agent is failing with AuthError. The default query is the request text, "Deploy atlas.", so retrieval cannot know about the error. This is why the evaluation passes query=f"deploy {project} {err}". What you search for matters as much as how you score it.

Checkpoint

  • The packed total never exceeds B, on 40 random block sets.
  • Required blocks are always present, or BudgetError is raised.
Step 10

Compress before you drop

Goal Four strategies with four different ways of losing information: extraction, summarisation, dropping and ordering.

Dropping is the budgeter's job, and you have seen it. The other three make a block cheaper first. Start with a long tool log, the most common thing in an agent's context. A test run prints hundreds of passing lines and one failure.

Only extraction keeps the assertion. Head-and-tail, the default for tool output, keeps the summary line but loses the reason. The figure shows which lines each strategy keeps. Lower the budget to see where each one fails.

Old conversation turns need a different treatment. We summarise them without a model: facts first, using the extractor from step 3, then the first sentence of anything else.

Look at what the summary did. The deploy region went from eu-west-1 to us-east-2, and only the latest value is kept. The hedge about the owner is gone, and the confident statement stayed. A plain "keep the first sentence" summary would have kept both regions.

It also kept "Thanks, that helps." and the lunch plan, because the 45-token cap allowed them. An extractive summary has no sense of what matters beyond its pattern list. model_summary asks a model instead, and it enforces the length cap after the call, because models do not reliably follow length instructions.

Read across the table: the strategies that lose more also fail more quietly. Prefer them in the order that keeps failures visible.

Nuance

edge_order follows the finding of Liu et al. that long-context models use the start and end of a prompt better than the middle. We implement and test the permutation, but our evaluation cannot measure its benefit. A rule reader reads every line equally well, so order cannot change its answers. Treat this one as a reasoned default, not a result from this post.

Checkpoint

  • extract_lines keeps AssertionError: 401 != 200 inside a 60-token budget.
  • A summary keeps the latest value of a fact and drops a retracted one.
Step 11

Assemble the memory and attach it to the harness

Goal One object for write, manage and read, connected to the C10 agent without editing its loop.

AgentMemory holds the stores and connects the pieces. Here is the write path.

The order is deliberate. We extract first because the writer needs to know whether this event would edit a stored fact. A session-scoped statement goes to session_notes, where it stays in context today and disappears at end_session. An event with no structured claim, such as "never deploy on Fridays", is kept as a plain note.

The read path gathers every kind of block and hands them to the packer.

C10 was built with two extension points, and memory uses them for reading and writing. EventLog.subscribe delivers every event to a hook, which is how memory writes. Agent(context=builder) lets us replace what each model call sees, which is how memory reads. attach_memory also does two things outside those points. It sets agent.builder on an agent that already exists, and it wraps agent.run. Neither change touches the loop.

Harness design inInside an AI agent harness

Four details here come from real failures in agent code.

  • Turns stay whole. group_turns keeps a tool result with the assistant call it answers. Dropping one without the other gives a message list that chat APIs reject.
  • The first and newest turns are required. Without them the model does not know what it was asked or what just happened.
  • The budget pays for the tool schemas. They are subtracted before packing. A budget that forgets them will overflow on the real call. A budget smaller than the schemas fails in attach_memory, not on the first model call.
  • A run that stops early is still summarised. A run that ends at max_steps or on a model error logs no Final event, so attach_memory wraps agent.run and closes the task when it returns. The loop inside is untouched.

Run the demo again and read it with the code in mind.

The breakdown shows one new section, memory, at 15 tokens. Everything else is unchanged. The hook wrote one episode, and end_task turned it into a retrievable memory. The agent loop did not change, which is the test of whether the harness was designed well.

Nuance

We found nine defects in this integration before the code was frozen. The offline tests passed with every one of them. Four examples:

  • attach_memory silently dropped the agent's repo section.
  • Every run shared one task id, which merged trajectories.
  • A successful call scored reward 0, so attach_memory could never produce a rule.
  • A fresh process reused ids after AgentMemory.load and overwrote stored memories.

Each now has a test. The lesson stands: test the integration by running it, with a restart, and read what reached the model.

Test

The integration tests run the real C10 Agent. One requires the same step counts from the harness loop and the standalone evaluation loop when memory is not involved. Another checks that no tool call is ever separated from its result.

Step 12

Test whether memory causes the improvement

Goal Compare no memory, full transcript, retrieved memory and oracle memory, with one thing changed at a time.

A demo that works proves little. We want a causal claim: this memory, and nothing else, changed the result. So we hold everything fixed except what the context contains. Same reader, same tasks, same seeds, one intervention.

Evaluation design inThe agent evaluation playbook

Two worlds

We test on two synthetic worlds, because synthetic worlds have exact gold answers.

The facts world is a team talking to its assistant over 8 sessions. Facts are stated, changed, hedged about, overridden for one day and retracted, with chit-chat and long logs in between. Every probe has a gold answer, computed by replaying the ground truth. Each probe kind tests one skill. A test checks that gold never depends on a later turn.

The deploy world is 24 deploy tasks over 8 sessions. Most projects have one quirk: the deploy fails with an error until a specific fix has run in this session. The error text does not name the fix. An agent with no memory must explore. The limit is 8 tool calls per task.

Run it. The rules are deterministic, so you will get the same accuracy as these tables. The saved run took 99 seconds on an AMD EPYC 7R13 CPU with 8 threads. A second run on the same machine gave identical tables.

At B = 1024, retrieved memory reaches 0.999 where the truncated transcript reaches 0.749, at 582 tokens against 970. At B = 4096 the whole transcript fits and reaches 1.000, but it costs 2,292 tokens where retrieved memory stays at 582. So when the budget is generous, memory saves cost. When it is tight, memory saves accuracy.

Accuracy by probe kind shows where each condition fails.

Nuance

No memory scores 1.00 on deleted and unseen, because the right answer is "unknown" and it knows nothing. Its overall 0.578 is therefore flattered by these easy probes. Look at stated (0.31) for its real recall. When you score a memory system, always check whether an empty memory gets credit for abstaining.

Is the memory the cause?

Now the ablations. Each row changes one thing in the retrieved condition. The last row is the causal check: the stores and retrieval stay the same, but every stored value is replaced with a wrong one.

If the reader were not really using its memory, corrupting the values would change nothing. Accuracy falls from 0.999 to 0.585, and stated falls from 1.00 to 0.31. It does not fall to zero, because deleted and unseen probes still score, and today's turns are still in the context. The test suite asserts this drop, so a refactor that disconnects memory from the reader fails.

The other rows rank what matters on this benchmark. Recency-only retrieval costs the most after corruption (0.686). Removing the writer and the margin gives 0.879. Removing the writer and the scope gate gives 0.946. Append-only gives 0.966. Dropping recency and importance from the score changes nothing.

The deploy world, and a warning about success rates

Insight

At B = 256 the truncated transcript succeeds on 0.394 of tasks, far below no memory at 0.713. One deploy log costs about 130 tokens, so at this budget the transcript holds little more than the newest log. The agent loses earlier steps of its own task and repeats them. The no-memory condition uses the budgeter, which keeps the short step lines and compresses the log. More history, handled badly, is worse than none. The transcript does not catch up with no memory until B = 1024.

Here is one complete run of the retrieved condition. Step through the tasks and watch the fixes move before the first deploy.

Two tasks in that trace stand out: granite and fjord. Both have MigrationError, both run to 8 calls, and both end on migrate with no calls left to retry. The exploration order tries migrate last, so a first encounter needs 9 calls. With a limit of 8 the attempt can never finish, and an unfinished attempt is never a recovery, so it teaches nothing to other projects.

That raises a question about the success metric. The evaluation sweeps the limit:

With one more call, both conditions reach 1.000. So the success gap of 0.713 against 0.929 comes from the step limit we chose. The evaluation script does not count failures by kind, so we wrote this short loop. It runs the same deploy evaluation at limits 8 and 9:

Every failure at a limit of 8 is a MigrationError task, and none remain at 9. So those tasks needed exactly one more call. At a limit of 9 the effect that remains is efficiency: 5.84 calls against 2.77.

Nuance

Steps is the better measure here, because it does not depend on an arbitrary limit. Figure 9 lists deploy steps before deploy success for this reason. If you report success, report the limit beside it.

Consolidation, and the real harness

With the analogy reader, rules change nothing. With the literal reader they do, as step 8 described. Oracle memory stays well ahead of both at 1.93 steps. Its episode line lets the agent run the fix before the first deploy, whereas a rule only helps after one failure.

The real run: a real model, a restart and a file on disk

A rule reader cannot be distracted, and it cannot lose a fact in a long prompt. So all of the above leaves a question open. Does the memory still work when a real model reads it?

scripts/run_real_agent.py answers that with nothing scripted. A local Qwen2.5-0.5B-Instruct drives the real harness.Agent from C10, and the deploy tool writes to a real file. The run has two phases, in two operating system processes.

  • Teach. The user states the deploy region of 16 projects, one run per statement. Then the user moves 8 of them. The memory hook writes through the harness event log. The store is saved to disk, and the process exits.
  • Deploy. A new process starts. For each project, a fresh agent is told "Deploy atlas to its usual region." We read the outcome back from the file, not from what the model says. The model decodes greedily: at each step it takes the most likely next token, so the same prompt always gives the same reply. All conditions use one prompt wording.

The model, the task and the tool are the same in all four conditions. The prompt differs, and so does the builder that makes it. No memory, full transcript and oracle use the harness's plain ContextBuilder, with text added to the instructions. Retrieved uses our budgeted builder, through attach_memory. So a difference in outcome comes from what the prompt holds and how it is laid out. Here is the tool, and the loop over conditions:

This saved run used C10 at source hash d359c7783defad33. C10 has since had a narrow fix in its truncation code, and its hash is now e7a4c5a60910af6d. We reran both real-model runs against the current C10. All 64 outcomes here and the 16 MiniLM outcomes below were identical. Only the seconds per call changed.

Read the rows from the top.

  • No memory: 0 of 16. The model made no tool call at all and repeated the task back. This zero is not 16 wrong guesses. The instructions tell it never to guess a region, so it says nothing about what a model would do without that line.
  • Full transcript: 3 of 16. Every prompt held the right fact. The model still deployed to a wrong region 13 times, at 944 prompt tokens. Only one of those was a stale value: atlas went to the region it had left. The other 12 were different wrong regions.
  • Retrieved: 13 of 16. All 8 moved projects were right, with no stale value, at 350 prompt tokens. The store had already closed the old values, so they were not in these prompts.
  • Oracle: 16 of 16. With one line of memory, the model copied it every time.

Insight

Having the fact in the prompt is not the same as using it. The full transcript holds every statement, so its 16/16 "fact in prompt" is true by construction. For retrieved memory, 16/16 is a measurement: the store put the right line in every prompt. The outcomes are 3 and 13. A rule reader cannot show this kind of gap, because it reads every line perfectly.

Nuance

Do not read these counts as accuracy in general. Here is what limits them.

  • 16 tasks, one small model, one prompt wording. Greedy decoding made a second run give identical outcomes. That shows the model is deterministic, not that the counts are stable.
  • The prompt changed twice before these numbers. A trial on 4 of these 16 projects gave oracle 0 of 4, because oracle used a different header and the model replied "1". So all conditions now share one header. An instruction about what to do when only told a fact was also removed. The trial projects are test tasks, so the prompt was tuned on part of the test set.
  • The retrieved store grows during its condition, so later tasks also see earlier deploys. The other conditions do not.
  • A larger model may do better on the transcript. We did not test one.

Why three retrieved tasks failed

Look at the misses in Figure 11: indigo, meridian and quartz. The right fact was in each prompt, but low in the list, at position 5 or 6 of 6. All of these facts share the words "deploy" and "region". With the hashing embedder, only the project name separates them. So a project that moved recently can outscore the right fact on recency.

The model deployed to the region on the top memory line in all 48 prompts that had a memory list: retrieved with hashing, retrieved with MiniLM, and oracle. With hashing, the right fact came first 12 times, and those 12 deploys were right. Ember is the one success with the fact lower down, and it was luck. Its top line was juniper's region, sa-east-1, which is also ember's region. So we changed one thing, the embedder, and ran the retrieved condition again:

Insight

With MiniLM the right fact came first in all 16 prompts, and every deploy was right. The rule reader could not show this, because it scans every line and order means nothing to it. In this run, the top line decided the outcome. That is 16 tasks, so it is a reason to test your own embedder and not a measured gain you can expect.

The fact probes, read by the real model

The deploy task is one kind of question. To see more kinds, we gave the same model the same fact contexts as the rule reader, at B = 1024. It answers each probe in words, and only the reader changes.

This table is less flattering than the deploy run. Retrieved memory scores 0.592 against 0.542 for the truncated transcript and 0.550 for the whole one. That lead is small, and we did not compute a confidence interval for it. As a rough guide, one standard error on a rate near 0.55 with 120 probes is about 0.045. So we do not claim that retrieved memory is clearly better on this measure.

The ceiling has moved too. Oracle memory reaches only 0.875, so this model gets one probe in eight wrong with nothing but the right fact in front of it. Some columns rest on fewer than 10 probes, so do not read them one by one. Compare this with the rule reader at the same budget: 0.999 against 0.749. Most of that gap did not survive contact with this model.

Nuance

Our two real-model measurements disagree in size: 13 of 16 against 3 of 16 on the deploy task, and 0.592 against 0.542 on the probes. Both are one small model, and neither is a general accuracy. Three things are not measured with a real model at all. Procedural memory is not exercised, because the real run has no failures to recover from. LLMFactExtractor is tested only on canned replies. OpenAICompatModel from C10, the client you would use for a hosted model, is tested here only against a local stub.

Checkpoint

  • Your tables match the ones above.
  • Corrupting the stored values lowers accuracy by more than 0.3 in the test suite.

Checks against trusted references

Most of this package has no library to compare with, so we check each part against the closest thing we can trust.

  • Fast index against PyTorch. TensorIndex.search gives the same ranking as F.cosine_similarity plus topk on 50 of 50 queries.
  • Greedy packer against an exact knapsack. On 300 random sets of 12 blocks, brute force finds the true optimum. Greedy reaches 0.982 of its value on average and 0.788 in the worst case, and it finds the optimum on 179 sets. That worst case is the failure from step 9, in numbers.
  • Token counter against a real tokenizer. The SmolLM2 tokenizer gives ratios of 1.00, 1.28 and 1.02 on three samples.
  • Fast index against the loop. TensorIndex and NaiveIndex return the same ids and the same scores to within 1e-5 on 500 random vectors, across several capacity doublings.
  • Mean pooling against padding. A MiniLM embedding must not change when padding is added. We ran this network test on the AMD EPYC CPU, and it passed.
  • Harness loop against standalone loop. With no memory and with oracle memory at B = 4096, the two loops produce identical step counts and outcomes on one world.
  • Conditions against the oracle. The reader scores exactly 1.000 given only the gold fact. This is what lets us call any other error an error of context.

Key insights and nuances

  • Stale facts mislead even when retrieved correctly. An append-only store keeps stated recall at 1.00 and drops updated accuracy to 0.66. An edit path matters as much as a write path. Step 4
  • The write gate protects against things that are true today and false tomorrow. Without the writer and the scope gate, accuracy on the day after an override goes from 1.00 to 0.00. Step 5
  • Fixing staleness at write time takes work away from retrieval. Semantic-only ties the full hybrid at 0.999, because superseding already removes old values. That holds on this benchmark and may not hold on yours. Step 7
  • A perfect reader hides ranking problems. The rule reader never rewards a better embedder. In the real run, 16 tasks with one model, the model deployed to the region on the top memory line every time. MiniLM put the right fact on top in every prompt, and retrieved went from 13 to 16 of 16. Step 12
  • A rule only pays when the reader would not generalise alone. It changes nothing for the analogy reader, and it saves 0.76 steps on new projects for the literal reader. Step 8
  • Greedy by value per token can drop the block you need most. At B = 160 the rule that fixes the current error is dropped, while a fact about another project stays. Step 9
  • Only extraction keeps the failure. At 60 tokens, head, tail and head-and-tail all lose the assertion from a 244-line log. Step 10
  • A badly truncated transcript is worse than no memory. At B = 256 in the deploy world it succeeds on 0.394 of tasks, against 0.713. Step 12
  • Success rates can come from your step limit. Raising the limit from 8 to 9 takes both conditions from 0.713 and 0.929 to 1.000. Steps is the better measure: 5.84 calls against 2.77 at a limit of 9. Step 12
  • Prove the memory is the cause. Same reader and same seeds, then corrupt the stored values: accuracy falls from 0.999 to 0.585. Step 12
  • A perfect reader is an instrument, not a forecast. It isolates what the context contains. On the fact probes it scored retrieved memory 0.999 against 0.749. One small real model scored the same contexts 0.592 against 0.542, a lead too small to claim. Step 12
  • Having the fact in the prompt is not the same as using it. On 16 deploy tasks, one small model got 3 right with the full transcript and 13 with retrieved memory, with the fact in every prompt. This is a demonstration, not a rate. Step 12

Exercises

  1. Protect the essential blockMedium Fix the failure from step 9, where the rule for the current error is dropped at B = 160. Try a floor for procedural memories, or a value bonus when a memory names the last error. Measure deploy steps at B = 256 before and after.
    Hint

    Section.min_tokens already reserves tokens. You would need a separate procedure section, or a higher value in memory_blocks. Run the deploy table in scripts/eval_memory.py to compare.

  2. Add a paraphrase worldHard Rewrite the probes in facts_world.py so they share few words with the facts, for example "Where does atlas run in production?". Compare HashingEmbedder with TransformerEmbedder. Does the tie between semantic-only and hybrid survive?
  3. Create a world where recency mattersHard Our benchmark gives recency nothing to do. Add free-text notes that have no key and go out of date, so superseding cannot catch them. Find a weight for β that beats zero, and report both numbers honestly.
  4. Measure the reader's effectMedium The lead of 0.592 over 0.542 has no confidence interval. Add one, using a bootstrap over the probes in scripts/eval_lm_reader.py, and raise the seeds until you can say whether the lead is real. Then apply edge_order to the memory block in scripts/run_real_agent.py with the hashing embedder. Does placing strong lines at the edges recover the three misses?
  5. Close the loop on proceduresMedium ProcedureStore.record_outcome exists, but nothing calls it during a run. Wire it through MemoryHook, add a world where a rule stops working after session 5, and show the bad rule losing rank.
    Hint

    You need to know which procedure was retrieved for the task. Record its id when the policy acts on it, then read the reward from the final deploy step.
