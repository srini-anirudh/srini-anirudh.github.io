Two answers to one question

Suppose you have to compute a billion independent fused multiply–adds, and a fixed budget to spend on silicon: some area on a wafer, some watts, some fabrication process. How should you spend it?

There are two coherent answers, and they pull in opposite directions.

The first answer is make each operation finish as soon as possible. The quantity to minimise is latency: the interval between issuing an instruction and having its result available for the next instruction. This is the right objective when the work arrives as a single chain in which each step needs the previous step's answer — parsing a file, walking a linked list, running an interpreter loop, deciding what to do next. There is only ever one thing to do, so the only way to go faster is to do that one thing faster.

The second answer is make as many operations finish per second as possible, and accept that any individual one may take a long time. The quantity to maximise is throughput. This is the right objective when a million independent operations are sitting in a queue and nobody is waiting on any particular one of them.

A CPU is the first answer built in silicon. A GPU is the second. Almost every architectural difference between them — cache sizes, core counts, clock speeds, the existence of branch predictors, the number of registers, the width of the memory bus — falls out of that single divergence of objective.

A note on the numbers before we start

This article is full of quantities, and they are not all equally trustworthy. Some are printed on a datasheet. Some I did not measure at all and have taken from someone else’s published microbenchmarks. Some I derived here from two other numbers. And some are the output of a deliberately simplified model. Conflating those would be the easiest way to mislead you, so every figure and table below is tagged:

Published by the vendor. Bandwidths, peak FLOP rates, capacities, architectural limits. Trust these to the precision given, while remembering that "peak" is a ceiling nobody reaches.

The shape of the ladder is robust across studies; individual cycle counts vary with clock, access pattern and measurement method. Treat them as within a factor of about 1.5.
derived
Computed here from spec figures. Ridge points, arithmetic intensities, traffic totals, collective timings. The arithmetic is shown wherever it matters so you can check it; if an input is wrong, the output moves with it.
model
The output of a simplified model, not a measurement. Every interactive lab is one of these. They reproduce the shape of real behaviour — where the cliffs are, which direction things move — while ignoring prefetchers, caches, overlap and instruction-level parallelism. Each one lists what it ignores.
schematic
The drawing is not to scale. Used where a true-to-scale rendering would be unreadable, such as a die floorplan or a six-order-of-magnitude capacity range.

Little's Law, the law that governs both

The two objectives are not independent. They are tied together by a relationship so general that it holds for queues at supermarkets and for load instructions in flight:

concurrency = latency × throughput C (operations in flight) = L (seconds per operation) × T (operations per second)

Read it as a constraint on the machine designer. Solve for throughput and you get T = C / L. There are exactly two ways to make a machine complete more work per second: shrink the latency of each operation, or increase the number of operations you keep in flight at once. That is the whole design space.

A CPU attacks L. It spends enormous resources making a single instruction stream advance quickly: multi-level caches so that operands are close by, branch predictors so that control decisions do not stall the pipeline, out-of-order execution to squeeze whatever concurrency exists out of a program that was never written to be parallel. That last mechanism is the tell — the CPU has to discover concurrency, at runtime, in hardware, because the programmer did not supply any.

A GPU attacks C. It gives up on making any individual operation fast — a global memory load can take five hundred cycles and nobody apologises — and instead demands that you hand it tens of thousands of independent operations up front. Then it keeps them all in flight, so that the long latencies overlap and the arithmetic units never go hungry.

This is why "is a GPU faster than a CPU?" is not a well-formed question. A GPU running a strictly sequential dependent chain is dramatically slower than a CPU — lower clock, longer latencies, no speculation. The GPU only wins when you can supply the concurrency it needs, and the amount it needs is set by Little's Law, not by preference.

Carry this forward

Throughput is bought with concurrency, and concurrency is something you must supply. Every GPU performance problem in the rest of this article is, at bottom, a failure to keep enough independent work in flight — or a failure to feed that work fast enough from memory.

The transistor budget

Silicon is a zero-sum allocation. Every square millimetre spent on a branch predictor is a square millimetre not spent on a multiplier. So the clearest way to understand what a processor is for is to open it up and ask what fraction of it does arithmetic.

Open a modern CPU core and the answer is uncomfortable: very little of it. The bulk is machinery whose only job is to keep a small number of arithmetic units busy despite a program that keeps branching, keeps missing in cache, and keeps expressing dependencies. Instruction fetch and decode. A branch predictor with tens of kilobytes of history tables. Register renaming. A reorder buffer holding hundreds of in-flight instructions. Load and store queues that track memory ordering. Hardware prefetchers guessing the next cache line. Two or three levels of cache. All of this exists to reduce latency — the CPU's stated objective — and none of it computes anything.

Open a GPU streaming multiprocessor and the proportions invert. There is no branch predictor, no register renaming, no reorder buffer, no speculation. In their place: a very large register file, a wide bank of arithmetic lanes, and a scheduler whose entire job is to pick which of the resident warps has an instruction ready this cycle. The GPU does not try to hide latency by predicting the future. It hides latency by having something else to do.

The numbers at the end of that figure are worth sitting with. The GPU has roughly sixteen times as many fp32 arithmetic lanes, but only about eleven times the fp32 throughput, because it clocks lower. And it has only about seven times the memory bandwidth. Width scales more easily than bandwidth — which is the entire subject of the next section.

Note also what the comparison omits. The H100's tensor cores deliver on the order of 989 TFLOP/s of dense BF16, roughly 150× the CPU's general fp32 rate. Specialised matrix hardware is where the gap becomes enormous, and it is also where the bandwidth problem becomes acute: units that fast will starve on anything but the most carefully staged data.

The memory wall

Arithmetic has become almost free. Moving the operands has not.

The physical reason is that arithmetic lives on the die and data does not. A 32-bit floating-point add costs on the order of a picojoule; reading the same 32 bits from off-chip DRAM costs several hundred picojoules — Horowitz's much-cited 45 nm figures put the ratio at roughly 700×. That gap is not a manufacturing accident that a new process node will fix. It is the cost of driving a signal across centimetres of package and board instead of micrometres of metal, and it scales with distance, not with transistor count.

Bandwidth is limited by the same physics from a different direction. You can double the number of arithmetic lanes by doubling the area you give them. You cannot double memory bandwidth that way, because bandwidth is set by how many wires leave the package and how fast you can toggle them, and both are constrained by pin count, signal integrity and power. HBM exists precisely because the industry ran out of room on the traditional route: stack the DRAM dice, put them on the same interposer as the GPU, and use a very wide, relatively slow bus instead of a narrow, fast one.

The result is a divergence that has been running for two decades and shows no sign of closing.

Two conclusions follow, and they organise everything that comes after.

First, performance work is mostly data-movement work. If your kernel sits at 2 FLOP/byte and the machine's ridge point is 295, then you are using about 0.7% of the arithmetic units no matter how elegant your inner loop is. The only lever that matters is moving fewer bytes, or moving them from somewhere closer.

Second, the hierarchy is the mechanism. Both CPUs and GPUs solve the distance problem the same way: build a graded series of storage levels, each one smaller, faster and closer than the last, and arrange for the working set to live as high up that ladder as possible. The CPU tries to do this for you automatically, with caches and prefetchers. The GPU hands you a shared-memory scratchpad and expects you to do it yourself. Both machines are, in the end, machines for shortening the distance to the data.

A note on what "peak" means

Every number in that figure is a theoretical peak: the rate you would achieve if no unit ever stalled. Real kernels reach a fraction of it. Quoting peak is still useful, because the ratio between peak compute and peak bandwidth is what determines whether a given algorithm can, in principle, be compute-bound on a given machine. That ratio is the ridge point, and it is a property of the hardware alone.

Inside a CPU core: the pipeline

Everything a CPU does to fight latency starts from one observation: executing an instruction is not a single act. It is a sequence — fetch the bytes, decode them, read the operands, do the arithmetic, touch memory, write the result back. If you build one lump of logic that does all of it, the clock period must be long enough for the slowest path through the whole lump, and only one instruction can be in the machine at a time.

Split it into stages separated by latches and two things happen at once. The clock can run faster, because each stage is shorter. And each stage can hold a different instruction, so five instructions are in flight simultaneously. The latency of any one instruction did not improve — it may have got slightly worse — but throughput went up fivefold. This is the same latency/throughput trade from §1, applied inside a single core, and it is the reason a modern core has fourteen to twenty pipeline stages rather than five.

Pipelining only pays if the pipe stays full, and three things empty it. A structural hazard is two instructions wanting the same unit. A data hazard is an instruction needing a result that is not ready. A control hazard is not knowing which instruction comes next, because the previous one was a branch. Most of the CPU core you saw in Figure 02 is dedicated to making these three problems disappear.

What all of that machinery is really doing

Step back from the mechanisms and they share a single purpose: finding concurrency in a program that does not declare any. The reorder buffer is a hardware search for independent instructions. The branch predictor is a way of extending that search across control-flow boundaries, by guessing which instructions will be needed and starting them early. Register renaming exists because the search keeps hitting false dependencies created by the compiler's reuse of sixteen architectural register names.

This search has hard limits. Empirically, general-purpose code contains only a few instructions' worth of extractable parallelism per cycle — sustained IPC of one to three is typical, against a peak issue width of four to eight. Doubling the reorder buffer buys very little; the window is already larger than the available independence. That diminishing return is precisely why the industry stopped making cores wider and started making more of them.

SMT is a two-way GPU

Simultaneous multithreading — Hyper-Threading, in Intel's branding — makes one physical core hold the architectural state of two threads and interleave them. When thread A stalls on a cache miss, thread B's instructions fill the empty issue slots. That is exactly the GPU's latency-hiding strategy: when this thread cannot proceed, run a different one. The difference is scale and honesty. A CPU keeps two threads resident and pretends it has twice the cores. An SM keeps up to sixty-four warps resident and builds its entire performance model around the fact.

SIMD: the CPU's answer to width

Out-of-order execution extracts concurrency the programmer did not declare. SIMD takes the opposite approach: it lets the programmer declare it, and then executes it almost for free.

The idea is to widen the registers and make one instruction operate on all of it. An x86 ymm register is 256 bits — eight fp32 values — and a single vfmadd multiplies and adds all eight in one go. The instruction fetch, decode, rename, schedule and retire costs are paid once for eight results instead of eight times for one. All that expensive front-end machinery from Figure 02 is amortised across the vector, which is why SIMD is so much more energy-efficient per FLOP than scalar code.

The width has grown in steps: 128 bits with SSE (4 fp32 lanes), 256 with AVX/AVX2 (8 lanes), 512 with AVX-512 (16 lanes). Arm's NEON is 128-bit; SVE is width-agnostic by design. Every step doubles peak throughput without touching the clock.

The catch is that a vector instruction imposes one control flow on all its lanes. If the loop body has an if, you cannot have half the lanes take the branch. You compute both sides and select with a bitmask — so the work is done whether or not it is needed. And if the array length is not a multiple of the vector width, the last iteration is partly wasted, either masked off or handled by a scalar clean-up loop. Both of those problems reappear in exactly the same shape on a GPU, where they are called divergence and tail effects.

One more property of SIMD matters for the comparison ahead. The eight lanes of an AVX register are positions inside one register belonging to one thread. They are not independent threads. They share a program counter, they share a stack, and — critically — a vector load expects them to come from consecutive addresses. Loading eight values from eight unrelated addresses requires a gather instruction, which is substantially slower than a contiguous load, because it is really eight separate accesses wearing a trench coat.

A GPU's thirty-two lanes are different animals: each is a thread with its own registers, its own address, and its own view of the program. The hardware then notices when their addresses happen to be contiguous and fuses them into one transaction. Same physical goal, opposite default. That difference is the subject of §14.

The CPU memory hierarchy

A core can issue two loads per cycle. DRAM answers in roughly three hundred cycles. If every load went to DRAM, the most sophisticated out-of-order engine ever built would spend more than 99% of its time waiting, and the pipeline diagram in Figure 04 would be almost entirely red.

The fix is not to make DRAM faster — nobody knows how — but to make most loads not go there. A cache is a bet that the address you just used, or one near it, will be used again soon. The bet pays because real programs have temporal locality (a variable read once tends to be read again) and spatial locality (an array element read once tends to be followed by its neighbour). Both are empirical facts about how people write code, not theorems, and a program that violates them will be slow on any CPU ever built.

How a cache actually decides

"The data was in cache" is a sentence that hides a mechanism worth knowing, because the mechanism has sharp edges you can fall off.

A cache cannot search itself. Comparing a requested address against every stored line would require thousands of comparators firing every cycle, which is unaffordable in both area and power. So the address itself is used to decide where a line is allowed to live. Chop the address into three fields: the low bits select a byte within the line (the offset), the next bits select which set the line must go in, and the remaining high bits are the tag that is stored alongside the data to identify which of the many possible lines is actually present.

Now a lookup is cheap. Index into one set, compare the tag against the handful of ways in that set — eight comparators, not eight hundred — and you have your answer in a couple of cycles. The price of that cheapness is that a line's address determines its set, and a set holds only as many lines as there are ways.

Which brings us to the most famous performance cliff in computing

Because the set index comes from the middle bits of the address, a stride that is a large power of two maps every access to the same small handful of sets. A 32 KB, 8-way cache has 64 sets; walk memory with a 4096-byte stride and every single access lands in set zero. You now have an eight-line cache. It does not matter that the other 504 lines are sitting idle — the index bits forbid their use.

This is why matrix code so often pads its leading dimension by one row, why FFT implementations avoid power-of-two strides, and why an innocent change from [1024][1024] to [1024][1025] can double a program's speed.

Virtual memory and the TLB

There is one more level of the hierarchy that is easy to forget because it stores no data at all. Every address your program uses is virtual, and something has to turn it into a physical one before any cache can be consulted. On x86-64 that something is a four-level page table, and walking it costs up to four dependent memory accesses — each of which can itself miss in cache.

Paying that on every load would be catastrophic, so translations are cached in the TLB. A hit is essentially free. A miss triggers the walk. And the TLB has a property worth internalising: its capacity is measured not in bytes but in reach — entries times page size. A 64-entry L1 TLB with 4 KB pages reaches 256 KB. If your working set is a gigabyte of randomly accessed memory, you will miss in the TLB constantly even when the data itself is comfortably in L3.

End of the CPU half

A CPU core is a latency-minimising machine: a deep pipeline kept full by speculation and out-of-order execution, fed by a cache hierarchy that bets on locality, addressed through a translation layer that bets on reach. Every one of those bets is a guess the hardware makes on your behalf. The GPU makes almost none of them — and asks you to make them instead.

The GPU floorplan

A GPU is organised as a hierarchy of replication, and almost every performance rule you will meet later is a statement about which level of that hierarchy something is shared at. So it is worth descending it once, carefully, from the outside in.

At the top is the whole device: a few graphics processing clusters, a large shared L2, a stack of HBM around the edges, and the links that connect it to other GPUs and to the host. Inside a cluster are texture processing clusters, and inside those are the streaming multiprocessors — the unit that actually runs your code. An SM is itself divided into four processing blocks, each with its own warp scheduler, its own slice of the register file, and its own arithmetic lanes.

The names are NVIDIA's, and AMD and Intel use different ones — compute unit, Xe-core — but the shape is the same everywhere, because it falls out of the same constraints.

Two numbers from the last stage deserve emphasis. 270,336 threads resident at once is the concurrency the device is built to hold — Little's Law's C, in hardware. And 33 MB of register file is larger than the last-level cache of many CPUs, which tells you where the GPU decided to spend its memory budget: not on caching things that might be reused, but on holding the state of an enormous number of threads so that none of them ever has to be swapped out.

That last point is the deepest architectural difference between the two machines. On a CPU, a context switch means saving registers to memory and restoring another thread's — hundreds of cycles, so the OS does it every few milliseconds. On a GPU, every resident thread's registers are already in the register file, permanently, for the lifetime of the thread. Switching warps costs nothing. It happens every cycle.

SIMT: one instruction, thirty-two threads

You write CUDA as if every thread were an independent program. The hardware does not run it that way. Threads are bundled into groups of 32 called warps, and a warp is the smallest thing a scheduler can schedule. One instruction is fetched, decoded once, and issued to 32 lanes at once.

This is where the amortisation from §2 actually happens. The fetch, the decode, the dependency check, the scheduling decision — all of that control machinery runs once and pays for 32 results. That is the whole trick, and it is why a GPU can afford to have 16,896 arithmetic lanes but only 528 schedulers.

It is close to SIMD, but not identical, and the difference matters. In SIMD you write one instruction operating on a vector, and the lane index is implicit in the data layout. In SIMT you write scalar code, and each lane has its own registers, its own addresses, and — since Volta — its own program counter. Lanes can do genuinely different things. They just cannot do them at the same time.

The practical consequence is a rule you can apply while writing code, not just while profiling it: divergence costs are determined by disagreement inside a warp, and warps are aligned to consecutive thread IDs. A branch on tid / 32 is free. A branch on tid % 2 halves your throughput. A loop whose trip count varies per thread costs the maximum trip count in the warp, for every warp.

The lab below makes that concrete. Pick how many distinct paths the code has, and how those paths are distributed across threads.

Why warps are 32 and not 8 or 128

Wider warps amortise control logic over more lanes, which is the whole point. But they also make disagreement more likely — a 128-wide warp diverges whenever any of 128 threads disagrees — and they coarsen the granularity of everything: memory requests, scheduling, occupancy. Thirty-two is a compromise that has survived fifteen years and is unlikely to be an accident. AMD, notably, uses 64 (a "wavefront") on CDNA and offers both 32 and 64 on RDNA, which tells you the optimum is shallow.

The execution hierarchy

CUDA gives you three levels of software abstraction — thread, block, grid — plus a fourth on Hopper, the cluster. Each maps onto a hardware level from Figure 10, and each level's mapping determines exactly one thing: what can be shared, and what can be synchronised.

The pivotal one is the block. A block is guaranteed to be resident on a single SM for its entire lifetime. That guarantee is what makes shared memory and __syncthreads() possible: threads can cooperate because the hardware promises they are neighbours. The flip side is that the guarantee stops at the block boundary. Two blocks may run on different SMs, at different times, in either order, or one may not start until the other has finished — so there is no way to synchronise them mid-kernel without deadlocking.

Latency hiding, and the occupancy trap

A CPU core hides latency by finding other work inside one instruction stream: reorder buffers, speculation, register renaming. All of that machinery exists to extract a few independent instructions from code that was written sequentially.

The GPU does not bother. It has thousands of instruction streams already, so when a warp stalls, the scheduler simply picks a different warp. There is no prediction, no rollback, no reordering — just replacement. This is the payoff for that 33 MB register file: because every resident warp's state is already in registers, switching between them costs nothing at all.

Which turns performance into an inventory question. How many warps do you need resident to keep the pipes full? Little's Law answers it, exactly as it did in §1.

That last stage is the important one, and it is the reason for the word trap in this section's title.

Occupancy — resident warps divided by the 64 slots an SM has — is the most quoted GPU metric and the most misread. It is not a performance target. It is one of two ways to buy the concurrency that Little's Law demands, and the other way is to give each thread more independent work. Volkov's demonstration that a well-unrolled kernel can reach peak bandwidth at 25% occupancy, while a naive one stalls at 100%, is fifteen years old and still surprises people every week.

What occupancy is good for is diagnosis. If a kernel is latency-bound and has neither warps nor instruction-level parallelism, occupancy tells you which resource is standing in the way. Usually it is one of three: registers, shared memory, or a badly chosen block size.

The rule that actually holds

Do not tune for occupancy. Tune for enough concurrency to cover the latency you have, and measure. Occupancy and instruction-level parallelism are substitutes, and the register pressure that lowers the first is very often what bought you the second.

The GPU memory hierarchy

The GPU's ladder has the same shape as the CPU's — small and fast at the top, large and slow at the bottom — but the rungs are in strange places, and one of them is not a cache at all.

Start at the top and the first surprise is the size. The register file is 33 MB, larger than the L3 of many server CPUs, and it is at the fastest level. That inversion is deliberate: registers are where the state of 270,336 threads lives, and the whole latency-hiding scheme of §12 depends on none of it ever being spilled.

The second surprise is the rung labelled shared memory. It is not a cache. It is a scratchpad — the same SRAM as L1, but with software-controlled placement and no tags, no eviction policy, and no automatic anything. You decide what goes in it and when. The GPU took the transistors a CPU spends on guessing what you will need, and handed you the keys instead.

Two rows of that last comparison deserve to be stared at.

GPU memory latency is worse than a CPU's, not better. Roughly 350 nanoseconds against roughly 80. HBM is optimised for bandwidth, and bandwidth is bought partly with latency. The GPU is not fast at getting one thing; it is fast at getting a hundred thousand things at once.

Placement is your job. On a CPU, moving data between L3 and L1 is something you influence — through access order, prefetch hints, blocking — but never command. On a GPU, moving data from HBM into shared memory is an instruction you write. That is more work and vastly more control, and it is the reason a hand-tuned GPU kernel can beat a compiler by an order of magnitude while a hand-tuned CPU kernel usually cannot.

Coalescing: the single most important access pattern

When a warp executes a load, it does not issue one request. It issues 32 addresses at once, and the memory system's job is to satisfy all of them. It does this by working out which sectors — aligned 32-byte chunks — those addresses fall into, and fetching each distinct sector once.

That is the entire mechanism, and everything follows from it. If the 32 addresses are consecutive 4-byte words, they span 128 bytes: four sectors, four transactions, every byte fetched is a byte used. If the same 32 threads read with a stride of 32 words, they touch 32 different sectors: 1,024 bytes moved to deliver 128 bytes of useful data. Same instruction, same number of threads, same total useful work — eight times the memory traffic.

Notice what this is not. It is not a cache effect, and it is not about reuse over time. It happens within a single instruction, before any cache has an opinion. A perfectly coalesced kernel and a perfectly scattered one differ in the number of transactions the memory controller has to perform, and on a machine whose bottleneck is bandwidth, transactions are the currency.

The rule, and why it is not the same as SIMD

The rule to carry is short: consecutive threads should touch consecutive addresses. Not consecutive per thread — consecutive across the warp. A loop where thread t processes elements t*N through t*N+N-1 looks tidy and is catastrophic. The version where thread t processes elements t, t+32, t+64 looks worse and runs many times faster.

This is where the SIMT/SIMD distinction from §5 becomes practical rather than pedantic. A CPU vector unit loading 16 floats issues one address and gets 64 contiguous bytes; a scattered access needs an explicit gather instruction, and gathers are slow and obviously so. A GPU warp always issues 32 independent addresses. Coalescing is not a special path — it is what happens when those 32 addresses happen to be adjacent. The hardware gives you gather semantics for free and charges you for the bandwidth afterwards.

Where this bites in practice

Almost every real GPU performance bug is one of three things: an array-of-structures layout that spreads each thread's fields across sectors; a transpose or reduction whose natural indexing walks columns; or an index vector that turns a contiguous read into a gather. The first two are fixed by changing layout or staging through shared memory. The third is usually fixed by sorting — which is why high-performance sparse and mixture-of-experts kernels spend real time permuting data before they touch it.

Shared memory has thirty-two doors

Shared memory is fast, but it is not magic, and it has one failure mode you will meet the first time you write a transpose.

The SRAM is divided into 32 banks, each four bytes wide, with addresses interleaved across them: word 0 in bank 0, word 1 in bank 1, word 32 back in bank 0. Each bank can serve one address per cycle. So a warp's 32 accesses complete in a single cycle if — and only if — they land in 32 different banks.

If several threads want different addresses in the same bank, the hardware serialises them: an n-way conflict takes n cycles. There is one important exception. If several threads want the same address, the value is broadcast to all of them for free. Conflicts come from different words in the same bank, never from the same word.

Which sets up the classic disaster. Store a 32×32 tile of floats in shared memory and have each thread read one element of a column. Thread t reads element t*32 + c, whose bank is (t*32 + c) mod 32 = c — the same bank, for every thread, with 32 different addresses. One instruction, 32 cycles.

The padding trick is worth understanding rather than memorising, because the reasoning generalises. Bank index is address mod 32. Any stride sharing a factor of two with 32 folds threads onto a subset of banks; the more factors it shares, the worse the fold. A row width of 32 shares all five, so every thread lands in one bank. A width of 33 is coprime with 32, so consecutive threads walk through all 32 banks in turn.

The same reasoning explains the strided cases in the lab: stride 2 gives a 2-way conflict, stride 4 a 4-way, stride 16 a 16-way, and any odd stride none at all. It is the same modular arithmetic that produced the cache conflict cliff in §7 — a hardware structure indexed by low address bits, meeting an access pattern aligned to a power of two.

Two power-of-two traps, one cause

Cache sets are indexed by middle address bits; shared memory banks by low ones. In both cases a power-of-two stride collapses a wide structure onto a narrow one. In both cases the fix is to break the alignment — pad the row, offset the array, choose a leading dimension that is not a round number. Round numbers are convenient for humans and pathological for hardware.

The roofline: one model that predicts almost everything

Everything so far can be collapsed into a single inequality. A kernel performs W floating-point operations and moves Q bytes. Its arithmetic intensity is I = W / Q, in FLOPs per byte. The machine can supply at most Ppeak FLOP/s of arithmetic and at most β bytes per second of bandwidth. Therefore:

Pattainable = min( Ppeak , β × I )

Plot that on log-log axes and you get a line that rises at 45 degrees and then flattens — a roof. Every kernel sits somewhere under it. To the left of the corner you are memory-bound and your performance is β × I, entirely determined by how many bytes you move. To the right you are compute-bound and no amount of bandwidth tuning will help you.

The corner is the ridge point, at I* = Ppeak / β, and it is the single most informative number about a machine. For H100 fp32 against HBM it is 20 FLOP/byte. For the tensor cores it is 295. That number is the entire reason deep learning kernels look the way they do.

Three things this plot tells you that are easy to state and hard to internalise.

Most deep learning operations are memory-bound, and it is not close. Elementwise addition, GELU, LayerNorm, softmax, dropout — all sit between 0.1 and 3 FLOP/byte, against a ridge of 295. They run at under one percent of the machine's arithmetic peak, and no rewrite of the arithmetic will change that. The only lever is traffic.

Making the arithmetic faster makes the problem worse. Every tensor core generation raises the ceiling without raising bandwidth proportionally, which pushes the ridge point to the right and drags more operations into the memory-bound region. This is the memory wall of §3, seen from the software side.

The way out is to change which memory you are measured against. Switch the lab's byte-counter from HBM to shared memory and the ridge point drops from 295 to about 33. Nothing about the kernel changed — only which level of the hierarchy the bytes came from. Arranging for that is the subject of the next section, and it is the single most valuable thing you can learn to do on a GPU.

What the roofline gets wrong

It is the most useful model in this article and it is still only a model, so it is worth knowing where it misleads.

It is an upper bound, not a prediction. The roofline tells you what you cannot exceed. A kernel sitting far below the roof is not explained by it at all — and that is the common case. Most kernels that disappoint are neither compute- nor bandwidth-bound but latency-bound: they lack the concurrency of §12 to saturate either ceiling, and the roofline gives no hint that this is what is happening.

Q is undefined until you name a memory level. "Bytes moved" against HBM, against L2 and against shared memory are three different numbers for the same kernel, giving three different intensities and three different verdicts. That is why the lab above makes you choose, and why comparing two published intensities is meaningless unless both counted against the same level.

The ceilings are peaks nobody reaches. Real achievable bandwidth is typically 80–90% of the published figure, and a well-tuned GEMM reaching 70–80% of dense arithmetic peak is doing very well. A more honest plot uses measured ceilings, which lowers both roofs and moves the ridge point.

It assumes perfect overlap. The min in the formula presumes that memory and arithmetic proceed simultaneously. If your loads and your math take turns — the un-pipelined case in §18 — you get closer to the sum of the two times than the maximum, and the model quietly overstates you by up to 2×.

Refinements exist that address some of this, notably cache-aware and hierarchical roofline variants that draw one sloped roof per level of the memory hierarchy. The dashed lines in the lab above are a gesture at that idea.

Tiling: manufacturing arithmetic intensity

The roofline says a memory-bound kernel can only be fixed by moving fewer bytes. But the FLOPs are fixed by the mathematics, and the data is as large as it is. So where does the improvement come from?

From reuse. Arithmetic intensity is not a property of an algorithm — it is a property of an implementation, and specifically of how many times each byte fetched from slow memory is used before it is thrown away. Matrix multiplication is the canonical demonstration, because its naive form has terrible intensity and its tiled form has excellent intensity, and the difference is nothing but bookkeeping.

The derivation behind that figure fits in three lines. A tiled matrix multiply of an n × n problem with T × T tiles performs 2n³ FLOPs and reads each of the n/T tile-pairs along k once per output tile:

Q = 2n³ / T elements  ·  W = 2n³ FLOPs  ·  I = W / (Q · b) = T / b

where b is bytes per element. Intensity is linear in the tile dimension and independent of the problem size. That is a remarkable result: it says the machine's arithmetic-to-bandwidth ratio dictates a minimum tile size, and that minimum is a property of the hardware alone. It is the reason tile sizes in fast GEMM kernels cluster around 128 — and the reason they had to grow every time a new tensor core generation raised the ceiling.

Bandwidth is not the only thing choosing that number, though, and it would be tidy but wrong to suggest otherwise. Tensor core instructions accept operands only in fixed tile shapes, so the tile must be a multiple of those. Shared memory capacity caps it from above, and occupancy pulls it down further, as the lab below shows. The tile must also divide the problem, or the ragged edge costs a separate code path. The intensity argument sets a lower bound on a useful tile size; the other three constraints choose among the candidates above it.

The general principle, stated once

Tiling is not a matrix multiplication trick. It is the general answer to a bandwidth-bound problem: restructure the computation so that data brought into a fast level of the hierarchy is fully exploited before it leaves. Convolution tiles over spatial windows, FFT over butterflies, attention over key–value blocks, graph kernels over vertex neighbourhoods. Same idea, different index arithmetic — and the next section is the case where it changed a whole field.

Tensor cores, and the pipeline that feeds them

By now the amortisation argument should feel familiar. A CPU amortises instruction fetch over one operation. SIMD amortises it over a vector. SIMT amortises it over 32 lanes. Each step spends less control per result.

Tensor cores apply the identical argument one level further down, but to a different scarce resource: register file bandwidth. An ordinary fp32 FMA reads two operands and writes one result — three register accesses for two FLOPs. Once an SM has 128 such lanes, feeding them becomes as hard as building them. A matrix instruction breaks that ratio, because a small matrix multiply reuses each operand many times inside the unit, where no register file is involved at all.

Two consequences of tensor cores are worth stating plainly, because they explain a great deal of what modern kernels look like.

They made almost everything memory-bound. Peak fp16 arithmetic went up roughly 15× relative to the fp32 lanes on the same die, and HBM bandwidth did not. The ridge point moved from 20 to 295 FLOP/byte, dragging every non-matmul operation deep into the bandwidth-limited region. Fusion, recomputation and custom kernels are not micro-optimisations any more; they are the difference between using the machine and not.

They made data movement the hard part of the kernel. When the arithmetic instruction consumes a 16×16 tile, delivering that tile in the right layout at the right cycle becomes most of the engineering. This is why cp.async, the TMA, and Hopper's warp specialisation exist, and why writing a competitive GEMM is now mostly a scheduling exercise rather than an arithmetic one.

A note on "peak"

Published tensor-core figures often quote the structured-sparsity rate, which is double the dense rate and requires a 2:4 sparsity pattern the model must actually have. The dense numbers in Figure 22 are the ones to reason with. And peak assumes every cycle issues a matrix instruction with operands already in place — a well-tuned GEMM reaching 70–80% of dense peak is doing very well.

Case study: FlashAttention

Everything in this article converges on one example. Attention is the operation that made the memory wall impossible to ignore, and FlashAttention is the fix — not a new approximation, not a cheaper mathematics, but the same arithmetic rearranged so that the intermediate never touches HBM.

Take one attention head with sequence length N = 4096 and head dimension d = 128, in fp16. The arithmetic is two matrix multiplications: S = QKᵀ and O = PV, together 4N²d = 8.59 GFLOP. The inputs Q, K, V are a megabyte each. And the intermediate S is N × N — 33.6 MB, thirty-two times larger than any of its inputs.

The result is worth restating because it is easy to mistake for an optimisation trick. FlashAttention computes exactly the same function, to the same numerics, using the same number of FLOPs. It is not sparse, not low-rank, not approximate. All it does is choose an order of operations in which the N × N intermediate is produced and consumed inside the SM.

The fused version's memory is linear in N, and that, far more than the speedup, is why context windows grew from 2,048 to hundreds of thousands of tokens in about two years.

The lesson, generalised

The expensive part of attention was never the arithmetic. It was a temporary array that had to be written to HBM because the algorithm was expressed in a phase order that required it. Look for that shape everywhere: an intermediate larger than its own inputs, materialised because of the order in which operations were written down. Layer norm followed by a matmul, a softmax followed by a dropout, a loss over a hundred-thousand-token vocabulary — every one of them is the same bug, and every one is fixed the same way.

Beyond one GPU: the ladder keeps going

The hierarchy does not stop at HBM. It continues out through NVLink to the other GPUs in the server, through PCIe to the host, and out through the network to other servers — and each of those steps is another order of magnitude of distance. Training a model of any size means living on the bottom three rungs, where the numbers get uncomfortable.

That last stage is the single idea behind every modern distributed training strategy, and it is the same idea as tiling. Route each byte over the shortest link that can carry it, and only send across the expensive link what genuinely has to cross.

And the same trick again: overlap

Every collective above can be started before it is needed and waited on later — gradients for layer n reduce while layer n−1 is still computing its backward pass. This is exactly the warp scheduler of §12 and the double-buffered tile loop of §18, one level further out. Latency you cannot remove, you cover. It is the same answer at every scale in this article, from four pipeline stages to four thousand GPUs.

A diagnostic order of operations

When a GPU kernel is slower than it should be, this sequence resolves it faster than guessing:

  1. Compute the arithmetic intensity by hand and place it on the roofline. This alone tells you whether to look at memory or at arithmetic, and it costs two minutes.
  2. If memory-bound, check the access pattern before anything else. A gather or a strided load can cost 8× the traffic and looks nothing like a bug in the source. Compare bytes requested against bytes transferred in the profiler.
  3. Then look for a materialised intermediate. Any temporary larger than its inputs is traffic you can probably delete by fusing. This is the FlashAttention pattern and it recurs everywhere.
  4. Then consider tiling — is the data being re-read from HBM when it could have stayed in shared memory or in registers?
  5. If compute-bound, check whether the tensor cores are actually being used, then whether they are being fed: a pipeline with no double buffering leaves them idle half the time.
  6. Only then look at occupancy, and treat it as a diagnosis rather than a target. Ask whether there is enough concurrency — from warps or from independent work per thread — to cover the latency you have.
  7. At multi-GPU scale, ask which link each byte crosses. Traffic on the wrong rung of the ladder is the most common and most expensive mistake in the list.

The one-sentence version

A CPU is a machine built to make one thing happen as soon as possible; a GPU is a machine built to make an enormous number of things happen per unit time. Both are limited by the same thing, and it is not arithmetic — it is the distance to the data.
