The plan

A pretrained model continues text. What has to change, tensor by tensor, before it answers a question, then prefers a right answer over a wrong one, and then earns a reward for being right?

Post-training is the name for those changes. We build three stages on one base model, in one codebase. Each stage gets a weaker signal than the one before it.

  • Supervised fine-tuning (SFT) is told the answer, token by token.
  • Direct preference optimization (DPO) is told that one answer is better than another.
  • Group relative policy optimization (GRPO) is told nothing in advance. It samples answers, and a checker scores them.

All three rest on one quantity: the log-probability of the completion tokens given the prompt. Figure 1 shows how each stage turns that quantity into a loss. The rest of the post builds each of those tensors by hand.

Nuance

Read the results with this in mind. SFT works here: the base model scores 0.0%, and full fine-tuning reaches 74.5% on held-out problems. Most of that gain is the answer format, as step 6 shows.

The later stages did not improve the model. DPO lowered held-out accuracy in all four runs, at both learning rates we tried. The reward model was weak. GRPO ended well below its start in all three seeds. REINFORCE ended 1 to 7 points below its start, mostly within noise.

The DPO and GRPO loss functions match TRL on the same tensors, which makes a loss-formula bug unlikely. The sampling, batching and training scripts are not covered by those tests. We did not search for settings that work. Steps 11, 12 and 16 give the numbers and the ideas worth trying.

We post-train a real pretrained model, HuggingFaceTB/SmolLM2-135M. The tiny from-scratch models of C4 and C5 are not capable enough for preferences or reinforcement learning. A model has to produce some right answers and some wrong ones before there is anything to prefer. Step 6 tests this claim with a control run from randomly initialised weights.

One task family carries the whole tutorial: small arithmetic problems. Because we generate the data, every label is exact and every reward is exact.

Step 01Stage 1: SFT

Generate conversations with answers we can check

Goal A dataset where the right answer is known exactly, so a label or a reward is never a matter of opinion.

A real post-training dataset is a list of conversations. Each conversation is a list of messages, and each message has a role and some content.

We keep that format and generate the content. A Problem holds a question, its worked steps and its answer. The method solution writes the reply in one fixed form, so the answer is easy to find later.

The next function turns a problem into messages. The flag with_answer matters later. Without the answer, the list stops at the user turn, and that is the prompt for generation.

Now the part the later stages depend on. A verifiable reward is a function a machine can run, with no judge and no model in the loop. Ours reads the first answer in the reply and compares it to the truth.

Test

The strictness is part of the contract, so a test pins it down. A reply with no answer sentence earns nothing, and the first claim counts when there are two.

The one conversation this post inspects came from make_problem with seed 0 and kind chain, plus one follow-up turn from add_follow_up with seed 1. It looks like this after the next step renders it.

Step 02Stage 1: SFT

Serialize messages with a chat template

Goal Turn a list of messages into one token sequence, in a form the model will also see when it answers.

A model reads one flat stream of tokens. The chat template decides how roles are written into that stream. We use ChatML, which wraps each message in two markers. The base SmolLM2-135M tokenizer ships without a template, but its vocabulary already holds the markers: <|im_start|> is id 1 and <|im_end|> is id 2.

The last line of the template adds <|im_start|>assistant\n when we ask for a generation prompt. That small detail decides what we train on. At inference we feed the header ourselves, so the model never has to predict it.

Test

We build token ids by hand in the next step. This test checks that they equal what the template produces, so the two paths cannot drift apart.

Step 03Stage 1: SFT

Build assistant-only labels and look at them

Goal A label for every token, set to -100 wherever the model should not be graded.

Pretraining grades every token. SFT does not. We want the model to write replies, not to write user questions, so we mask everything except the assistant’s words.

What each kind of token gets as its label
TokenLabelWhy
system and user content-100Context only. We never want the model to write these.
<|im_start|>assistant\n-100We feed this at inference through the generation prompt.
assistant contenttoken idThis is the skill we are teaching.
<|im_end|> after a replytoken idThis is how the model learns to stop.
\n after a message-100Generation stops at <|im_end|>, so this is never produced.

We could tokenize the rendered text and then search for assistant spans. Instead we tokenize one piece at a time and record who produced each token. Then no search can go wrong.

The check is to print it. Here is the part of the table around the first assistant reply, and the end of the second reply.

Insight

In this conversation, 66 of 122 tokens are masked. They still run through every layer, because they are the context. So more than half of the forward pass here produces no loss term. It also means a loss value only compares with another loss built on the same mask. Our mean divides by the target count. The label counts are 21, 56 and 122 across the three modes. The loss denominators are 21, 56 and 121, because the shift drops the first label, and that label is a target only in mode="all".

Break it

Set the pad token to <|im_end|>, which many tutorials do. A common collator then runs labels[input_ids == pad_id] = -100. That line also erases every stop target. The model gets no training signal to end a reply, and nothing crashes. The loss even looks fine. Exercise 1 measures what happens.

To debug it, print the labels and count how many equal the stop token. The test test_pad_token_is_not_end_of_turn guards the configuration.

Step 04Stage 1: SFT

Write the masked loss

Goal Next-token cross-entropy on target positions only, equal to what Hugging Face computes.

Logits at position t predict the token at position t + 1. So we drop the last logit and the first label, and the two line up. Cross-entropy already knows how to skip -100.

Shapes in the masked loss
TensorShapeMeaning
input_ids, labels(B, L)Tokens, and their targets or -100.
logits(B, L, V)One score per vocabulary entry per position.
shift_logits(B, L−1, V)Positions 0 to L−2, each predicting the next token.
shift_labels(B, L−1)Positions 1 to L−1.
lossscalarSum over targets, divided by the number of targets in the batch.

The first assistant token in Figure 2 sits at position 48. Its prediction comes from position 47, the newline at the end of the header. The header is masked as a target, but it still does the predicting.

Test

Our first comparison against a trusted implementation. On a padded batch, our loss must equal the loss that Hugging Face returns when given labels.

Step 05Stage 1: SFT

Batch by padding, then by packing

Goal Spend less compute on empty slots, without letting one conversation read another.

Start with the simple version. Each conversation gets its own row, and short rows are filled with pad tokens. The width is rounded up to a multiple of 32, because a device that compiles kernels per shape pays a cost for every new length.

Packing puts several whole conversations into one row. We use first-fit-decreasing bin packing, a classic greedy rule: sort by length, then put each conversation in the first row with room. Conversations are never split, because a second half without its prompt teaches nothing useful.

Packing is only safe if the model cannot tell the conversations are neighbours. That takes two things: positions that restart, and attention that cannot cross a boundary. The second is a block-causal mask.

Shapes of a packed batch
TensorShapeMeaning
input_ids, labels(B, max_len)Several conversations end to end in each row.
position_ids(B, max_len)Restarts at 0 for each conversation.
seq_ids(B, max_len)Which conversation owns each token. -1 marks padding.
attention_mask(B, 1, max_len, max_len)Boolean. True where query i may attend to key j.

Figure 3 runs the packer on five conversations, the same lengths the unit test uses. Move the slider to change the row length.

Now measure it on the real data. The benchmark compares padded batches of 8 with packed batches of 4 rows of 256 tokens.

The CPU run is first. It times 12 steps on an AMD EPYC 7R13 with 8 threads.

The same benchmark on one NVIDIA H100, timed over 20 steps.

Packing fills 89.8% of its slots with real tokens. Padding fills 63.7%. The slot fractions are exact and do not depend on the hardware. The target tokens per step depend on the batches drawn, so they differ a little between runs. So a step of about the same size carries more of what we grade. On the CPU run that is about 331 target tokens per packed step against 222 per padded step. On the H100 run it is 329 against 224.

On the CPU, a packed step took 2.48 s and a padded step took 2.25 s. That gives 134 target tokens per second against 99. On the H100, a packed step took 0.16 s and a padded step took 0.17 s. That gives 2,118 against 1,332 target tokens per second. The hardware was shared with other jobs, and step times vary from run to run, so read the seconds as rough. Each number comes from one run.

Break it

Pack the row but pass no block mask. The model now sees one long causal sequence, and the second conversation reads the first. The test test_naive_packing_leaks_across_conversations asserts that the logits change. The script below measures how much, on the real model.

Nuance

Hugging Face can also build a block mask for you from position-id resets. But in the version we tested (transformers 5.22.2, TRL 1.17.1, PEFT 0.21.2) it only does so when no KV cache is created. The test test_position_ids_alone_need_use_cache_false pins this down: with use_cache=True the conversations leak, and with use_cache=False they do not. So a packed training loop that forgets use_cache=False and relies on that path loses its isolation silently. Our loop passes both the explicit mask and use_cache=False.

Checkpoint

  • Packed logits equal the logits of the conversation run alone.
  • test_block_mask_is_causal_and_block_diagonal passes.
Step 06Stage 1: SFT

Write the SFT loop and train

Goal A plain PyTorch loop that teaches the base model the answer format, plus a measure of what it learned.

The loop is ordinary, which is the point. It uses the masked loss, AdamW, gradient clipping, and a schedule with linear warmup and cosine decay down to 10% of the peak.

Accuracy is measured with greedy decoding on held-out prompts, and split by problem kind. We also record format: the fraction of replies that contain a parseable answer. The two can move apart, and that gap tells us what was learned.

Full fine-tuning ran on both machines. Overall accuracy is the same, 74.5%. The split by problem kind differs by a couple of points, so the two runs are not identical.

The H100 took 132.5 s and the CPU took 2463.8 s. Both times include an evaluation every 50 steps. Both machines were shared with other jobs, and the repository README records an earlier identical H100 run that took 102 s. So these times are single observations, and we make no speed claim from them.

Two controls follow, both on the H100. The first starts from random weights instead of the pretrained model. The second packs the batches.

The random-weights run is the clearest control in this tutorial. It is a randomly initialised SmolLM2-135M, trained with SFT only. We tried no DPO or RL from it. It learns the format: 100.0% of its replies contain a parseable answer. It does not learn the arithmetic: accuracy is 1.5%.

At step 500 its logged training loss is 0.35, against 0.02 for the pretrained model, and it was still falling. So 500 steps may simply be too few for a model trained from scratch. Within this budget, the arithmetic does not come from SFT alone. The likely reading is that pretraining put the capability in the weights, and SFT teaches the model to show it in the right form. The base model scores 0.0% before SFT because it never writes The answer is N., and its format score is also 0.0%.

The packed run scored 69.0%, below the padded run. It used 5 rows of 256 tokens per batch, chosen to give about as many tokens per step as the padded batch of 16. The two runs took the same number of steps, but the packed run saw fewer target tokens. By step 500 it had seen 206,376 and the padded run 230,348 (the target_tokens field in each saved history). This is one seed, and one standard error on 200 prompts is about 3 points. The gap is confounded by that token deficit and by the different batch size. A 5.5-point gap is also within the noise we expect. So this run does not show that packing hurts quality.

Each script draws its own 200 held-out prompts. The periodic evaluation inside a run uses only the first 100 of them, and the final evaluation uses all 200. So the two can differ even at the last step. The H100 full run read 77.0% on 100 prompts at step 500, and 74.5% on all 200. Later stages draw different prompts again, so the same checkpoint has a different “before” value there.

Checkpoint

  • A checkpoint exists at c06-post-training/checkpoints/sft-full. Every later stage loads it.
  • format rises after training. A flat format means the labels are wrong, not that the model is weak.
Step 07Stage 1: SFT

Compare full fine-tuning with LoRA

Goal Write a LoRA layer by hand, confirm it matches PEFT, and compare it with full fine-tuning on the same task.

Full fine-tuning updates every weight. LoRA freezes them and learns a small correction made of two thin matrices. The derivation is in the theory post, so here we only write the layer.

Derivation inHow LoRA changes a model without rewriting it
Shapes inside one LoRA layer
TensorShapeTrains
base.weight (W)(out, in)No
lora_A(r, in)Yes
lora_B(out, r)Yes, starts at zero
x, output(..., in), (..., out)Output is W x plus the scaled correction.

The wrapping function walks the module tree and replaces each target projection in place. Merging reverses this and folds B A into W, so later stages can load a plain model.

LoRA matches full fine-tuning on this task, 75.0% against 74.5%, with 4,884,480 trainable parameters instead of 134,515,008. The saved adapter is 18.7 MB, against 513.2 MB for the full model. A gap of half a point is well inside the noise of one seed. The two runs use different learning rates, 1e-3 for LoRA and 5e-5 for full fine-tuning. A larger learning rate for adapters is common practice.

The table leaves out time on purpose. The H100 runs took 132.5 s for full fine-tuning and 208.5 s for LoRA, one run each. Run-to-run variation on this shared hardware was large enough that we do not call that a speed difference.

Memory needs its own benchmark. Peak memory only ever goes up, so one evaluation that generates text would hide the training number. bench_memory.py therefore runs each mode in a fresh process that only loads the model and takes optimizer steps. The H100 run is below. It used 20 steps at batch 16.

On the H100 at batch 16, LoRA's peak is 4,695 MiB and full fine-tuning's is 5,938 MiB. That is about 21% lower for LoRA. The seconds per step in the last column are single runs and are noisy, so we draw no speed comparison from them.

The same benchmark on the CPU gives a different answer. The CPU number is the peak resident memory of the whole process, so it includes Python and the libraries. These runs took 10 steps each, at batch 16 and at batch 2.

Nuance

Whether LoRA saves memory depends on the setting. On the H100 at batch 16, it did: 4,695 MiB against 5,938 MiB. On the CPU at batch 16, LoRA’s peak was higher: 7,381 MiB against 7,045 MiB. On the CPU at batch 2, it was lower again: 1,897 MiB against 3,165 MiB.

A likely cause of the batch-size flip is this. Full training keeps a gradient and two Adam buffers for every weight, and LoRA keeps them only for the adapters. That saving is fixed. The activations kept for the backward pass grow with the batch, and LoRA does not obviously shrink them. At a large batch the fixed saving may be small next to the activations. We did not isolate this.

One CPU number is unexplained. The LoRA run reached 7,001 MiB already after the first forward pass, against 5,432 MiB with full fine-tuning. Extra activations in the LoRA layers, or allocator and resident-memory effects of the whole process, are possible. Both are untested. On the H100 the first forward was lower with LoRA, 4,275 MiB against 4,516 MiB. We ran no H100 batch-size sweep, so LoRA does not cut memory in proportion to its trainable parameters, and that is all we can say.

Step 08Stage 2: DPO

Build a preference dataset

Goal Prompt, chosen and rejected, laid out as tensors so that the prompt can never enter the score.

The SFT model can write in the right form, but it still gets sums wrong. Now we change the signal. Instead of giving the answer, we say which of two answers is better. A preference pair has three parts.

We build pairs in two ways. The first is synthetic. The chosen reply is the correct solution, and the rejected reply is the same solution with a carry-sized error, so the two differ only in the digits that matter.

The second way is on-policy. We sample from the SFT model itself, then pair one of its right answers with one of its wrong answers on the same prompt. These are the mistakes this model actually makes. A prompt where every sample is right, or every sample is wrong, gives no pair.

Next, tensors. We tokenize the prompt with its generation header. Each completion is whatever follows the prompt in the full rendered conversation, so it includes <|im_end|> and the trailing newline.

Shapes of a preference batch with B pairs
TensorShapeMeaning
input_ids(2B, L)Rows 0 to B−1 are prompt + chosen. Rows B to 2B−1 are prompt + rejected.
attention_mask(2B, L)1 on real tokens, 0 on right padding.
completion_mask(2B, L)1 on response tokens, 0 on prompt and padding.

Checkpoint

  • A chosen row and its rejected row have identical prompt tokens.
  • completion_mask sums to the reply length for each row.
Step 09Stage 2: DPO

Compute sequence log-probabilities

Goal The probability the model gives a whole reply, as a sum over tokens. DPO, REINFORCE and GRPO all use it.

The chain rule says a reply’s log-probability is a sum: log π(y | x) = Σt log π(yt | x, y<t). Start with the naive version, which is a Python loop. It sits in a test, because it is the reference every faster version must match.

Now the batched version. gather_logprobs picks the target’s log-probability without building the whole log-softmax tensor. For a vocabulary of size V that saves a large allocation at every position.

Shapes in a sequence log-probability
TensorShapeMeaning
logits(2B, L−1, V)After dropping the last position.
targets(2B, L−1)input_ids[:, 1:].
logps(2B, L−1)Log-probability of each actual next token.
mask(2B, L−1)completion_mask[:, 1:].
total(2B,)One number per row.

Figure 6 walks through these tensors for one pair.

Break it

Use the wrong shift on the mask: completion_mask[:, :-1]. Each mask entry now lines up with the token after the one it describes. So the score skips the first reply token, and it picks up a pad token wherever a row has padding. The shapes still match, so nothing crashes.

Step 10Stage 2: DPO

Freeze a reference and write the DPO loss

Goal The DPO loss in a few lines, with a reference model that takes no gradient and no updates.

DPO rewards the policy for moving probability toward the chosen reply, relative to where it started. Where it started is the reference: a frozen copy of the SFT model. The theory post derives why this ratio acts as an implicit reward.

Derivation inTeaching a model what we prefer

Before any training we can predict the first loss. The reference equals the policy, so both log-ratios are 0, the margin is 0, and the loss is −log σ(0) = log 2, about 0.6931. Any other first value means the two models differ. Dropout left on, for example.

Play with the loss in Figure 7. The readout that matters most is the gradient weight.

Insight

The sigmoid weight σ(−m) is what makes the gradient fade, and the reference sets what “far from the start” means. Differentiating the loss gives −σ(−m) β (∇ log π(chosen) − ∇ log π(rejected)). At margin 0 the weight is 0.5, and it falls toward 0 as the pair gets separated. So the pull on a pair weakens once the policy has moved far enough from the reference.

That is one brake on how far DPO moves. The learning rate, the number of steps and the data limit it too. A reference that tracks the policy keeps the margin at 0, so the weight never falls, as step 11 shows. The brake works on the margin, not on accuracy. Step 11 shows runs where the margin grew and held-out accuracy fell.

Test

Three tests hold this down: the first loss is log 2, the reference receives no gradient, and the loss on a real batch equals the loss from TRL’s DPOTrainer on the same tensors.

Checkpoint

  • The first logged DPO loss is 0.6931.
  • test_matches_trl_dpo_trainer_on_the_same_batch passes. It downloads a tokenizer.
Step 11Stage 2: DPO

Train DPO, then debug it on purpose

Goal Run DPO on both kinds of pairs, then see what each classic bug looks like.

All four runs below are on one NVIDIA H100, start from the SFT checkpoint trained on that machine, and use full fine-tuning with beta 0.1 and a batch of 4 pairs. The first two use the default learning rate, 5e-6.

The accuracy went down. These prompts are unseen by the stage being trained, but about 26 to 29% of their questions also appeared in the SFT training set. Before and after numbers within the stage still compare like with like. The same checkpoint scored 79.5% before DPO on this script’s 200 held-out prompts, and 44.5% after DPO on synthetic pairs and 42.0% after DPO on on-policy pairs. Note that 79.5% is not the 74.5% of the SFT step. Each script draws its own held-out prompts, so compare a stage only with its own “before” value. A lower learning rate hurts less. It does not fix it.

Nuance

DPO made held-out accuracy worse in all four runs, and the training signals looked as expected. The margin grew above 0 in every run, and pair accuracy in the logged batches of 4 pairs was mostly high, as the table shows. The loss equals TRL’s DPOTrainer loss on the same batch, so the loss formula is unlikely to be the cause.

A possible cause is likelihood displacement. The chosen and rejected replies share almost every token, as the pair in step 9 showed. Pushing the rejected reply down can pull the chosen reply down with it, and the margin still grows. We did not measure this.

We also did not tune beta, the number of steps or the learning rate beyond the two values shown. A smaller beta, an added SFT term on the chosen reply, or fewer steps are the obvious things to try. On-policy pairs came from 305 of 800 prompts, because the SFT model answered the other prompts all right or all wrong in four samples.

DPO fails quietly. Every bug below produces a loss that runs and often goes down. Each bug in the list has a test here. The script break_it.py runs most of them on the real model.

Step 12Stage 3: reward model, optional

Train a pairwise reward model

Goal See the explicit reward model that DPO lets us skip, and see that its loss has the same form.

The older route to preferences trains a separate model to score replies, and then trains the policy with reinforcement learning against that score. This step is optional. We build only the scorer, because seeing it clarifies what DPO removes.

Insight

Put this loss next to the DPO loss. Both are −log σ(r(chosen) − r(rejected)). In the reward model, r is the output of a trained head. In DPO, r is β log(π / ref). So DPO is a pairwise reward loss in which the reward model has been replaced by a ratio the policy already computes. That removes a second model to train and a separate RL phase, at the cost of having no separate scorer to reuse elsewhere.

This reward model is weak. Chance is 50%. With 300 steps it scores 55.5% on 200 held-out pairs, which is within about two standard errors of chance. A likely reason is that to score an answer, the head has to do the arithmetic itself from one hidden state. We did not test that. The practical lesson is that when an exact checker exists, a learned reward model is the wrong tool, and Stage 6 uses the exact reward instead. Both runs used one seed.

Step 13Stage 4: REINFORCE

Write REINFORCE and measure its noise

Goal The simplest policy gradient, plus a meter that shows why nobody stops there.

Now the model samples its own answers, and a checker scores them. The simplest update is REINFORCE: raise the log-probability of each sample in proportion to its reward.

Derivation inReinforcement learning from first principles

With a 0 or 1 reward and no baseline, every wrong sample contributes nothing. Every right sample pushes up whatever it happened to say. A baseline fixes the first problem. We compare four weightings on the same budget of rollouts.

Try them in Figure 8. Each cell is one sampled reply. Click a cell to flip its reward. Then step through the estimators.

To measure noise, we draw several independent gradient estimates for the same policy. Two estimates of one gradient should point the same way, so we report their mean pairwise cosine and a signal-to-noise ratio.

Two limits on this measurement. The gradient is that of the last transformer block only, 3,540,096 of the 134,515,008 parameters, and not of the whole model. And each of the 12 estimates for an estimator uses a fresh slice of prompts from one pool, 32 prompts for the two one-sample estimators and 8 for the two group estimators. So the estimates are independent draws over prompts and samples, and not repeated draws for one fixed batch. The estimators also see different prompt slices from each other.

The CPU run used the SFT checkpoint trained on the CPU. The H100 run used the checkpoint trained on the H100, so the two runs differ in both hardware and model.

Pure noise gives an SNR of about 0.091 with 12 estimates. Every estimator on both machines sits close to it, or modestly above it. For the last block, two independent gradients from 32 rollouts barely agree on a direction. That is the point of this measurement: at this budget, policy-gradient estimates of that slice are very noisy. We did not measure the other layers.

The measurement does not rank the estimators. On the CPU, the estimator with no baseline had the highest SNR, 0.147. On the H100 it did not stand out, 0.115. The two runs differ in checkpoint and in hardware, and 12 estimates per estimator is a small sample. So we cannot say whether the gap between those two numbers is real.

Do not read the CPU result as “no baseline is best”. A possible reason for its higher SNR is that, without a baseline, every rewarded sample pushes up its own log-probability. That shared direction is consistent without saying much about the reward. We did not test this.

Nuance

A group where all samples score the same has weight 0 everywhere. If each sample is right with probability p, a group of G is flat with probability pG + (1−p)G. For G = 4 that is 12.5% at p = 0.5 and about 66% at p = 0.9. So group baselines learn the most where the model is unsure, and little on problems it almost always gets right or almost always gets wrong.

Checkpoint

  • test_reinforce_sums_over_tokens_and_ignores_padding passes.
  • test_estimators_zero_out_constant_rewards_except_vanilla passes.
Step 14Stage 5: GRPO

Write the GRPO loss

Goal Group advantages, old log-probs, clipping, a KL penalty and token masks, each on its own line.

GRPO samples G completions per prompt and uses the group as its own baseline: Ai = (ri − μr) / σr. There is no value network to train. The reasoning behind this is in the theory post.

Derivation inHow reinforcement learning teaches models to reason

We can check this by hand. With rewards [1, 0, 0, 0] the mean is 0.25 and the unbiased standard deviation is 0.5, so the advantages are [1.5, −0.5, −0.5, −0.5]. test_group_advantages_by_hand asserts exactly these numbers.

Now the loss. Every line below works per token, and old_logps comes from the policy that sampled the data.

Shapes in the GRPO loss, for N = P × G completions of up to C tokens
TensorShapeMeaning
logps(N, C)Log πθ of each sampled token, with gradient.
old_logps(N, C)Log πold. Fixed for all inner steps.
ref_logps(N, C)Log πref, from the frozen model. Used by the KL term.
advantages(N,) → (N, 1)One scalar per completion, broadcast to its tokens.
mask(N, C)1 up to and including the first <|im_end|>.
per_token(N, C)Clipped surrogate plus β times KL.
lossscalarMean over tokens in each sequence, then over sequences.

The clip is the part most people find hard to picture. Drag the ratio in Figure 9, and flip the sign of the advantage.

Nuance

Clipping is one-sided. With a positive advantage, moving past 1 + ε earns nothing more, but falling below 1 − ε still costs you. With a negative advantage the flat part flips to the low side. Raising the probability of a bad token keeps getting punished however far it goes. test_negative_advantage_is_never_clipped_upward asserts this.

The KL term uses the k3 estimator: with d = log ref − log π, it computes ed − d − 1. This is at least 0 for any d, and it is exactly 0 at the reference. It has the same purpose as the DPO reference: it stops the policy drifting too far from where it began. Setting beta=0 removes the reference model altogether.

Nuance

There are two ways to average. loss_type="grpo" averages per sequence first, so a short reply counts as much as a long one. loss_type="dapo" averages over all tokens. test_grpo_loss_is_length_normalised_but_dapo_is_token_weighted gives a case where the two disagree on sign: 1.0 for GRPO and −0.2 for DAPO, on the same tensors. Choosing a reduction therefore decides whose gradient wins.

Nuance

The two divisions in GRPO are not neutral. Liu et al. argue that both bias the objective. Dividing by the standard deviation gives more weight to questions whose rewards spread less. By hand, for a group of 4 and binary rewards: one right answer gives it an advantage of +1.5, and two right answers give each one about +0.87.

Dividing by reply length weakens the penalty on long wrong replies, and the paper reports that this inflates response length. Their Dr. GRPO removes both divisions. We keep them, because we are matching GRPO and TRL, and scale="none" removes the first. We have not measured whether this matters on our tasks. The exercises ask you to try.

Break it

Recompute old log-probs inside the inner loop, instead of holding them fixed. The ratio is then exactly 1 at every step, clipping never fires, and the update loses its limit. No error appears. The stat ratio_mean is your only clue, so log it.

Test

Our loss is checked against TRL’s GRPOTrainer._compute_loss, on the same tensors and for both reduction modes. The advantage formula is checked against TRL’s too.

Checkpoint

  • test_first_inner_step_has_ratio_one_and_no_clipping passes.
  • test_matches_trl_grpo_loss_on_the_same_tensors passes for both grpo and dapo.
Step 15Stage 7: rollout engine

Build the rollout engine

Goal A small system that turns prompts into a training batch, and records which policy version made each sample.

The GRPO loss needs tensors that do not exist yet. Something has to sample them, score them and pad them. This machinery becomes the larger part of an RL system once rewards get slow, so we write it as its own layer.

Sampling needs left padding, so that the last prompt token of every row sits in the same column and the next token is always generated from there. The completion is then right-padded, and its mask ends at the first stop token.

To score those tokens we run one forward pass over prompt plus completion, and keep only the last C positions. That matches TRL’s layout.

Each rollout records the problem, the tokens, its reward, and the version of the policy that produced it.

Figure 10 follows one batch through the engine.

The CPU run is first, on an AMD EPYC 7R13 with 8 threads. Each run generates 64 rollouts of up to 48 new tokens.

The same benchmark on one NVIDIA H100.

Sequential generation gave 1.8 rollouts per second on the CPU and 3.9 on the H100. One batched call gave 6.8 on the CPU and 33.7 on the H100. Batching is the big lever on both machines.

Two threaded workers gave 7.2 on the CPU, about the same as one batched call. On the H100 they gave 24.8, below one batched call. A likely cause is that both workers share one GPU and one Python process. The two-worker design should pay off when replicas sit on different devices or the environment is slow, as in agent RL. We did not test that here.

Pushing new weights to two replicas took 191 ms on the CPU and 14 ms on the H100. Scoring with the exact reward took under a millisecond in every run. Each figure is one run on shared hardware.

Nuance

These are weak results, and we report them as they are. At learning rate 1e-5, GRPO ended below its start in all three seeds, by 14.5 to 21 points. REINFORCE ended 7, 4 and 1 points below its start. One run has a standard error of about 3 points, so the REINFORCE gaps of 4 and 1 points are within noise, the 7-point gap is borderline, and the GRPO gaps are larger than noise.

At learning rate 1e-6, one seed each, both stayed within noise of the start, 78.5% for GRPO and 81.0% for REINFORCE. The policy moved far less, and the accuracy stayed near its start. We have one learning-rate pair, so this shows the two moving together and does not show the cause.

We did not search over learning rates, batch sizes or group sizes. A comparison of GRPO and REINFORCE from these runs is not safe: each has three seeds at one setting.

Nuance

The reward in a training log is measured on samples at temperature 1, from 32 rollouts per step, so it is noisy. In the last 12 steps of the GRPO seed 0 run it ranged from 0.31 to 0.69. Accuracy is measured with greedy decoding on other prompts.

They answer different questions. The sampled reward tells you what the update sees. The greedy accuracy tells you what a user would get. Report the second one, and watch the first one to debug. That is why Figure 11 plots the greedy accuracy.

Why did the model not improve? We did not isolate a cause. The SFT model already solves about 80% of problems, so some groups probably have identical rewards and so no advantage. We did not measure how many. That could slow learning, but it would not explain a fall in accuracy. Things worth trying are a harder task or a weaker start, a larger group, a smaller learning rate with more steps, and the exercises at the end.

Key insights and nuances

  • Most of a conversation is context, not targets. In the example here, 66 of 122 tokens are masked, yet all of them run through the model. A loss value compares only with a loss built on the same mask. Step 3
  • The stop token is the target people lose. Setting pad to <|im_end|> erases it without any error, and the model gets no training signal to finish a reply. Step 3
  • Packing depends on more than position ids. The Hugging Face path that builds a block mask from position resets only applies when no KV cache is created. Step 5
  • Pretraining carries the capability, and SFT shows it. The same SFT recipe from random weights learns the answer format (100.0%) and almost none of the arithmetic (1.5%). From the pretrained model it reaches 74.5%. Step 6
  • LoRA's memory saving depends on the setting. On the H100 at batch 16 its peak was lower than full fine-tuning's. On the CPU at batch 16 it was higher, and at batch 2 it was lower. A likely cause is the activations kept for the backward pass, which LoRA does not obviously reduce. We did not isolate it. Step 7
  • The sigmoid weight makes the DPO gradient fade, and the reference sets the starting point. A self-reference gives a margin of 0 and a loss stuck at log 2, but the gradient is not 0. Step 10, Step 11
  • DPO lowered held-out accuracy in all four runs. The margin grew and the loss matches TRL on the same batch, yet accuracy fell from 79.5% to between 42.0% and 65.5%. Likelihood displacement is a possible cause. We did not measure it. Step 11
  • Compare each stage only with its own “before”. Each script draws its own 200 held-out prompts, so one checkpoint scores 74.5% in the SFT step and 79.5% in the DPO step. Step 11
  • A learned reward model is the wrong tool when an exact checker exists. Ours reached 55.5% and 59.5% held-out pair accuracy, against 50% for chance. Step 12
  • DPO is a pairwise reward loss without the reward model. Both have the form −log σ(r(chosen) − r(rejected)). In DPO, r is a log-ratio the policy already computes. Step 12
  • On the last transformer block, a 32-rollout gradient estimate is mostly noise. All four estimators had a signal-to-noise ratio close to, or modestly above, the pure-noise value of 0.091 on both machines. The highest was 0.147, so the measurement does not rank them. Step 13
  • Group baselines teach nothing on flat groups. A group of 4 is flat 12.5% of the time at p = 0.5 and about 66% at p = 0.9. Step 13
  • Clipping is one-sided. A bad token that gains probability keeps being punished, however far it goes. Step 14
  • The reduction decides whose gradient wins. GRPO and DAPO averaging can disagree even on the sign of the loss. Step 14
  • Neither RL run improved the model. At lr 1e-5, GRPO ended at 64.5%, 65.5% and 59.0% from a start of 80.0%. REINFORCE ended at 73.0%, 76.0% and 79.0%. At lr 1e-6 both stayed near the start. Step 16
