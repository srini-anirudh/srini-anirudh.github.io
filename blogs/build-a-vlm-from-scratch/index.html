The plan

A vision encoder returns vectors. A language model reads token ids. What has to happen between them, tensor by tensor, before a language model can answer a question about a picture?

Less than you might expect. We will not write a new attention layer. We take two pretrained models that have never seen each other: SigLIP for vision and SmolLM2 for language. Then we write the small projector that joins them, plus the bookkeeping around it.

Most of this tutorial is that bookkeeping. It decides how many tokens a picture costs, which token the loss may look at, and which picture each token belongs to. Almost every bug in a VLM lives here, and many of them raise no error.

In the shapes below, B is the number of samples, N is the padded sequence length, and n is the number of crops in the whole batch.

Step 01

Write the image processor

Goal Turn any picture into exactly the tensor SigLIP expects, and match Hugging Face's processor to the last bit.

SigLIP learned from pictures prepared in one exact way. If we prepare them differently it still returns numbers, and nothing raises. So the first thing we write is the part with no room for error.

The recipe has four parts: convert to RGB, resize to 224 × 224 with bicubic filtering, scale to [0, 1], then subtract the mean and divide by the standard deviation. For SigLIP both are 0.5, so pixels land in [-1, 1].

Look at the highlighted lines. np.asarray(..., dtype=np.float32) / 255.0 gives floats in shape H × W × 3. The next line applies the mean and standard deviation. The last line moves channels first, because the encoder's patch embedding is a convolution that expects 3 × H × W. The .copy() gives the tensor its own contiguous memory rather than a view with shuffled strides.

The class wraps these in a call that takes a list of pictures and returns one flat batch of crops. For now each picture is one crop. Step 9 changes that.

Now run it on a 480 × 360 picture of two red circles, and compare with Hugging Face's own SigLIP processor.

Shapes in step 1
TensorShapeMeaning
PIL image480 × 360Width first in PIL. Mode RGB.
after resize224 × 224The aspect ratio is lost here. Step 9 deals with that.
pixel_values(1, 3, 224, 224)float32, channels first.

The first pixel is 0.937. The canvas shade was 247, and (247 / 255 − 0.5) / 0.5 = 0.937, so the arithmetic checks out by hand.

Insight

The red in our picture is (220, 40, 40), so the lowest value should be (40 / 255 − 0.5) / 0.5 = −0.686. In step 2, where the picture is already 224 × 224 and no resize happens, the minimum is exactly −0.686. Here it is −0.788. Bicubic filtering overshoots at sharp edges and invents values the picture never held. So the filter is part of the input the encoder sees, and a processor that swaps it does not match the training recipe.

Test

The trusted implementation is Hugging Face's SigLIP processor. We test three sizes of random noise, so nothing can agree by luck.

The script above printed a maximum difference of 0.00e+00, so the two agree exactly.

Break it

Remove to_rgb and pass an RGBA picture, for example a PNG with transparency. It fails loudly, which is the good case.

Four channels meet a three-number mean. The shape in the message, with a 4 last, is the clue. A wrong mean is worse: it raises nothing, and you only notice when captions get worse. Step 13 measures how much.

Is this code fast enough? We start naive and measure before changing anything.

At 1920 × 1080 the resize takes 11.71 ms of the 12.75 ms total. Normalising takes 0.79 ms. So rewriting our NumPy lines would save almost nothing. The bottleneck is the resize, which belongs to Pillow, and our version already takes less time than the Hugging Face one, which needs 25.70 ms. We stop here.

Checkpoint

  • max |ours - hf| prints 0.00e+00.
  • test_matches_hf_siglip_processor passes.
Step 02

Run the pretrained vision encoder

Goal See what the encoder returns: one 768-number vector for each of 196 patches.

We use the encoder as it comes. The theory post explains what is inside it. Here we only want to see what comes out.

Theory inInside a modern vision encoder

SigLIP was trained for contrastive matching, so its last piece pools all patch tokens into a single vector. A VLM needs to read the picture, so we want every patch. Setting vision_use_head = False removes the pooling head and leaves the patch tokens alone.

The count is easy to derive. A 224 px crop with 16 px patches gives a grid of 224 / 16 = 14 per side, so 14 × 14 = 196 tokens. SigLIP has no class token, so all 196 are patches. Each has 768 numbers. In the usual notation this is B × Nv × dv, and here it is (2, 196, 768).

The script also checks that these vectors mean something. Two background corners of a picture have cosine similarity 0.600, against 0.349 for an average pair. Similar patches give similar vectors, which is the property the language model will later rely on.

Shapes in step 2
TensorShapeMeaning
pixel_values(2, 3, 224, 224)Two crops.
last_hidden_state(2, 196, 768)The final layer, after a closing LayerNorm.
hidden_states13 tensors of (2, 196, 768)Patch embeddings, then one tensor per layer. No closing LayerNorm.
sim(196, 196)Cosine similarity between the patches of one picture.

Nuance

Papers often say "use the second-to-last layer". LLaVA-1.5 does: its config sets vision_feature_layer to −2. Look at what that changes in SigLIP. hidden_states[-2] ranges from −212 to +70. last_hidden_state ranges from −43 to +27. Part of the gap is that last_hidden_state has passed through post_layernorm and the entries of hidden_states have not. We checked with one line. The first value asks if hidden_states[-1] equals last_hidden_state. The second applies post_layernorm first.

So switching layers also switches off a normalisation, and the projector then has to cope with those outliers.

Test

test_vision_tower_matches_full_siglip loads the complete SigLIP model and asserts that our headless encoder gives the same patch tokens, within 1e-5. Removing the head changed nothing upstream of it.

Checkpoint

  • last_hidden_state has shape (2, 196, 768).
  • test_vision_tower_matches_full_siglip passes.
Step 03

Write the projector

Goal Map vision features to the language model's size, starting with one linear layer, and fold tokens to spend fewer of them.

Vision features have 768 numbers. SmolLM2 expects 576. Something must map one to the other, and this is the only new neural network in the model. We start with the smallest option, then add to it.

Each layer works on the last axis only, so every patch token is mapped on its own. The token count does not change. Let us run both, and compare their output with real SmolLM2 token embeddings.

The parameter counts can be derived by hand. A linear layer has din × dout weights and dout biases, so 768 × 576 + 576 = 442,944. The MLP adds a second layer of 576 × 576 + 576 = 332,352, for a total of 775,296.

Insight

Read the std column. Real token embeddings have a standard deviation of 0.107. A fresh Linear(768) emits 1.162, about 11 times larger. The fresh MLP emits 0.452, about 4 times larger. The language model has only ever seen inputs on the first scale. So a new projector does not hand it a weak signal. It hands it a loud one. You might expect training to bring that down. Step 13 measures where it ends up, and the answer is a surprise.

Spend fewer tokens with pixel shuffle

196 tokens per crop is a lot for a small language model. Every token costs attention time and cache memory. The SmolVLM family folds neighbouring patches together before projecting. It does not average them. It concatenates them, so no numbers are lost.

The output above confirms it: after pixel shuffle has shape (1, 49, 3072) with exactly the same mean, standard deviation and range as the input. The same numbers, in a different arrangement.

Read it as a trade. Shuffle makes the projector about 2.7 times bigger and cuts the language model's sequence and cache by more than 3 times. The projector is the only part we pay for in training, and even at 2.1 million parameters it is under 1% of the model. Cheap tokens are worth a slightly bigger bridge.

Assemble the model

Now we can join the parts. A language model needs one more thing first: a token for the picture.

Three lines matter most:

  • add_tokens gives <image> its own id, 49152. It must be special, or the tokenizer could split it.
  • resize_token_embeddings(..., pad_to_multiple_of=64) grows the embedding table from 49152 rows to 49216. That is why logits have 49216 columns. Only one new row is used.
  • with torch.device("meta") builds a skeleton with no memory, so we do not spend time randomly initialising weights we are about to replace.

Test

test_only_projector_gets_gradients freezes the encoder and language model, runs one backward pass and asserts that gradients exist only on the projector. test_pixel_shuffle_matches_loop rebuilds each token with plain Python loops. test_pixel_shuffle_equals_idefics3 compares our function with Idefics3Connector.pixel_shuffle from transformers, using torch.equal.

Checkpoint

  • The model prints 2,102,400 projector parameters.
  • test_only_projector_gets_gradients passes.
Step 04

Put image features into the sequence

Goal Replace placeholder rows with image features, first with a loop and then with one call that gives the same result.

SmolLM2 does not need a new input path. Like most Hugging Face language models, it accepts inputs_embeds in place of input_ids. So the plan is short: embed the tokens as usual, then overwrite the placeholder rows with image features.

The reference version does this one position at a time, so nobody can misread it. It starts with a check, because a count mismatch is the most common VLM bug.

Now the fast version. masked_scatter copies values from a source into the true positions of a mask, in reading order. That is the same order as our loop.

The model wraps this into two methods.

Shapes in step 4
TensorShapeMeaning
input_ids(1, 63)14 text ids and 49 placeholder ids.

text_embeds(1, 63, 576)Placeholder rows hold a meaningless vector for now.
features(1, 49, 576)From the projector.

Nuance

masked_scatter is 8 times faster than the loop here: 0.461 ms against 3.764 ms for 8 samples. That is not why we use it. Encoding just 7 crops takes 438 ms in the benchmark in step 9, so even the loop is a tiny share of the work. We use it because it is one line with no index to get wrong. It is also what Hugging Face does: LLaVA and Idefics3 both end in inputs_embeds.masked_scatter(...) in transformers 5.22.

Test

The two versions must agree exactly, and gradients must reach the features through the merge.

test_gradient_flows_to_features sums the output, calls backward() and asserts that every feature gradient is exactly 1. If the merge had detached the features, the projector could never learn.

Break it

scripts/break_it.py builds a processor that expects 196 tokens per crop and feeds it to a model that shuffles down to 49.

Why write our own check when PyTorch has one? Because PyTorch only checks one direction. With too few features, masked_scatter raises Number of elements of source < number of ones in mask, which says nothing about tokens per crop. With too many, it fills the seats, ignores the rest and raises nothing. To debug a mismatch, print processor.image_seq_len and model.config.image_seq_len side by side. They must be equal.

The last frame of Figure 3 is the harder case. Reverse pixel_values and each sample reads another sample's picture. Counts match, so nothing raises. The check we just wrote cannot catch it. Only order protects you, so keep crops and prompts in the same order all the way through the collator.

Checkpoint

  • Position 3 equals features[0, 0], and text rows are untouched.
  • test_naive_equals_masked_scatter passes.
Step 05

Build the multimodal sequence

Goal Turn a conversation and a picture into token ids, with one seat per image feature.

The placeholders have to come from somewhere. The sequence builder turns a conversation and a picture into token ids, with the right number of seats. The layout we want is:

SmolLM2-Instruct uses ChatML. Its tokenizer's BOS token is <|im_start|> itself, so every ChatML sequence already starts with BOS, and we add nothing in front of it. We render the conversation in pieces, and each piece knows if it will be supervised. Step 6 needs that.

A <image> marker in the text then has to become one placeholder per feature vector. This is the rule that joins the processor to the model.

The text costs 20 tokens. The picture costs 49. Note how the model's tokenizer really behaves: assistant is two tokens, ass and istant, and Ġ marks a leading space. You would not guess this, so we print it.

Test

Rendering in pieces could give different ids than tokenising the whole string, because tokenizers can merge across a boundary. test_piecewise_tokenisation_equals_whole_string proves they match for this template. test_chat_template_matches_smollm2 compares our string with the one the SmolLM2 tokenizer renders from its own template, for a conversation that has a system message. Without one they differ on purpose. SmolLM2's template then inserts a default system message, You are a helpful AI assistant named SmolLM..., and ours adds none. test_we_leave_out_smollm2s_default_system_message pins that difference.

Break it

Forget the marker, or use a tokenizer that never got the new token. Both fail early, and that is deliberate.

The second check matters more than it looks. A plain SmolLM2 tokenizer does not fail on <image>. It splits the text into three ordinary tokens, [44, 5028, 46], and looking the string up as one token returns the unk id, 0. So without this check every <image> would become a few normal text tokens. The count check in merge.py would then find no seats at all.

Checkpoint

  • The sequence has 69 tokens, 49 of them placeholders.
  • test_placeholders_expand_to_image_seq_len passes.
Step 06

Choose what the loss sees

Goal Supervise only the reply and its stop token, and see what happens otherwise.

Language models learn by predicting the next token. In a VLM we do not want a loss on every position. The model should not be asked to predict <image>, or the question. It should be asked to write the answer, and to stop.

The rule fits in one line. Any position outside a supervised piece gets label −100, the value cross-entropy ignores.

The table in step 5 shows the result: 69 positions, of which 5 are supervised and 64 are ignored. Try other choices in the figure.

The readout on the right shows a detail that catches people out. The label at position t is scored against the logits at position t − 1. The first target, Two at position 63, is predicted from position 62, the newline after assistant. Hugging Face shifts the labels inside the model, so you pass them unshifted.

labels(B, N)−100 everywhere except the reply and its stop token, and always on padding.

Test

test_forward_shapes_and_loss_matches_manual_cross_entropy shifts the logits and labels by hand and calls F.cross_entropy with ignore_index=-100. The result equals out.loss to within 1e-6. So we know what the number in the training log means. test_labels_supervise_only_the_answer decodes the supervised ids and asserts they read exactly as the reply followed by <|im_end|>.

Break it

Put a label on every token. Nothing raises, and the model trains. The only clue is the loss, on a fresh projector with one example:

The script counts 69 labels. After the shift only 68 are scored, because nothing comes before position 0, so the first label is never predicted. Loss 11.458 is above ln(49216) = 10.8, the score of a uniform guess, so the model is confidently wrong on most positions. It has never predicted a placeholder, and that id's embedding row is brand new. Worse, 49 of the targets now ask for <image>, so most of the loss now rewards predicting a meaningless id. If your first loss is above ln(V), look at your labels before your learning rate.

Checkpoint

  • 5 positions are supervised and 64 are ignored.
  • test_labels_supervise_only_the_answer passes.
Step 07

Give every token a position

Goal Number a sequence that mixes pictures, text and padding, and see why a picture pushes text away.

Every token needs a position for RoPE. The simplest answer treats an image token like any other token: it takes the next integer. SmolLM2, LLaVA and SmolVLM all work this way.

Theory inPosition bookkeeping in VLM pipelines

Why not just use 0, 1, 2 up to N? Because of left padding, which generation needs. A left-padded sample starts with a pad, and its first real token must still get position 0. cumsum handles this. We print it on a tiny model, with 4 image tokens per crop and one token per character, so the whole tensor fits on screen.

Look at sample 1. Its attention mask starts with a 0, and its positions read 1, 0, 1, 2, 3, 4. The first value belongs to the pad slot. The real tokens start from 0.

There is a cost to 1D positions. A 49-token picture pushes the following text 49 places further away. Qwen2-VL takes a different route, M-RoPE, where each token gets three coordinates and a picture only advances the text by its longest side.

Rows are t, h and w. The four image tokens share t = 0 and spread over a 2 × 2 grid. The text then resumes at 2, not 4. At our real size, 7 × 7, text would resume after 7 positions in place of 49.

Nuance

position_ids_3d is here to look at. TinyVLM does not use it, because SmolLM2's attention applies a 1D rotation, and three coordinates would need the language model itself to split its rotary dimensions by axis. Qwen2.5-VL's config shows that split: mrope_section is [16, 24, 24]. So 3D positions are a change to the language model, not something a processor can add.

Test

test_left_padded_batch_generates_like_single_samples generates a left-padded batch and then each sample alone. The tokens must be equal. If position_ids_1d counted padding, this test would fail. test_position_ids_3d_compresses_image_extent checks a 2 × 3 picture: text resumes at 5, not at 8.

Checkpoint

  • Left-padded positions start from 0 at the first real token.
  • test_position_ids_1d_left_padding passes.
Step 08

Build the attention mask

Goal Build the causal and padding mask as a tensor, then prove it equals the one inside Hugging Face.

Two questions decide whether query position i may read key position j. Is j in the past? Is j a real token? We build that as a tensor, so we can print it and test it.

The broadcasting is worth reading slowly. causal[None] is 1 × N × N. attention_mask.bool()[:, None, :] is B × 1 × N, so it masks out padded keys in every query row. The final [:, None] adds a head axis, so the mask broadcasts over all heads.

# means may attend. The default is an ordinary triangle. Image tokens are causal just like text. The first image token sees nothing of the picture but itself, and only the last one sees all of it. The second block opens up the picture, so every image token can see every other one. PaliGemma goes further, with full attention over the picture and the question together. Change the sizes and see how the tensor reacts.

In practice TinyVLM.forward passes the 2D attention_mask straight to the language model, which builds this same mask internally. So why build it ourselves? So we can see it, and so a test can tie the two together.

Break it

Look at the row labelled pad above. A pad query has no key it may read. Fill that row with minus infinity, as most textbooks do, and softmax divides zero by zero.

The nan then spreads through every later layer, and the whole loss with it. to_additive in masks.py uses the type's minimum value, which gives a harmless uniform row. A nan that appears only with left padding points at this.

Nuance

Opening the image block is a choice, not a fix. PaliGemma states its reason: with full attention over the input, image tokens can look ahead at the question and update their representation. It also trains its decoder with that mask. SmolLM2 was trained on causal attention only, so we keep the causal default, and bidirectional_images stays an option you can measure. We have not measured it in this tutorial.

Checkpoint

  • The printed mask is a triangle with an empty padding row and column.
  • test_explicit_4d_mask_matches_hf_default passes.
Step 09

Handle pictures of any size

Goal Support fixed resize, aspect-ratio padding and tiling, with token counts that change per picture.

So far every picture becomes one 224 × 224 crop. Real pictures are not square. There are three common answers, and each gives a different trade. We write all three behind one method, so the rest of the code does not care.

A fixed resize squashes the picture. Padding keeps the shape by centring it on a square filled with the mean colour.

Tiling keeps local detail. It picks a grid close to the picture's shape, cuts the picture into crops, then adds a thumbnail so the whole scene is still visible in one view. The grid rule is the one in the InternVL model card.

Each crop then becomes image_seq_len tokens. That is the dynamic token length: _expand from step 5 writes num_crops × 49 placeholders, so every picture can have a different count. Try it.

The script prints the same thing for seven sizes, using real crops and no model.

Insight

Compare the 640 × 480 and 2048 × 1536 rows. One picture has more than ten times the pixels, yet both cost 343 tokens. With a tile cap, the token count follows the aspect ratio, not the resolution. The big picture loses detail, and the small one is enlarged to 672 × 448 to fit its grid. If you serve many large documents, your token budget is really set by max_tiles.

Nuance

The docstring says small pictures should not be blown up, and the area check in select_grid does guard against that, but only when two grids tie. The 100 × 50 row shows the gap. Its shape matches 2 × 1 exactly, so there is no tie, and an icon becomes two tiles and a thumbnail. It costs 147 tokens, three times as many as a full 224 × 224 photo. InternVL's rule behaves the same way. If your data has many small pictures, add a minimum size before tiling.

Now we can ask what a picture really costs. The benchmark times one forward pass and measures the KV cache that the language model keeps.

The cache column follows a formula. SmolLM2-135M has 30 layers, keys and values, 3 KV heads of 64 dimensions, and 4 bytes per float32: 30 × 2 × 3 × 64 × 4 = 46,080 bytes per position. Times 63 gives 2.90 MB. Times 1386 gives 63.87 MB. Both match the measured column exactly.

Break it

Excessive resolution is the failure that never raises. break_it.py feeds one 4032 × 3024 phone photo to the model twice: once with a fixed resize, and once with 48 tiles and no pixel shuffle.

The second call costs 49 crops and 9618 tokens. One forward pass takes 18.17 s against 0.29 s, and the cache alone holds 443.2 MB for one sample. The prompt is also past SmolLM2's max_position_embeddings of 8192, and still nothing raises. RoPE computes its rotations on demand and has no table to overflow, so the model just reads positions it never saw in training. Check the token count first when a VLM is slow, runs out of memory or gets strangely worse on big pictures.

Insight

Read the encode column against the shuffle column. With 7 crops, encoding takes 438 ms with shuffle and 414 ms without. The difference is noise, because the encoder has already run by the time shuffle happens. All of the saving is in the language model: 267 ms against 955 ms, and 16.5 MB of cache against 63.9 MB. So token compression after the encoder cannot help when encoding is your bottleneck. Only fewer crops can.

Nuance

These timings come from a CPU on a server that was also running other work. Trust the token and cache columns fully, and treat the milliseconds as rough.

The same benchmark ran once on a GPU. It is a single run, so read it as one measurement.

On the H100 every row takes 33 to 36 ms, whatever the token count. That suggests one sample leaves the GPU mostly idle, so the extra tokens cost almost nothing in time. We did not profile it. They still cost memory: peak memory grows from 980 MB to 1636 MB, and the cache column is the same as on the CPU. So on a GPU at batch size 1, token count shows up in memory first. Larger batches have not been measured.

Test

Checkpoint

  • test_tile_count_matches_prediction passes.
Step 10

Accept several pictures

Goal Pass two pictures in one prompt and record which token belongs to which picture.

Nothing new is needed for two pictures. The processor already writes placeholders per marker, and masked_scatter already fills them in order. What we add is a record of which token belongs to which picture.

Insight

image_index plays no part in the forward pass. The model works without it. It exists for what comes later: per-picture masks, debugging a wrong answer, and checking that a collator kept things in order. Remember also what the model sees. Between pictures there are only the words we chose, here \nImage 2: . Two markers with nothing between them would give a single run of 98 identical-looking seats, with no sign of where one picture ends. Idefics3 and SmolVLM put a dedicated <fake_token_around_image> around each one for this reason. Ours relies on the prompt.

Test

test_multi_image_boundaries checks that each picture owns exactly its share of seats and that the second starts right after the first when no text separates them. test_features_land_in_order_and_text_is_untouched does the same for a batch where two crops belong to one sample and the third to another. test_batch_with_different_crop_counts_lands_features_in_order tiles one sample into 5 crops and leaves the other at 1, then checks that every placeholder holds the feature of its own crop.

Checkpoint

  • Two pictures occupy positions 8 to 56 and 63 to 111.
  • test_multi_image_boundaries passes.
Step 11

Generate text

Goal Reuse the language model's decoder, and write it by hand once to see what it does.

We do not need a new decoder. The language model already has one, so we build the multimodal embeddings once and hand them over.

One line is easy to trust and hard to see inside, so we write the same thing by hand as a reference.

Follow step_input. On the first pass it holds all the embeddings, images included, and the language model stores keys and values for each position. After that it holds a single row. pixel_values is never used again. The encoder runs once per generated answer.

The answer is confident and useless: I see that you have a question about the "What is the difference between a "variable" and. That is correct behaviour. The projector is random, so the language model gets noise where the picture should be, and it falls back on what it knows. The pipeline works. It has not learned anything yet. Step 13 fixes that.

Dropping the cache on this short prompt makes 20 tokens 2.0 times slower: 2.42 s against 1.24 s. Does that factor stay the same for bigger pictures? We ran the same comparison across the prompt lengths from step 9. Its first row is also a 63-token prompt, timed with the same function, yet it gives a factor of 1.4 where the script above gives 2.0. The benchmark takes the best of 3 runs, the script the best of 5, and the machine had other work on it. So read the factors as rough, and look at how they grow down the table.

Insight

The cache's value depends on how much picture sits in the prompt. At 63 tokens it saves a factor of 1.4 in this run. At 1386 tokens it saves a factor of 7.9. As the prompt grows 22 times, the cached time grows only 1.9 times, from 1.49 s to 2.79 s, because each decode step still pushes only one row through the model. The recomputed time grows 10 times, because every step reruns the whole prompt. So the bigger your pictures, the more a VLM depends on its cache, which is the memory that grew by 22 times in step 9. Pictures make decoding expensive in memory far more than in time.

Step 12

Save and load it like any Hugging Face model

Goal Add a config, a model class and a processor that survive a round trip with identical logits.

The next tutorial trains this model, and it expects the usual Hugging Face calls. Three pieces make that work: a config, a PreTrainedModel subclass, and a registration.

The properties below it derive the token counts from the config, so the processor and the model cannot disagree unless someone overrides one by hand. That is the bug we caused in step 4.

The checkpoint is 889.86 MB. That matches the arithmetic: 222,451,392 parameters at 4 bytes each is 889.8 MB, so the tied head is stored once. After reloading, the logits are identical to the last bit, and tied: True confirms the head and embeddings still share memory.

Nuance

This directory loads through AutoModel only in a process that has run import tinyvlm, because registration lives in the package. A stranger who only has the folder gets an unknown model_type. Publishing to the Hub for them means shipping the code too, with an auto_map entry and trust_remote_code=True. The Hugging Face tutorial covers that path.

Test

test_save_pretrained_round_trip runs the whole trip on a tiny model, offline, and asserts torch.equal on the logits. test_processor_round_trip does the same for ids, labels and pixels. test_full_save_load_round_trip does it on the real checkpoints, and is marked slow.

Checkpoint

  • logits identical: True.
  • test_save_pretrained_round_trip passes.
Step 13

Train the projector and see if the model can see

Goal Train only the projector on captions we can score exactly, and measure if the model uses the picture.

All the parts run. We still have not shown that the model can see. The cheapest proof is to train only the projector on a task where the answer is exact.

We draw pictures of one to three coloured shapes and ask for a caption such as Two red circles. Because we drew them, we can score a generated caption by parsing it. The encoder and language model stay frozen. Gradients still flow through the frozen language model into the projector, because the loss sits on caption tokens and the image features sit in their context.

Theory inWhich components are trained

The run took 869 s for 300 steps on AMD EPYC 7R13, 8 threads, on a machine with other work running. The loss starts at 4.768 and averages 0.004 over the last 20 steps. On 96 held-out pictures, the share of captions with count, colour and shape all correct goes from 0% to 100%.

Before training the model writes The image is a photograph of a woman wearing a white dress. After training it writes Three orange squares. That is what the picture shows. Only the 2.1 million projector parameters changed.

Insight

Step through Figure 8 and watch the bars. By step 25, colour is at 94% and shape at 94%, while count is at 34%. Count catches up later, at 97% by step 100. A colour or shape can be read from a few patches, while counting needs the model to compare patches across the picture. That would explain the order, but we have not tested it.

Nuance

Do not read 100% as good vision. There are only 54 possible captions, and test pictures come from the same generator as training pictures. They are new drawings, but not new kinds of drawing. So this run answers one narrow question: does the picture reach the language model, in a form it can use? We test that next, then push on the limits.

Is the picture really being used?

A caption can be right for the wrong reason. evaluate_alignment.py reruns the same 96 pictures with one thing broken at a time. Nothing in this list raises an error.

The sample captions all describe one picture, and the first row shows its true caption. Four results stand out.

  • Blind. With the pixels zeroed, 0% of captions are right. The captions keep the trained format, but count and colour are worse than random guessing, which would give 33% for count and 17% for colour. So the right answers above come from the picture.
  • Wrong normalisation. This is the mistake promised in step 1. Colour falls to 83%, count holds at 99% and shape at 100%. Pixels in [0, 1] are brighter than the encoder expects, and orange and red both become yellow in the samples. Shape survives it. An overall score of 82% could pass a quick check, and it comes entirely from one wrong line in a processor.
  • Right padding. 29 of 96 captions fail, and the question lengths differ by only one token. Describe the image. has 4 tokens and the other two questions have 5, so a third of the prompts, 32 of 96, get one pad token on the right. evaluate_alignment.py also splits the score by group. Of the 64 unpadded samples, 64 give the exact caption. Of the 32 padded samples, 3 parse as right and only 1 is the exact caption. With left padding, all 32 of the 32 padded samples are exact, as the conditions.correct.padded field of the same results file records. The next token is read from the last position, and under right padding that position is a pad slot, not the end of the prompt. The parser is also generous here: it scores What is something you saw? Two purple circles as correct, so the real damage is worse than the table shows.
  • Reversed crops. This is the last frame of Figure 3, now measured. Against each sample's own target the score is 0%. Against the reversed targets it is 100%. So every caption is perfect, for the wrong sample.

Insight

In step 3 we saw a fresh projector emit features far louder than token embeddings, and it would be natural to expect training to fix that. It does the opposite. After training, the projector's output has a standard deviation of 4.83, up from 0.462 when fresh. Across the whole embedding table the figure is 0.136, the same as the "all embedding rows" line in step 3, so image features end up about 36 times larger. The model still reaches 100%. Nothing in the loss asks for the two scales to match, and weight_decay is 0, so nothing pulls the output back down. So a matched scale was not needed for this task. We have not measured whether one would help on harder data.

Where it stops working

Now for pictures the generator could never draw. These are the honest test of what the projector learned.

Break it

The last row is the bug from step 6, trained for real: a label on every token, placeholders included. Nothing raises. Its loss is not comparable with the others, since it averages over every token of the prompt, and it only falls from 11.6 to 8.47, where the correct runs end near zero. Key insights and nuances

  • The resize filter is part of the encoder's input. Bicubic overshoot moves the darkest value from −0.686 to −0.788. A processor that swaps the filter does not match the training recipe. Step 1
  • Choosing a vision layer also chooses a normalisation. hidden_states skips the closing LayerNorm, so layer −2 ranges down to −212 where the last layer stops at −43. Step 2
  • A fresh projector is loud, not quiet. A new Linear(768) outputs about 11 times the standard deviation of real token embeddings. Step 3
  • PyTorch's own check on masked_scatter only works one way. Too few features raise an error. Too many are silently dropped, and reversed crops are not detectable from counts at all. Step 4
  • A loss above ln(V) points at your labels. Labels on every token give 11.458 against a uniform score of 10.8, and nothing raises. Step 6
  • 3D positions are a change to the language model. A processor can compute them, but the attention layers must be able to use them. Step 7
  • With a tile cap, cost follows the aspect ratio, not the resolution. 640 × 480 and 2048 × 1536 both cost 343 tokens. A 100 × 50 icon costs 147. Step 9
  • The KV cache matters more as pictures grow. Its saving over 20 tokens goes from a factor of 1.4 at 63 tokens to 7.9 at 1386 tokens, while its memory grows 22 times. Step 11
  • Token compression cannot speed up the encoder. Pixel shuffle runs after it. All the saving is in the language model and its cache. Step 9
  • Silent bugs show a pattern in the scores. Wrong normalisation lowers colour and leaves shape alone. Reversed crops score 0% against their own targets and 100% against the reversed ones. One pad token on the wrong side breaks almost every padded sample. Step 13
  • Training does not match the scales. The trained projector's output is about 36 times larger than token embeddings, and captions on this task are still all correct. Step 13
  • A perfect score here is a narrow claim. It shows that the picture reaches the language model. A red circle next to a blue square still comes back as Two red circles. Step 13
