What a benchmark score claims

Open almost any vision-language model report and you will find a sentence like this one: "our model achieves state-of-the-art results on 20 benchmarks." Below it sits a table with a few dozen columns of numbers. The sentence sounds like one claim. It is really twenty separate claims, and each one rests on choices the table does not show.

This article asks a simple question. When a VLM report says "state of the art on 20 benchmarks", what was actually measured, and what was not?

Start with one concrete item. VQAv2 shows a model a photo from COCO and asks "What color is the bus?" Ten people answered the same question when the dataset was built. The model replies "Red." The benchmark gives it a score of 1. Repeat for every question in the test split, average, and you have a VQAv2 number.

Even this tiny example hides five decisions. Someone chose which photos and questions to include. Someone decided that the answer is a short phrase rather than a sentence. Someone wrote the prompt that told the model to answer briefly. Someone wrote the code that turns "Red." into "red". Someone defined how "red" is compared with ten human answers. Change any of these and the number changes, even though the model has not.

So a benchmark is not a dataset. It is four things bound together:

  • Task. The skill the item is supposed to need, such as reading text, counting objects or locating a region.
  • Data. The images and questions, and the distribution they were drawn from: phone photos, scanned forms, arXiv charts or screenshots.
  • Metric. The rule that compares the model's answer with the reference and returns a number.
  • Protocol. Everything around the model call: the prompt, the image resolution, the number of video frames, whether chain-of-thought is allowed, how the answer is extracted, and which split is scored.

Each of the four can fail on its own. The task can be solvable without the skill. The data can leak into training. The metric can reward the wrong thing. The protocol can differ between two papers that report the "same" benchmark. Much of this article is about learning to see those four parts behind every number.

The plan is as follows. We first take one benchmark item apart and follow it through the evaluation pipeline. We then derive the metrics that VLM papers use, from exact match to Elo ratings. Next comes a map of capabilities and the benchmarks that measure each one, collected in a single atlas table. After that we study the ways benchmarks fail, the tooling that standardises evaluation, and how to read a results table without being misled. We finish by asking what a vector of benchmark scores tells us about a model's capabilities, and which training choices move which scores.

The previous article in this series, One Model, Many Visual Skills, covered how post-training teaches a model many skills at once. This article is about how those skills are measured. The next one, Aligning Vision-Language Models, uses several of the hallucination benchmarks introduced here. For the agent-side view of the same problem, see The Agent Evaluation Playbook.

The anatomy of a benchmark

Follow one item from start to finish. We will use a chart question, because charts make every step visible. The image is a small bar chart of company revenue. The question is "What was revenue in 2021?" The reference answer is 4.2.

The item passes through seven stages before it becomes part of a score.

  1. Data. The image, the question and the gold answer. Someone collected them, and their distribution decides what the benchmark can detect.
  2. Prompt. A template wraps the item. It places the image, adds the question, and often adds an instruction such as "Answer with a single number."
  3. Model input. The image is resized or tiled to the model's resolution and turned into visual tokens. A chart that is readable at 896 pixels may be a blur at 336 pixels. Inside a Modern Vision Encoder explains this step in detail.
  4. Raw output. The model writes text. It may write "4.2", or it may write a full sentence that contains several numbers.
  5. Parser. Code, or another language model, extracts the answer from the text. This step is easy to forget and it is often where two evaluations of the same model diverge.
  6. Metric. A rule compares the extracted answer with the gold answer. Exact match, relaxed accuracy and edit distance all give different verdicts on the same pair.
  7. Aggregation. Per-item scores are averaged over a split. Which split, which subsets, and whether sub-scores are averaged equally all change the final number.

The figure makes one point. A benchmark number is a property of the whole pipeline, not of the model alone. Two papers can report ChartQA for the same checkpoint and differ by several points because of the prompt, the resolution, the parser, or the split average.

The parser deserves special attention because it is invisible in most reports. Benchmark authors know this. MathVista's official pipeline uses a language model to extract the answer from the response before matching, and its README reports that GPT-4 extracted the answer correctly in more than 99.5% of a 200-example check. MMBench first tries rule-based matching of the option letter and falls back to a language model that maps a free-form answer onto one of the choices. Both designs exist because models do not answer in the format the metric expects.

Insight

The parser is part of the metric. MMBench introduced an LLM-based choice extractor precisely so that models with weak instruction following would not be scored as wrong when their answer was right but badly formatted. The consequence is that a "MMBench score" with regex extraction and one with LLM extraction are different measurements. When you compare models, check that the extraction step is the same, or re-run both through the same toolkit.

Why evaluating a VLM is harder than evaluating an LLM

Text-only language models have their own evaluation problems: contamination, prompt sensitivity, and judge bias among them. Vision-language models inherit all of these and add several of their own. Five stand out.

The image can be ignored

A language model is always tested on the input it is given. A VLM can often score well while ignoring half of its input. This problem is as old as visual question answering. The first VQA dataset contained many questions whose answer could be guessed from the question alone. "What color is the banana?" is usually "yellow". "Is there a ...?" is usually "yes".

VQAv2 was built to fix this. For each question, its authors collected a second, similar image for which the same question has a different answer. A model that answers from the question alone now gets one of each pair wrong. The paper's title states the goal plainly: making the V in VQA matter.

The fix was partial. GQA, a later dataset with balanced answer distributions, reports that a "blind" LSTM that never sees the image reaches 42.1%, against 54.1% for strong vision models of the time and 89.3% for humans. Years later, the MMStar authors found the same problem in modern multiple-choice benchmarks. Gemini Pro scored 42.9% on MMMU with no image at all. We return to this finding, and to the benchmark it led to, in the section on how benchmarks fail.

Nuance

Balancing the answer distribution does not remove language priors. Cambrian-1 evaluated models with vision disabled and found that SQA-I, MMMU, MathVista and AI2D change by less than 5% when the image is removed. TextVQA and GQA showed a gap of about 40% between random guessing and the vision-disabled score. So a "vision" benchmark can be mostly a language benchmark. The practical rule: run a blind baseline (same model, no image) before you trust a benchmark to measure seeing.

Answers have many valid surface forms

A language model answering a maths question writes a number. A VLM answering "How many people are in the photo?" may write "2", "two", "Two people." or "There are two people standing near the door." All of these are correct. A metric that compares strings must first decide which forms count as the same answer. This is why every VQA metric comes with a normalisation step, and why so many benchmarks are multiple choice: a letter is easy to compare.

The input pipeline is part of the model

For a text model, the input is the text. For a VLM, the image must first be resized, cropped or tiled, and the choice changes what the model can see. The same weights evaluated at a higher maximum resolution read small text better. The Idefics2 ablations make the size of this effect concrete. On DocVQA, the same architecture scored 22.6 at 384 pixels and 42.9 at 768 pixels, before any OCR-specific data was added. Adding OCR data at 768 pixels raised it to 49.9. Resolution is therefore an evaluation setting, not only a model property, and reports do not always state it.

Contamination has two channels

An LLM can memorise a test question it saw during pretraining. A VLM can memorise the question through its language backbone, the image through web-scale image-text data, or the pair through instruction data that reused a benchmark's training split. MM-Detect, a framework for detecting multimodal contamination, separates unimodal from cross-modal leakage. Across twelve models and five benchmarks it found significant contamination, most pronounced in proprietary models and older benchmarks, and sometimes originating in the language model's text pretraining rather than in multimodal training.

Outputs are not only text

Many VLM tasks produce a box, a mask, a click position or a sequence of actions. Scoring these needs geometry (how much two boxes overlap) or an environment (did the file actually get saved). Free-form answers, such as a long description, need a judge. Each of these brings its own metric, and its own ways of being wrong. The next section derives them one by one.

How metrics score an answer

A metric is a function from a (prediction, reference) pair to a number. That sounds simple. The difficulty is that each metric encodes a view of what "correct" means, and that view is rarely stated. We will build the common metrics in order of increasing tolerance: first strict string matching, then human-consensus scoring, then edit distance, numeric tolerance, overlap of n-grams, geometric overlap, and finally scores given by models and by people.

Exact match

The strictest rule: after normalisation, the prediction must equal the reference. GQA uses it. So do multiple-choice benchmarks such as MMBench, SEED-Bench, MMStar and MMMU, where the "string" is an option letter.

The normalisation does a lot of work. The standard VQA evaluation code lower-cases the answer, strips punctuation, removes articles such as "a" and "the", and maps number words such as "two" to digits. Without these steps, "Two." and "2" would be different answers. With them, a model that writes a full sentence still fails, because "there are 2 people" is not "2". That is why prompts for short-answer benchmarks almost always end with an instruction like "Answer the question using a single word or phrase." LLaVA-1.5 made this formatting prompt a standard part of its training mixture.

VQA accuracy: agreement with people

Exact match assumes there is one right answer. For open-ended questions about photos, there often is not. Is the umbrella red, pink or maroon? The original VQA dataset dealt with this by asking ten different people to answer every question. A model's answer is then scored by how many of those people gave the same answer.

Why not simply count the fraction of people who agree? Because that would punish a correct answer whenever annotators disagree. If four people say "red" and three say "pink", "red" is still a good answer. The VQA authors chose a softer rule: an answer is fully correct if at least three people gave it.

Acc(a) = min( #humans who said a / 3 , 1 ) one matching human gives 1/3, two give 2/3, three or more give full credit

There is a second detail that most descriptions skip. To make the score comparable with human performance, the official code computes this rule ten times. Each time it leaves out one of the ten human answers and scores against the remaining nine. The final score is the average of the ten. An answer that exactly three people gave scores slightly less than 1, because in three of the ten subsets only two matching people remain.

VQA accuracy is used by VQAv2, TextVQA, VizWiz and OK-VQA. OK-VQA collected five answers per question and counts each one twice, so the same formula applies. VizWiz adds a twist that matters in practice: its questions come from blind people taking photos with a phone, many images are blurry or do not show the object, and "unanswerable" is a valid gold answer. A model that always produces a confident guess is penalised there.

ANLS: partial credit for reading

Now consider a document question. The gold answer is "SPRINGFIELD". The model reads "SPRlNGFIELD", with a lower-case L instead of an I. Exact match gives zero. That seems too harsh: the model found the right field and made a one-character recognition slip. A metric for reading should give partial credit for small slips, but no credit for reading the wrong field.

The ST-VQA authors built such a metric from the Levenshtein distance. The Levenshtein distance between two strings is the smallest number of single-character insertions, deletions and substitutions that turn one into the other. Divide it by the length of the longer string and you get a normalised distance NL between 0 and 1. Then apply a threshold:

s(a, o) = 1 − NL(a, o)  if NL < τ,  otherwise 0    (τ = 0.5)
ANLS = (1/N) ∑i maxj s(aij, oi) a = a gold answer, o = the model's answer; take the best gold answer per question, then average over N questions

The threshold is the important design choice. Without it, a completely wrong answer that happens to share letters with the gold answer would still earn some credit. With τ = 0.5, any answer that needs edits to more than half of its characters scores zero. Figure 3 steps through several predictions, and lets you type your own.

ANLS is the metric of DocVQA, InfographicVQA and ST-VQA. It has a known weakness: it treats all characters as equal. For a name, one wrong letter is a small slip. For a number, "1,250" and "7,250" differ by one character, score 0.8, and mean very different things. MTVQA's authors computed ANLS alongside accuracy and found ANLS scores roughly 5 to 10 points higher. They chose accuracy as their main metric because ANLS does not reliably show whether the correct text was produced.

Relaxed accuracy: tolerance for numbers

Charts raise a different problem. A model reading a bar's height may answer 4.19 when the label says 4.2. That is a correct reading, not an error. ChartQA, following the earlier PlotQA benchmark, uses relaxed accuracy: a numeric answer counts as correct if it is within 5% of the gold value, and a text answer must match exactly.

correct ⇔ |p − g| / |g| ≤ 0.05   (numeric)   or   p = g   (text)

Nuance

A relative tolerance is generous for large numbers. In the widely used implementation, both strings are converted to numbers when possible, so a year is treated like any other value. "2020" against a gold "2019" differs by 0.05% and is scored correct. A revenue of 104 against a gold 100 is also correct. ChartQA's test set is about half human-written questions and half machine-generated ones (1,250 each), and the machine-generated half is easier. So a single "ChartQA" number hides both a lenient metric and a split average. When a chart score matters, read the human-written split on its own and check how the code treats years and units.

Caption metrics: agreement with references

For captions, there is no single correct sentence. Caption metrics therefore compare the output with several human references. BLEU counts overlapping n-grams. CIDEr weights each n-gram by how informative it is (TF-IDF), so that "a" and "the" count for little and "giraffe" counts for a lot, and measures consensus with the references. SPICE parses captions into objects, attributes and relations and compares those. In the SPICE paper, system-level correlation with human judgments on COCO was 0.88 for SPICE, against 0.43 for CIDEr. All three reward similarity to the references, which penalises a correct caption that mentions details the annotators did not. Crossmodal-3600 extends caption evaluation to 36 languages with 3,600 geographically diverse images.

IoU and Acc@0.5: overlap of regions

When the answer is a region, the metric compares shapes. Intersection over union (IoU) divides the area where the predicted and gold boxes overlap by the area they cover together. IoU is 1 for a perfect box and 0 for a box that misses.

IoU(Bpred, Bgold) = area(Bpred ∩ Bgold) / area(Bpred ∪ Bgold)

Referring expression benchmarks such as RefCOCO turn this into a pass or fail. A prediction is correct if its IoU with the gold box exceeds 0.5. The reported number is the fraction of correct predictions, usually written Acc@0.5. For masks, two averages are common. gIoU is the mean of per-image IoUs, so every image counts equally. cIoU is the total intersection over the total union across the whole set, so large objects dominate. GUI grounding benchmarks such as ScreenSpot use a simpler rule: the predicted click point must fall inside the target element's box.

The figure shows why the same pixel error is not the same mistake everywhere. An error of 18 pixels barely matters for a dog that fills half the photo. For a 30-pixel icon it means the box misses. ScreenSpot-Pro was built around this: its targets occupy on average 0.07% of the screen, against 2.01% in ScreenSpot. Later in this series, When Language Must Point covers how models produce boxes, points and masks.

Edit distances for long outputs

Document parsing produces whole pages: paragraphs, tables, formulas. Scoring them needs distances over long sequences. Character error rate (CER) and word error rate (WER) are the Levenshtein distance divided by the length of the reference, measured in characters or in words. OmniDocBench uses normalised edit distance for text and for reading order. Tables are compared with TEDS, the tree-edit-distance similarity introduced with PubTabNet. TEDS turns each table into its HTML tree and counts the edits needed to transform one tree into the other, so a missing row costs more than a typo in one cell. Formulas are compared with CDM, which matches the characters of rendered formulas so that two LaTeX strings that look the same when typeset are not penalised for different markup. How VLMs Read Documents covers these tasks in depth.

Yes or no: precision, recall and the yes-ratio

Hallucination benchmarks often ask yes/no questions. POPE asks "Is there a <object> in the image?" for objects that are present and objects that are absent, in equal numbers. Accuracy alone hides a common failure: a model that leans towards "yes" can look fine on accuracy while inventing objects. POPE therefore also reports precision, recall, F1 and the yes-ratio, the share of questions answered "yes". A yes-ratio far above 50% on a balanced set is a direct signal of hallucination. CHAIR measures the same failure in free captions. CHAIRi is the fraction of mentioned objects that are not in the image. CHAIRs is the fraction of captions that mention at least one such object.

Judges: a model gives the score

Some answers cannot be checked with a rule. "Describe what is unusual about this image" has no gold string. Benchmarks such as LLaVA-Bench (In-the-Wild) and MM-Vet hand the comparison to a strong language model. MM-Vet prompts GPT-4 with a few graded examples and asks it to score each answer between 0 and 1. LLaVA-Bench asks GPT-4 to rate the model's answer relative to a reference answer. MMHal-Bench asks GPT-4 for a rating from 0 to 6 and counts a response as a hallucination when the rating is below 3.

A judge is itself a model, with its own biases. The MLLM-as-a-Judge study found diverse biases, hallucinated judgments and inconsistent scores, even for GPT-4V. Two practical consequences follow. A judge-based score is only comparable when the judge model and its version are the same. And a score from a retired judge model cannot be reproduced exactly.

Elo: scores from pairwise human votes

Arenas skip the gold answer altogether. A user uploads an image, asks a question, sees two anonymous answers and votes for the better one. WildVision Arena collects such votes for VLMs, following Chatbot Arena for text models. The votes are turned into ratings with the Bradley–Terry model, which assumes that the probability that model i beats model j depends only on the difference of their ratings:

P(i beats j) = 1 / (1 + 10(Rj − Ri)/400) a 400-point gap means the stronger model wins about 10 times out of 11

The ratings are fitted by maximum likelihood over all votes. An arena measures what users ask and prefer, which is close to real use. It also inherits whatever users happen to ask, and what they find persuasive, such as length and confident tone. WildVision's offline companion, WV-Bench, uses 500 arena prompts, each answer judged by a GPT-4 model against a fixed reference model, and its ranking has a Spearman correlation of 0.94 with the arena's Elo ratings.

Task success: did the world change

For agents, the answer is an effect. OSWorld gives a model a real desktop and 369 tasks. Each task comes with an evaluation script that inspects the final state of the machine, for example whether a file exists with the right content. AndroidWorld does the same for 116 tasks across 20 Android apps. The metric is the success rate. It is the most faithful metric in this article, and the most expensive to build. VLMs That Act covers these benchmarks in detail.

A map of capabilities and their benchmarks

With the metrics in hand, we can organise the benchmarks. The useful organising question is not "which benchmark is newest" but "which capability does it try to isolate". A capability here means a skill a user would recognise: reading a receipt, counting objects, solving a geometry problem, finding the button to click. Each capability has a cluster of benchmarks, and each cluster tends to share a metric family.

Figure 5 links each capability to its main benchmarks, and each benchmark to the metric it uses. Click a capability to see its cluster. Notice how the metric changes with the output type: short answers use accuracy, reading uses ANLS, regions use IoU, actions use task success.

The sections below walk through the clusters in the order of the figure. For each one, the question is the same: what does the benchmark ask, how big is it, how is it scored, and what can a model exploit?

Perception and general visual question answering

The oldest cluster asks short questions about natural photos. VQAv2 has about 1.1 million questions on roughly 200,000 COCO images, each with ten human answers. GQA generates 22 million compositional questions from scene graphs. VLM papers report its balanced test-dev split of 12,578 questions with exact match. OK-VQA (about 14,000 questions) and A-OKVQA (about 25,000) require knowledge that is not in the image, such as what a tool is used for. VizWiz contains over 31,000 questions asked by blind people about photos they took themselves, so blur, odd framing and unanswerable questions are part of the test.

Counting has its own benchmarks, because counting fails differently from naming. TallyQA has 287,907 counting questions, with a test-simple split of 22,991 questions and a test-complex split of 15,598. Complex questions such as "how many dogs are lying down" need attributes and relations, not just detection. CountBench has 540 images, sixty for each count from 2 to 10. It was built to test CLIP's counting and is now used as a counting question set for VLMs.

The large language model era added broad multiple-choice suites. MME asks two yes/no questions per image, one whose answer is "yes" and one whose answer is "no". It reports accuracy and accuracy+, where accuracy+ requires both questions about an image to be right. It sums ten perception subtasks (maximum 2,000) and four cognition subtasks (maximum 800), which is why MME scores look like "1,500" rather than a percentage. MMBench has 3,217 multiple-choice questions over 20 ability dimensions, in English and Chinese. SEED-Bench has 19,000 multiple-choice questions over 12 dimensions that include video. MMStar has 1,500 questions selected so that the image is needed. RealWorldQA, released by xAI with Grok-1.5V, has over 700 real-world images, some taken from vehicles, each with a verifiable multiple-choice question.

A last group targets low-level perception that the broad suites under-sample. BLINK reformats 14 classic computer vision tasks, such as relative depth, visual correspondence and multi-view reasoning, into 3,807 multiple-choice questions. MMVP pairs images that CLIP embeds almost identically but that differ visibly, and scores a pair as correct only if both questions are right. CV-Bench (2,638 items, from Cambrian-1) tests 2D and 3D spatial relations. HR-Bench uses 4K and 8K images, and MME-RealWorld (29,429 questions on 13,366 high-resolution images) targets scenes that are hard even for people. NaturalBench uses 10,000 human-verified pairs built to defeat answers that ignore the image.

Insight

A high general score does not imply basic perception. When BLINK was released, humans scored 95.70% on average while GPT-4V scored 51.26% and Gemini 45.72%, only 13.17 and 7.63 points above random guessing. The same models were strong on the broad suites of the time. BLINK's subtitle states the conclusion: models "can see but not perceive". If your application depends on depth, correspondence or fine spatial judgments, test it directly; an MMBench average is not evidence for it.

Text in images

Reading text in natural scenes is a separate skill from recognising objects. TextVQA has 45,336 questions on 28,408 images that require reading, scored with VQA accuracy. ST-VQA (31,791 questions on 23,038 images) introduced ANLS for the same kind of task. OCRBench collects 1,000 question-answer pairs from 29 datasets in five groups: text recognition (300), scene-text VQA (200), document VQA (200), key information extraction (200) and handwritten mathematical expressions (100). Its score is the number of correct answers, so it is reported out of 1,000. OCRBench v2 expands to 10,000 human-verified pairs across 31 scenarios in English and Chinese, adds text localisation and layout tasks, and keeps a private test set of 1,500 images. At release, most models scored below 50 out of 100 on it.

Documents, charts, infographics, diagrams and tables

Documents add layout and length. DocVQA has 50,000 questions on 12,767 document images, scored with ANLS on a test split of 5,188 questions. InfographicVQA (30,035 questions on 5,485 infographics) requires combining text, layout, icons and numbers. ChartQA has 9,600 human-written questions and 23,100 questions generated from chart summaries. Its test set is 1,250 human-written plus 1,250 generated questions, scored with relaxed accuracy.

CharXiv was built because the older chart benchmarks looked solved. Its authors found that open models which appeared to beat proprietary ones on existing chart benchmarks lost up to 34.5% under a simple stress test with slightly different charts or questions. CharXiv uses 2,323 real charts from arXiv papers, with descriptive questions (four per chart) and one reasoning question per chart, judged by GPT-4o. At release, GPT-4o scored 47.1% on reasoning, the best open model 29.2%, and humans 80.5%.

AI2D contains over 5,000 grade-school science diagrams and 15,000 questions. VLMs report its 3,088-question test set, but in two settings: with the answer regions masked, or outlined. Reports do not always say which. TableVQA-Bench has 1,500 questions over table images from Wikipedia and financial reports. For whole-page parsing, OmniDocBench evaluates text, tables, formulas and reading order with the distance metrics described earlier. Its first release had 981 pages of nine document types, in English, Chinese and mixed text. The later v1.7 has 1,651 pages. How VLMs Read Documents goes deeper into this cluster.

Nuance

DocVQA is often called "solved" because model scores now exceed the human figure in the original paper. The comparison mixes metrics. The paper's 94.36% human figure is accuracy. The human ANLS, the metric models report, is 0.981. Qwen2.5-VL-72B reports 96.4 ANLS. That is close to the human level, but still below it on the matching metric. Whenever a model is said to beat humans, check that both numbers use the same metric and the same split.

Expert knowledge and reasoning

This cluster asks questions that need domain knowledge and several reasoning steps. MMMU has 11,500 college-level questions across 30 subjects and 183 subfields, with images ranging from charts to music sheets and chemical structures. Papers usually report its validation split of 900 questions. Human experts scored 76.2% (worst), 82.6% (median) and 88.6% (best) on that split. At release, GPT-4V scored 56%. MMMU-Pro rebuilds 1,730 MMMU questions in three steps: it removes questions that text-only models can answer, expands the options from four to ten, and adds a "vision" setting in which the whole question is embedded in a screenshot. Scores fell by 16.8 to 26.9 points relative to MMMU.

Visual mathematics has its own family. MathVista has 6,141 problems drawn from 28 existing datasets plus three new ones; papers report its 1,000-question testmini split, where human performance is 60.3%. MathVerse takes 2,612 problems and writes each in six versions that move information from the text into the diagram, about 15,000 items in total. This tests whether a model reads the diagram or only the text. MATH-Vision has 3,040 competition problems across 16 disciplines and five difficulty levels. We-Math (6,500 problems, 67 knowledge concepts) decomposes problems into sub-problems to separate missing knowledge from failed generalisation. DynaMath writes 501 seed questions as programs and generates ten variants of each. It reports worst-case accuracy, the share of seeds answered correctly in all ten variants, which is far lower than average accuracy.

Science and broader reasoning complete the cluster. ScienceQA has about 21,000 multiple-choice science questions with lectures and explanations. OlympiadBench has 8,476 Olympiad-level mathematics and physics problems in English and Chinese; GPT-4V averaged 17.97% at release. EMMA has 2,788 problems in mathematics, physics, chemistry and coding that are designed to need reasoning across the image and the text together, not in each one separately.

Nuance

A MathVista gain is not necessarily a mathematics gain. The VL-Rethinker authors note that OpenAI's o1, much stronger than fast-thinking models at text mathematics, performed similarly to them on MathVista, MathVerse and MathVision. And the benchmark-redundancy study found that 30 to 40% of MathVista is not traditional mathematics. Visual maths scores mix perception (reading the figure) with reasoning. To attribute an improvement to reasoning, check a benchmark like MathVerse, whose versions control how much information sits in the diagram. Rewarding What the Model Sees and Thinking With Images cover the training side.

Grounding

Grounding benchmarks ask the model to say where. RefCOCO (142,209 expressions for 50,000 objects in 19,994 images), RefCOCO+ (which bans location words such as "left") and RefCOCOg (longer expressions) are scored with Acc@0.5. RefCOCO and RefCOCO+ have two test splits with different content: testA contains images with several people, and testB contains images with several objects of other kinds. Flickr30k Entities links phrases in captions to 276,000 boxes and tests phrase grounding, usually as recall at an IoU of 0.5. ReasonSeg (from LISA) has 1,218 image-instruction-mask triples whose target must be inferred, such as "the thing you would use to cut the bread". Its test split has 779 samples, scored with gIoU and cIoU. ScreenSpot (1,272 instructions on mobile, desktop and web screenshots) and ScreenSpot-Pro (1,581 instructions across 23 professional applications) test GUI grounding with click accuracy. When Language Must Point covers this cluster.

Hallucination

Hallucination benchmarks test whether the model claims things that are not there. POPE uses 500 COCO images and asks six yes/no object questions per image in three settings. In the random setting, absent objects are drawn at random. In the popular setting, they are the most frequent objects in the dataset. In the adversarial setting, they are the objects that most often co-occur with what is actually in the image. CHAIR checks the objects mentioned in free captions against the image annotations. AMBER combines both: 1,004 images with a captioning task and 14,216 yes/no questions on existence, attributes and relations, summarised in one AMBER score. HallusionBench has 1,129 expert-written questions on 346 images, many in pairs that differ by a small edit; at release, GPT-4V reached 31.42% question-pair accuracy. MMHal-Bench has 96 image-question pairs scored by GPT-4. Aligning Vision-Language Models uses these benchmarks to evaluate preference training.

Insight

POPE's three settings measure different things. The POPE authors found that objects which appear often in visual instruction data, or which co-occur with objects in the image, are especially prone to be hallucinated. So the adversarial setting, which asks about exactly those co-occurring objects, is the one that separates models. A model's random-setting F1 mostly says it can detect objects. Report the adversarial setting, and the yes-ratio, if the claim is about hallucination.

Multiple images and video

Multi-image benchmarks ask the model to compare, order or match across images. MuirBench has 2,600 multiple-choice questions over 11,264 images, in 12 tasks. Each question is paired with an unanswerable variant that differs minimally, so that guessing is punished. At release, GPT-4o scored 68.0% and models trained only on single images stayed below 33.3%. Mantis-Eval has 217 multi-image questions with two to four images each. Part of BLINK is also multi-image.

Video benchmarks add time. Video-MME has 900 videos totalling 254 hours, with 2,700 questions split evenly across short (under 2 minutes), medium (4 to 15 minutes) and long (30 to 60 minutes) videos. It reports results with and without subtitles. MVBench has 20 tasks with 200 questions each that cannot be solved from a single frame. LongVideoBench has 6,678 questions on 3,763 videos of up to an hour, with interleaved subtitles. MLVU has 2,593 questions on 1,334 videos from 3 minutes to over 2 hours. EgoSchema has over 5,000 questions on 250 hours of egocentric video; at release, the best models scored below 33% where random is 20% and humans about 76%. Seeing in Time covers how models read video.

Nuance

The number of frames is a protocol choice, and so are subtitles. Video-MME reports scores with and without subtitles because subtitles can carry the answer. A model that reads subtitles well will gain on the "with subtitles" column without understanding the frames any better. When two video scores are compared, check the frame count, the frame-sampling rule and the subtitle setting before comparing the numbers.

Agents

Agent benchmarks score sequences of actions. ScreenSpot-Pro measures the grounding step alone. Mind2Web has over 2,000 tasks recorded on 137 real websites and scores each step offline against the human's action. OSWorld (369 tasks on real desktop applications) and AndroidWorld (116 tasks in 20 apps) run the agent live and check the final state with scripts. At release, the best OSWorld model succeeded on 12.24% of tasks while humans succeeded on 72.36%; the OSWorld authors attribute much of the gap to GUI grounding and operational knowledge. VisualWebArena does the same for web tasks that need images. VLMs That Act covers this cluster.

Insight

A cheap grounding score can predict an expensive agent score. The SeeClick authors report that improvements in GUI grounding on ScreenSpot consistently carried over to better performance on downstream agent benchmarks, and the OSWorld authors name GUI grounding as a main failure mode. Live agent benchmarks are slow and noisy to run. During development, track a click-accuracy benchmark as a fast proxy, and run the live benchmark less often to confirm.

Many languages and cultures

Most benchmarks above are English-only, or English and Chinese. Multilingual evaluation comes in two kinds, and they measure different things.

The first kind translates existing English questions. xGQA translates GQA into seven languages: German, Portuguese, Russian, Indonesian, Bengali, Korean and Chinese. Its authors measured a drop of about 38 accuracy points in zero-shot cross-lingual transfer. xMMMU, part of PangeaBench, translates MMMU's validation questions with GPT-4o into seven languages including English. Parrot's MMMB has 12,000 questions in six languages (English, Chinese, Portuguese, Arabic, Turkish and Russian), and Parrot also extends MMBench to the same six. Translated benchmarks keep the images fixed, so they measure whether the model can understand the question in another language.

The second kind collects questions natively, often with culturally specific images. CVQA has 10,374 questions on images from 30 countries in 31 languages and 13 scripts, written by native speakers. MaXM is a test-only VQA set in seven languages (English, French, Hindi, Hebrew, Romanian, Thai and Chinese) built from Crossmodal-3600 images. MTVQA tests reading text in nine languages (Arabic, Korean, Japanese, Thai, Vietnamese, Russian, French, German and Italian), with 6,778 questions on 2,116 images. M3Exam uses 12,317 real exam questions in nine languages (English, Chinese, Italian, Portuguese, Vietnamese, Thai, Swahili, Afrikaans and Javanese); about 23% need the image. CMMMU (12,000 questions) and JMMMU are MMMU-style benchmarks written for Chinese and Japanese. M5 covers 41 languages across eight datasets. ALM-bench covers 100 languages across 13 cultural aspects. PangeaBench bundles 14 datasets in 47 languages, including its own open-ended xChatBench. For captioning, Crossmodal-3600 has references in 36 languages.

Nuance

A translated benchmark cannot detect cultural gaps. xGQA and xMMMU ask about the same images in another language, so a model that understands the language but knows nothing about local food, festivals or signage still scores well. CVQA, M3Exam and ALM-bench were written with local content, and they test that knowledge. "Multilingual" in a model report should say which kind was measured, and for which languages; high-resource European languages are not evidence for Swahili or Javanese.

Open-ended answers and arenas

The last cluster accepts free-form answers. LLaVA-Bench (In-the-Wild) has 60 questions on 24 images, scored by GPT-4 relative to a reference answer. MM-Vet has 218 questions on 200 images that combine six core capabilities, such as OCR plus spatial awareness plus maths, and scores them with a few-shot GPT-4 judge. MM-Vet v2 adds interleaved image-text sequences. Vibe-Eval has 269 prompts with expert-written gold responses, including 100 hard ones; over half of the hard set was answered incorrectly by every frontier model at release, and scoring uses Reka Core as the judge. MEGA-Bench scales to 505 real-world tasks with over 8,000 samples and more than 40 metrics, chosen per task. WildVision Arena ranks models from user votes, and WV-Bench distils 500 of its prompts into an offline test.

How benchmarks fail

We now know what each benchmark tries to measure. This section is about the ways a benchmark can report a number that does not mean what it seems to mean. Each failure maps onto one of the four parts from the start: the task, the data, the metric or the protocol.

The question can be answered without the image

This is a failure of the task. The MMStar authors tested it directly. They ran language models with no image, and VLMs with the image removed, on six popular multiple-choice benchmarks. Gemini Pro reached 42.9% on MMMU with no visual input, and across six benchmarks it beat random choice by over 24 points on average. Some questions can be answered from the options alone. Others can be answered from world knowledge.

The authors defined two quantities to make the problem measurable. Let Sv be a VLM's score with images, Swv its score with the images removed, and St the score of the language model it was built on.

MG = Sv − Swv      ML = max(0, Swv − St) multi-modal gain: what the image adds · multi-modal leakage: what the VLM knows without the image that its base LLM did not

Multi-modal gain is the part of the score that actually needs the image. Multi-modal leakage needs a second look. A VLM that answers better than its own language model, without seeing the image, must have learned something about these questions during multimodal training. The most likely source is the benchmark's data, or something close to it, in the training mixture.

The authors then built MMStar by filtering. They pooled 22,401 candidate questions from MMBench, SEED-Bench, MMMU, ScienceQA, AI2D and MathVista. They removed every question that more than two of eight language models could answer without the image, leaving 11,607. Three experts then reviewed the remainder and selected 1,500 balanced across six capabilities. Figure 6 replays the idea.

The test data leaked into training

This is a failure of the data. MMStar found that Sphinx-X-MoE scored 43.6% on MMMU without seeing any image, far above what its language backbone could do. MM-Detect found contamination across twelve models and five benchmarks, and it was worst for older benchmarks: the longer a test set has been public, the more chances it has had to enter a training mixture.

There are three defences. A private test set, such as OCRBench v2's 1,500 held-out images, can be compared with the public one; if a model does much better on the public set, that suggests leakage. A live benchmark keeps generating new items. LiveXiv creates questions automatically from figures and tables in newly posted arXiv papers, so the items did not exist when the model was trained. Generated variants, as in DynaMath, test whether a model solves the problem or remembers one instance of it.

Insight

A VLM that beats its own base language model with the image removed has learned the test, not the skill. That comparison costs two extra evaluation runs and needs no access to the training data. MMStar's multi-modal leakage turns it into a number. Run it on any benchmark that a new model's training mixture might overlap with, and treat a large leakage score as a reason to distrust the headline score.

The answer was right but scored wrong

This is a failure of the protocol, and the most common reason two papers disagree. The model writes "The answer is (B) 8/11." A strict parser looks for a bare letter and fails. A permissive one finds "B". An LLM extractor maps it to option B even when the model wrote only "8/11". VLMEvalKit handles multiple-choice and yes/no benchmarks by trying exact matching of option letters and option contents first, and then optionally an LLM choice extractor. MathVista's official pipeline always uses an LLM extractor. The same model output can therefore score differently under two toolkits.

Prompting adds a second layer. Whether chain-of-thought is allowed, whether a system prompt is used, the decoding temperature and the maximum output length all change scores. A reasoning model that is cut off at a short output length will be scored as wrong on problems it would have solved.

The model prefers a position, not an answer

Multiple-choice questions have a quiet weakness. Models can prefer some option positions, and a model that guesses gets 25% on four options for free. MMBench introduced CircularEval to fix both. Each question with N options is asked N times, with the options rotated each time. The model gets credit only if it picks the correct option every time.

The effect on guessing is large. If a model guesses uniformly at random on each pass, the chance of being right on all four passes is

P(all 4 correct by chance) = (1/4)4 = 1/256 ≈ 0.4% compared with 25% under a single pass

Figure 7 shows the passes for a model with a position bias.

CircularEval lowers scores for most models, and it lowers them most for models that guess or depend on option order. That is the point. It also means that an MMBench number is only comparable to another MMBench number computed the same way.

The benchmark has saturated

A benchmark saturates when the best models reach the ceiling set by annotation noise or human agreement. After that, differences between models mostly reflect noise and formatting. Figure 8 plots the verified data points we have for several benchmarks: the best score when the benchmark was released, a later score where a primary report gives one, and the human baseline on the same split.

Saturation has a less obvious cousin: redundancy. The benchmark-redundancy study analysed hundreds of models across more than 20 benchmarks. It found that most benchmarks have at least 50% redundant items: halving them keeps the model ranking almost unchanged (rank correlation of 0.95 or higher). Predicting a model's exact score, though, needed more than 90% of the items. Within mathematics, MathVerse and MATH-Vision were highly redundant with each other.

The benchmark is too small to separate models

A benchmark score is an average over a finite sample, so it has a standard error. For an accuracy p measured on n independent items,

SE(p) = √( p (1 − p) / n ) a 95% interval is roughly ±2 SE

Put in real sizes. At p = 0.6, MathVista's 1,000-question testmini gives SE ≈ 1.5 points, so a 95% interval of about ±3 points. MM-Vet has 218 questions: SE ≈ 3.3 points, about ±6.6. LLaVA-Bench (In-the-Wild) has 60 questions: SE ≈ 6.3 points, about ±12.6. Judge scores are not binary, so these are rough, but the order of magnitude holds. A two-point gain on a 200-question benchmark is not evidence of anything. The MME-RealWorld authors list "small data scale leads to large performance variance" as the first problem they set out to fix.

Nuance

Small benchmarks are not useless; they are useful for different questions. A 60-question judged benchmark can catch a model that has lost its ability to chat. It cannot rank two good models. Before reading a difference, compute the standard error from the benchmark size, and for judge-scored benchmarks also check that the judge and its version are the same.

Other ways a number misleads

Three more failures are worth naming. First, resolution. HR-Bench's authors note that models claim to process 4K images while most benchmarks only go up to 2K, so high-resolution ability goes untested. The reverse also happens: a model evaluated at a lower maximum resolution than its authors used will lose points on OCR and documents. Second, judge bias. Judges can prefer longer answers or answers in their own style, and the MLLM-as-a-Judge study found inconsistent judgments even from GPT-4V. Third, suite selection. A report chooses which benchmarks to show. Twenty benchmarks from the same cluster are close to one measurement, and a cluster that is missing from the table is often missing for a reason.

Evaluation tooling and protocol

Most of the protocol problems above have the same cure: run every model through the same code. Two open toolkits do most of this work for VLMs.

VLMEvalKit, from the OpenCompass team, implements over 450 model configurations and over 330 benchmarks according to its latest paper version. It generates answers, extracts them with exact matching and an optional LLM extractor, and scores them with each benchmark's metric. It powers the OpenCompass multimodal leaderboard. In the VLMEvalKit paper, that leaderboard's average score is the mean of eight benchmarks: MMBench v1.1, MMStar, MMMU (validation), MathVista (testmini), HallusionBench, AI2D (test), OCRBench (rescaled to 0 to 100) and MM-Vet.

lmms-eval, from the LMMs-Lab team, started with over 50 tasks and more than 10 models and has grown since. Its paper makes two further contributions. LMMs-Eval Lite selects a small coreset of items, about 9,100 of 90,200 across 15 datasets, whose scores correlate above 0.9 with the full sets. LiveBench builds new questions from recent news and forum screenshots and scores them with a GPT-4o judge, to limit contamination.

Even with shared tooling, numbers from different sources often disagree. These are the usual reasons, roughly in order of how often they matter:

  • Split. MMMU validation or test; MathVista testmini or test; ChartQA human split or the average of both splits.
  • Metric variant. ANLS or accuracy; AI2D with or without masks; MME accuracy or the summed score; MMBench single pass or CircularEval.
  • Prompt and reasoning mode. Direct answer or chain-of-thought; with or without a system prompt; the output-length limit.
  • Input settings. Maximum resolution or number of image tokens; number of video frames; with or without subtitles.
  • Extraction and judging. Regex or LLM extractor; which judge model and which version.
  • Source of the number. Self-reported by the model's authors, reproduced by a toolkit, or copied from another paper's table.

Insight

A leaderboard average is a choice of weights. The OpenCompass average in the VLMEvalKit paper weights eight benchmarks equally. Three of them (MMMU, MathVista, AI2D) are among those Cambrian-1 found change by less than 5% without the image, and none of them tests grounding, video or multiple languages. A model can rise on that average by improving knowledge and reasoning alone. Use the average to shortlist, then read the per-benchmark columns for the capability you need.

Reading a results table critically

We can now read a results table the way a reviewer would. The aim is to decide, for each pair of numbers, whether they are comparable. Start with a real row. The Qwen2.5-VL technical report gives these scores for its 72B model:

  • DocVQA 96.4. ANLS on the test split. Close to the human ANLS of 98.1; the 94.36 human figure in the DocVQA paper is accuracy and is not comparable.
  • ChartQA 89.5. Relaxed accuracy, averaged over the human and generated splits. The human split alone would be lower.
  • AI2D 88.7. The report marks this as "with mask". A "no mask" number from another model is a different test.
  • MMMU 70.2. Validation split. A test-split number from another paper is not directly comparable.
  • MathVista 74.8. Testmini. Above the 60.3% human baseline on the same split.
  • OCRBench 885. Count correct out of 1,000. Leaderboards often rescale it to 88.5.

Each line needed one or two checks. Now apply the checks to a whole table. Figure 9 shows a mock comparison table of the kind found in model reports, with hypothetical models and numbers. Each cell carries the details that reports usually put in footnotes, if anywhere. Tick the checks one at a time and watch which comparisons survive.

The mock table is exaggerated, but not by much. Real reports mix self-reported numbers with numbers copied from other papers, and footnotes are often the only place where the split or the mode is mentioned. The practical habit is simple: before comparing two numbers, name the split, the metric variant, the reasoning mode, the extractor or judge, and the source. If any of the five differ, the comparison needs a re-run, not a reading.

From benchmark scores to capabilities

A results table is a vector. For each model we get

S = [ SVQA, SOCR, Sdoc, Schart, Smath, Sground, Shalluc, Smulti-image, Svideo, Smultilingual, … ]

It is tempting to read each coordinate as an independent capability. Two facts get in the way.

First, the coordinates are correlated, because benchmarks in the same cluster measure overlapping skills. Cambrian-1 grouped its benchmarks into four categories: general (MME perception, MMBench, SEED, GQA), knowledge (ScienceQA, MMMU, MathVista, AI2D), OCR and charts (ChartQA, OCRBench, TextVQA, DocVQA) and vision-centric (MMVP, RealWorldQA, CV-Bench). The redundancy study found strong overlap inside domains such as maths. A table with twenty columns may carry only a handful of independent measurements.

Second, a coordinate can move for reasons unrelated to its name. A knowledge benchmark rises when the language model gets better, even if vision does not change. An OCR benchmark rises when the evaluation resolution goes up, even if the weights do not change.

The more useful question is causal: which training or design choice moves which coordinate? The primary sources give direct evidence for several levers.

  • Resolution and OCR data move OCR and documents. In the Idefics2 ablations, DocVQA rose from 22.6 at 384 pixels to 42.9 at 768 pixels, and to 49.9 when OCR data was added. Splitting images into sub-images helped most on tasks that involve reading text. Monkey reached a similar conclusion from higher-resolution patches.
  • Multi-image instruction data moves multi-image benchmarks. Mantis trained on 721,000 multi-image instructions and beat Idefics2-8B by an average of 13 points on multi-image benchmarks, although Idefics2 had been pretrained on 140 million interleaved examples, about 200 times more.
  • Preference training moves hallucination benchmarks. LLaVA-RLHF, trained with factually augmented RLHF, reported a 60% improvement on MMHal-Bench over its baselines. Aligning Vision-Language Models covers this lever.
  • Reinforcement learning moves visual maths. VL-Rethinker used RL with forced rethinking and reported 80.4% on MathVista and 63.5% on MathVerse. The same paper notes that strong text reasoning alone (o1) did not translate into better visual maths, so perception limits this lever.
  • Multilingual instruction data moves multilingual benchmarks. Pangea trained on 6 million instructions in 39 languages and reports large gains on PangeaBench. Its ablations point to the proportion of English data, the popularity of each language, and the number of multimodal training samples as important factors.
  • Grounding and pointing data move grounding. A model never trained to emit coordinates cannot be scored on RefCOCO at all. Molmo collected a 2D pointing dataset and uses pointing to count, linking grounding data to counting. When Language Must Point covers this lever.

Insight

Targeted data can beat sheer scale for a capability that the benchmark isolates. Mantis gained 13 points on multi-image benchmarks over Idefics2-8B with an instruction set about 200 times smaller than Idefics2's interleaved pretraining data. The general lesson is that a capability coordinate responds most to data shaped like its benchmark's task. When one coordinate lags, look first for missing task-shaped data, not for a larger pretraining run. How Vision-Language Models Scale discusses when scale does help.

This also explains why model reports look the way they do. A team that adds document data at high resolution will see the OCR and document columns move together, and will usually report all of them. A team that adds no grounding data will often leave RefCOCO out of the table. Reading which columns are missing tells you as much about the training mixture as the numbers in the columns that are present. Model-by-model details of what each family trained on are collected in How the Open VLM Families Were Built.

A checklist for practice

Everything above reduces to a short list of habits. They apply both when you write a model report and when you read one.

  1. Name the four parts. For every benchmark you report, state the split, the metric variant, the prompt and reasoning mode, and the extractor or judge with its version.
  2. Run the blind baseline. Score the model with the image removed, and score its base language model. Report the multi-modal gain, and treat a large leakage as a warning.
  3. Report uncertainty. Give the benchmark size, and compute or estimate a confidence interval. Do not claim wins inside it.
  4. Cover the clusters, not the count. One benchmark from each capability cluster says more than five from the same cluster. Include at least one vision-centric benchmark such as MMStar, BLINK or CV-Bench.
  5. State the input settings. Maximum resolution or image-token budget, number of frames, and subtitle use.
  6. Separate translated from native multilingual results, and list the languages.
  7. Reproduce before comparing. When a comparison matters, run all models through one toolkit, such as VLMEvalKit or lmms-eval, with the same settings.
  8. Prefer fresh or private data for headline claims. Live benchmarks, private test sets and generated variants are harder to contaminate.
