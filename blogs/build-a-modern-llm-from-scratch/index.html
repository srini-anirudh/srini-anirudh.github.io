The plan

What is inside a modern language model, tensor by tensor? And how do you prove that your version is correct, and not only plausible?

We answer both by building one. The model follows the Llama design, which is also the design of SmolLM2 and close to that of Qwen and many others. It differs from the 2017 transformer in four places. It uses RMSNorm instead of LayerNorm. It uses RoPE instead of added position vectors. It shares keys and values across query heads. It replaces the plain MLP with a gated one.

Why these changesWhat changed inside the transformer

This post does not repeat those arguments. It writes the code, runs it, and looks at the tensors. Each step adds one module and one check. At step 12 we hand our weights to Hugging Face and ask for the same logits. Then we run the other direction and load a real pretrained model into our own code.

The attention code comes from Build Attention From Scratch. We keep its GQA and RoPE design and its names, trimmed to what a decoder needs, and a test checks that the two agree. Unless a block says otherwise, the numbers below came from an AMD EPYC 7R13 CPU with 8 threads. The GPU blocks came from one NVIDIA H100 80GB HBM3 and are labelled. Commands run from the repo root.

Step 01

Put every number in one configuration

Goal A dataclass that describes the whole architecture and rejects impossible shapes early.

Every module reads its sizes from one object. That lets us save the architecture next to the weights, translate it to Hugging Face later, and build Llama 3 8B on the meta device from one line.

Three of the checks encode real constraints. Head width must be an integer. Query heads must divide evenly among key and value heads. RoPE rotates pairs of channels, so head width must be even.

Step 02

Token embeddings and weight tying

Goal Turn ids into vectors, and use one matrix for both reading and scoring tokens.

An embedding is a lookup table: X = E[ids]. The table has V rows and D columns. The same id always returns the same row, at any position. Position enters later, inside attention.

We use a byte tokenizer, so V is exactly 256 and nothing needs downloading or training. The next tutorial replaces it with a trained byte-pair encoding (BPE) tokenizer.

Weight tying means the output layer reuses the embedding matrix. Tying is one assignment in the constructor. After it, both names point to the same Parameter, and gradients from both uses add up in one place.

Shapes in step 2
TensorShapeMeaning
input_ids(B, T)Integers in 0 to V - 1.
embed_tokens.weight(V, D)One learned row per token.
x(B, T, D)The row for each token.

Nuance

Tying saves little in this model: 65,536 of 4.36M parameters, or 1.5%. In SmolLM2-135M it saves 28.3M of 162.8M, or 17%. The saving grows with vocabulary size, while the body of the model does not depend on V. That is one reason large models with big budgets, such as Llama 3 8B, can afford to leave it off.

Checkpoint

  • Both uses of a byte give the same vector.
  • test_weight_tying_shares_storage passes.
Step 03

RMSNorm from scratch

Goal Rescale each token vector to unit root-mean-square, with no mean subtraction and no bias.

Derivation inThe geometry of normalization

RMSNorm is LayerNorm without the centring. It divides each token by its own RMS, then applies a learned gain per channel. It has D parameters and needs no running statistics.

Read forward from the inside out. x32.pow(2).mean(dim=-1, keepdim=True) gives one number per token, the mean square across its channels. keepdim=True leaves a dimension of size 1, so the result broadcasts over all D channels. torch.rsqrt returns one over the square root. Last, self.weight scales each channel by its learned gain.

The first lines hold a surprise. An input with RMS 0.0194 comes out at 0.9869, and one with RMS 0.001 comes out at 0.2921. The reason is epsilon. The output RMS is r / sqrt(r² + eps), so with eps = 1e-5 the norm stops rescaling once r falls near sqrt(eps), which is 0.0032. Drag the slider to see it.

Insight

Our freshly initialised embeddings have RMS 0.020, so the first norm in the model loses about 1.2% to epsilon. That is harmless at this scale. It would not be harmless at initializer_range = 0.002. Here the first norm would return vectors far below unit scale, and every layer after it would see a weak signal. Check what eps does before you shrink an init.

Test

test_rmsnorm_matches_torch compares against torch.nn.RMSNorm, which PyTorch added in 2.4. The maximum difference above is exactly 0.

Checkpoint

  • Output RMS is 1 for any input much larger than sqrt(eps).
  • test_rmsnorm_output_has_unit_rms passes.
Step 04

Rotary position embeddings

Goal Make the query-key score depend on the distance between two tokens, and not on where they sit.

Derivation inHow models know where they are

RoPE adds nothing to the token vector. It rotates each pair of channels by an angle proportional to position. Each pair rotates at its own speed. Queries and keys are rotated. Values are not. This is the same module as in Build Attention From Scratch.

Walk through the constructor first. inv_freq holds one speed per channel pair, from 1.0 down to 0.000178 in the tiny preset. torch.outer multiplies every position by every speed, so freqs holds one angle per position and per pair. torch.cat((freqs, freqs), dim=-1) gives channel i and channel i + d/2 the same angle, because they form a pair.

Then rotate applies the usual 2D rotation. For a pair (a, b), x * cos + rotate_half(x) * sin gives (a cos - b sin, b cos + a sin). Rotation keeps the length of the vector, which the output below confirms.

Read the last four lines. The first three have offset 3 and identical scores, even after the pair moves by 98 positions and then by 200. The fourth has offset 2 and a different score. That is the whole property, measured.

Shapes in step 4
TensorShapeMeaning
inv_freq(d/2,)One rotation speed per channel pair.
cos_cached, sin_cached(max_seq_len, d)Tables indexed by absolute position.
cos, sin(B, T, d)The rows for these T positions.

Break it

Some codebases pair channels as (0, 1), (2, 3) instead of (i, i + d/2). Both are valid RoPE, so a model trained with one is broken under the other. We load SmolLM2-135M and swap only the pairing. The result is the most dangerous kind of bug, because the model still writes readable English.

Only the loss reveals it. It rises from 2.076 to 3.385, which is more than a nat per token. This small model repeats itself with or without the bug, so reading samples would not catch it. This is why step 12 compares numbers.

Checkpoint

  • Rotation keeps the vector norm.
  • test_rope_dot_product_depends_only_on_offset passes.
Step 05

Grouped-query attention, naive first

Goal A readable reference, a fast version on PyTorch’s scaled dot-product attention (SDPA), and a test that they agree, with a cache slot ready for step 14.

Derivation inHow attention moves information

Grouped-query attention keeps all H query heads and reduces keys and values to H_kv heads. Several query heads read each key and value head. It sits between multi-head attention (MHA), where every query head has its own keys and values, and multi-query attention (MQA), where all query heads share one. The reshape helpers below are trimmed copies from the attention tutorial.

Follow one call of naive_attention. repeat_kv inserts a dimension and expands it, which turns (B, H_kv, T, d) into (B, H, T, d). Query head h now lines up with KV head h // n_rep. q @ k.transpose(-2, -1) gives one score per query and per key, and dividing by the square root of d keeps those scores from growing with head width.

masked_fill sets every forbidden pair to minus infinity, so softmax gives it weight 0. Each row of probs then sums to 1, and probs @ v is a weighted average of the values, one per query.

Next we hand the same maths to PyTorch’s fused kernel. There is one trap, and the code comments mark it. is_causal=True builds a triangle aligned to the top-left corner. That is correct only when queries and keys have the same length.

The module itself is mostly projections. RoPE tables come in from the model, so they are computed once per call and shared across layers.

How much does the fused kernel save inside the full model? We time forward plus backward, per training step.

Nuance

Timings on a shared CPU move between runs, so we ran this benchmark twice. The second run, saved in results/timing_rerun.txt, gave 0.91x at 128 tokens, 1.08x at 256, 1.92x at 512 and 4.53x at 1024. At 128 and 256 tokens the two kernels are too close to call, and SDPA was even slower once.

At 512 tokens SDPA was faster in both runs, but the size of the win moved a lot: 3.09x, then 1.92x. Only at 1024 tokens is the win both large and steady: 4.23x, then 4.53x. Read the table above as a trend, not as exact factors. That trend fits what the naive path does. It builds a full (T, T) score matrix and mask, and copies keys and values with repeat_kv. Each of these grows with T.

Which kernel did SDPA use here? On this PyTorch build, the CPU path dispatches to aten::_scaled_dot_product_flash_attention_for_cpu, a flash-style CPU kernel that runs in float32. So the CPU numbers above already use a fused kernel.

A probe of the PyTorch backends is saved in results/sdpa_cpu_backend_probe.txt. The CUDA FlashAttention kernel is a different one. It needs a GPU. As far as we could tell, it runs only in bf16 and half precision.

We ran the GPU commands on one NVIDIA H100 80GB HBM3, with PyTorch 2.15.0 and CUDA 13.2. The five GPU tests pass. Four of them force the FlashAttention backend, so PyTorch raises an error instead of falling back. Three compare it with the naive path for MHA, GQA and MQA, and one checks a single cached decode step against a full forward pass. The fifth is a float32 test of chunked prefill on a cache, with the shifted mask.

On the GPU the clear result is memory, not time. At 1024 tokens the naive path peaks at 3,460 MiB and SDPA at 594 MiB, almost 6 times less. The naive path stores a (T, T) score matrix per head. Its peak grows about 3.5 times from 512 to 1024 tokens, and the SDPA peak about 1.8 times. We did not record which SDPA backend this benchmark used, so we do not name a kernel.

The naive path also takes its softmax in float32, with torch.softmax(scores.float(), dim=-1). So the bf16 naive run holds a float32 score matrix. That is why its 1024-token peak (3,460 MiB) is higher than the float32 naive run (3,242 MiB). It also means the bf16 time comparison includes that upcast.

The times say little. SDPA takes 20.0 to 20.3 ms at every length, and the naive path 25.1 to 27.3 ms. That is a speed-up of about 1.2x to 1.4x, in single runs. The flat shape is consistent with a step limited by kernel launches, because a model this small cannot keep an H100 busy. We did not prove that. The speed-up tells you little about large models.

In float32 the same run gives about 1.2x to 1.6x, again in single runs. The naive times there are 21.9, 23.9, 23.0 and 27.8 ms, which are not monotone, so read that range as noise and not as a trend. The 1024-token peak is 3,242 MiB for naive and 1,045 MiB for SDPA. The run is saved in results/bench_attention_gpu_float32.txt.

A first run on a heavily loaded host gave SDPA speed-ups from 0.88x to 1.51x. We discarded it and re-ran. Treat all GPU timings here as single runs on a shared machine. This benchmark leaves PyTorch’s default backend choice in place (see the note in Step 14). A 20 ms forward and backward step over 6 layers cannot include a cost of about 10 ms per attention call, so that slow call does not seem to affect it.

Break it

Pass is_causal=True whenever more than one query arrives (q_len > 1), and prefill the prompt in chunks of 8 on top of a cache.

The first chunk is correct because it starts at the top-left. Every later chunk is wrong by up to 0.9 logits on random weights. Token-by-token decoding does not hit this bug, because with q_len == 1 the buggy line passes no mask at all.

That condition matters. With is_causal=True, PyTorch aligns the triangle to the top-left, so a single query may only see key 0. If you pass is_causal=True on every call, token-by-token decoding breaks too: on the same random model, it differs from the full forward by up to 1.167 logits. Only position 0 stays correct. These two checks are saved in results/is_causal_single_query.txt. So the flag is safe only when queries and keys have the same length.

Checkpoint

  • Naive and SDPA differ by about 1e-7.
  • test_naive_and_sdpa_agree and test_same_output_as_attnzoo pass. The second one checks tinyllm against the C3 library, including its cache protocol.
Step 06

SwiGLU, the gated feed-forward

Goal Implement down(silu(x W_gate) * (x W_up)) and understand why F is not 4D.

Background inWhy neural networks need nonlinearity

Attention mixes across positions. The MLP, a multilayer perceptron, works inside each position. SwiGLU makes two wide copies of the token. One copy, after silu, becomes a gate that scales the other copy channel by channel. A third matrix projects back down.

Shapes in step 6, tiny preset, B = 1, T = 11
TensorShapeExample
x(B, T, D)(1, 11, 256)
gate_proj(x)(B, T, F)(1, 11, 704)
up_proj(x)(B, T, F)(1, 11, 704)
silu(gate) * up(B, T, F)(1, 11, 704)
down_proj(product)(B, T, D)(1, 11, 256)

A classic MLP with F = 4D has 8D² weights. SwiGLU with width F has 3DF. They match at F = 8D/3. That is the origin of the odd-looking numbers in real configs. SmolLM2-135M uses exactly 8D/3: 1536 for D = 576. Llama 3 8B uses more, 14,336 for D = 4096, which is a ratio of 3.5.

Insight

The word “feed-forward” undersells this layer. In all three models we count in step 11, SwiGLU holds the largest share of the parameters: 75% of tiny, 59% of SmolLM2-135M and 70% of Llama 3 8B. So if you need to shrink a model, F is the first number to look at, before heads or layers.

Checkpoint

  • Output shape equals input shape. Gate values never fall below -0.278.
  • test_swiglu_shapes_and_formula passes.
Step 07

The decoder block

Goal Assemble two pre-norm residual branches into a block whose output shape equals its input shape.

Each branch normalises its own input, computes, and adds the result to the stream. The stream itself is never normalised inside a block. That gives gradients a clean path from the loss to the first layer.

A fresh block is close to the identity function. With a unit-scale input, the attention branch has RMS 0.016 and the MLP branch has RMS 0.008. Training gradually grows these branches.

Step 08

The decoder stack and LM head

Goal Repeat L blocks, add a final norm, and score every token in the vocabulary at every position.

The stack is a loop. Two details matter. Positions must start after the cached tokens, which is the job of past. And the final norm is needed because the stream has never been normalised.

Read it top to bottom. past is the number of tokens already in the cache, and it is 0 without one. position_ids counts from past, so a new token gets its real position. The RoPE tables are looked up once and passed to every layer. Each layer returns the new stream and an optional auxiliary loss, which is None for a dense block. After the loop, self.norm and self.lm_head turn the stream into one score per vocabulary entry.

The last output line is a causality check on the whole model. Changing tokens at position 8 and later leaves logits 0 to 7 bitwise unchanged.

Step 09

The shifted cross-entropy loss

Goal Score each position against the token after it, and let callers mask positions out.

The model predicts the next token, so targets are the inputs moved left by one. The last position has no target. The first token is never predicted.

Shapes in step 9
TensorShapeMeaning
logits(B, T, V)One score per token, per position.
labels(B, T)Usually the input ids.
shift_logits(B, T-1, V)Drops the last position.
shift_labels(B, T-1)Drops the first token.
flattened(B*(T-1), V) and (B*(T-1),)The form cross_entropy expects.
lossscalarMean over positions not marked -100.

Break it

Remove the shift, then train for 100 steps. The loss falls close to zero, and the model has learned nothing useful.

Each position can read its own target, because attention includes the current token. So the model learns to copy, and sampling repeats the last character, here a colon. A loss of 0.022 after 50 steps is far below the entropy of English text. That is a bug, not progress.

Checkpoint

  • The hand computation and causal_lm_loss agree to four decimals.
  • test_loss_is_shifted and test_loss_ignores_masked_labels pass.
Step 10

Initialisation

Goal Start near the uniform loss, and keep the residual stream stable at any depth.

Derivation inWhy transformers do not explode

Two rules cover it. Every weight starts small, with standard deviation 0.02. The two projections that write onto the residual stream are scaled down further by the square root of 2L, because each block adds two random contributions and their variance accumulates.

A correct model should start near ln V, the loss of a uniform guess. That number is your first sanity check on any new model, and it costs one forward pass. Here we also test what happens without the depth scaling, in a 48-layer model.

The first block shows the sanity check at work. With a standard deviation of 0.02, the loss starts at 5.611, close to ln 256. At 0.2 it starts at 10.418, and at 1.0 it starts at 46.022. A bad init is visible before the first training step.

Insight

Without the depth scaling, a 48-layer model's stream reaches RMS 0.69 at the last layer. With it, the stream reaches 0.059, even though both start from embeddings of RMS 0.02. So the scaled model begins close to a stack of identity blocks. The unscaled stream is already about 12 times larger before it has seen any data.

Checkpoint

  • Initial loss on the tiny model is near ln 256 = 5.545.
  • test_initial_loss_is_near_uniform passes.
Step 11

Derive the parameter count, then verify it

Goal Write the size of every component as a formula, and check it against real modules and published model sizes.

If you can write the parameter count by hand, you understand the architecture. Every term comes from a matrix we already built.

The check builds each model on PyTorch’s meta device, which records shapes and allocates no memory. So Llama 3 8B fits on a laptop for counting.

Formula and module agree on all three. The totals also agree with outside sources. SmolLM2-135M has 134,515,008 parameters when loaded from the Hub in step 12. Llama 3 8B’s published size is 8.03B, and our formula gives 8,030,261,248. Try the formula yourself. A preset button fills in a real model, and a bad combination raises the same error as ModelConfig.

Insight

Our script shows Llama 3 8B's attention at 2.147B parameters with 32 KV heads, 1.342B with 8, and 1.107B with 1. Going from 32 KV heads to 8 removes about 9% of the whole model, but it removes 75% of the KV cache: 2.00 GiB becomes 0.50 GiB for 4096 tokens. So GQA is mainly an inference-memory decision, and only secondarily a parameter saving.

Checkpoint

  • All three totals print equal=True.
  • test_parameter_count_formula_matches_model and test_parameter_count_of_real_models pass.
Step 12

Prove it against the trusted implementation

Goal Give our weights to Hugging Face’s LlamaForCausalLM and get the same logits. Then load real pretrained weights into our model.

So far each module passed its own small test. That cannot catch a wrong design choice that we made consistently, such as the RoPE pairing. A second, independent implementation can. Because we named our attributes after Hugging Face’s, the conversion is a config translation and a key prefix.

The logit difference is exactly zero, in both directions. A real pretrained model runs through code we wrote today, and greedy decoding matches generate() token for token. The model itself is a small one, which shows in its answer.

Nuance

Exactly zero suggests both paths ran the same floating-point operations in the same order, here through the same SDPA kernel. The script does not record which implementation Hugging Face used. Do not expect that as a general rule. Our naive backend computes the same function and differs by about 1e-6, because its operations run in a different order. So the test uses a tolerance of 1e-5, and a bitwise match is not a requirement.

Checkpoint

  • Random tiny model and SmolLM2-135M both match within tolerance.
  • test_logits_and_loss_match_llama passes. test_smollm2_135m_logits_match passes with -m network.
Step 13

Generation: greedy, temperature, top-k, top-p

Goal Turn one row of logits into one token, with each filter as a small pure function.

Derivation inChoosing the next token

Generation is a loop around one decision. Each filter takes logits and returns logits, so they compose, and each can be tested alone.

Take the filters in order. apply_top_k finds the k-th largest value in each row and blanks everything below it. apply_top_p sorts the row, computes the probability mass before each token, and blanks a token once that mass already reaches p. The final scatter puts the survivors back in their original positions. sample_next_token then draws one id per row from what remains. A temperature of 0 skips the draw and takes the largest logit, which is greedy decoding.

Run them on the model we train in step 15. Below is the real next-byte distribution after the prompt ROMEO:\nI will . Move the sliders to see what each filter does to it. The filters run in the same order as the code.

Here is what each setting does to the text, same model and seed.

Nuance

A fixed k and a fixed p are not the same kind of filter. After this prompt, top_k=40 keeps 40 tokens, while top_p=0.95 keeps 18 and still holds 95% of the mass. So top-p sets its width from the distribution, and top-k does not. The samples show the two ends of temperature: greedy loops on “the sea that will”, and temperature 1.5 invents strings such as “alGo”. These are single samples from one seed, so they illustrate the filters and do not rank them.

Checkpoint

  • Same seed gives the same output, through both generation paths.
  • test_top_p_keeps_smallest_nucleus and test_top_k_keeps_k_largest pass.
Step 14

Cached generation: same tokens, far less work

Goal Keep past keys and values, prove the output does not change, and measure the saving.

Theory inThe mechanics of LLM inference

Start naive. To get one new token, run the whole sequence again and keep the last row of logits. This is correct and very wasteful, because past tokens do not change. Their keys and values do not change either. So we store them and pass only the new token.

The decode branch is the whole optimisation. ids[:, -1:] passes one token. TinyLLM.forward reads past from the cache, so that token gets its true position. Inside attention, kv_cache.update appends its key and value, and sdpa_attention takes the q_len == 1 branch, because one new token may see everything before it and needs no mask.

Test

A cache must change speed and nothing else. So we compare the logits of a full forward with token-by-token decoding, on both backends.

Now measure. The benchmark times each decode step separately.

Insight

The cache cuts tokens far more than it cuts time. In the tiny run, uncached decoding processes 130,696 tokens and cached decoding processes 511, which is about 256 times fewer. Total time falls only 4.9 times. SmolLM2-135M, over its shorter run, processes about 71 times fewer tokens and takes 2.2 times less time. A second run of both benchmarks gave 3.7x and 2.1x, so take the exact factors as rough.

The tables show why. On tiny, one cached token costs about 3 to 4 ms, while re-running all 511 tokens costs only 26 ms. So on this CPU each forward call has a large fixed cost, which we have not profiled. The saving grows with T.

At T = 17 the first run gave 5.97 ms without the cache and 4.43 ms with it. The second run had the cache slightly slower, 4.72 ms against 4.18 ms. At T = 511 the cache was 7.6 times faster per step in the first run and 5.6 times in the second. So short outputs see little of the gain. These are single runs on a busy shared CPU.

On the GPU the cache gives almost nothing at this size. We measured it on the H100 at batch 1, and the run is shown below. Do not read the CPU result as a general one.

Nuance

On the H100 at batch 1, the tiny model runs at 176 tokens per second without the cache and 197 with it. That is about 10% more, from one run. At the SmolLM2-135M size it is 39.3 and 40.4 tokens per second, 1.0x. The files are results/bench_generation_gpu.txt and results/bench_generation_smollm2_gpu.txt. The GPU SmolLM2 run used 496 new tokens, while the CPU run used 128.

The step costs about 5 ms whether the forward pass covers 17 tokens or 511. That is consistent with a step limited by launching kernels from Python, not by arithmetic. We did not profile this case, so it is not proven. If it is right, skipping the recomputation saves nothing.

We checked the cache logic on logits, not on generated text. On the CPU, test_token_by_token_with_cache_equals_full_forward and test_chunked_prefill_equals_full_forward in test_cache.py compare logits. On the GPU, test_gpu.py has test_flash_attention_decode_step_matches_full_forward and a float32 chunked-prefill test. We did not compare bf16 generation output token for token. A larger batch, a longer context or a bigger model could change the picture, and we did not measure any of them.

Nuance

A slow default on the GPU. With PyTorch’s default attention backend choice, generation was much slower than the numbers above.

  • Symptom. Both the cached and the uncached tiny runs were about 10 times slower from T = 48 on: about 48 to 62 ms per step instead of about 5 ms. At T = 17 they were normal, 5.40 ms and 5.93 ms. At the SmolLM2-135M size the slowdown was about 3 times, from about 24 ms to 71 to 81 ms.
  • What we measured. A profiler run pointed at aten::_cudnn_attention_forward, at about 10 ms of CPU per call. That profile is not saved.
  • What we did not find. We do not know why the call is slow, or why T = 17 is spared.
  • What to do. Call tinyllm.utils.disable_cudnn_sdp() once before you generate. bench_generation.py calls it on CUDA unless you pass --allow-cudnn-sdp. The library does not call it for you, because it sets a global PyTorch flag.

The generation numbers above have it off. The attention benchmark leaves PyTorch’s default backend choice in place. The slow runs are saved in results/bench_generation_gpu_cudnn_default.txt and results/bench_generation_smollm2_gpu_cudnn_default.txt. They are not normal speed.

Break it

Forget that positions must continue from the cache. Every decode step then rotates its token as if it sat at position 0.

Prefill still uses the right positions, so the first new token is correct. New token 1 is the first wrong one. After that the text collapses into repeated syllables, because every new key sits at position 0 while the older keys keep their real positions. This case loads the trained model because random weights hide the bug in the text. In a separate check on a random tiny model, cached and uncached generation gave identical tokens for each of 5 seeds. That check is saved in results/position_offset_random.txt.

That has a direct effect on testing. With this bug patched in, test_cached_generation_matches_uncached_greedy still passes, because it compares tokens on random weights. test_token_by_token_with_cache_equals_full_forward and test_chunked_prefill_equals_full_forward compare logits, and both fail. So test a cache on its logits, not on its tokens.

The same run also failed the three test_matches_c3.py tests, which compare against the C3 attention library. The full pytest output is saved in results/pytest_position_offset_bug.txt.

Checkpoint

  • Cached logits match full-forward logits within 1e-5.
  • test_token_by_token_with_cache_equals_full_forward, test_chunked_prefill_equals_full_forward and test_cached_generation_matches_uncached_greedy pass.
Step 15

A quick training run, then save and load

Goal Show that the architecture learns, with loss going down and samples improving, and that a checkpoint round-trips exactly.

Theory inHow LLMs are pretrained

This is a sanity check and not a training recipe. It has no packing, no mixed precision and no resume. Those belong to the next tutorial. We train the tiny preset on Tiny Shakespeare, about 1.1 MB of text, one byte per token.

Nuance

The run took 670 seconds here, and 737 seconds in a second run on the same shared CPU, with the same losses. Falling training loss alone would oversell this run. Between steps 800 and 1000 the training loss goes from 1.152 to 1.131, while validation goes from 1.496 to 1.500. Validation has stopped improving, and the gap between the two is now 0.37 nats. That gap is rough, because the training loss is from one batch while validation averages 20 batches.

The samples agree: the layout of a play is there, and invented words such as “BALTHBruptial” are too. This shows that the architecture learns. It says nothing about how good a well-trained model can be, which is the job of the next tutorial.

A native checkpoint is a folder with config.json and model.safetensors. Tied weights are stored once, because safetensors refuses shared tensors and the duplicate would waste space.

Check the size on disk against the parameter count. The tiny model has 4,295,936 parameters at 4 bytes each, which is 17,183,744 bytes. The file holds 5,640 bytes more, for the safetensors header. A second copy of the tied head would have added V × D × 4 = 262,144 bytes.

Checkpoint

  • Loss starts near 5.5 and falls below 2 within a few hundred steps.
  • test_round_trip_reproduces_logits, test_tied_weights_are_stored_once_and_retied, test_training_resumes_identically and test_save_hf_loads_with_automodel pass.
Step 16

An optional mixture-of-experts block

Goal Replace SwiGLU with a router and several expert MLPs, and see why routing needs its own loss.

Skip this step if you only want Llama. MoE keeps the parameter count of a large model and the compute of a small one. Each token runs through only k of E experts. Mixtral and DeepSeek use this idea, with more engineering around it.

Three ideas carry this listing. Routing logits come first: self.router is one linear layer that gives each token a score per expert, and topk keeps the best k. Each token’s kept scores are divided by their sum, so its weights add to 1.

Expert capacity comes next. With capacity_factor set, each expert accepts at most ceil(factor * N * k / E) assignments. Earlier tokens win, and later ones skip that expert, so only the residual stream carries them through it. The default of None never drops anything, and the demo below uses that default.

The auxiliary loss comes last. load_balancing_loss multiplies each expert’s share of the assignments by its mean router probability. The share is not differentiable, but the probability is, so the gradient lowers the probability of busy experts.

Does the load-balancing loss matter in practice? We train a small MoE model twice on the same batches, once with the loss switched off.

Insight

A very small coefficient changes the routing a lot. A balanced router gives each of the 8 experts 0.125 of the load. With the loss off, the busiest expert in either layer reaches 0.49 after 300 steps, and the auxiliary loss sits at 1.835 per layer. With a coefficient of only 0.01, the busiest expert stays at 0.18. Both numbers come from layer 1.

The printed shares are for layer 0, where the peaks are 0.27 and 0.17. All shares come from the last training batch only. With balancing on, the auxiliary loss stays near 1. Balance cost nothing visible here: the training loss at step 300 is 1.912 with balancing and 2.010 without. That gap comes from one seed on a small model, so do not read it as balancing improving the loss.

Key insights and nuances

  • A wrong design choice can still write readable text. Swapping the RoPE channel pairing left SmolLM2 readable and raised its loss by over a nat per token. Only a numerical comparison catches this. Step 4
  • A bitwise match is a bonus, and a tolerance is the requirement. Our SDPA path differs from Llama by exactly 0, and our naive path by about 1e-6, though both are correct. Step 12
  • RMSNorm has a floor. Below an input RMS near sqrt(eps) it stops rescaling. Real embeddings at RMS 0.02 already lose about 1.2%. Step 3
  • SwiGLU is where the parameters are. It holds 59% to 75% of the three models we counted. Step 6
  • GQA is an inference-memory decision. Going from 32 KV heads to 8 in Llama 3 8B removes 75% of the cache and about 9% of the parameters. Step 11
  • Depth scaling keeps a new model near identity. Without it, a 48-layer stream ends about 12 times larger before any training. Step 10
  • is_causal=True is safe only when queries and keys have the same length. With a cache it aligns the mask to the wrong corner. A single decode query then sees only key 0, and later prefill chunks are wrong by up to 0.9 logits. Step 5
  • Test a cache on logits, not tokens. A cached decode with wrong positions passes a token comparison on random weights, and it fails a logit comparison. On trained weights the same bug wrecks the text. Step 14
  • A KV cache saves fewer seconds than its token count suggests. On tiny it processes about 256 times fewer tokens and takes 3.7 to 4.9 times less time, over two runs on a CPU. Short outputs see even less of the gain, and on an H100 at batch 1 the cache saved almost nothing (1.1x). Step 14
  • A falling training loss is not the whole story. From step 800 to step 1000, training loss still falls while validation stays near 1.50. Step 15
  • A small balancing loss has a large effect on routing. A coefficient of 0.01 holds the busiest of 8 experts at 0.18 of the load. Without it, the busiest expert reaches 0.49, over one batch. Step 16
